## 第 0 部分 · 开篇：两大核心待攻克问题

管线在板卡上跑起来之后，被两个问题卡住了：**难题一 GMC** 吃掉了端到端时延的 78.5% 且时延账算不准；**难题二 NPU** 让"编译通过"不等于"跑在 NPU 上"、让 FLOPs 外推彻底失效。

本阶段 9 个工作汇报点，全部围绕这两个问题展开：
- **战线 A · GMC 之战**（打难题一）→ 战果 A1 树状锚点级联、A2 纯函数缓存
- **战线 B · NPU 之战**（打难题二）→ 战果 B1 算子回退清零、B2 弃用 FLOPs 外推、B3 RGA 拼图、B4 精度账
- **公共底座**（两条战线共用）→ 三级流水线、OpenCL 融合内核、端到端库交付

### 0.1 难题一 · GMC 账本：开销、延时、稳定性

GMC 是整条管线的瓶颈；它的稳定性已改善，但换来了一条必须守住的前提。

| 维度 | 硬证据 |
|:--|:--|
| **算力开销** | PC 侧归因：拟合 **21.6%** + warp **43.7%** + median **33.7%** + 读帧 1% ⇒ native 合计 **183.32 ms/帧** |
| **延时** | 板卡 `gmc_total` **62.765 ms** / 端到端墙钟 **79.952 ms** = **78.5%**；角点多的序列 step10 **p50 35.1 / max 63.870 ms**（超 40 ms 硬保证 60%）；step2 精确等价档 p50 **111.1** / max **216.5 ms** |
| **稳定性** | ✅ **深原始缓冲已把丢帧归零**：`--input-queue 1024/4096` ⇒ 相机丢帧 **0**、历史洞 **0**、GMC 特征帧 **11810/11810**（25 fps 真相机全量）<br>🔴 **但零丢帧是"锚定等价"的前提**：物理帧号锚定 ≡ 消费计数锚定 **当且仅当 `dropped == 0`**，**深缓冲不能替代这个条件** |

**⭐ 战线 A 的弹药表：三段成本，各对应一招**

| GMC 的成本段 | 占 CPU 侧 | 本阶段的招 | 战果 |
|:--|--:|:--|:--|
| **warp 43.7% + median 33.7% = 77.4%** | 最大的一块 | **OpenCL 融合内核**（搬到 GPU，Mali-G610） | 战果 **A1** |
| **拟合 21.6%** | 21 次/帧全量重拟合 | **Tree 锚点级联**（22 → 6.19 次/帧） | 战果 **A2** |
| **fit 内部 gFTT 65.8%**（相对 fit 自身） | 纯函数被反复重算 | **纯函数缓存**（按绝对帧号缓存） | 战果 **A3** |

> 💡 **A1 与 A2 互补而非重复**：A2（step10）明确"**warp 一次没少**"，它砍不动的那 77.4% 正是 A1（OpenCL）搬走的那一块。
> ⇒ **三招合起来才构成 GMC 的完整降本。**

**新的硬约束（比"丢帧"更硬）**：**零丢帧且有界延迟 ⇒ GMC 吞吐 ≥ 相机率**（25 fps ⇒ ≤40 ms/帧）。
- step10 实测 **60.8~61.2 ms** ⇒ **接近但仍超**（需深缓冲兜底）
- step2 实测 **157.6~161.1 ms** ⇒ **差 4 倍**（只能靠深缓冲换延迟 ≈ 24 分钟）

**⇒ 稳定性从"能不能不丢帧"变成了"能不能一直守住 `dropped == 0`"。**

### 0.2 难题二 · NPU 账本：算子匹配与效率反直觉

NPU 不是"算得慢"，是**算的东西和算的方式都不对**。

| 维度 | 硬证据 |
|:--|:--|
| **算子匹配** | `trial_0474` v1 有 **1 个计算算子**（`p0_highway/pool/Reshape`）悄悄落到 CPU —— **不抛异常、不改指标** ⇒ "编译通过" ≠ "全在 NPU 上" |
| **效率反直觉** | multi-scale 要 **3 次前向** ⇒ 板卡约 **3 fps**；删 P0 后 **MAC 只降 6.8%，时延却降 46.5%** ⇒ FLOPs 外推彻底失效；上限卡在**空间乘积** `H*W ≤ 16384` |
| **量化闸门** | PTQ 配置轴全部封死；**输入 dtype 是硬闸门**（只有 toolkit 自己全图 int8 量化才能停在 INT8：0.34 ms vs FLOAT16 45.41 ms）；QAT **不能兼得"更准"与"INT8 输入延时"** |

## 第 1 部分 · 战线 A · GMC 之战

### 战果 A1 ｜ OpenCL 融合内核：warp + median 搬上 GPU

> **归位说明**：OpenCL 融合内核**不是公共底座** —— 它搬走的是 GMC 的 `warp + 21 帧 median + 三通道组装`，即 **CPU 侧 77.4%** 的那一块，**正是 step10（A2）砍不到的部分**（step10 只砍拟合，warp 一次没少）。
> ⇒ 因此它属于**战线 A**，并排在 A1 位：**先打最大的一块**。


**做了什么**：把 `warp + 21 帧 median + 三通道组装`从 CPU 搬到 GPU（Mali-G610）。CPU 侧保留 Shi-Tomasi / LK / RANSAC / 锚点网格。

**排序网络：完备证明，不是抽样**
```
PASS exhaustive 0/1: 2097152 / 2097152, 112 comparators
prune round 1 -> 109 comparators
PASS exhaustive 0/1 after prune: 109
```
- 修正：验收标准写的"**91 次比较**"复现不出来 —— 任何**可构造并可证明**的方案都落在 **109**
- **证伪公开的 Batchers 奇偶归并伪码**：只在 n 为 2 的幂时成立；n 为奇数时丢掉最后一格且递归会 `CE(lo, lo+r)` 越界（**静默越界写**）
- sentinel-drop 是**严格正确**（归纳可证）而非启发式

**完备验证抓到 3 个真缺陷（全部表现为"时好时坏"）**
1. `unsigned char a[N]` 声明在 `#pragma omp parallel for` 循环体**外** ⇒ 所有线程共享
2. reduction 变量在 `#pragma omp critical` 内 `bad |= 1` ⇒ 偶发丢失更新，**约 1/200 次调用假 FAIL**
3. 🔴 **剪枝恢复不是真 undo** ⇒ 在删除点留洞 + 把 `saved` 放到下一轮左移 ⇒ "最终有效性检查"在一个**从未真正损坏**的网络上失败 ⇒ 修法是**右移撤销**

> 💡 **用来给内核背书的工具本身出现间歇性失败，比工具报错危险得多。**

**OpenCV 语义：全部实测，未靠记忆**（上一阶段 11 个缺陷全来自"读源码/凭记忆"）

| 事实 | 证据 |
|:--|:--|
| dst→src，**无半像素偏移** | 36 模型扫描：`(x,y)` **99.58%** 精确；`(x+0.5,y+0.5)` 仅 0.79%，MAE 39.1 |
| 位置量化到 **1/32，四舍五入半上取整** | 阶跃 oracle 33 级阶梯 ⇒ 排除 round-half-even；round32 **65/65** vs trunc32 33/65 |
| `CLK_FILTER_LINEAR` 在 PoCL 上不可用 | 改手动 2×2 后 Max\|Diff\| **34→0**、MAE 1.74→0.000 |
| 边界规则 = **两个 tap 各自反射** | 96,000 个越界 tap：模型 A 错 **29.0%**，模型 B 错 **0.0%** |
| 坐标表达式形式**无关紧要** | 5 种结合/FMA 次序，600 万样本，极差 ≤ 0.0004% |

🔴 边界踩过大坑：曾认为 OpenCV 是"先反射基址再取 base+1"，把反射搬进内核 ⇒ 640 宽序列 Ch1 Max\|Diff\| 从 7 恶化到 **239**。

**最终精度（8 序列 / 136 帧 / 4345 万像素）**

| 通道 | Max\|Diff\| | MAE |
|:--|--:|--:|
| **Ch0** | **0** | **0.00000** |
| Ch1 | 7 | 0.00073 |
| Ch2 | 6 | 0.00033 |

- ⭐ **Ch0 逐位精确是承重结论** —— Ch0 是当前帧纯拷贝，一次性验证 padding、通道序、ring 索引、平面排布、坐标约定。**任何坐标反转/通道错位/系统性漂移都会立刻打崩 Ch0**
- 残余 ~600 像素（**1.4e-7**）超到 ≤7，已定量排除（不在边界 / fp64 不改变结果 / 5 种表达式差异 ≤0.0004%）⇒ 是 OpenCV 增量式定点映射表与直接仿射求值的**舍入分歧**，在 1/32 格 tie 上翻格
- 🔴 **要压到 Max\|Diff\| ≤ 1 需要 double-float 坐标运算**（ALU 成本约翻倍，换 4340 万像素里 **13 个**像素变化）⇒ RK3588 上不划算 —— **但这是显式决策，不是默认忽略**

**Mali 平台适配：7 条写进代码形态的约束**
1. **21 个具名标量 `v0..v20`，绝不用 `v[k]`** —— 循环索引会让编译器假定索引动态，把数组溢出到 private memory，而 **Mali 用全局显存模拟 private** ⇒ 排序网络以 `CAS(v3, v11)` 形式拼接
2. 只用 float —— **Mali-G610 无可用 FP64**（实测 `cl_khr_fp64` ❌ 缺失）
3. 无 local memory / barrier / atomic
4. **22 个独立 `image2d_t`，而非一个 `image2d_array_t`** —— array 布局每输出帧要重写全部 21 层（512×512 下 **5.5 MB vs 256 KB**）⇒ 在 RK3588 上比内核本身要省的算力还贵
5. kernel 参数地址空间规则：image/sampler **不能**带限定符；指针参数**必须**带
6. 不用 `-cl-mad-enable` / `-cl-fast-relaxed-math` —— 放开重结合会让验证失去意义
7. `CL_R8` 优先、`CL_RGBA` 兜底 —— 22 张 padded 图 **10.5 MiB vs 42 MiB（4 倍）**

**两个埋点时抓到的测量缺陷**
1. 🔴 **`clEnqueueNDRangeKernel` 在"入队"时就返回** —— 围绕它计时得 0.04 ms，而阻塞式回读报 116 ms ⇒ 第一版结论"回读主导"**完全是错的** ⇒ enqueue 后立刻 `clFinish`（随后两个独立测量一致：118.086 vs 118.081）
2. 🔴 **取模环不是内容环** —— 设备槽位按 `绝对索引 % N` 键入；冷启动时 `frame_at_lag()` 把越过首帧的 lag 钳到 `first_` ⇒ **当前帧与被钳历史帧可以同余** ⇒ 跳过上传、留住上一帧内容 ⇒ **Ch0 有 31% 像素错、最大偏 80 灰阶，预热后消失** ⇒ 改按**内容身份**分配槽位，使该碰撞**不可表示**

**可复用结论**
- 💡 **"Ch0 必须逐位精确"这道闸门存在的意义，就在这里** —— 它一次性把 6 类坐标/通道/索引错误全部挡住
- 🔴 **工具自身的错误会被当成被验证对象的错误** ⇒ 结论必须靠**交叉验证**（GPU 直测 ↔ 独立 CPU 探针）才敢采信

### 战果 A2 ｜ GMC Tree 锚点级联（`anchor_step=10`）：拟合次数砍到 1/4，精度不可区分

**问题**：冻结 native GMC 每帧做 **22 次长基线直接拟合**（lags 2..42，每个 lag 独立从原图拟合）。但这 22 个拟合**高度冗余** —— 相邻 lag 描述的是同一段相机运动。

**方案：树状锚点级联**
- 只在**锚点网格**上直接拟合：`{2, 12, 22, 32, 42}`（5 个）
- 其余 16 个 lag 由**已缓存的 stride 步变换连乘**推导：`R_L = p_{ci−L} · p_{ci−L+2} · … · p_{ci−a−2} · R_a`，`a = max{anchor ≤ L}`
- 连乘深度 = `(L − a)/stride_step ≤ anchor_step/stride_step − 1` = **4**
- 缓存 `pstep(i) = H_{i→i+2}` 跨帧复用 ⇒ 摊销仅 **~1.19 次/帧**
- 硬约束：`anchor_step` 必须整除 `stride_step`，否则链式递推落不到锚点上（脚本直接 `ValueError`）

| 臂 | 直接拟合/帧 | 缓存步拟合/帧 | 连乘/帧 | 最大深度 | **warp/帧** |
|:--|--:|--:|--:|--:|--:|
| ctrl（= native 本身） | 21.00 | 0.00 | 0 | 0 | **22** |
| **tree** | **5.00** | **1.19** | 40 | **4** | **22** |

⇒ **拟合 22 → 6.19（省 71.9%），但 warp 一次没少（22/帧）**

**代数等价性（已实测，但只覆盖一半问题）**
- 纯 Python 验证（随机相似变换，300 次/配置）：`anchor_step = 4/6/10/14/20` 全部 `tree_vs_fullchain_maxdiff = 0.00e+00`；有界深度树合成与全长链**逐位完全相同**（同一批因子重新结合，SIMD 组结合精确），所有 lag 均可达
- 🔴 **但这只证明「结合律无损」，不证明「5 次长基线拟合 + 复用短基线步」与「21 次独立长基线拟合」的估计偏差相同** ⇒ 后者只能靠端到端 F1 判决，**任何像素级误差数字都不得从本条推导**

**精度判决（官方 val 24 序列 / 31,613 帧 / 25,111 GT，th=0.25，Distance ≤ 8 px）**

| 臂 | 拟合/帧 | F1 | ΔF1 | TP | FP |
|:--|--:|--:|--:|--:|--:|
| native（冻结基线） | 22 | 0.9062 | — | 21,640 | 1,007 |
| **ctrl**（native 重编码空对照） | 21 | 0.9062 | **+0.0000** | 21,640 | 1,007 |
| **tree（anchor_step=10）** | **6.19** | **0.9060** | **−0.0003** | 21,639 | 1,020 |
| no-GMC | 0 | 0.9009 | −0.0054 | 21,504 | 1,126 |

- **tree 保住了 GMC 精度的 99.6%**（0.0054 → 0.0003）
- **8 个门限 7 正 1 负，均值 +0.00016**；**th=0.25 恰是最不利工作点** ⇒ 按单点报数会系统性低估本方案
- **delta 来源是 FP +13，不是 TP −1**：按 `F1 = 2TP/(2TP+FP+FN)` 拆，TP −1 仅贡献 −0.00002，**FP +13 贡献 −0.00025** ⇒ 报数必须写「**TP 零损失、代价是 FP +13**」
- 两条最硬序列全部救回：`wg2022_ir_052_split_08` dTP **−74 → 0**、`DJI_0051_2` **−22 → −3**

**⭐ 空对照臂（本轮方法论关键）**
- 动机：tree 臂读新写的 JPEG，native 臂读冻结集原始文件，不对等 ⇒ 必须区分 ΔF1 来自「树的估算偏差」还是「JPEG 重编码漂移」
- 构造：`--mode tree --anchor-step 2` ⇒ 锚点 = 每个偶数 lag = **native 的算法本身**（21 次直接拟合、0 连乘），唯一差别是重写一遍 JPEG
  （🔴 **`anchor_step=2` 是与冻结 native 精确等价的唯一设置** —— 精确等价 ⟺ 每个 lag 都做长基线直接拟合；任何用短基线步连乘的省算力做法，**估计量输入都与 native 不同，不存在恰好相等的可能**）
- 实测：`200/200 抽样文件 md5 与冻结集完全相同`；`dF1 = +0.0000, TP +0, FP +0`；8 个门限全 +0.0000；24 个序列全 +0.0000
- ⇒ **JPEG 重编码对结果零漂移 ⇒ tree 的 −0.0003 是 100% 树自身估算偏差，不含任何编码器伪影**

- 跨 **15 档门限**：均值 **−0.000078**，区间 [−0.000653, +0.000272]，负档 7/15 ⇒ 无系统性差异；峰值门限两臂同为 `th=0.25`，**无工作点漂移**

**特征层证据（stage compare，tree vs native）**
- Ch2 中值残差偏离从 no-GMC 的 **1.4046 → 0.4835（降 65.6%）**，24 个序列**无一变差**
- 改善恰好落在吃 dTP 的序列上（`02_6321` 3.675→0.595、`wg2022_ir_052_split_08` 6.969→1.238、`wg2022_ir_040_split_04` 5.423→1.312）⇒ 印证 no-GMC 的 136 个 dTP 丢失主要来自 Ch2

**成本（builder 侧，同一测量条件：24-worker 竞争，仅可横向比）**：ctrl 110.21 → **tree 57.24 ms/帧（−48.1%）**
🔴 **口径纪律**：builder 的 ms 测于 **24-worker 竞争**，`stage timing` 测于**单进程串行**，**两组数字严禁混比**；桌面 CPU 数字**不得**外推 RK3588 板端。

**在 e2e 总账里的位置**：MOSAIC e2e 全链路 E 臂（raw IR → **GMC step10** → RGA → 板端 f16）F1 0.891676，其中 **C→E 的 step10 语义代价 = −0.003879**（ΔTP −94 / ΔFP −32）。

**🔴 两条被明令禁止的表述（memory 原文）**
1. ❌ **「累计几何误差严格压在 0.2 px 以内」—— 从未测量，必须删除**。唯一实测的是**合成代数**逐位为 0。可写：Ch2 偏离降 65.6% + 24 序列无一变差 + 端到端 F1 全等，**不提任何像素级误差数字**
2. ❌ **「消灭 75% 算力」—— 只有拟合省了 71.9%，warp（管道约 43.7%）一棵没动**。准确表述：**「GMC 拟合次数 22 → 6.19，GMC+warp 实测降 48.1%，但 warp 次数不变」**

**可复用结论**
- ⭐ **树状/级联近似必须配一个「同算法重编码」空对照臂** —— 否则分不清"算法近似偏差"与"数据往返漂移"
- ⭐ **级联近似的代数等价性只证明结合律无损，不证明估计量等价** ⇒ 后者只能端到端判决
- ⭐ **报 delta 必须拆到 TP/FP 分量** —— 否则"TP 零损失"会被误读成"完全无损"

**未决项（不得当作已完成）**
- `anchor_step` **只测了 10**；6（深度仅 2）与 14 未测 ⇒ **不得声称 10 最优**
- **未做串行成本对账**（需 `--workers 1` 跑同一序列）
- **PC 侧三套时延互相矛盾 5 倍**（183.32 / 137.33 / 271.45 ms；反解 f=9.06 vs 直接测 1.80 ms/次）⇒ **机制未查明，禁止引用任何一方的 PC 数字作为嵌入式预算依据**
- JPEG 往返是磁盘存储格式特有 ⇒ 生产环境不经 JPEG ⇒ **−0.0003 是保守上界**

### 战果 A3 ｜ 缓存优化：收益 = 占比 × 命中率

**第一步是剖析，且推翻了一个既有假设**

| 阶段 | 耗时 | 占比 |
|:--|--:|--:|
| **goodFeaturesToTrack** | **136.19 ms** | **65.8%** |
| LK（金字塔在内部构建） | 56.76 ms | 27.4% |
| resize | 10.54 ms | 5.1% |
| RANSAC | 3.64 ms | 1.8% |
| **buildOpticalFlowPyramid 本身** | **5.73 ms** | **3.2%** |

⇒ **"金字塔是瓶颈"是错的**（只占 3%）。大头是角点检测 —— 它和金字塔一样是**单张输入图的纯函数**，却在每次拟合里被重复计算（每帧约重算 3.25 次）。

**方案**：把"每帧纯函数"按**绝对帧号**缓存 —— resize + 角点 + 金字塔三项（不是只缓存金字塔）。

| cache-parts | fit | 加速 | | 生产结果 | 值 |
|:--|--:|--:|:--|:--|
| 0（无） | 23.215 ms | 1.00× | | fit | **18.46 → 3.94 ms（4.68×）** |
| 1 resize | 17.798 | 1.30× | | 端到端 | 20.2 → 8.5 ms（49.5 → **117.6 fps**） |
| **2 角点** | **10.834** | **2.14×** | | 精度 | **MD5 与基线逐位相同** |
| 4 金字塔 | 18.733 | 1.24× | | | |
| **7 全部** | **4.506** | **5.15×** | | | |

**为什么复用金字塔是位精确而不是"差不多"**：`calcOpticalFlowPyrLK` 的 `prevImg/nextImg` 接受 `std::vector<Mat>` 时跳过内部构建，并用"层数为奇 + 通道/深度比值"识别预计算梯度（`lvlStep=2`），**连每层 Scharr 重算都一并省掉**；关键前提是 `buildOpticalFlowPyramid` 的默认值（`withDerivatives=true, pyrBorder=BORDER_REFLECT_101, derivBorder=BORDER_CONSTANT`）**正是 `calc()` 内部构建时传的参数** ⇒ 平面是同一批字节。

**精度让步档的代价（没有免费的加速）**

| 配置 | fit | 端到端（板卡） | **max\|Δ平移\|** | 旋转 cos |
|:--|--:|--:|--:|--:|
| `--pyr-cache`（默认） | 18.45 ms | — | **0.00** | 1.0000000 |
| + `--fit-corners 200` | 12.75 | — | 0.99 | 1.0000000 |
| + `--fit-corners 60` | 4.60 | — | 2.69 | 0.9999987 |
| + corners 50 + L1 + iters10 + win11 | **2.32** | 7.49 | **5.44** | 0.9999990 |

⇒ **减角点几乎只伤平移**（旋转/缩放在所有档位几乎不动）—— 机理：旋转与缩放由更多点约束住，平移对点的分布更敏感。

**可复用结论**
- ⭐ **任何"每帧纯函数可缓存"的优化，收益 = 该阶段占比 × 缓存命中率** —— 纹理贫瘠（**15.7** 角点）**4.30×** vs 纹理丰富（**291.9** 角点）**1.37×** ⇒ **引用任何加速比前必须先报该序列的点数/纹理水平，否则不可迁移**
- 🔴 **两个静默失效的坑**：① **环形槽不能用"是否已填充"的布尔量**（槽填满后恒为真，`slot(43)` 与 `slot(0)` 同址 ⇒ 第 43 帧后一直拿第 0 帧像素，**不崩溃、不断言、只出静默错误数据**）② **`t_` 是 0 起始，clamp 下界必须是 0**（否则只让**组合 lag** 的矩阵漂移，5 个锚点完全正常 ⇒ **肉眼 diff 会误判成"RANSAC 抖动"**）⇒ 内置 `GMC_VERIFY_CACHE=1` 运行时自检，不一致 `exit(3)`

### 战果 A4 ｜ 多缓存的深度是个帕累托旋钮：D=3 与 D=64 各司其职

**问题**：A1/A2/A3 把 GMC 的**算力**压下去了，但"算得快"不等于"跟得上"——真机还要回答**延时**与**吞吐**这两个互相冲突的指标。

**机制（已封装成库）**：特征在 NPU service 前面的 **Buffer A 多槽位缓存**（每槽 2,457,600 B）里排队。
深度 **D** 就是旋钮：**D 越大 ⇒ 越能吸收 GMC 的突发溢出 ⇒ 丢帧越少、fps 越高；但排队越久 ⇒ 延时越大、内存越大**。

| 交付档位 | D | 臂 | fps | 延时 p50 / p95 | 丢帧 / 交付帧 | Buffer A 内存 | 结论 |
|:--|--:|:--|--:|:--|:--|:--|:--|
| **实战闭环档**（Real-Time Mode） | **3** | CANON28 | **12.880** | 335.5 / **481.0 ms** | **1039 / 6090** | **7.3 MB/Worker**（两 Worker 14.7 MB） | **在线跟瞄唯一兼顾可用帧率与亚秒级响应** |
| **吞吐交付档**（Throughput Mode） | **64** | CANON36 | **14.037** | 2113.6 / 8058.8 ms | 312 / 6740 | 157.3 MB/Worker（两 Worker 314.6 MB） | 硬考核 14+ fps 唯一过线档；纯吞吐场景最优 |

**两档都不损精度**：稳态逐位相同 —— D=3 **7045/7045**、D=64 **7030/7030**，F1 均 = ref（`0.905183` / `0.915359`）；
管线健康度全 0（`gmc_void_frames` / `gmc_history_gaps` / `deadline_blows` / `bufA_full_drops` / `bufB_dropped`）。

**差账**：D=64 换来 **+1.16 fps / +650 交付帧 / −727 丢帧**，代价是 **p95 延时 ×16.75**（481 ms → 8059 ms）与 **每 service 内存 ×21.4**（7.37 MB → 157.3 MB）。
相对纯串行基线 5.415 fps，D=3 已是 **+137.8%**。

**为什么不是唯一最优（两条反证）**
1. **硬考核 14+ fps 只有 D=64 过线**（D=3 差约 1.1 fps）⇒ 在以帧率为唯一验收指标的交付场景里，D=3 不合格。
2. **离线录像回放 / 事件检索 / 战后复盘延时无关** ⇒ D=3 丢 1039 帧（14.6%）成为劣势。

**D=3 仍是实战闭环档的理由**：反无人机伺服转台闭环中，**超过 1 秒的延迟会导致 PID 跟踪控制相位滞后，直接引发脱靶**
⇒ D=64 的 p95 **8.06 s** 在跟瞄链路上**不可用**；D=3 的 p95 **481 ms** 全时段半秒内，且每 Worker 仅 3 槽位 ≈ 7.3 MB，**零总线压力、无大内存分配碎片风险**。

**库封装状态**：`MOSAIC_API_VERSION` = **10**（v8→v9 机会主义动态最新帧调度；v9→v10 解耦架构 + Buffer A 槽位三态机 FREE/READY/INFLIGHT 同锁）；
轮转游标**零公开 ABI 变更**并入 v10；板卡契约测试 **104 passed / 0 failed**（14 条为新增解耦断言）；
产能均衡实测 per-service **3042 : 3048 = 1.002:1**。

**可复用结论**
- ⭐ **帕累托旋钮要按"交付场景"选档，不是按单一指标选最优** —— 同一份代码，两套参数，两种交付口径
- ⭐ **调深缓存换取吞吐是有代价的**：代价记在延时与内存上，必须与业务约束一起报
- 🔴 **对 servo 闭环类场景，延时 > 1 s 是物理不可用，不是"慢一点"**

## 第 2 部分 · 战线 B · NPU 之战

### 战果 B1 ｜ 算子回退清零：静默失效的交付硬闸门

**问题**：RKNN 链路上存在一类**不抛异常、不改指标、只让部分算子悄悄退回 CPU** 的失效。"编译通过" ≠ "模型全在 NPU 上"。

**取证**：`trial_0474` v1 有 **1 个计算算子**（`p0_highway/pool/Reshape`）落到 CPU。

**方案**：把布局变换**改写成算术** —— 用 stride-2 depthwise conv 读窗口写小图，绕开需要 transpose 的算子。

| 项 | v1 | v2 |
|:--|--:|--:|
| CPU 计算算子 | **1** ❌ | **0** ✅ |
| `rknn_run` | 151.2 ms | **103.7 ms** |
| 精度 | — | 4 种形状 `torch.equal` **EXACT**、31 帧输出**逐字节相同** ⇒ **加速零精度代价** |

**可复用结论**
- 固化为**交付前硬闸门**：NPU 上板模型必须 **0 个 CPU 计算算子**（I/O 边界的 `InputOperator`/`OutputOperator` 不计入）
- 🔴 **"静默失效"优先于"崩溃"** —— 守卫与断言必须**能被证伪**；一个永远 PASS 的检查等于没有检查

### 战果 B2 ｜ NPU 时延不能靠 FLOPs 外推 —— 全项目最反直觉的一条

**问题**：需要给 NPU 提速，但不知道该动哪里。

**方案**：删掉 P0 Highway 支路（同时达成 CPU 算子 0 + 警告 0）。

| 项 | v2 | v3（去 P0） | 变化 |
|:--|--:|--:|--:|
| `rknn_run` | 103.7 ms | **55.5 ms** | **1.87×** |
| Conv MAC | — | — | **只降 6.8%** |
| **时延** | — | — | **降 46.5%** |
| 全量 F1 | 0.906361 | **0.905736** | **−0.000625** |
| 端到端 fps | 9.5 | **17.7** | 累计 **2.69×** |

**机理解释**：P0 那几层是 `640×640 / C=16` 的**最劣形状** —— 空间乘积逼近 RKNN 的 `H*W ≤ 16384` 上限，**上限卡在"空间乘积"，与张量怎么拼无关**。

**可复用结论**
- 新铁律：**禁止用 MAC/FLOPs 外推 NPU 时延**；**禁止用 `onnx.shape_inference` 估计算量，必须用 RKNN 算子表**
- 决策模型：**宁可牺牲 0.0006 F1 换 1.87× 时延**，但**精度代价必须全量实测钉死**
- 口径纪律：**CPU fp32 代价与 int8 代价不可相加**

### 战果 B3 ｜ 640×640 Multi-Scale 拼图 × RGA 硬件画布：3 次前向压成 1 次，且逐位等价

**问题**：PC 侧 multi-scale 是**逐尺度各跑一次前向**（native 640×512 / thumb160 / thumb80，各自 letterbox 到 640×640）⇒ **3 次 NPU 前向**。板卡单次 ~100 ms ⇒ **≈3 fps，完全不可交付**。

**支点洞察**：RKNN 输入张量**静态是 `[1,3,640,640]`**，**卷积代价由形状决定、与像素无关** ⇒ 把三张画布压进**同一张 640×640**，**NPU 时间与单尺度完全相同**（实测 `rknn_run` 100~102 ms，与单尺度一致）。

**画布布局（640×640×3，背景 114 填满 3 通道）**
```
┌────────────────────────────────┬──────────────┐
│   native 640x512  (1:1)        │  背景 114    │
│   = 画布 (0, 0, 640, 512)      │              │
├──────────┬──────────┬─────────┤  ← 行 512
│ thumb160 │ thumb80  │ 背景114 │              │
│ 160x128  │  80x64   │         │              │
└──────────┴──────────┴─────────┴──────────────┘
   0      160        240
```

**方案：RGA 硬件画布，3 次 `improcess` 一次装配，逐帧零 CPU 拷贝**
- `improcess` = 缩放 + 落位**一步到位**；stb_image 解出的缓冲**直接** `importbuffer_virtualaddr` 交给 RGA
- 画布背景是**逐帧常量** ⇒ 初始化 `memset` 一次即可
- **装配耗时 0.943 ms**（含 fill + 3× improcess），相对 102 ms 的 NPU 前向可忽略；native 区与 CPU 参考**字节级一致**（max=0）

**RGA 能力实测（板端实测，非文档抄录）**

| 项 | 实测值 |
|:--|:--|
| RGA_VERSION | `v1.10.0_[9]`，**RGA_2_Enhance + RGA_3** |
| RGA_SCALE_LIMIT | **0.0625 ~ 16**（1/16 ~ 16×） |
| RGA_BYTE_STRIDE | 16 |
| MAX_INPUT / MAX_OUTPUT | 8192×8192 / 8128×8128 |
| RGA_FORMAT | RGB_888 / RGBA_8888 / RGB_565 / YUV / YUYV / Y4 … |
| RGA_FEATURE | color_fill / color_palette / ROP / quantize / src1_r2y_csc / dst_full_csc / FBC_mode / blend_in_YUV / BT.2020 |
| **核能力差异** | RGA2-Enhance 最小 2×2、1/16~16；**RGA3 最小 128×128、1/8~8** |
| 调度 | `imconfig(IM_CONFIG_SCHEDULER_CORE, n)`：**n=0 非法**（`ILLEGAL_PARAM`），n=1/2 合法 |

⇒ thumb80（80×64）低于 RGA3 最小尺寸，但实测调度器**会自动避开**（core 1/2 都成功）。

**🔴 三条 RGA 静默失效坑（全部板端实测）**

| # | 现象 | 真相 |
|:--|:--|:--|
| 1 | 缓冲区路径 | 裸 dma-buf fd + `wrapbuffer_fd_t()` → **SUCCESS 但一个字节没动**；`importbuffer_fd()` 同样空操作；**只有 `importbuffer_virtualaddr()` + `wrapbuffer_handle()` payload IDENTICAL** |
| 2 | `imcheck()` | 内部拿**全零 pat 缓冲**做检查，且**紧随其后的真实操作会静默失效** ⇒ 禁用，改显式字节预算校验 |
| 3 | 接口边界 | `imfill` **只支持 RGBA**；`imtranslate` **要求 src/dst 宽高一致**（小图放不进大画布）⇒ **只能用 `improcess`** |

附加：**必须"先填数据、后 import"**（import 时刻捕获内容）；**缓冲区尺寸精确等于 `w*h*bpp`**（多分配同样空操作）；SDK 的 dma-heap 样例针对**本板不存在的设备** ⇒ 不能照抄。

**RGA 数值语义 vs PC 侧（实测，决定能否替代）**

| 用例 | vs INTER_AREA | vs INTER_LINEAR | 结论 |
|:--|--:|--:|:--|
| **1/4 降（thumb160）** | **0.4665** | 0.5807 | **≈ INTER_AREA（0.18%）** |
| **1/8 降（thumb80）** | **1.4765** | 1.7146 | **≈ INTER_AREA（0.58%）** |
| 2× 升（热图 320→640） | 71.5131 | **0.5628** | ≈ INTER_LINEAR |
| 4× 升（thumb160→native） | 35.0962 | **1.0075** | ≈ INTER_LINEAR |
| 8× 升（thumb80→native） | 14.5688 | **0.3631** | ≈ INTER_LINEAR（max 差 1） |

⇒ **降采样方向不构成口径断裂**；**升采样方向反投影可交给 RGA**（前提：热图是 float32，而 RGA 只吃 8bit ⇒ 需量化）。
🔴 **插值参数被忽略**：`INTER_NEAREST` 与 `INTER_LINEAR` 输出**完全相同** ⇒ **RGA 恒为双线性，不要依赖这个参数**。

**服务化后（交付形态）**：**14.951 fps**（空载）/ **15.599 fps**（他人占小核），TSV md5 `0bf598a1` 与服务化前**逐字节相同**；关键路径 = NPU 单服务串行链 128.255 ms ÷ 2 = **64.128 ms ⇒ 天花板 15.60 fps**，实测墙钟 66.884 ⇒ **调度损耗仅 4.1%**（旧架构 17.187 ms）。

**可复用结论**
- ⭐⭐ **跨计算图的差值必须先拆成「同图对照」** —— 没有 B 臂（PC f32 + 同一画布 + 同一次前向），C 与 A 的差值只是「打包 + 量化」的**合计**。⇒ **「量化损失」这类结论必须能报出同口径的 f32 对照臂，否则报的是差值，不是量化损失**
- ⭐ **「差值集中在某子集」要先确认那个子集是不是唯一没被别的 bug 覆盖的子集** —— 用**配对中间量**（2,188 对的 Δx/Δy/Δpeak 中位数）而不是聚合数来定性
- ⭐ **口径参数必须从各轨 gate 产物现场抽取**（`th_base=0.3` + `dedup_radius=768`）；脚本默认值（0.22/32）得到 **0.848330**，不可与 0.897694 并列
- ⚠️ `dedup_radius=768` **大于帧内任意两点距离** ⇒ 每帧基本只保留最高分的那一个候选（det/帧 ≈ 0.5~0.8）⇒ **不是常规多框平均精度**

### 战果 B4 ｜ 精度账：7 臂对照 —— f16 代价 ≈ 0，打包的账要单独算

**方案**：设计 7 个 arm，**全部用同一个打分器重算**，关键是补 **B 臂**（PC f32 + 同一画布 + 同一次前向）。

| arm | 计算图 | 用途 |
|:--|:--|:--|
| **A** | PC f32 逐尺度 3 次前向 | **冻结基准**（gate 产物，0.897694） |
| A0 | PC f32 逐尺度仅 native | 多尺度增益的逐尺度口径基线 |
| **B** | PC f32 **拼图 1 次前向** | **隔离「打包损失」** |
| B1 | PC f32 拼图（INTER_LINEAR ≈ 板端 RGA 语义） | 隔离「缩略图重采样语义」 |
| B0 | PC f32 拼图 1 次前向，仅 native | 多尺度增益的拼图口径基线 |
| **C** | **板端 f16 拼图 1 次前向** | **本次交付的产物** |
| C0 | 板端 f16 拼图 1 次前向，仅 native | 隔离「画布里塞了缩略图」对 native 检测的扰动 |

**T3 盲测（11,810 帧）**

| arm | TP | FP | FN | F1 | ΔF1 vs A |
|:--|--:|--:|--:|--:|--:|
| A | 8,972 | 482 | 1,563 | **0.897694** | — |
| A0 | 8,530 | 286 | 2,005 | 0.881608 | −0.016086 |

⇒ ③ T2 上拼图反而**比逐尺度高 +0.000840**（FP 33→5）—— 逐尺度臂三尺度各出候选，merge 后留下的那个偶尔是误检；拼图只有一张画布 ⇒ 更稳

**可复用结论**
- ⭐⭐ **「量化损失」这类结论必须能报出同口径的 f32 对照臂，否则报的是差值，不是量化损失**
- ⭐ **用配对中间量（Δx/Δy/Δpeak 中位数）而不是聚合数来定性局部差异**
- 🔴 **被证伪的假设要给出量化上限，不能只说"不是主因"** —— 本轮把"缩略图重采样语义导致小尺度崩掉"量化到 **T3 0.000709 / T2 0.000000**

3. `slots` 在钳制**之前**算 ⇒ 环按荒谬值分配（契约测试抓到 `slots=20001`）
4. `push()` 接受错误尺寸首帧 ⇒ 静默改写管线几何
5. `push()` 恒返回 0，与头文件「Returns the frame id」矛盾

修复后：mats 60/60、特征三通道 60/60 **逐位一致**；11,810 帧 TSV 有/无缓存两版**逐字节相同**。
⚠️ 三个**已作废的数字**（坏构建/小样本，勿引用）：F1 0.824029、fps 13.905、fps 13.885。

3. **构建官方语义特征数据集** —— 通道契约固定 `[I_t, |I_t − W(I_{t−2})|, (I_t − B_t)^+]`
4. **数据集自检与 GT 对账** —— 🔴 **GT 分母 = 标注框行数（≥5 字段），不是文件数**（龙泉山：目录 **165,224 是文件数**，GT 分母 **133,279 行** ⇒ 用错**系统性偏低约 20%**）；统计技巧：用「打印一行再 `wc -l`」而不是「`awk` 累加 n」（`xargs` 会把上万个文件拆成多次 `awk` 调用，**累加变量每次调用重置 ⇒ 少算**）

### 4.4 方向 C ｜ 算法库与嵌入式组对接与集成：把"能跑"变成"能交" 〔解 L6〕

**目标**：把交付从"我们的 demo"变成"**别人能接、能验、能维护**"的库。

**已知基线**：纯 C ABI `libmosaic_pipeline.a`（主机 + 交叉均纯 C 编译通过）+ 契约测试 **42 断言** + `--feature-md5-golden` 部署自检 + 服务化 14.951 fps。

**八项改进**

| # | 事项 | 说明 |
|:--|:--|:--|
| 1 | **C ABI 的版本化** | 现在**没有版本号、没有兼容性承诺、没有变更日志** ⇒ 需要 ABI 版本号 + 语义化版本 + 弃用策略 |
| 2 | **接口契约文档化** | 42 条断言隐含了契约，但没有写成人读文档：参数语义、错误码、**线程安全边界**（`push()`/`collect()` 互相线程安全，但 NPU 服务**乱序完成**）、生命周期、回调约束（跑在 dispatcher 线程、必须短） |
| 3 | **错误可观测性分级** | 现在只有 3 个丢帧计数器 ⇒ 需要**分级告警 + 退出码语义** —— 嵌入式组要能据此判断"正常降级"还是"该上工单" |
| 4 | **背压策略参数化** | `input_queue` / `jitter_depth` 现在是编译期常量 ⇒ 需要按**相机帧率 × 算力配比**的自动推荐表 |
| 5 | **跨平台构建与版本对齐** | 需要 CMake 包 + 交叉工具链版本锁定 + `DT_NEEDED` 断言进 CI（`LC_ALL=C` 也要固化，readelf 中文输出会让断言失配） |
| 6 | **板卡运行时版本兼容矩阵** | toolkit 2.3.0 / 2.3.2 行为不同 ⇒ 需要「toolkit 版本 × 交付参数」兼容表 |
| 7 | **部署自检产品化** | `--feature-md5-golden` 已覆盖 **4 类事故**（kernel 目录 / OpenCL ICD / OpenCV 构建 / 输入帧）⇒ 变成**上板前的一键体检**，输出人读报告 |
| 8 | **验收基线固化** | 需一份**可交给第三方执行的验收脚本**，一键跑出 PASS/FAIL 清单 |

**必须随库一起交接的认知**
🔴 **OpenCV `Mat::operator=` 是浅拷贝**（只 `refcount++` 复制数据指针、**不 clone**）—— 嵌入式组若自己封装并把**非拥有视图**喂进引擎，会**原样重现**本项目的悬垂指针事故。**必须显式 `.clone()` 或持拥有型 `cv::Mat`**。

**验收判据**：第三方在**干净环境**上按文档即可跑通验收脚本拿到 PASS/FAIL；ABI 版本变更可被旧版调用方识别；告警分级能让嵌入式组区分"降级"与"故障"。

### 4.5 方向 D ｜ f16 → int8：把板端带宽、存储和输入时延压下来 〔打战线 B〕

**目标**：把 f16 换成真正的 int8 —— **输入侧 45.41 ms → 0.34 ms（133×）**，同时把存储与总线压力降下来。

**已知基线：六条硬结论（PTQ 主线，配置轴已全部封死）**

| # | 结论 |
|:--|:--|
| 1 | **PTQ 配置轴全部封死**：`quantized_dtype` 只有 `w8a8`；`algorithm` 只有 `normal`；`method=layer` 更差（cos_hm 0.96791 vs 0.97309）；`group{SIZE}` 平台死路；`optimization_level` 与 `flash_attention` **逐位零影响** |
| 2 | 🔴 **校准集轴不是能单独兑现的杠杆**：6 个 set **全部泄漏评测帧**（226/240/216/500/300/245 路径命中），四集里**只有 `set_A` 干净**；干净集全量复评**只验证过 set_6**；⚠️ `set_4`/`set_5` 尚未全量，**是否成立未知** |
| 3 | ⭐ **输入 dtype 硬闸门**：只有「toolkit 自己全图 int8 量化」能让输入停在 **INT8**（**0.34 ms** / 20,400 KB）；`--no-quant` / hybrid / **QDQ ONNX + `build(False)`** 全是 **FLOAT16**（**45.41 ms** / 105,600 KB）⇒ **混合精度 / 混合 QAT 产物不是延时意义上的 int8 模型**。判定法：开 verbose 构建后 grep 日志的 `InputOperator` 一行 |
| 4 | ⭐ **QAT 判定为负**：rk3588 + toolkit 2.3.2 上**不能兼得"比 int8 基线更准"与"INT8 输入的延时"** ⇒ 维持 toolkit 原生 int8 + **逐轨阈值重标定**（T3 0.45 / T2 0.30 / T1 0.50） |
| 5 | 两条工程更正：`mean_values/std_values` **必须给**（不传 ⇒ 255 倍输入 ⇒ null control 判死）；uint8 图输入 ONNX 在 build 期被拒 |
| 6 | 环境事实：toolkit build **非 bit-reproducible** ⇒ 引用 `.rknn` **必须带 md5**（⇒ 呼应 L6） |

**改进动作（按价值排序）**
1. ⭐ **把 LSQ 从 3 个头部位点扩到全网络（约 85 个 conv）** —— 让 Q/DQ 覆盖主体，`build(do_quantization=False)` 才能**既保住 INT8 输入又不让主体退化成 fp16**
2. **跑完 QAT 臂的全量集合**（T3 11,810 / T2 17,187 / T1 anti 31,613；板端 ≈ 5.8 h）
3. 🔴 **把 int8 与 f16 放到同一条 e2e 库管线上比** —— 现在两者是在**不同计算图**上比过的，必须补「**同图对照臂**」
4. 把**逐轨阈值重标定**从报告写进**交付参数文件**
5. 补 **`set_4` / `set_5` 的全量验证**

**验收判据**：输入张量 dtype = **INT8**（构建日志 `InputOperator` 一行自证）；三轨全量 F1 不劣于 int8 基线；**子集 F1 不能选型**（100 帧 → 2000 帧 → 全量，同类错误第 3 次）；**固定阈值 vs 各臂各自最优阈值会给出相反的赢家** ⇒ 报选型结论必须写明口径；**校准集先过泄漏自检**。
