   (5) 🔴 一条本周最值钱的工程发现：NFS 软挂载上大于 1 MB 的文件读取会损坏
       - 现象：板卡从 NFS 直接运行二进制 ⇒ 直接 `SIGILL`，板卡 dmesg 出现 NPU 超时与 soft reset，
         **表象与「驱动中毒」高度相似，但完全不是驱动问题**。
       - 判别实验三步：① 主机直读 NFS 与流式送板卡的 md5 一致（服务端数据正确）；② 板卡 NFS
         视图与流式副本逐字节比对 ⇒ **同尺寸 8,386,040 B 但有 3,741 字节被清零**，首个差异位置
         5,046,273；③ 板卡清页缓存后**立刻读回正确 md5** ⇒ 损坏发生在**板卡端客户端页缓存**。
       - 规律：坏的只有 8.3 MB 级别的可执行文件，592 KB 的静态库与 575 KB 的目标文件完全正常
         ⇒ 与软挂载的读块大小吻合 ⇒ **超过一个读块的大文件，内核会把瞬时读错误缓存成零页**。
       - 处方并升级为纪律：**大于 1 MB 的二进制一律先落到板卡 tmpfs 再执行**，绝不跨挂载直跑；
         同源坑一并修掉（软挂载「刚写完立刻读」会假阴性，验收脚本须留稳定期并对失败自动重试）。
       - 沉淀判别口诀：**「同尺寸、不同内容 = 传输或缓存损坏，不是算法 bug」**。

3. 多尺度结果融合后处理提速：单帧耗时下降一个数量级以上，输出逐字节等价（本周性能主线）

   (1) 问题定位：瓶颈不是算力，是「无效扫描」
       - 旧实现对每个 tile 做**全图双线性上采样 + 全图连通域分析**，板卡实测单帧
         **45.72 ms**（端到端全量 11,810 帧口径）/ **37.856 ms**（600 帧口径）。
       - 关键事实：**每帧扫描 983,040 个像素，而真实前景只有 1,822 像素，占比 0.185%**
         ⇒ **99.8% 的像素是白扫的**，这一条直接决定了整个优化方向。

   (2) 优化手段：稀疏反投影 + 8 连通域（CPU NEON 路径）
       - 核心原理：由于双线性插值是凸组合，**插值结果必然不高于其源热图的最大值** ⇒ 可以先在
         源热图上筛出候选位，只对候选位做上采样求值，无需全图扫描。
       - 实现上以「阈值减去浮点余量」构造安全上界，保证筛选不漏候选；配合 8 连通域提取，
         候选数实测仅 2~4 个。
       - 附带把稳态堆分配次数也降为 **0**（用保序稳定插入排序替代归并缓冲，候选数极少时 O(n²)
         无压力，相等时保序 ⇒ 与原实现逐字节相同；候选数超过阈值时自动退回原排序路径）。

   (3) 实测结果（同一台板卡、同一序列、同一口径）
       - 端到端全量 11,810 帧：**45.7246 ms → 0.6753 ms/帧**。
       - 600 帧口径：**37.856 ms → 0.531 ms/帧**（σ 0.728 → 0.219）；单帧最坏 40.665 ms → **1.037 ms**。
       - 板上零参数直接运行：**0.625 ms/帧**。
       - 端到端延时 p50/p95/p99 由 363.7 / 493.3 / 526.5 ms 降到 **312.1 / 445.0 / 464.2 ms**
         （**−10~14%**）；吞吐基本不变（12.872 → 12.764 fps，−0.8%）。

   (4) 精度影响：零损伤（逐字节等价，不是「误差可忽略」）
       - **ΔF1 = +0.000000**：TP / FP / FN 逐项相同，输出 TSV 的 md5 逐字节相同，业务侧判定翻转
         **0 帧**。
       - 全序列对齐门禁 **VERDICT PASS**（特征 md5 逐位相同、检测流差异 0）。
       - 🔴 由此得到一条本周必须写清的判定：**后处理是「延时税」不是「吞吐税」** —— 优化掉 98.5%
         的后处理时间，吞吐只动了 −0.8%（真实瓶颈在 NPU 推理段），但每帧交付延时降了 10~14%
         （它在串行依赖链上）；POST 线程由「忙不过来」变为 **77% 时间在等活干**。
       - 由此，**已认证臂的历史数字不需要重跑** —— 因为稀疏路径与旧路径逐比特一致。

   (5) GPU（OpenCL）路线也做了实测：结论是「可用但不占优」，已作为备选保留
       - 稳态 **0.857 ms/帧**（上传 0.213 / kernel 0.564 / 回读 0.072），与 CPU NEON 路径处于同一
         量级但**慢 1.6×**（GPU 的派发与回读仍发生在 CPU 侧）。
       - 🔴 有一个 **54.324 ms 的首帧尖刺**：逐帧样本定位到只有第 0 帧出现，且不在 GPU 计算里 ⇒
         是 **OpenCL 上下文/程序/缓冲区的一次性懒初始化**。⇒ 短跑看到的「3.6 ms/帧」是把首帧摊薄
         后的假象，**任何 GPU 后处理的短跑数字都必须先问一句首帧摊了多少**。
       - 精度侧曾掉分（ΔF1 −0.0081，FP 19→29），根因已定位：旧实现与旧实现取「峰」的量纲不同
         （上采样后原图分量最大值 vs 源热图局部极大值，双线性是凸组合故后者偏高）⇒ 同一个阈值在
         两侧变成了两把尺子。修正后 FP 回落、判定翻转归 0。
       - 全序列门禁 **FAIL**（检测流存在差异、虚警率高于稀疏路径）⇒ **默认采用 CPU NEON 稀疏路径**，
         GPU 保留为环境变量可切换的备选（需要腾空小核、无 NEON 平台或希望独占 GPU 时用）。

   (6) 已固化为默认
       - 后处理默认模式由 DENSE 改为 SPARSE（库内初值 / 环境变量缺省 / 示范程序缺省 / 公开头文件
         注释四处同步），并完成板卡复验（契约 196 passed、交付包独立编译通过、一键脚本 EXIT=0）。

【不可外推的纪律】
(1) 本周产出分属两个互不相通的口径 —— **嵌入式组交付件（板卡实测口径：fps / 延时 p50 / 契约
    196 passed / ΔF1 = +0.000000）** 与 **算法评测口径（业务域与官方域 F1 / FAR）** ——
    **不可相互比较、不可取平均、不可跨口径做差值归因**。
(2) **后处理耗时是「延时税」不是「吞吐税」**：优化 98.5% 的后处理时间，端到端吞吐只动了 −0.8%
    （真实瓶颈在推理段）⇒ **不得用「后处理提速」推出「整链提速」或「帧率提升」的结论**。
(3) **GPU 后处理的任何短跑数字都不可直接引用**：短跑会把 OpenCL 一次性初始化摊薄（实测首帧
    54.324 ms、短跑假象 3.6 ms/帧），**必须报稳态值**（0.857 ms/帧）并标注是否剔除首帧。
(4) **编译产物 md5 不可跨构建路径比对**：同源码不同构建路径会因编译期嵌入的绝对路径不同而
    md5 不同（字节数一致）⇒ 属路径差异而非代码差异，**行为等价须由输出指纹与精度判据证明**。
(5) **软挂载上的大文件读取不可信**：大于 1 MB 的文件在软挂载下存在读错误被缓存成零页的可能
    ⇒ 跨挂载执行前必须先落到本地 tmpfs，并以「同尺寸、不同内容 = 传输或缓存损坏」的判别
    口径区分「环境问题」与「算法 bug」，**不得直接归因为驱动或算法缺陷**。
(6) **汇报只呈现已验收结论**：未经认证的实验不上片，其数据仅保留在实验室页与遗留清单中；
    汇报中的每个数字必须可溯源回事实层，**汇报与档案冲突时以档案为准**。
