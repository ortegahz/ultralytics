二、核心进展

1. 跟踪算法与时空滤波后处理：**板端 SDK 纯追加「跟踪结果回调」，两板实测达成「一目标一框」，并与嵌入式组完成联调**

   (1) 先把现象说清楚：「一个目标身上 2~3 个框」**不是 SDK 的 bug**
       - mosaic 检测器是**三尺度**的（原生 640×512 瓦片 + 160 px 缩略图 + 80 px 缩略图），回投影后
         **每个尺度各自做 8-连通域** ⇒ 同一个目标在每个尺度上各出一个连通域。
       - 板卡实测（60 帧）：每帧 **2 个框 × 9 帧 / 3 个框 × 51 帧**；`tag` 直方图 `tag0=60 / tag1=60 / tag2=51`
         （`tag` 字段即标尺：0=原生瓦片 / 1=thumb160 / 2=thumb80）；同帧框对中心距
         **min 0.53 / p50 4.99 / max 10.64 px**（100% ≤ 20 px 合并半径）⇒ 三个框其实是同一个目标。
       - 另一组对照（2500 帧）：原始候选流 **26,493 框** vs 跟踪流 **1,448 框**（**18.3×**）；
         原始流每帧 **2~69** 框（含大量低于阈值 `th_base=0.48` 的弱杂波），跟踪流每帧 **0~2**。
       - ⇒ 结论：这是「**多尺度候选流按设计未合并**」的正常语义，**不是缺陷**；要「一目标一框」必须走**跟踪通道**，
         而原始接口的公开语义**不许动**（在它上面加去重会打破已认证的交付物判据）。
       - 库内其实**已经**合并了：`FeedFusion()` 先用 `MergeCandidatesByRadius(radius=20 px)` 把跨尺度重复候选压成 1 个
         再喂进跟踪引擎；合并半径可用环境变量 `MOSAIC_TRACK_MERGE_RADIUS` 标定（就是为做 A/B 留的旋钮）。

   (2) 算法侧：在**交付底座**上重搜「跳帧」参数，并测出「**帧率降到多少，跟踪器就不能用了**」
       - 上轮跳帧（Δn）超参搜索跑在**旧底座**上，不是交付底座 ⇒ 参数不能直接用于交付
         ⇒ 本周在交付底座 + 交付工作点上重搜，目标函数加了「逐帧口径不回退」硬约束。
       - 结果：新最优参数组 `cc2_md10`（连续帧确认 **2** / 间隙容差 **8** / 分数衰减斜率 **5** /
         关联距离 **10** / 最小命中 **3** / 物理帧龄不限），并已**同步进板卡 C++ 默认值**
         ⇒ 嵌入式同事**直接用交付包即可，不需要手动传这 8 个参数**。
       - **跨尺度合并（半径 20 px）在跳帧交付口径下是决定性的一刀**（同一 `tag_mask=7`、仅半径不同的严格可比 A/B）：
         合并关 FAR **0.4912** / F1 **0.5751** / Precision **0.5484**
         ⇒ 合并开（交付值）FAR **0.0985**（**−80%**）/ F1 **0.6733**（**+9.81 pp**）/ Precision **0.8482**（**+29.98 pp**）。
       - **交付帧率网格（第 91 轮）**把「降到多少帧率，跟踪器就不能用了」算成一张可查的表：
         `v3` 基座的可用下限落在 **14~17 fps** 之间 —— `f17`（17.1141 fps）F1 **0.854244**，
         `f14`（14.1043 fps）F1 **精确为 0**；交付参数组 `cc2_md10` 把下限压到 **≤ 12.11 fps**
         （全档 F1 ≥ **0.943001**、FAR ≤ **0.027166**，红线 0.03）⇒ **要救的是参数组，不是板卡速度**。
       - **机制已钉死**：最长连续交付帧数 < 连续帧确认数 的航迹整条丢弃（`v3` = 7/0，`cc2_md10` = 2/8）
         ⇒ 规则与观测 **8/9 场景吻合**，其中 5 个场景 `v3` 的 F1 精确为 0。
       - ⚠️ **机制只解释 8/9，不是充分条件**：`f14` 恰在门槛上（最长连续交付帧数 = 7 = 确认数），
         机制只「允许 >0」，实测却是 0 ⇒ 对外只能讲「8/9 吻合」。

   (3) 交付侧：SDK **纯追加**一个跟踪结果回调，嵌入式「改 1 个函数名 + 1 个结构体类型」即可
       - 接口：`mosaic_pipeline_set_tracked_callback(p, cb, user)`，回调形参
         `(void* user, int64_t frame_id, const MosaicTrackedDet* dets, int32_t n_dets)`。
       - **公开接口 34 → 35**，`MOSAIC_API_VERSION` 仍为 10，既有 34 个接口**签名与语义一字未改**
         （头文件与实现的导出符号集合**双向差集为空**，已实测）。
       - 三条语义写死在接口契约里：**注册即切换**（注册后跟踪结果走回调、不再进轮询队列）/
         **退回**（置空即回到原队列）/ **pending 不丢帧**（切换时两边待派发帧互搬）。
       - 为什么要给回调：轮询接口被当成队列用会**无界泄漏**（不取就每帧涨一条）⇒ 嵌入式被迫自己写轮询线程。

   (4) 两块板实测（同一套库、同一套验收工具）
       | 板卡 | 契约测试 | 原始候选（raw） | 跟踪结果（tracked） | 帧内 track_id 重复 |
       |---|---|---|---|---|
       | EVM3588 实验板 | **217 通过 / 0 失败** | 60 帧 / **171 框** / 单帧最多 3 | 60 帧 / **60 框** / 单帧最多 **1** | **0 帧** |
       | Orange Pi 5 实际交付板 | **217 通过 / 0 失败** | 60 帧 / **168 框** / 单帧最多 3 | 60 帧 / **60 框** / 单帧最多 **1** | **0 帧** |
       - **零行为漂移**：同板旧库 vs 新库，检测 TSV md5 **逐字节相同**（实验板 `8e556afa…`、
         交付板 `ceea5fe6…`），且与**改动前**的归档基线三方 md5 全等
         ⇒ 本次新增接口**没有改变任何既有输出**。
       - **验收补强**：补上 `flush()` 生命周期与派发顺序的契约断言（此前实现是对的，但**没有断言钉住**，
         以后有人改派发逻辑会静默回归）⇒ 断言数 199 → **217**。
       - 🟢 **「两个回调不是必须同时注册」两板实测钉死**：只要「一目标一框」，**只注册跟踪回调一个即可**
         （代价是原始候选流不再缓冲，`collect()` 返回 -1 并告警一次）；第二个回调只用于同帧对照。

   (5) 与嵌入式组的联调：适配**实际交付板** + 交付包口径收口
       - **实际交付板不是我们一直用的那块**（Orange Pi 5 / Debian 12 / glibc 2.36 / gcc 12.2.0），
         **三个真问题**定位到根因并修掉，根因都不是「参数没调好」，而是「**环境假设错了**」：
         ① **OpenCV 版本被选错**（最要命）：旧逻辑是「哪个 multiarch 目录存在就选哪个」
            ⇒ 同一进程装了两套 OpenCV（4.8 的头配 4.6 的运行库）⇒ 次版本 ABI 不匹配；
         ② 板上 OpenCL **只有 ICD loader、没有 `libOpenCL.so` 开发软链** ⇒ `-lOpenCL` 链接必失败；
         ③ demo **硬编码旧板的 NFS 路径**（新板根本没有 NFS 挂载）。
       - 改造：新增板卡无关的路径解析层、**随包提供 4.8 版 OpenCV 头**（211 个文件）、板卡原生构建脚本；
         并修掉一个真 bug（`size_t` 缺 `<cstddef>`，板卡 gcc 12.2 直接编译失败）。
       - **上板零漂移验收**：静态版 / 共享版 / 零参数版三份产物检测 TSV md5 **全部相同**，
         且与改造前基线**逐字节一致**（60 帧 / 168 检出 / 0 丢帧）。
       - **板卡原生重编闭环**：整包（**299 文件** = 286 包体 + 13 个产物）tar 到板卡，
         用板载 g++ 12.2.0 跑包内构建脚本 ⇒ 构建通过，原生产物 md5 **同为 `ceea5fe6…`**
         ⇒ 两条独立编译路径产出逐字节一致。
       - **线上库已替换并复验**（经集成方授权、确认 app 处于停止状态后才动手）：三处
         （app 实际加载点 / `/usr/lib/` / `/root/bts/`）同目录临时文件 + `mv` 原子替换（不动运行中进程的 inode），
         保留可回滚备份；替换后 `ldd` 无 `not found`，公开接口 34 → 35，
         **检测 TSV md5 仍是 `ceea5fe6…`**，契约 **217 / 0**。
       - **交给嵌入式组的东西**：集成清单（MANIFEST）+ 集成说明（README），含两个可直接跑的样板
         （最小单线程原型 / 多线程生产-消费+回调模板），并把「板卡无关」与「板卡相关」分清写死。

   (6) 本条目的已知边界（如实留档，不掩盖）
       - 🔴 **一个已知缺陷未修**：单独注册「扩展结果回调」时，产出原始结果处**只判了普通回调、没判扩展回调**
         ⇒ 该回调**永不触发**，且契约测试**无覆盖**；修法是一行，但会改变既有客户端的行为
         ⇒ 已定位、**未擅自动**，提交决策。
       - 🟡 **客户 app 实跑未验证**：替换线上库时 app **未运行**，**未擅自启动客户 app**
         ⇒ 这一项留给集成方复验。

         ≡ C++ 对齐器**（5 序 / 14,745 帧三方 md5 逐位相同）」⇒ 差异在**检测灵敏度边界**，不在跟踪实现；

3. 图像质量评估：**初版完成 —— 把「好片 / 坏片」的红线算出来，而不是给一个模糊的印象**

   (1) 做成了什么
       - 规模：**25 条片**（好 18 = 红外 6 + 可见光 12；坏源 4 = 红外 2 + 可见光 2；坏 OSD 3 作参考组）、
         **13,207 个逐秒窗口**、**211,312 次模拟点击**、**26,490 次 48 宫格逐秒评估**、
         **396 个退化变体**（18 片 × 22 档）。
       - 机制：先把「画面局部纹理可跟踪性 → 跟踪效果」的因果链做实（推翻过「拿检测器跑无无人机视频」的错误路线），
         再从膝点**反解画质合格线**；采用原则是「片级坏片 100% 拦截 + 片级好片误杀尽量小」。
       - **结论不是「晃」，是「糊 + 灰 + 压」**：`global_contrast` / `edge_density` / `lap_var`
         三个指标（红外另加 `blockiness` / `entropy`）⇒ **5 个有效指标**；
         `snr_db` / `noise_sigma` / `dog_snr_max`（AUC 0.111~0.333）**一律不得当合格线**，
         另有 **13 个「指标对但方向反」的组合被剔除**。

   (2) 初版结论（红外 / 可见光**分列**，不混池）
       | 模态 | 采用线（短时程 5 帧） | 坏片拦截（片级） | 好片误杀（片级） | 过线好片跟住率 |
       |---|---|---|---|---|
       | 红外 | `global_contrast ≥ 0.577855` **AND** `lap_var ≥ 6.49303` | **100%（2/2）** | **16.67%（1/6）** | 95.97% |
       | 可见光 | `lap_var ≥ 306.474` | **100%（2/2）** | **0%（0/12）** | 91.99% |
       - 盲测：**4 条未参与标定的坏片 + 18 条好片**，两族方法给出**逐位相同**的坏片拦截率。

   (3) 最有说服力的一步：**用两族原理完全不同的跟踪器独立反推**（方法无关性）
       - 一族是**像素互相关**（逐帧重切模板 + ±12 px 搜索），另一族是**经典相关滤波 KCF**
         （高斯核 + 傅里叶域滤波 + 在线模型更新）。
       - 结果：**被采用的两条线几乎逐位复现**（红外短时程 `global_contrast` **0.577855 逐位相同**、
         长时程 `lap_var` **7.843251 逐位相同**），**盲测坏片拦截率 100% 相同**
         ⇒ 说明这条红线卡的是**图像本身的物理信息底线**，不是某一个跟踪器的实现细节。
       - 🟢 顺带定位到一个只有真机才会暴露的坑：KCF 家族里 `detect_thresh=0.5` 是**全部失锁的唯一来源**
         ⇒ 关掉它之后，同一批点击原本第 4~20 帧就断的链条**全部跟满 30 帧**。

   (4) 初版的三条边界（必须一起讲，别把「完全一致」讲过头）
       - 🔴 **跨家族的绝对锁定率刻度不可互换**：KCF 家族的一致性校验 **CHECK 1 FAIL**
         （平均差 **0.161** > 容差 0.12；像素互相关侧 0.082 PASS）⇒ 两族**数值并列呈现、不做合并**。
       - 🔴 **可见光长时程两家族差 58%** ⇒ 该格**不采用**（且该格本来也按「不采用」处理）。
       - 🔴 **坏源片只有 4 条** ⇒ 「坏片拦截 100%」仍属**小样本结论**，上线前必须扩样重标；
         实测还发现其中一条坏源片本身尾部截断 5,205 字节。
       - ⚠️ 测的是「**画面局部纹理可跟踪性**」，**不等于无人机跟踪成功率**（测试片里没有无人机，
         用的也不是交付模型）。

       - ✅ **两族方法的比较是同口径**：同一批片、同一套点击协议、同一份阈值复算口径。
