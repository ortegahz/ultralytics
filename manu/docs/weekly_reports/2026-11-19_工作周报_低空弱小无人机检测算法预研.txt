二、核心进展

1. 与嵌入式组联调：**RGA 内核 Oops 定位并根治**（用户态结构性修复，给嵌入式组 2 个文件即可）

   (1) 现象与决定性定位
       - 嵌入式组报的「push 帧报错」**不是应用层 bug，是内核 RGA 驱动被打挂**：SDK 每帧用
         `importbuffer_virtualaddr()` 导入画布，内核因此给该 buffer 打上 `RGA_MEM_FORCE_FLUSH_CACHE`，
         作业时执行 `dma_sync_single_for_device(dev, buffer->phys_addr, size, dir)`，而 `phys_addr`
         在这条链路上可以是 **0** ⇒ 内核拿 `phys_to_virt(0)` 刷 cache ⇒ `Internal error: Oops: 96000146`
         ⇒ **整个进程 + 内核挂掉**（嵌入式组 `log.txt` 与我方复现完全同型）。
       - **两种表现必须分开看**（决定了排查方向）：客户端**启动**（首次 `ComposeFrame`）时 1~5 组报错 + 1 次 Oops
         ⇒ **只打死调用线程，板卡存活**；客户端**收尾释放**时 ⇒ **整机静默复位**；**稳态运行全程 0 次报错**。
       - 排除项（A/B 矩阵，全部实测）：换 2024 版 `librga` 仍崩（与 librga 版本无关）、不 release 仍崩、
         画布只 import 一次仍崩、**CPU 拼图完全不调 RGA ⇒ 零 OOPS 干净跑完**、2 线程并发不崩
         ⇒ **RGA 作业就是触发器**，不是并发、不是版本、不是 buffer 生命周期。
       - 内核栈 7 次逐字节一致：`rga_job_commit → rga_mm_map_job_info → rga_mm_get_channel_handle_info →
         rga_mm_get_buffer → rga_mm_sync_dma_sg_for_device → dma_sync_single_for_device`，驱动未判空。
       - 顺带修掉第二个真 bug：`rga_buffer_handle_t` 是 uint32，失败哨兵 `-1` 实为 `0xFFFFFFFF`，
         原代码用 `handle > 0` 判「import 成功」⇒ **失败 import 被当成成功**、坏句柄塞进作业。
         已改为显式 `kRgaInvalidHandle` + `bool imported` 标志。

   (2) 根治方案（用户拍板的方案二）：RGA 的输入/输出缓冲全部改成**初始化时一次性分配的 dma-buf**
       - `/dev/dma_heap/system-uncached` + `mmap` + `importbuffer_fd()` ⇒ `wrapbuffer_handle()`，
         **任何虚拟地址都不再传给 RGA**。内核里 fd 路径走 `rga_mm_map_dma_buffer()`，它**不打**
         `FORCE_FLUSH_CACHE` ⇒ **那条崩溃分支在结构上不可达**（不是"概率降低"，是路径不存在）。
       - 改造面（`manu/pipeline/npu/mosaic_core.h`）：新增 `DmaHeapAlloc()` / `BufAllocDma()`；
         `RgaBuf` 增 `fd / map / map_len / cached`；`BufImport()` 按 `fd >= 0` 分流
         `importbuffer_fd()` / `importbuffer_virtualaddr()`；`BufFree()` 增 `munmap` + `close(fd)`；
         `ComposeFrame()` **源帧先 memcpy 进 dma-buf staging buffer** 再把 staging 的 fd 交给 RGA；
         画布改成**初始化时 import 一次**、每帧复用。
       - 附一条实测更正：RGA 的 buffer 内容是「**作业时读取**」而非「导入时快照」⇒ 画布只需 import 一次；
         同时实测**fd 路径能真正搬数据**（旧笔记「只有 virtualaddr 能搬数据」已过时，待同步更正）。

   (3) 验收（板卡实测，交付包同款件）
       - SDK 流水线 25 / 60 帧全绿：`RGA native-tile self-check: OK`、`fallback summary: clean`；
         400 帧（56 s）`fallback summary: clean` ⇒ **OOPS 计数 7→7（零新增）**。

3. 量化部署准备：**QAT 线按证据收口，交付前置条件固化成可执行闸门**

   (1) 本周结论：QAT 精度攻关到此收口（负结果已定案，不再在不可用路线上投入）
       - **在 rk3588 + toolkit 2.3.2 上，QAT 不能兼得「比 int8 基线更准」与「INT8 输入的延时」。**
       - 三条约束互锁：① 要 INT8 输入 ⇒ 只能用工具链全 int8 配方 ⇒ **只能用 base 权重**
         （A2f 证明 QAT 权重走这条路必炸）；② 要 QAT 权重 ⇒ 必须 Q/DQ + `build(do_quantization=False)`
         ⇒ **InputOperator 退化为 FLOAT16**（`inputs_set` **45.41 ms**，比 int8 的 **0.34 ms** 慢两个数量级；
         板端 **5.64 vs 13.16 fps**）；③ 即便接受 FLOAT16 输入换来的精度，**T3 仍低于 int8 基线**
         （0.6863 vs 0.7090）。
       - 根因**四刀定位**（逐条排除，不是"量化范围问题"）：ORT 在 **float** ONNX 上就已爆炸
         （001324 检出 7847→51373，×6.55）⇒ 排除量化范围；算子直方图相同 ⇒ 排除图错；
         RKNN 算子表逐项相同 ⇒ 排除构建/导出 bug；权重级 diff `head.heatmap.0.weight` rel_l2=0.266、
         均值 +0.004326→+0.006635（**+53%**）⇒ **根因＝QAT 把 heatmap 头搬坏**（logit 正偏置 ⇒ sigmoid 饱和
         ⇒ 过自信 ⇒ 固定阈值下 FP 爆炸）。
       - **训练损失不得作为 QAT 有效的证据**：train_loss 0.3487→**0.3243**（降了）而 F1@0.30 0.7817→**0.5304**。

   (2) 量化精度基线固化（全量口径，可对外引用）
       - int8 vs PT float，**同帧 / 同 GT / 同阈值**，**60,610 帧 / 123 块 / 0 失败 / 0 缺失 GT**：
         T1 官方域 **−0.0189**、T2 黄金池 **−0.0394**、T3 盲测 **−0.0795**（@th=0.30）；
         逐轨各自最优阈值处 **−0.0232 / −0.0401 / −0.0370**。
       - ⇒ **量化损失的正确解是「逐轨阈值重标定」，不是「换一个量化模型」**。
       - **逐轨部署阈值固化**：T1 **0.35** / T2 **0.55** / T3 **0.55**，阈值位移**逐轨给**（**0 / −0.10 / +0.05**），
         **不是通用 +0.10**。
       - **部署模型维持 toolkit 原生 int8**（`p0_off_A_normal.rknn`，md5 `cedaeb74…`，`InputOperator INT8`，
         `inputs_set` 0.34 ms）—— 明确**不替换现有 PTQ 模型**。

   (3) 部署前置闸门固化为 10 条**可执行判据**（不是口号，逐条可查）
       ① `InputOperator` 必须 INT8（须用 verbose 打印算子表，`verbose=False` 时该表不打印）；
       ② `mean_values` / `std_values` 必须给，否则运行时把 uint8 拓宽成 FLOAT16、null 输入直接死在
       `FATAL: NPU output independent of input`；③ 引用 `.rknn` **必须带 md5**（toolkit 构建**非 bit-reproducible**，
       同一配方出过 3 个 md5）；④ QAT ckpt 必须连同 `*.qdq_meta.json` 的 scale 一起发布；
       ⑤ 板卡身份从换板档取，**不硬编码 IP**；⑥ **板卡根分区余量必须进预检**（97% 满时 RKNN 上传会**静默失败**，

【不可外推的纪律】
(1) **板卡身份已变，两块板并存**：`.64` = **EVM3588**（Ubuntu 20.04.6 / rknnrt 2.3.0 / 原实验板）、
    `.211` = **Orange Pi CM5**（Debian 12 / rknnrt 2.2.0 / 嵌入式同款）⇒ **上周「旧板 `.64` 已彻底作废」已失效**
    （11-18 实测 `.64` 重新上线、身份核对为原始 EVM3588）；任何时延 / fps / 帧率数字**必须标注是哪块板**。
(2) **「位级不一致」不等于「精度退化」**：换板后 md5 一致率低，根因已定性为 **OpenCV 4.10→4.6 的亚像素差**
    （实测坐标差中位 0.0000 px、≤0.5 px 帧占比 99.48%、ΔF1 = −1.03e-4）
    ⇒ **不得把「md5 不全等」表述为精度下降**。
(3) **dma-fd 的 A/B 是「同一个新库换开关」**，不是两个版本对比 ⇒ 修复点确凿；
    但 `MOSAIC_RGA_DMA=0` 那条路径**会打死内核** ⇒ **禁止在生产板卡上复现**。
(4) **量化损失必须标口径**：全量口径（T1 −0.0189 / T2 −0.0394 / T3 −0.0795 @th=0.30，60,610 帧）与
    QAT 臂子集口径（2000 / 1197 / 100 帧）**不可混用、不可取平均**；逐轨部署阈值 T1 0.35 / T2 0.55 / T3 0.55
    属**全量口径**，误引子集阈值（0.50 / 0.30 / 0.45）即错。
(5) **QAT 是负结果，不得当作候选**：A2 臂在 T2 子集打过 int8 基线，但那是**子集口径**且 T3 反而输
    ⇒ 不得引用为「量化精度已提升」；**训练损失下降也不得作为 QAT 有效的证据**。
(6) **`verdict=FAIL` 不等于交付失败**：`gate_report.json` 的 FAIL 来自早期冻结红线，
    判交付必须用**任务书交付红线**口径 ⇒ 两个参照系必须分开记账。
(7) **标注效率目前只有定性结论**：自检 101/101、拷贝 md5 全一致是**可核事实**；
    但「提升多少效率、降低多少成本」**没有实测前后对比** ⇒ 对外只能讲机制，**不得编造百分比**。
(8) **自检 101/101 只在 X11 / Windows 通道成立**（断言条数随环境变）⇒ 引用该数必须带环境说明。
(9) **设备凭据与连接口令不得进入任何对外汇报材料**；汇报只呈现已验收结论，
    **汇报与档案冲突时以档案为准**，未经认证的实验不上片。
