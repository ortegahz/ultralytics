一、本周任务承接
===================================================================================================
承接上周「标注质检收口、嵌入式耗时调研立项、业务域全量评测」的三条线，本周工作重心进一步向
「工程化交付能力」推进，具体分四条线并行展开：

1. 新采集视频域的模型可用性摸底：纵横AI数据采集域 58 条视频是本周新增的交付候选域，此前算法侧
   从未在该域上运行过。此前的多尺度评测工具全部以「帧序列 + 已有特征缓存」为输入假设，而新域只有
   裸 mp4、无 GT、无预抽特征。本周打通该域的多尺度推理链路，并对输出做人工目视定性，形成第一批
   问题清单。

2. 快速标注工具开发：业务域交付要求逐帧 GT，而龙泉山域的标注经验暴露出「人工逐帧找未看帧」与
   「反复画同一个目标」是纯手工环节的主要时间成本，远大于画框本身。本周把这部分工程化，做成
   可复用的半自动标注工具。

3. RK3588 板卡环境配置与测试程序开发：上周时延调研的结论是「现有四套数字口径分歧、无一可直接进
   预算」，根因是板卡侧环境本身未建立。本周从板卡环境勘察入手，把「有没有这个硬件能力」这个问题
   一次性问清楚，并配套开发可复用的探针与对账程序。

4. GMC 特征管线的 CPU/GPU 拆分与精度对齐：上周定位到板卡瓶颈在 CPU 侧的 warp 与时域中值（合计
   86.1%），而非 GPU。本周据此把这两段整体迁往 GPU 融合内核，并对迁移前后做严格精度对账，
   保证「加速」不以牺牲数值一致性为代价。

本周工作性质以「打通链路、建立工具、建立口径」为主，不涉及底模结构调整，Trial 0474 单帧基线
保持冻结；Anti-UAV 官方域指标维持不变。


二、核心进展
===================================================================================================
1. 纵横AI新采集域 58 条视频多尺度推理与目视定性（推理已完成，定性发现 3 类问题）
   (1) 新域基本情况与首要障碍——画幅契约不一致：
       新增交付域「纵横AI数据采集」共 58 个 mp4 / 1920x1080 / 25fps / 约 174k 帧，帧数跨度较大
       （长序列约 3150 帧，短序列 243~1741 帧），【无 GT】。算法侧的输入假设是原生 640x512 红外帧，
       而原始素材是 1920x1080 视频，首要问题是画幅还原参数必须逐域重新测定，不能沿用旧域经验。
       本周用 ffprobe + 逐帧投影双重取证，确认该域 letterbox 内容框为 x[320,1599] y[0,1023]，
       58 条视频取值完全一致，还原参数确定为
           --crop-left 320 --crop-top 0 --crop-width 1280 --crop-height 1024  ->  原生 640x512。
       🔴 与龙泉山域的关键差异：龙泉山是 --crop-top 28，本域是 --crop-top 0。同一模型下 crop-top
       相差 28 行不是小误差，静默沿用旧参数会导致画面整体错位、推理结果不可用。本周把该参数固化为
       工具的域级配置项，避免后续任何一次「想当然的复用」。

   (2) 多尺度推理工具（面向无 GT 域的流式渲染）：
       新增 render_multiscale_osd_video.py，直接吃 mp4 流式出带 OSD 的视频，不落帧、不落 pkl。
       关键设计是【推理链与评测大盘复用同一份代码】：特征与多尺度算子复用既有实现，OSD 绘制复用
       既有实现，因此本域的定性观察与龙泉山域的全量评测在算子层面完全同源，不存在第二套实现漂移。
       默认工作点与业务域评测大盘一致（多尺度 160/80、主门限 0.30、跨尺度合并半径 64、区域门限
       0.06、最小连通域面积 4），确保「换个域跑一遍」不改变判定口径。
       工程配套：--shard i/n 多卡分片、--skip-existing 断点续跑、--out-json 落每视频的检出帧数与
       首末检出帧号，用于在无 GT 域快速定位目标出现的帧区间。

   (3) 一处必须写明的时序陷阱：
       --start 参数只门控渲染、不门控 GMC 历史——早于起始帧的画面照样喂进全局运动补偿与 21 帧时域
       中值窗口。这是刻意设计：若让渲染帧坐在冷历史上，前若干帧的运动估计与背景建模都不可信。
       但代价是「截断渲染」得到的结果不能与全量渲染直接混比，这与此前 Tree-GMC 对照实验中
       「前 22 帧完全相同、之后才分叉」属同一类陷阱，已在工具说明中显式标注。

   (4) 推理执行情况：58 条视频已全部完成多尺度推理与 OSD 渲染。

   (5) 人工目视定性发现（本周主要结论，均为定性、待 GT 定量）：
       a. 悬停目标召回差，且复杂背景下悬停更差；相对地，运动目标的检出明显更稳定。
          机理与既有认知一致——悬停目标在 21 帧时域中值窗口内会被同化成背景，而运动目标持续偏离
          背景，天然保留对比度。复杂背景会进一步抬高同化速度（背景更新更快、干扰更密）。
          这也印证了「悬停目标与静态坏点在特征层同构」这一既有认知，需要专门的高置信驻留保护机制，
          不能指望调门限解决。
       b. 近距离大目标的检出不如中等距离目标稳定，倾向仍是感受野/尺度失配问题。
          与上周在龙泉山域做过的「近距离大目标直接 160 下采样」定性实验结论一致：目标并非没有
          输入能量，而是点目标微架构与大目标尺度不匹配。属旁路候选，不能替换现有生产分支。
       c. 路灯与窗户存在误检，且置信分数不低——纯工作点问题无法解释，需要专门压制。
          与业务域此前定位的「地表路灯虚警」是同一类。
       ⚠️ 以上三条均为目视定性结论。该域【无 GT】，本域产物只有单色检测框、无 TP/FP 语义，
       因此【不得据此宣称 Recall / Precision / F1 提升或下降】。下一步需补最小人工标注，
       才能把这些观察转成可验收的定量指标。

   (6) 本条线的工程价值：打通了一条「裸 mp4 进、带检出的视频出」的无 GT 域推理通路，并与评测大盘
       同源；更重要的是拿到了第一份新域问题清单，使后续精力可以对准真实失效模式而非盲目调参。


2. 网页快速标注工具开发与交付（manu/annotate/，已完成并部署运行）
   (1) 定位与痛点：
       视频标注的瓶颈不是画框，而是两件事——在十几万帧里找到还没看过的帧，以及反复手画同一个
       目标。本工具把这两项工程化，定位是「压人工逐帧标注的时间成本」，不涉及任何模型改动。
       链路：递归扫描视频 -> 多尺度 Trial 0474 预标注 -> 浏览器逐帧标注 -> 导出 YOLO 格式 GT，
       导出格式与现有交付链路（扁平每帧一文件、空文件即无目标）完全对齐，可直接回灌。

   (2) 架构上两个关键取舍：
       a. 【候选与人工彻底分离】：模型候选写入 prelabels/，人工结果写入 labels/，模型重跑
          永不覆盖人工。这不只是目录隔离，而是让「未复核」有了明确定义——仍是原样的帧就是还没看
          过的帧，工作队列因此天然成立。
       b. 【零依赖服务端】：本机无任何可用 Web 框架，服务端只用 Python 标准库 http.server 实现，
          不引入任何新依赖，任何解释器都能起；推理侧按环境能力自动选择「就地推理」或「远程推理」。

   (3) 效率机制（工具的核心价值）：
       航迹传播（按上一帧实测速度外推，遇已有标注自动停）、航迹插补（当前帧到下一标注帧之间线性
       插值，一次请求批量落盘）、跳未复核（沿时间线直达下一个未复核帧）、三色时间线（蓝=候选、
       绿=已标注、深绿=已复核，剩余工作量一眼可见）。另有候选直接采纳、候选阈值过滤、帧预取与
       服务端 JPEG 环缓存等配套机制。
       ⚠️ 一处刻意的设计取舍：前后帧各自裁成最小外接框，不继承上一帧的框尺寸，避免目标缓慢形变
       时尺寸被锁死在旧值上。这是设计选择而非缺陷。

   (4) 测试与实测（数字已较 memory 导航行更新，以本节为准）：
       端到端自测 Python 146/146 全部通过；另有独立的浏览器交互自测 85/85（本地 fixture 与真实
       数据各跑一遍）。真实数据集扫描 24 序列 / 165,223 帧约 1.5 s；时间线统计接口经 RLE 压缩后
       由 12,460 帧实测 3.31 s 优化到 0.07 s；帧读取（SSHFS 冷读）实测 265.8 帧/s、缓存命中瞬时；
       真实模型预标注跑通一次 1,239 帧 / 1,282 候选 / 194 s。
       ⚠️ 265.8 帧/s 是【服务端帧读取吞吐】，不是人工标注速度，也不是预标注吞吐，引用时勿混用。

   (5) 精度相关的工程细节：
       标签往返做到像素级无损；候选写入走「临时文件 + fsync + 原子替换」，杜绝半写文件；导出实测
       3 个标注帧可正确合入 12,460 文件的扁平 GT，并与 base 逐字节一致。
       同时量化了一个真实风险：本域主目标中位仅 6x6 px，一次标注往返掉 0.5~0.75 px 就相当于框
       尺寸的 10%，贴边框每存一次缩 1 px 相当于 16%——因此逐像素级别的坐标保真是该工具的硬需求，
       不是锦上添花。

   (6) 环境约束与遗留：
       本机 uav 环境 torch 与 numpy 版本不兼容、张量互操作直接报错，故预标注默认走远程 GPU 环境；
       若服务本身部署在具备推理能力的环境上则就地推理。
       遗留项：真实模型前向的【输出质量】尚未验证（权重装载与算子口径已分别验证通过，但完整前向需占
       GPU，用户保留算力）；分片当前按 GPU 轮询分配序列，未做单序列内部切分；预标注要求源视频在
       服务器侧可见，纯本机视频只能人工标注。

   (7) 一条值得记录的纪律：测试必须指向一次性临时工作区。本工具的浏览器自测会真实执行保存、传播、
       插补、采纳等写操作，早期曾三次误在正式标注工作区上跑测试、写入假标注。对一个「要标十几万
       帧的工作区」而言，测试污染比测试失败更严重——该约束已固化为工具使用说明。


3. RK3588 板卡环境从零打通，GMC 特征管线 GPU 化落地（本周最大工程产出）
   (1) 板卡环境勘察（硬件与系统事实，本周首次系统摸清）：
       Ubuntu 20.04.6 LTS / 内核 5.10.160 / arm64；8 核 = 4x Cortex-A76 + 4x Cortex-A55（A76 最高
       2.352 GHz）；内存 7.7 GiB；GPU 为 Mali-G610 r0p0，OpenCL 3.0，4 compute units，设备节点
       /dev/mali0；governor = performance、实测频率 CPU0 1.8 GHz / CPU4 2.352 GHz；板卡本地可用
       编译器（gcc/g++ 9.4.0、make、cmake、pkg-config），可原生编译。
       ⚠️ 需与磁盘区分：本地盘仅 16G、可用约 1.7G；「7.7 GiB」是内存。
       本周确立的引用纪律：【任何板卡时延数字必须随附 governor、实际频率与根分区余量一并上报，
       否则该数字不可被引用】。

   (2) 环境配置工作：
       a. NFS 挂载拓扑两次调整，最终确立「板卡挂 host」并把导出目录迁至独立大盘（880G 总 / 782G
          可用），彻底解除此前「根分区仅剩 15G 可用」的存储红线；板卡写入 host 的读写链路已做
          回环验证。⚠️ 旧路径在 host 上仍留有一份内容一致的遗留拷贝，极易被误判为「还是老地址」，
          但已不再导出，照旧命令挂载必然失败。
       b. 交叉编译 arm64 OpenCV 4.10.0（静态库、仅 6 模块、约 4 分钟构建）——动因是板卡 apt 的
          OpenCV 仅 4.2.0，比 x86 侧低 8 个版本，直接安装会破坏跨架构数值一致性的前提。这是本周
          GPU 化改造能够「先证明等价、再上板」的前提条件。

   (3) 配套开发的探针与对账程序（本周形成的可复用测试资产）：
       a. OpenCL 环境探针：枚举平台/设备与扩展、解析 ICD、跑平凡 kernel 并逐元素校验，板卡实跑
          PASS。设计要点是用运行期动态加载而非链接期依赖——交叉工具链内无任何 OpenCL 库，链接期
          根本满足不了；改成运行期决定后，「没有 OpenCL」变成一条干净的报告而非编译错误。该探针
          还查实了 ICD 配置文件指向的库实际不存在、真正生效的是另一路径，以及 Khronos 标准 ICD
          loader 并未安装。
       b. OpenCV SDK 探测：结论为板卡【无】OpenCV C++ SDK，四路探针与两次实际编译尝试双证据一致。
          附带查实「import cv2 成功」不等于装了 OpenCV——板卡上那是 pip wheel 的自包含模块，不含
          头文件与可链接库。
       c. 融合内核精度对账工具：在 x86 侧用真实 OpenCV 生成含 CPU 基准的用例包，板卡侧无 OpenCV 依赖
          地运行真 kernel 并逐元素对账。CPU 基准必须在 x86 算——否则等于在板卡验证「我自己的重实现」，
          构成循环论证。
       d. 跨架构逐算子一致性工具：x86 侧解码一次，两端读同一份原始像素，逐算子 dump 后对比。59 帧
          x 1933 万元素的比对结果：resize / 角点检测 / LK 状态标志 / RANSAC 内点掩码【全部位精确】；
          LK 亚像素坐标与 RANSAC 矩阵存在 1e-5~1e-4 量级差异；warpAffine 在 1933 万像素中仅 11 个
          像素不同（0.000057%）。工程判定：arm64 OpenCV 4.10.0 可用于特征通道。

   (4) 本周踩坑归档（均为「不抛异常、不改指标、只给看起来有点不对的答案」的静默失效类）：
       沉淀 10+ 条环境与部署类静默失效坑，典型如：NFS 目录项缓存会给出假的「文件不存在」；以及一条
       跨架构方法论教训——第一轮仅用 23 帧样本曾把 warp 判成位精确，扩到 59 帧后被推翻。
       【稀疏差异的「零观测」不等于「不存在」，任何「全一致」判决必须附样本量】。


4. GMC 特征管线的 CPU/GPU 分段拆分与精度对齐（板卡时延攻坚收口）
   (1) 拆分前先用实测定位瓶颈，而不是按直觉下手：
       板卡单线程 156.5 ms/帧的构成分解为：CPU 侧 warp + 时域中值合计 134.6 ms（86.1%），拟合
       17.3 ms（11.1%），GPU 融合尾段 5.4 ms（3.4%）。⇒ 瓶颈在 CPU 侧的 warp 与中值，不在 GPU。
       本周据此确定方案：CPU 侧保留运动估计与仿射拟合，把【warp + 时域中值 + 三通道组装】整段迁往
       GPU 融合内核，一次 kernel 出三个通道。

   (2) 实现与迁移验证：
       融合内核源码原样交叉编译后在板卡跑通完整链路（读帧 -> 拟合 -> GPU 融合 -> 三通道输出），
       未修改任何一行源码；运行期提供 CPU / GPU / 双臂三种模式，双臂消费同一份拟合矩阵，因此
       A/B 不可能靠「两边输入不同」蒙混过关。
       🔴 一条关键技术判决：板卡 GPU 的硬件双线性采样器【连整数坐标都不还原原值】（承重通道最大
       偏差 130），故必须改走采样器最近邻 + 手写 2x2 双线性，改后该通道 Max|Diff| 归零、精确率
       100%。这是否决硬件路径、强制手写实现的直接依据。

   (3) 精度对齐结果（板卡 vs x86 纯 CPU 权威基线，同一份输入、同一参数、60 帧）：
       承重通道 Max|Diff| = 0、MAE = 0、位精确 100%；差分通道 Max|Diff| = 0、位精确 100%；
       中值残差通道 Max|Diff| = 1、位精确 100%——59/60 帧三通道完全一致，唯一差异是第 41 帧中值
       通道的单个像素，前后帧完全一致，属舍入边界抖动而非系统性漂移。变换链 126/126 条目全等。
       ⇒ 三链路闭合：板卡 GPU 约等于 x86 CPU 权威实现约等于 x86 融合实现。
       ⚠️ 诚实边界：单像素抖动的根因未定位到指令级；且跨架构逐算子测试比端到端更严（逐算子
       warp 有 11/1933 万像素差，放到完整流水线只剩 1 个），【端到端通过不代表每个算子位精确】。

   (4) 拟合段优化（配套完成，收益显著且全程位精确）：
       按绝对帧号缓存每帧派生量（resize + 角点 + 金字塔）+ 多线程 + 绑大核，板卡拟合
       18.46 -> 2.65 ms（6.96x）、48.93 -> 9.57 ms（5.11x），端到端 49.5 -> 128.8 fps 与
       -> 81.9 fps，全程输出 MD5 不变。
       ⚠️ 收益强依赖画面纹理：纹理贫瘠序列（15.7 角点/拟合）缓存收益 4.30x，纹理丰富序列
       （291.9）只有 1.37x。机理是缓存消不掉光流的逐点迭代。⇒ 【引用任何此类加速比必须同时报该序列
       的点数/纹理水平，否则不可迁移】。
       另有一条重要的归因教训：立项时假设「金字塔构建占拟合的 50%」，实测只有 3.2%，真正的大头是
       角点检测占 65.8%。按错误假设做方案只拿到 1.16x，按实测定位后拿到 5.3x。
       ⇒ 【立项假设与实测冲突时，先花十分钟测阶段占比，再决定优化对象】。

   (5) 40 ms 硬保证交付（5 序列 x 400 帧，稳态 1500 帧）：
       从基线 21 帧超线做到 0 帧超线；最坏单帧 31.85 ms（余量 8.15 ms）；承重通道五序列
       100.0000% 位精确；小核满载干扰条件下同样 0 超线。配套四个开关（预分配、pad 钉死、角点预算、
       拟合看门狗），其中「pad 钉死」是本周新增且是达成 40 ms 的关键——仅做预分配不够。
       ⚠️ 看门狗类开关默认关闭，且有实测依据。
       一条工具性教训：计数器只覆盖它设计要覆盖的事件，覆盖率未经验证时「计数器归零」不能当作
       「该类开销消失」——本轮正是靠另一个计数器才发现真正的开销路径。

   (6) 一条被证伪的假设（fit 与 warp 解耦能否双降）：
       另做了一组「锚点级联」方案：在少数锚点上直接拟合、其余由锚点因子链式合成。实测拟合次数
       22 -> 6.19 次/帧（省 71.9%），但【warp 次数一次没少，仍为 22 次/帧】。精度代价极小（ΔF1
       −0.0003，且空对照证明该差值 100% 来自方案自身、不含编码器伪影），可作为正式预处理方案归档。
       准确表述必须是：【拟合次数 22 -> 6.19，实测降 48.1%，但 warp 次数不变】——严禁写成
       「消灭 75% 算力」。这与本周第 (1)(2) 条的结论互相印证：真正削减 warp 成本的是 GPU 融合，
       而不是拟合次数的减少。

   (7) 本条线的工程价值与遗留：
       板卡特征管道从「不知道瓶颈在哪」推进到「瓶颈已定位、已拆分、已迁移、已对齐、已达 40 ms
       硬保证」，且全程以位精确为前提，没有用精度换速度。
       遗留：拟合侧仅覆盖 2/24 序列、400/31,613 帧（1.27%），全量位精确验证未做，是当前最大证据
       缺口；中值段的内存访问模式仍按列跨 21 个矩阵取数，对缓存不友好，改行块拷贝同样位精确，是
       CPU 臂剩余最大一块；跨架构逐点对账与跨序列统计亦未做。
