3. 新的多线程测试程序（进行中）：为嵌入式组提供可直接照抄的集成骨架

   (1) 测试程序本体
       - 新增 `manu/pipeline/npu/mosaic_async_client_example.cpp`：**387 行 / 有效代码 281 行**（18,429 B），
         依赖仅 C++ 标准库 + OpenCV + `mosaic_pipeline.h`，**无第三方依赖**；
         交付包内副本与仓库**逐位一致**（md5 `b4ff7757…`），预编译二进制与板卡实跑二进制**逐位一致**（md5 `6b33afa0…`）。
       - 三段式线程模型：**相机线程（Producer，每 40 ms 一帧 / 25 FPS）→ 算法线程（Worker，一推一收）→ 业务回调**。
         `feed_frame()` 只做**一次 memcpy + 一次 notify**，帧在库内**深拷贝** ⇒ 相机可立刻把 DMA buffer 归还驱动复用，
         **无野指针、无撕裂**；相机节奏（40 ms）与算法节奏（8~13 fps）**解耦**。
       - 三条设计硬规矩：**① 相机线程绝不阻塞（但应用层不丢帧）② Worker 严格「一推一收」且同线程
         ③ 帧号走库 API 原样带回**。真正需要嵌入式组照抄的只有 `AsyncMosaicRunner` 一个类（约 125 行）。

   (2) 三种模式（`--mode`）
       - `serial`：单线程 push→collect 成对、**不丢帧** ⇒ **参照基线**（等价于老 demo 语义）。
       - `push-all`（默认）：多线程 Producer **带反压** `--inflight N`（默认 4，与 e2e 同口径）、**不丢帧**
         ⇒ **精度验收 / golden 对标用**。
       - `app-drop`：多线程 Producer **不带反压**（相机一秒都不等），**丢帧交给 SDK 内部**做
         （丢队列里**最老**的帧 ⇒ GMC 输入仍物理连续）⇒ **在线生产用**。
       - 反压谓词 `cv_.wait(lk, [this]{ return stopping_ || (pushed_-delivered_) < inflight_; })`
         —— **谓词必须含停机信号**，这正是下面 Fix 1 的落点。

   (3) 库 API 改造：新增 `mosaic_pipeline_push_frame()`（**只追加**）
       - 新增接口：推帧时带上调用方自己的帧号（`client_frame_id`），取结果时**原样带回**；
         **返回值仍是库自己的稠密 handle**（与老接口一致），出错返回 -1。
       - **老接口 `mosaic_pipeline_push()` 签名 / 返回值 / 行为一字未改**，实现上抽成共享的
         `PushImpl(..., auto_client)`（`auto_client=true` 即「客户端没有自己的帧号」⇒ 行为零变化）；
         头文件遵守「**只追加、不改布局**」⇒ **ABI 未破**，既有 8 个调用点**一行都不用改**。
       - ⭐ 最关键的设计决定：**内部稠密号与客户端帧号必须解耦**。内部号是 GMC 21 帧历史的锚点、
         也是相机流空洞检测的依据；若拿客户端号顶替，客户端跳号会让引擎**误报 HOLE、拉伸时间窗、静默掉精度**。

   (4) 4 个 Fix（都是实测暴露的真实缺陷，不是预防性改动）
       - **Fix 1 关机死锁**：停机信号没进流控谓词、且 `flush()` 早于 Producer 退出 ⇒ join 永久挂起。
         实测症状：11,810 帧喂完卡在收尾、13 线程全 `futex_wait`、**30 s CPU 零增长、一条错误日志都没有**、
         e2e 自带 `--watchdog-ms` 也看不见（它住在调用方，而这次卡在**库内部**的 `join()`）。
         修法：谓词含 `stopping_`、Producer 推完显式 `signal_eos()`、**`flush()` 严格在 Producer join 之后**；
         并把库内等待全部改成 timed wait + 标志在**等待方持有的互斥量**下发布再 notify（杜绝「丢唤醒」）。
       - **Fix 2 帧号竞态**：帧号映射在 push 成功后才写外部表，`collect()` 可能先到 ⇒ 输出出现 -1。
         修法：**删掉外部映射表**，改用库原生 `push_frame` ⇒ **结构性消除竞态**，输出不可能有 -1；
         `frame_map.tsv` 降级为只读审计记录。
       - **Fix 3 应用层跳帧**：应用层「最新帧覆盖」私自跳帧 ⇒ 喂进 SDK 的时间轴 40 ms → 120 ms
         ⇒ **打散 GMC 的 21 帧物理历史**（实测特征静默漂移、F1 波动 ~8e-4）。
         修法：**应用层绝不跳帧**，丢帧交给 SDK 内部（丢最老的帧）⇒ 硬规矩：**抽帧只能在推理阶段做，
         不能在前处理（历史窗口）阶段做**。
       - **Fix 4 生命周期**：统一收尾 `drain_and_stop()`（置停止 → flush → join Worker），删除双重 collect 循环，
         **退出码严格 0**。

   (5) 板上实测（新 `.so`，25 FPS，序列 `VIDEO00007_19700101_001324`）
       - 契约测试 **199 passed / 0 failed**（原 196，新增 3 条 `push_frame` 用例：句柄是库稠密号 /

       - `serial` 300 帧 ⇒ EXIT=0、**300/300**；`push-all` 300 帧 ⇒ EXIT=0、**298/300**

【不可外推的纪律】
(1) **新旧板卡的时延与 fps 不可混用**：旧板 `192.168.0.64` 已于 11-10 作废；新板 `192.168.0.211`
    整体慢 11~22%（热节流：GPU 300 MHz / NPU 800 MHz / SoC 82~86 °C）⇒ **旧板数字只能标注为旧板口径，
    不得直接当作交付平台性能引用**；本报告所有 e2e fps 数字均已标注板卡。
(2) **「位级不一致」不等于「精度退化」**：换板后 md5 一致率低，根因已用三条对照构建定性为
    **OpenCV 4.10→4.6 的亚像素差**；实测坐标差中位 0.0000 px、≤0.5 px 帧占比 99.48%、
    检出数变化帧 0.56%、ΔF1 = −1.03e-4 ⇒ **不得把「md5 不全等」表述为精度下降**。
(3) **验收判据不得再写「跨物理硬件 md5 100%」**：该目标换板后不可达且**原因不可消除**
    （与「用板卡自带库」的交付形态直接冲突）；跨环境只认**离散决策等价 + 坐标容差 + 数值中性**三件套。
(4) **覆盖率 ≠ 精度对齐**：被引擎跳过的帧在线上会丢检测框（=漏检）；app-drop 覆盖率低但 ΔF1 反而为正
    只说明「被跳过的帧偏空帧/难帧」，**不得据此推出「跳帧有益」的结论**。
(5) **`push-all` 必须限流**：不限流会灌爆 GMC→NPU→POST 之间的队列，症状是「特征算完了但 `collect()` 永远阻塞」
    且**零错误日志**（所有线程 `futex_wait`）⇒ 集成方漏配 `--inflight` 会被误判成「板卡/库有问题」。
(6) **Fast Infer 的两个数不可混引**：「24 序 Δ=3 replay F1」在权威报告里有两个配置
    —— m=0 裸配置 **94.7861 / FAR 0.025523**，m=6 交付推荐档 **94.8094 / FAR 0.024337** ⇒ 引用必须带 m 值。
(7) **8 序 gate 集只做机理筛选与 A/B，不能给交付档排序** ⇒ 所有排序结论一律取自 **24 序官方口径**。
(8) **Δ 是假设值**：Δ=3 = 假设检测链路延时 3 个 record（120 ms @25 Hz）；管线绝对精度由模型决定，
    Δ 只决定外挂要补多少 ⇒ 不得把 Δ 当成「实测延时」。
(9) **设备凭据与连接口令不得进入任何对外汇报材料**；汇报只呈现已验收结论，
    **汇报与档案冲突时以档案为准**，未经认证的实验不上片。
