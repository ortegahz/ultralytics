# NPU fp16 vs int8 受控对照（去 P0）

> 实验日期：2026-10-16
> 板卡：RK3588 `evm3588` @192.168.0.64，runtime `api=2.3.0 (c949ad889d@2024-11-07T11:35:33)`，driver 0.9.8
> 转换 toolkit：**rknn-toolkit2 2.3.0**（与板卡 runtime 同版本）
> 唯一变量：**模型数值精度 int8 → fp16**。特征、抽峰、坐标、阈值扫描、匹配容差全部不变。

---

## 〇、一句话结论

**fp16 几乎消除了量化精度损失**：相对 FP32 只掉 **−0.000533** F1，而 int8 掉 **−0.019704**；
相对 int8 挽回 **+0.019171** F1（**挽回率 97.3%**，15 档里 14 档为正）。
代价是 **NPU 段时延 ×1.85、整帧时延 ×1.90**。这是一个明确的「用速度换精度」选项。

对业务判据（F1 ≥ 88% / R ≥ 85%）的含义：int8 臂 R 82.90% **不达标**，
fp16 臂 R 85.81% **达标**（F1 0.9014 两种精度都远超 88%）。

## 一、动机：为什么这次能做（修正了旧结论）

2026-10-13 记录过「同图 fp16 在本板卡提交失败」，并据此写下
`CONVERT_HM.md` 坑表 #3 / `rules.md` §四·2f：*fp16 不能当安全对照臂*。

**那条结论当时成立，但对本轮的模型不适用**，原因在失败算子上：

```
failed to submit!, op id: 8, op name: Conv:/model/p0_highway/p0_dw/Conv
```

失败算子位于 **P0 Highway 支路内部**。而本轮交付模型是**去 P0** 图（`Conv:/model/p0_highway/*`
整条支路不存在），该算子不在图里。

⇒ 旧结论的适用边界应改写为：**「带 P0 的图上 fp16 提交失败」**，而不是「这块板子不支持 fp16」。
这正是 `rules.md` §四·2f「对照臂必须自己上过板」的价值 —— 板子没变，是对照臂换了。

## 二、模型构建（可复现）

### 2.1 为什么不用板卡上已有的 `fp_no_p0.rknn`

板上 `fp_no_p0.rknn`（6,327,393 B，md5 `fcdc7111…`）是 `hm_struct_variant.py` 的结构变体
产物，不是交付模型那条转换路径产出的。**体积与本轮重建结果相同但内容不同**：

| 模型 | 大小 | fnv1a32 |
|---|--:|---|
| 板上 `fp_no_p0.rknn`（结构变体脚本） | 6,327,393 | `e2443a11` |
| 本轮 `trial0474_hm_nop0_fp16.rknn`（交付路径） | 6,327,393 | `aaf9cf62` |

两者**是否输出等价已于板卡实测**（跑完全量、板卡空闲后补测）：

| 对照 | 结果 |
|---|---|
| 实见输入 | **12/12 逐字节一致** |
| 输出张量（hm + off） | **24/24 文件逐字节一致** |
| 整帧时延 | 165.276 ms vs 155.841 ms（同量级，差值在运行间波动内） |

即：结构变体脚本并没有「算错」，只是**不可复现**（缺一条可重跑的构建命令）。

**决策仍然是用重建版**：本轮所有数字只建立在「同一脚本 + 同一 ONNX + 同一 config +

用户要求「板卡上生成的 rknn 不一定正确，用生成 int8 的代码重新生成」在**方法论上完全正确** ——
它消除的正是「结果依赖一个来源不明的二进制」这一类风险，哪怕两者最终等价。

### 3.2 105.6 MB 内部内存：实测没有卡死并发

构建日志给出 fp16 内部内存 105,600 KB，是 int8 的 5.18 倍。**若按 2 上下文线性外推需要
~206 MB**，第一反应是「P=2 并行必然失败，提速无从谈起」。

**实测推翻了这一外推**：P=2 双 worker 全量跑完，**0 次 soft reset / job timeout /
failed to submit**，吞吐 12.55 fps（见 §五）。

⇒ 「Total Internal Memory Size」不能当作每上下文预留量直接线性外推并发上限。
这与 memory 里既有的教训同源：**禁止用构建期指标外推板端行为**（如禁止用 MAC/FLOPs 外推时延）。

## 四、tensor 级精度：NPU vs 原始 ONNX（用户指定的关键校验）

**方法**：板卡把**实际喂进 NPU 的 uint8 NHWC 缓冲**原样落盘（`--dump-input`），把读回的
输出落盘为 float32（`--dump`）；host 用同一份字节喂 onnxruntime 跑**原始去 P0 ONNX**。
预处理零重建 ⇒ 比的是模型本身，不掺 letterbox/解码/插值差异。

**脚本**：`manu/pipeline/npu/compare_npu_onnx_tensor.py`（本轮新增）
**输入约定**：uint8 NHWC `[640,640,3]` → NCHW → `/255.0` → `[1,3,640,640]`，
与 `hm_common.to_input_tensor` 及 rknn config `std_values=[[255,255,255]]` 一致。

12 帧（`01_4485_1167-2666` 前 6 + `34_1` 前 6）：

| 指标 vs ONNX-FP32 | **fp16** | int8 | fp16 相对优势 |
|---|--:|--:|--:|
| heatmap worst max_abs | **7.099e-03** | 1.914e-01 | **27.0×** |
| heatmap avg mean_abs | 1.715e-03 | 1.565e-04 | — |
| heatmap 峰值 worst \|Δ\| | **4.665e-03** | 1.914e-01 | **41.0×** |
| heatmap argmax 一致 | **10/12** | 8/12 | — |
| offset worst max_abs | **1.978e-01** | 1.092 | **5.5×** |
| offset avg mean_abs | **2.840e-03** | 7.462e-02 | **26.3×** |

闸门：`tol_hm=2e-2` / `tol_off=2e-1` → **PASS**（int8 臂 **FAIL**）

### 4.1 机制：int8 掉召回的物理来源

int8 的 **offset 平均误差 7.46e-2**，而 offset 直接决定峰值中心坐标
（`x_canvas = (gx + dx) * stride`）。也就是说 int8 的误差主要作用在**位置**而非强度，
峰值被搬离 GT ⇒ 8px 匹配失败 ⇒ 召回掉。fp16 offset 平均误差 **2.84e-3**，小 26 倍。

### 4.2 两条必须随数字一起引用的限定

1. **fp16 的 offset worst max_abs = 1.978e-1，已到门限 2e-1 的 99%**，只是勉强通过。
   offset 是无界回归量（无 sigmoid），门限本身偏松，**不能据此说 fp16 offset 已经很准**。
2. 表中 `max_rel` 被**近零分母**放大（fp16 1.82e+02、int8 1.38e+05），**不可作为判据**。
   判据一律用 `max_abs`。

## 六、精度结果

### 6.1 子集冒烟（4 序列 / 4,206 帧 / GT 3,455）

两臂喂**逐字节相同**的输入（preprocess fnv1a32 均为 `d48a3c7c`，12/12 输入 dump `cmp` 无差异）。

| 指标 | NPU-int8-P0 | **NPU-fp16-P0** |
|---|--:|--:|
| 峰值 th | 0.35 | 0.35 |
| 峰值 F1 | 0.860303 | **0.866450** |
| P / R | 94.74% / 78.78% | 93.35% / **80.84%** |
| TP / FP | 2722 / 151 | **2793** / 199 |
| 每帧检出均值 | 1.06 | 1.24 |
| **0 检出帧** | **735（17.5%）** | **424（10.1%）** |

峰值 ΔF1 **+0.006146**；15 档均值 +0.002526，区间 `[-0.034878, +0.015092]`，**负档 3/15**。

**机制**：int8 保守到 17.5% 的帧一个检出都没有，fp16 压到 10.1%，召回因此上来，
代价是 FP 从 151 涨到 199。

**负档 3/15 全在阈值两端**（0.05 / 0.10 / 0.75）：低阈值区 fp16 的 FP 2237 vs int8 1594 ——
fp16 会吐出更多低置信峰。**这条性质对下游阈值标定有直接含义**。

### 6.2 ✅ 全量结果（31,613 帧 / GT 25,111 / tol 8.0 px / 15 档）

两臂闸门均 **PASS**（臂2 期望 0.901935/21586/1169、臂3 期望 0.882231/20818/1265，
均为从昨天 JSON 取，非手填；复现不出一律 exit 2）。

| 臂 | 峰值 th | F1 | P% | R% | TP | FP |
|---|--:|--:|--:|--:|--:|--:|
| 臂1  PC-FP32 **+P0**（冻结基准） | 0.25 | 0.902316 | 94.87 | 86.02 | 21,601 | 1,167 |
| 臂2  PC-FP32 **−P0** | 0.25 | 0.901935 | 94.86 | 85.96 | 21,586 | 1,169 |
| 臂3  NPU-**int8** −P0 | **0.20** | 0.882231 | 94.27 | 82.90 | 20,818 | 1,265 |
| 臂4  NPU-**fp16** −P0 | **0.25** | **0.901401** | **94.93** | **85.81** | 21,548 | **1,151** |

代价分解：

| 分解项 | ΔF1 | ΔTP |
|---|--:|--:|
| 去 P0（臂1→臂2） | −0.000382 | −15 |
| int8 量化（臂2→臂3） | −0.019704 | −768 |
| **fp16 量化（臂2→臂4）** | **−0.000533** | **−38** |
| **fp16 挽回（臂3→臂4）** | **+0.019171** | **+730** |
| 合计（臂1→臂3，int8） | −0.020085 | −783 |
| 合计（臂1→臂4，fp16） | −0.000915 | −53 |

**int8 残留损失 = 0.019704 ⇒ fp16 残留损失 = 0.000533 ⇒ 挽回比例 = 97.3%**

15 档对比（臂3 int8 → 臂4 fp16）：峰值 ΔF1 **+0.019171**，
跨档均值 **+0.014483**，区间 `[−0.007605, +0.024622]`，**负档仅 1/15**（th=0.75）。

**对照 PC-FP32 的 15 档（臂2→臂4）**：峰值 ΔF1 **−0.000533**，
跨档均值 −0.002132，区间 `[−0.009074, +0.000652]`，**负档 12/15**。
即 fp16 与 FP32 在高阈值区**系统性略低**，但幅度都在噪声量级附近。

### 6.3 三条判读要点

1. **业务判据分水岭**：int8 臂 R = 82.90% **不满足 R ≥ 85%**；fp16 臂 R = 85.81% **满足**。
   F1 两者都远超 88%。若业务判据的召回硬线必须过，int8 在这台板子上就**不合格**，fp16 合格。
2. **最优阈值回到 0.25**：fp16 的峰值 th = 0.25，与 PC-FP32 一致；int8 的峰值 th = 0.20。
   意味着 e2e 脚本里固化的 `TH=0.25` 对 fp16 是**正确工作点**，对 int8 则偏保守
   （int8 固 0.25 同点 F1 0.880949，比其峰值低 0.001282）。
3. **fp16 的 −0.000533 是否是噪声**：噪声下限 ±3 TP ≈ ±0.0002 F1，
   而 fp16 差 **−38 TP**，超出噪声约 12 倍 ⇒ **是真实的小损失，不是抖动**。
   但它只有 int8 损失的 1/37，在工程上可以接受。

## 七、为什么没有用 3 级并行程序跑精度

用户要求「使用昨天验证好的 3 level 并行程序提速」。**该程序无法用于本次精度口径**，实测确认：

`e2e_par_demo` 强制要求 `--raw-root`，其内部第一级就是 GMC
（`raw -> gmc_stream_ocl -> feat -> NPU`）。而昨天的受控精度口径刻意**跳过 GMC**，
直接喂 PC 版 BMP 特征，以实现「特征不变、只换推理后端」。

把 PC 特征当 `--raw-root` 会导致 GMC 被跑两次 ⇒ 口径失效，不是提速。

**实际采用的提速手段**：P=2 双 worker 并行（§5.2），这是与 int8 臂**同一套并行策略**，
因此 int8 与 fp16 的精度表在同一条件下成立。

**顺带的物理事实**：fp16 的 `rknn_run` 102.6 ms 是硬地板，3 级并行能把 GMC/letterbox 藏到
NPU 背后，但在 NPU 占 81% 的情况下能藏掉的比例比 int8 小得多。fp16 的提速天花板由 NPU 本身决定。

## 九、尚未回答 / 后续可做

1. **`Conv:/model/b5/conv/Conv` 的 3Core→单核回退是否就是 fp16 时延劣化的主因** —— 未做归因。
   int8 无此回退且 `rknn_run` 55.3 ms，fp16 有回退且 104.4 ms（1.89×），但
   **MAC 数相同**，所以「回退」只是候选解释，不是结论。
2. **`inputs_set` 的 21–31 ms**：fp16 输入要求 uint8→fp16 转换，占单帧 19%，
   且在 P=2 下涨到 31 ms。预转换可消除，本轮未做。
3. **e2e 三级流水线下的 fp16 fps 未测** —— §七说明了它无法复现本次精度口径，
   但若决定上 fp16，e2e 口径的 fps 仍需单独测（int8 是 14.07 fps）。
4. **int8 去 P0 臂未重新标定/重训**：fp16 已证明量化本身不是主要误差源，
   若 fp16 因 1.85× 时延不可接受，可考虑先重训 int8 再量化，而不是直接上 fp16。
5. **`--no-quant` 的 fp16 与 RK3588 原生 fp16 支持**：本轮已实测可提交、可跑通，
   这条旧禁令的适用边界应按 §一 改写。
