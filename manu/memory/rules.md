  本条是**禁止 Agent 越界写入服务器**。两者方向相反、互不豁免：

### 4. 图像分辨率与坐标空间契约铁律 (Resolution & Coordinate Space Contract) 【2026-09-17 新增，必读】
- **数据集是混合分辨率，绝不是统一的 640×640**：`uav_gmc_median` 验证集存在 `512×512` 与 `640×512` 两种原生尺寸（`DJI_0051_2`/`DJI_0175_2` 等为 512×512，`wg2022_ir_*`/`02_6321` 等为 640×512）。凡是将归一化坐标统一乘 640 做 y 轴换算的脚本，都会产生约 50px 的系统性偏移，采样到纯背景；
- **两个坐标空间严禁混用**：
  1. **原生图像空间**：`labels/val/*.txt` 归一化是相对原生图（`box[0]*W, box[1]*H`），用于直接采样图像像素/通道；
  2. **640×640 Letterbox 空间**：推理缓存 `uav_median_trial0474_cache.pkl` 里的 `gt_pts` 与 `pred_points` 均在 Ultralytics 等比例 letterbox + padding 后的 640×640 画布内（`cache_trial0474_inferences.py` 用 dataloader 的 `batch["bboxes"]*imgsz` 生成，是正确的）。评测链路（如 `eval_bidirectional_track_fusion.py`）自洽地工作在此空间；
- **正确姿势**：采样图像通道用原生坐标；算模型响应距离直接复用缓存内的 `gt_pts`（无需反推 letterbox），按帧内索引配对；
- **已修复脚本**：`probe_wg020_03_deep.py`、`analyze_wg020_03_gt_trajectory.py` 已改为逐图读真实尺寸；历史结论中凡依赖 640×640 假设的（如"走走停停 39.3%"、"829.6px 里程"、"时序通道坍塌"）均已作废。

### 5. 输入通道语义与多通道数据契约铁律 (Channel Semantics Contract) 【2026-09-21 新增，必读】
- **铁律：任何扩展现有数据集通道数的操作，已有通道必须逐字节读取官方数据集图像，严禁从 raw 序列重新生成。** Trial 0474 训练/评测时看到的是官方 `uav_gmc_median` **JPG 有损压缩后的解码像素**；从 raw 以无损 PNG 重生成前三通道（即使 GMC/中值管道参数完全相同）会使基线从 **0.9064 漂移至 0.9023**（TP −206 / FP −35），直接丧失 Epoch 0 浮点级零回归校验能力，导致整个对照实验失去判决价值；
- **铁律：官方 `Format._format_img` 仅在通道数 == 3 时执行 BGR→RGB 翻转（`img[::-1]`），N≠3 通道图像不会翻转。** 因此多通道数据生成阶段就必须把已有通道按**模型实际接收顺序**写入（Trial 0474 为 `[(I_t−B_t)^+, |I_t−W(I_{t-2})|, I_t]`），训练脚本直接 `x[:, :3]` 切片，**严禁在训练端做隐式重排**。违反此条会使模型收到完全相反的通道序，基线暴跌至 **0.6492**；
- **多通道读取支持**：`ultralytics/data/base.py::load_image` 已改为 `cv2.IMREAD_UNCHANGED if self.channels > 3 else self.cv2_flag`（含 stale/corrupt `.npy` 回退路径），配合 `data.yaml` 中显式声明 `channels: N` 生效；4 通道及以上数据必须以 PNG 等无损格式落盘（JPEG 不支持 4 通道且会引入有损伪影）；
- **强制校验**：任何通道扩展实验在正式训练前，必须先跑 **Epoch 0 零回归校验**并确认与 SOTA 标称值浮点级一致（Trial 0474 单帧：`F1=0.9064 / Recall=86.19% / Precision=95.57% / TP=21,643 / FP=1,004`），否则立即停止，不得带着错位基线训练。


## 三、计量、计时与 A/B 判定纪律 (Measurement & Timing Discipline) 【2026-10-08 新增，必读】

> 本节六条全部来自 No-GMC 消融全链的实测教训（详见 `memory/falsified_archive.md` 第三十条与
> `memory/gmc_net_pending.md` 第八节）。**每一条都曾让一次已发出的结论当场失效或方向写反。**

### 1. 标签/索引路径必须实测断言，禁止从同级脚本抄
冻结官方数据的布局是 `images/<split>/` 与 `labels/<split>/`。漏掉 `<split>` 这一层时，
脚本**不会报错**，而是静默写出 31,613 个空标签，评测输出 `F1=0 / GT=0` —— 形似一个刺眼的负面结论。
- 任何镜像/重建官方标注的 builder，开跑前必须做**标签存在性前置断言**，缺失即 `FileNotFoundError` 退出；
- **禁止「写空文件兜底」**；
- 若 builder 含 `if not dst.exists()` 类断点续跑保护，**重跑前必须先删除上一轮产物**，否则错误产物永不被覆盖；
- 标签路径**只能实测得出**，不得从相邻脚本照抄。

### 2. 判定「某步骤贡献很小」的定性，必须建立在跨全量跨序列统计上
小样本抽检只能用来发现异常，**不得用于「贡献小」这类定量结论**。
实测反例：头部连续 8 帧测得 GMC 的像素级贡献 Ch1/Ch2 = 0.019 / 0.032，
全量 24 序列实测为 **0.803 / 1.405**，**低估 40~70 倍，方向性结论作废**。
- 抽样必须**剔除窗口尚未填满的起始区**（本项目为每序列前 2 个窗口 = 84 帧；
  根因是 `ci − 2×21 < 0` 时 21 帧历史里 20 帧被钳到 frame 0）；
- 抽样报告必须同时打印**序列数**与**窗口填充状态**，让偏差无处隐藏。

### 3. 计时器的操作次数必须与真实生产管道一致，并把该次数打印进报表
原 `stage timing` 只拟合 1 个 GMC 矩阵就复用给 21 个 lag，而真实管道是**每 lag 一次拟合 = 22 次/帧**，
导致 `GMC ms` **低估约 22 倍**——而这正是嵌入式移植唯一需要的数。
- 任何计时类结论落地前，先核对被计时的**操作次数**与生产管道一致；
- 报表**必须包含 `fits/frm` 之类的次数列**，让读者能自行判断计时是否可信；
- **快路径/复用优化不得进入计时器**；
- 计时/探针中的**热身计算必须与生产管道逐字等价**，否则既会崩，也会量错耗时。

### 4. 跨块聚合统计量：累加器必须与分母同量纲，并做落盘后的量纲自洽检查
反例：全局 MAE 累加的是**逐帧均值之和**，分母却用**像素总数**，量纲不匹配，
结果被除小约 **6000 倍**（打印出 `1.7e-06` 的假象），而同一张表的 `|d|>=2` 计数却是 1.33e9（13.2%）。
- 累加「和 ↔ 元素数」、「均值 ↔ 份数」，禁止混用；
- 落盘后强制自洽检查：`MAE × 总元素数 >= |d|>=阈值 的计数 × 阈值`，不满足即判定聚合有 bug。
  **同一张表内数字互相矛盾，是聚合 bug 唯一的可靠破绽，必须逐表核对。**

### 4b. 【2026-10-13 新增】禁止用 `onnx.shape_inference` 估计算量；**必须用 RKNN 算子表**

RK3588 上实测 151.7 ms，用户怀疑「有层 fallback 到 CPU」。
为判断「这个时延是否合理」，先估模型计算量 —— **估错了，而且错在最让人放心的方向**：

| 口径 | MACs | 依据 |
|:---|---:|:---|
| `onnx.shape_inference` + Conv 属性 | **2.31 G** ❌ | 91 个 Conv **只解析出 11 个**的输入形状 |
| onnxruntime 实跑导出全部中间形状 | 仍只解析出 2 个 ❌ | 其余 Conv 的输入来自它传播不过去的算子 |
| **RKNN build 日志的算子表** | **25.5 G** ✅ | 每行直接带 `InputShape/OutputShape`，**就是板上真正跑的张量** |

**相差 11 倍**。按 2.31 G 算，「板卡跑到理论峰值的 0.004%，一定有 fallback」；
按 25.5 G 算则是 5.6% —— 仍然偏低，但**方向和结论完全不同**。

- **规则**：任何「模型计算量 / 理论时延 / NPU 利用率」的估算，
  **一律以 RKNN build 日志的 Network Layer Information Table 为准**。
  该表同时给出 `Target` 列（**逐算子 NPU/CPU/GPU**）与 `Cycles(DDR/NPU/Total)` 列，
  一次拿到「谁在 CPU」和「谁最耗时」两个答案。
- **配套**：这张表比 ONNX 图更可信，因为它就是**编译后**的图 —— 融合、量化、
  以及各种 `replace_*` / `convert_*` pass 都已生效。
- **推广**：形状推断**静默返回部分结果**（不报错、不警告，只给能算的那些），
  这种「部分成功」比彻底失败更危险 —— 它产出的数字看起来完全正常。
  凡是「统计了 N 个对象但只匹配上 M 个」，**必须把 M/N 打印出来**，
  `M << N` 时结论一律作废。本条与 §三·4「同表内数字互相矛盾是聚合 bug 唯一的可靠破绽」同源：
  **静默的部分失败不会自己举手，必须由你主动去数分母。**

### 4c. 【2026-10-13 新增】NPU 交付**零算子 fallback** 是硬性要求，必须逐次验收

用户明确要求：**不允许任何算子 fallback 到 CPU**。这不是性能优化建议，是验收闸门。
（背景：Trial 0474 上板 151.7 ms，复查发现 `p0_highway` 的 pixel-unshuffle 有 Transpose 落到 CPU。）

**验收方法固定为「读 build 日志，不靠推断」**：

```bash
grep -inE 'fallback|unsupport|exceed' build.log        # 必须 0 条
# 再解析 Network Layer Information Table 的 Target 列：
#   CPU 且 op 不是 InputOperator / OutputOperator 的，即为 fallback，必须为 0
```

⚠️ **`InputOperator` / `OutputOperator` 标 CPU 是正常的**，它们是 host 缓冲区的 I/O 边界、
cycles 恒为 0，**不算 fallback**。把这两者和真正的 fallback 混为一谈会导致「永远无法达标」。

**RKNN 的硬约束（本项目实测踩中）**：NPU 的 `Transpose` 要求 **2-D 乘积 `H*W ≤ 16384`**（约 128×128）。
所以**任何在 640×640 = 409600 上的布局变换都不可能留在 NPU 上** —— 换写法没有用：

| 写法 | build 日志的 fallback | CPU 算子数 |
|:---|:---|---:|
| `nn.PixelUnshuffle` 原样（reshape+permute） | `height(4)*width(102400)=409600` | 4 |
| 改写为 strided Slice+Stack+Reshape（逐位等价） | `height(1280)*width(320)=409600` | **10（更差）** |
| 改写为 **固定 stride-2 depthwise 卷积** | **0 条** | **3（仅 I/O）** |

- **规则**：遇到「大批量数据布局变换跑不动」，**不要改写张量表达式**，
  要找**能一步完成该变换的原生算子**。卷积读窗口写小图，不需要 transpose。
  `PixelUnshuffle(f)` ≡ 固定 `f×f / stride f` 的 depthwise 卷积，
  权重是 `f*f` 个 delta 平面，`groups=C` 时输出通道号 `c*f*f+i*f+j` **恰好就是 PyTorch 的排布**，无需置换。
- **陷阱**：该权重的 0/1 张量**必须用 Python 字面量在首次 forward 内直接构造**。
  用 `buffer` / `.repeat()` / `torch.tile` 会导出成运行时 `Tile`/`Expand` 算子，
  然后 rknn-toolkit2 2.3.0 在 `fold_constant` 里直接崩：
  `UFuncNoLoopError: ufunc 'multiply' did not contain a loop ... dtype('<U21')`（拿字符串去乘）。
- **推广**：`rules.md` §四·2f「对比臂必须自己上过板」的姊妹条 ——
  **性能与 fallback 都必须上板实测**。本例若只信 ONNX 图和参数规模，会把 151.7 ms 当成「模型就这样」，
  而真实原因是**一条可定位、可消除的布局约束**。

### 5. 混精度算术：OpenCV 算术函数拒绝混合 dtype
`cv2.absdiff(uint8_图, float32_中值)` 抛 `(-5:Bad argument) ... have different types`。
统一走 `np.clip(im.astype(np.float32) - bg, 0, 255).astype(np.uint8)`，与 builder 保持一致。

### 6. A/B 判定必须先确立「复现噪声下限」，效应小于它一律不下结论
本次 native 臂复现冻结标称时差 **3 TP / 3 FP / 0 GT**（`F1 -0.000165`），
原因是抽峰深度差异（本次 `conf_thresh 0.02 / top_k 100`，权威口径 `0.08 / 80`）。
据此确立本项目官方评测口径的**复现噪声下限 = ±3 TP ≈ ±0.0002 F1**。
- 任何 `stage eval` 必须先看 `[SELF-CHECK]`：`TP / FP / total_gt` 三项对齐后，`|ΔF1|` 效应需 **> 2× 噪声下限**才可下结论；
- **「指标差 ±0.0002」级别的一切差异一律不下结论**，也不得写入汇报；
- 判决还须检查 **`dF1` 跨阈值是否恒定**：若随门限单调变化，那是工作点漂移；
  若跨全区间恒定且两臂峰值同门限，则是真实信息损失，**重调门限救不回来**。

### 6b. 比例/匹配率类指标必须带样本量与置信区间；小样本会系统性高估

【2026-10-13 新增】本节与 6 是同一类噪声陷阱，只是发生在**比例统计**上。

RKNN 重新量化的留出集验证：**10 张图**给出的「与官方模型匹配率 **94.1%**」，
扩到 **300 张 / 1369 个检出**后真实值是 **84.5%（95% CI [82.5, 86.3]）** ——
小样本把比例**抬高了约 10 个百分点**。

更糟的是小样本还会**凭空造出规律**：10 张图上「所有分歧都集中在低置信/小框的决策边界」
看起来干净漂亮（同类率 50% / 100% / 100% 三档分明）；
在 1369 个框上，同类率变成 94.5 / 96.6 / 98.9 / 100.0% 的**平滑单调**，
**根本不存在边界效应**，大框（>150 px）反而最低（93.3%），与小框假设相反。
**17 个检出时看到的「规律」，只是回归到均值。**

- **规则**：任何以「X/Y = Z%」形式汇报的一致率、匹配率、命中率，必须同时给出：
  1. **分子分母的绝对数**（不是只有百分比）；
  2. **Wilson 置信区间**（比例统计不要用正态近似，样本少时会越界）；
  3. **至少两个数量级以上的分母**才允许下分层结论。
- **禁止**：用 < 50 个样本的分层比例去宣称「规律」「阈值效应」「分布差异」；
  这类结论必须扩样复测后才能写进汇报。
- **推广**：这与「±0.0002 F1 一律不下结论」是同一条纪律的两个面 ——
  **不是效应量小就不能下结论，而是样本量不足就不能下结论。**

### 6c. 配对实验必须用配对检验；「两个 Wilson 区间重叠」不是显著性判据

【2026-10-13 新增】本节是 6b 的**反面**，也是本轮 NPU 移植中**自己踩并自己纠正**的一条。

**错在哪**：int8 NPU 臂与 CPU fp32 臂跑的是**同一批 600 帧**（配对数据）。
初版据「剔除 DJI 后两臂 recall 的 Wilson 区间大幅重叠
（NPU [0.8383, 0.9007] ∩ CPU [0.8634, 0.9207]）」写下结论：
*「在 n = 440 个 GT 上不足以判定为统计显著劣化」*。

**为什么错**：两个**独立样本**的置信区间是否重叠，绝不能用来推断**配对**数据的显著性。
配对数据里绝大部分样本在两臂上结论相同，这些样本把两个区间都撑宽了，
**区间重叠但差异高度显著**是完全正常的。本例改用配对 McNemar（只看不一致帧）：

| 口径 | 不一致帧（CPU 更好 / NPU 更好） | 精确二项双侧 p |
|:---|:---:|:---:|
| 全部 600 帧 | 19 / 2 | **0.0002** |
| 剔除 DJI 后 550 帧 | 12 / 2 | **0.0129** |

⇒ 剔除混淆项后，int8 的 **−2.27 pp** recall 损失**是显著的**，初版结论被推翻。
（精确值 −2.2727 pp，由 **394/440 − 384/440** 得出；⚠️ 不要拿四位小数的舍入值再相减。）

- **规则**：两臂跑同一批样本时，显著性判定**必须**用配对检验
  （McNemar / 配对 bootstrap / 逐样本差值的符号检验），**禁止**用区间重叠代替。
- **配套**：报告时必须同时给出**效应量**（绝对数 + 百分点差）与 **p 值**，
  仍受 6b 约束 —— p 显著 **不等于** 效应量已被定量刻画（discordant n = 14 仍偏小）。
- **推广**：凡「区间重叠 ⇒ 无差异」「区间分离 ⇒ 有差异」的写法，一律视为未完成的 A/B 判定，
  与 §三·7「先立空对照臂」同源：**混淆项没钉死之前不要下结论，检验方法没选对也不要下结论。**

### 7. A/B 判定前必须先立「空对照臂」，把混淆项钉死

**反例**：tree 臂读新写的 JPEG，native 臂读冻结集原始文件，两臂存储条件不对等。
ΔF1 = −0.0003 既可能来自「新方案的估算偏差」，也可能来自「JPEG 重编码漂移」，**当时无法区分**。

**规则**：任何跨数据源的 A/B（重建数据集、换存储格式、换预处理分支），
必须先建一条**只改变混淆项、不改变被测变量**的空对照臂，把它量化出来再判主结论。
零代码构造法（本项目）：让「被测变量」退化为恒等 —— 例如把锚点步长设成等于 lag 步长，
使每个 lag 都直接拟合（连乘为 0），此时新臂在数学上等于基线，与基线的差即纯混淆项。

- 空对照臂的 Δ **必须为 0**（本轮：8 个门限、24 个序列全部 `+0.0000`，TP/FP 全 0）。
  非 0 即说明 harness 或编码路径有漂移，**主结论一律不可引用**。
- 空对照同时兼作**编码路径等价性验证**：本轮据此确认 `cv2.imwrite` 在输入数组相同时
  **产出逐字节相同的文件**（200/200 抽样 md5 相同），my builder 与冻结 builder 二进制等价。

### 8. 三通道 JPEG 的 4:2:0 色度下采样会污染 Ch0

3 通道 JPEG 默认色度下采样，**Ch1/Ch2 的内容一旦变化，Ch0 的解码值就会跟着变**
（本轮 Ch0 MAE 达 0.478 灰阶、11.2% 像素 ≥2）。
- 因此「Ch0 必须逐字节相同」是**错误**的验收判据（`ch0_exact_frames` 永远达不到 100%）；
- 空对照（同数组重编码）可证明这层漂移**在数组相同时为零**，
  所以观察到的一切 Ch0 漂移都是 Ch1/Ch2 变化的伴生效应，不是编码器噪声；
- 该效应属**磁盘存储格式特有**：生产环境特征在内存中直接喂模型、不经 JPEG，
  故基于磁盘数据集测出的 A/B 代价是**保守上界**。

### 9. 附：「代码已同步」绝不等于「权重已就位」
SOTA 权重位于 `runs/`，而 `runs/` **未纳入代码同步链路**（同步只覆盖 `manu/` 与 ultralytics 包）。
凡涉及推理/评测的交付，必须把**权重路径存在性**单列为前置检查项，不得凭 memory 中的路径直接下发命令。

### 10. 🔴【2026-10-13 新增】ONNX/PyTorch 对账的参考值必须在 BatchNorm **可证处于 eval 态**时抓取

【2026-10-13 新增】RK3588 NPU 移植（Trial 0474 热图检测器）实测教训，详见 `memory/heatmap_npu_trial0474.md` 第七·1 节。

**`torch.onnx.export` 返回后 `model.training == True`，且不会把它恢复回去。**
于是**任何在导出之后、在同一进程内**做的 PyTorch↔ONNX 比较，实际是在拿
**eval 态的 ONNX 图**去比 **train 态的 PyTorch 模型** —— BatchNorm 改用**批统计**而非 running stats。

| 参考值取法 | heatmap max abs diff | offset max abs diff |
|:---|---:|---:|
| ❌ 导出**之后**取参考 | **0.2801**（均值 1.597e-4） | **1.677**（均值 0.131） |
| ✅ 导出**之前**取参考 / 导出后强制 `model.eval()` | **5.07e-7** | **2.48e-5** |

- **为什么这条特别危险**：第一行**看起来完全就是「导出坏了」**——差异大两个数量级，
  而导出本身没问题。若不查 BN 模式，很容易把一个**几行就能修好**的环境状态问题
  升级成「ONNX 路径不可信 / 换框架 / 重训」的重大结论。
- **同轮实测排除的两个假设**（排除过程与结论同样有复用价值）：
  ① Resize / PixelUnshuffle 往返 **max diff 恰为 0.0**；
  ② 逐块导出（`b0..b10`、`c13/c16/c19/c22`、`fuse_p1/p2`）**每一块都在 8.6e-6 以内**。
  ⇒ **差异不来自算子子图，只来自采样状态。**
- **规则**：
  1. 任何 `torch.onnx.export` 之后，**先 `assert not model.training` 再使用该模块**；
  2. **参考值必须在导出之前抓取**（不能靠事后 `eval()` 补救后就当作没发生过——两种做法都要写进脚本）；
  3. 「PyTorch vs 导出产物」类对账，**必须显式打印 BN 模式**作为闸门之一，
     判据形态与 `rules.md` §三·4「闸门必须打印比较样本数」同源：**静默的状态位不许进入比较链路**。
- **推广**：这是「空对照 / 状态自检」在**导出工具链**上的同型问题 ——
  凡是比较，必须先证明**两侧处在同一状态**，否则差异里混着状态差。

## 四、流式 / 状态管理与协议复现纪律 【2026-10-08 新增，必读】

### 1. 环形缓冲必须按「绝对帧号」索引，绝不能移位 + 按 lag 取槽

反例：`push()` 里 `buf = [new] + buf[:-1]` 每帧左移一格，移位后恒等式是 `buf[j] = f_{t-j}`
（**1 帧 lag** 语义）；而读取写成 `buf[lag // stride_step]`（**stride 帧 lag** 语义）。
两者不匹配的必然后果是**所有历史帧被取到一半的 lag**（lag 2 取到 `f_{t-1}`、lag 42 取到 `f_{t-21}`），
并且**被 warp 后的差分/中值通道一起算错**。实测症状：只有 Ch1 与 Ch2 出错、Ch0 正确，
锚点矩阵 diff 高达 198.9，最大链式 lag 全部继承。

- **规则**：环形缓冲用**绝对帧号 mod depth** 索引，读写两侧语义必须同源；
  **禁止用列表移位实现 lag 检索**。
- **配套**：帧环深度必须是 **`max_lag + 1` 个连续帧**，不能用「22 格步长 2」的压缩环 ——
  因为**每一帧都是它自己那次 push 的当前帧**，任何一帧都必须存活 `max_lag` 次 push。

### 2. 同一脚本内禁止混用 `(H, W)` 与 `(W, H)`

本轮**连续三次**在同一处翻车：构造函数期望值按 `(w, h)` 存取、内部比较按 `(H, W)`；
形状守卫写成 `(s.shape[2], s.shape[1], 3)` 而实际是 `(H, W, 3)`。
其中一次造成 **G2 假 PASS** —— 守卫恒真导致全部帧走 `continue`，一帧未比却显示 `max|d|=0`。

- **规则**：统一采用 **numpy 原生 `(H, W)`**；跨维度转换必须显式且**伴随打印**；
  守卫条件写完后要用一次已知尺寸的输入**验证它真的能通过**（假 PASS 比 FAIL 更危险）。

### 2b. 坐标字段的命名必须无歧义：转换只做一次，禁止「中心+w/h」这类可两解的表示

【2026-10-13 新增，必读】RK3588 NPU 解码实战教训，详见 `memory/rknn_npu_board_run.md` 第 6.4 节。

- **症状**：yolov5 检测框**整体往左上偏**、宽度偏小，像「尺度没变换回去」。
- **根因**：参考实现的解码最后一步已经做了 center→left（`box_x -= box_w/2`），
  移植方**照抄了这一行**，于是数据结构里存的**已经是 left/top**；
  但画框时又按「中心点」语义处理，**再减了一次 `w/2`**。
- **为什么所有自检都失效**：框仍是矩形、仍与目标部分重叠、**置信度与任何指标都不变**，
  不抛异常、不触发任何既有闸门。**纯平移类错误对所有统计型验收都是隐形的。**

- **规则**：
  1. 检测/几何结构一律存**显式四角** `left/top/right/bottom`，宽度高度用 `w()`/`h()` 访问器派生；
     **禁止**用 `x/y` 承载「语义已转换过」的量。
  2. 「移植自参考实现」时，**逐行确认该行的输入语义与输出语义**，不要默认「照抄即等价」。
  3. 凡涉及坐标换算，**必须有第二条独立路径与之对账**（见下条 2c）。

### 2c. 有权威参照实现时，必须把它跑起来做逐样本对账，禁止「照抄源码 = 正确」的循环论证

【2026-10-13 新增】本轮唯一能定位 2b 那个 bug 的手段，是**把 Rockchip 官方 demo 交叉编译并在板卡上跑起来**，
逐框对比 `(l,t,r,b)`，偏差 ≤6 px 才收口。

- **规则**：当 SDK/论文/上游仓库提供了可运行的参照实现时，**「抄它的代码」不构成验证**——
  抄来的代码与参照实现可能共享同一个理解错误。必须让**参照实现本身产出数字**，再逐样本比对。
- **对账的判据**：给出**逐条明细表**（不是「基本一致」），并**解释残差来源**
  （本例是 stb_image vs libjpeg-turbo 的 JPEG 解码差异，而非逻辑错误）。
- **配套**：参照臂要**可复现构建**（本项目 `manu/pipeline/npu/{build,run}_sdk_demo*.sh`），
  否则这次对账无法在后续 Session 重放。

### 2d. 「输出非零」不是模型可用的证据；必须同时校验**耗时量级**

【2026-10-13 新增】RKNN 转换踩坑，详见 `memory/rknn_npu_board_run.md` 第 9.1 节。

用版本不匹配的 toolkit 转出的 `.rknn`，`rknn_init` 成功、张量属性也读得出来，
但**每次推理都在 NPU 提交阶段被拒绝**：

```
E RKNN: failed to submit!, op id: 145, op name: OutputOperator:328, ...
```

它**不报错退出**，而是超时 ~6.4 s 后返回，输出缓冲区**从未被填充**。于是下游看到的是：

| 指标 | 真实值 | 会被误读成 |
|:---|---:|---|
| 单次推理 | 6395 ms | 「模型慢」 |
| 检出分数 | 全部 ≈ 0.9976 | 「模型很自信」 |
| 检出框 | 退化、坐标乱 | 「框算错了」 |

- **规则**：任何「模型/管线跑通了」的结论，必须**同时**满足三条，缺一不可：
  1. **耗时落在量级内**（本例 6395 ms vs 正常 23 ms，差 270 倍——这一条最先暴露问题）；
  2. **输出分布合理**（不能所有分数都挤在 0.99 附近）；
  3. **空对照有效**（见 `rules.md` 三·G0）。
- **推广**：这与「假 PASS 比 FAIL 更危险」是同一类错误。**任何被当成 PASS 的判定，
  都要问一句：这个 PASS 的量级对不对？** 一个恒真的守卫也会「全绿」，因为它从不产生数。
- **版本纪律（RKNN 专属）**：转换前必须核对 **toolkit 与板卡 `librknnrt` 的 commit hash**。
  本例 SDK 只附带 toolkit 1.4.0，板卡 runtime 是 2.3.0（commit `c949ad889d`）——
  **SDK 自带的转换器版本 ≠ 能在本板卡上跑通的版本**，不得默认「SDK 里的就一定能用」
  （与「SDK 自带 librknnrt.so 是 1.4.0 过期版」是同一个坑的两面）。

### 3. 对账必须先立「空对照」，且必须有一道「重编码后比文件」的闸门

- **G0（空对照）**：脚本内的非因果 replay 重编码后与冻结集文件比 —— 若非 0，说明**基准抄错**，
  而不是被测代码错。本次正是靠 G0 一步排除了「reference 有问题」，把矛头精确指向引擎。
- **G2（重编码闸门）**：流式输出**按生产方式重新编码**后再与冻结文件比。
  前置数组相同 ⇒ 文件逐字节相同，所以该闸门**界必须是 0**。
- **禁止**直接拿内存数组去比 decoded JPEG 判严格阈值：三通道 JPEG 的 4:2:0 色度下采样
  与量化本身就有 MAE ~2~9 的残差，任何 `< 0.05` 级别的要求在文件层面**物理上不可达**。

### 4. 「静默失效」优先于「崩溃」：守卫/断言必须能被证伪

本轮四个静默 bug（形状约定错、形状守卫写反 ×2、环取一半 lag）**全部不抛异常、不打印警告**，
只产出「看起来有点不对」的指标。对策：
- 每个闸门必须打印**它实际比较了多少样本**（`matched 198/200`），
  数量为 0 时必须显示 `SKIP` 而**绝不能显示 `PASS`**；
- 差异定位探针要能指出「第一个不一致的环节」（本项目用 `[MATS]` 逐 lag 矩阵比对做到）。

### 5. 评测协议：抽峰深度会改变贪心匹配结果，引用前必须先验证敏感性

`extract_peaks` 在未触发 `top_k` 时返回**空间顺序**、触发时返回**分数降序**；
`evaluate_point_detections` 用 `np.argsort(dists)` 做**并列敏感**的贪心匹配。
因此 `conf_thresh / top_k` 理论上会影响 TP/FP。

**但本项目实测四个臂对抽峰深度全部不敏感（0.02/100 与 0.08/80 给出相同 TP/FP）**，
故该假设**已证伪**，不得再作为差异归因使用（详见 `gmc_net_pending.md` 第十一节）。

- **规则**：任何「A 与 B 差 N 个样本」的现象，**先测敏感性**（换一个合理的 A 参数看差是否变），
  再决定归因；**禁止**先写一个听起来合理的机制解释再去找证据。

### 6. 缓存中的**坐标类数据一律禁用 float16**（本项目最隐蔽的一次口径漂移）

反例：`cache_trial0474_inferences.py` 曾把 `pred_points` 与 `gt_pts` 存成 float16。
预测点与 GT 中心都在 640×640 letterbox 空间，float16 在该量级的最小间隔为 **0.25~0.5 px**：

| 值 | 16 | 64 | 256 | 320 | 512 | 640 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| float16 ULP | 0.0156 | 0.0625 | **0.25** | **0.25** | **0.5** | **0.5** |

在 **8 px 匹配容差**下这点误差足以推翻边界帧，实测造成 **TP −3 / FP +3（F1 −0.00016）**。
权威评测路径全程 float32，所以这是一次**纯属缓存引入**的偏差，模型本身毫无问题。

- **规则**：`pred_points / gt_pts / gt_bboxes` 等**坐标量纲**一律 **float32**；
  只有 `pred_scores` 这类 0~1 的量才可用 float16。统一 dtype 以杜绝复发。
- **配套**：写盘后打印实际 dtype；把 cache 体积记入铁律二预算（float32 后 5.1 → 5.5 MB，
  远低于 100 MB 上限，**没有理由为省 0.4 MB 牺牲精度**）。

### 7. 复现失败时的排查顺序（本项目实测有效的次序）

1. **缓存精度与 dtype**（最隐蔽，先查）
2. 评测器的**并列敏感贪心匹配**是否被抽峰顺序影响 —— 但**必须实测敏感性再下结论**
3. checkpoint 身份（比对写盘时刻 + 可辨识的标量，如 BN 统计或 gate 值）
4. `model.eval()` / `no_grad`
5. 坐标空间与缩放的往返一致性
6. `stride` / DataLoader 构建参数
7. 权威产出脚本到底是哪一个（同功能脚本常有多个，且架构参数不同）

### 8. 引用复现基线时必须区分「冻结标称」与「本 harness 实测」

根因定位后（见上一条），本 harness 在权威抽峰 `0.08/80` + float32 坐标下
**已精确复现 `0.9064 / TP 21,643 / FP 1,004`**（残余 F1 差 −3.9e-05 仅为四位舍入）。
此前记录的 `0.9062` 是 float16 缓存缺陷造成的伪值，**作废**。
任何复现失败都应先按上一条的 7 步次序排查，再考虑「基线本身有误」。

### 9. 精度等价与算力等价是两件事，「bit-exact」不能跨命题引用

Tree 类方案里被证明的是：**给定同一批变换因子时，有界深度链式合成与全长链 `max|diff| = 0`**
（结合律无损）。这**不**证明「短基线连乘得到的因子 == 长基线直接拟合得到的因子」。

- **精确等价的充要条件**：每个 lag 都单独做一次**长基线直接拟合**。任何复用短基线步的省算力做法
  都不可能恰好相等，只能「足够接近」。
- **规则**：引用「bit-exact」时必须写清**在哪个命题上**。把「合成等价」当作「估计等价」的证据，
  会得出「省算力不掉点」的错误结论。
- **配套**：报「等价」时必须同时给出**覆盖范围**（序列数 / 帧数 / 分辨率）。
  本项目两次踩坑：①`ls | head -200` 因按文件名排序而只覆盖单个序列；
  ②只在 1 个序列 200 帧上验证却被称为「全量一致」。

### 9b. 🔴【2026-10-10 新增】"多线程会破坏位精确性"在本工程已被证伪 —— 不得再当作事实引用

**旧记载（已失效，保留原文以便追溯）**：`gmc_stream_ocl.cpp` 浮点契约第 3 条称
"OpenCV 必须同版本，且两端都单线程运行（`cv::setNumThreads(1)`）。
**多线程下 RANSAC 与 Lucas-Kanade 不可位复现**，一次锚点拟合可能在两个同样合理的解之间翻转，
从而移动整条 warp 边缘。"

**实测反证**：板卡 `evm3588` 与 x86、2 条序列（`01_4485_1167-2666` / `02_1610_0001_1500`）、
**缓存与非缓存两条 LK 路径**、`threads=1/2/4/8/12`、每档重复 3 次
（x86 共 40+ 次、板卡共 30+ 次运行）—— **输出 MD5 全部一致**。
`fit_profile` 的 LK 逐点比对亦为 `max|Δpoint|=0, max|Δstatus|=0, max|Δerr|=0`。

**机理（非侥幸）**：
- `calcOpticalFlowPyrLK` 的 `parallel_for_` 切分的是**点**；`LKTrackerInvoker::operator()`
  对每点只读共享的 const 图像、写互不相交的 `nextPts/status/err` 槽位 ⇒ **与切分方式无关**。
- Scharr 导数在 `parallel_for_` **之外**计算（`lkpyramid.cpp:1388`），不存在跨线程争用
  `derivIBuf`；走预建金字塔时 `lvlStep=2`，连该缓冲都不需要。
- `estimateAffinePartial2D` 的 RANSAC 是顺序循环，按固定次序消费全局 RNG，
  线程数不改变取数序列 ⇒ 原条款所称"解翻转"没有发生条件。
- `_compose` 是标量 float64 代码，不经 OpenCV 并行。

**规则**：
1. **不得**再以"为了位精确必须单线程"为由拒绝可测量的多线程优化。
   多线程是本项目嵌入式提速的**主力手段**（板卡 CPU 臂 139 → 65 ms/帧）。
2. **但保留的边界**：本条只证明"**这个 C++ 二进制**的输出不随线程数变化"，
   **未**重新验证"Python/cv2 参考端多线程下仍与本端一致"——那才是原条款的原始语境。
   ⇒ **正式改写或废除该铁律前，必须补一次 Python 多线程 vs C++ 单线程的对账**；
   在那之前，这条只能当作"**已证伪但边界未闭合**"，不得反向用来放松**其它**等位精确要求
   （编译器 flag、OpenCV 版本、`-ffp-contract=off`、RNG 顺序等仍然照旧生效）。
3. 证据档：`gmc_fit_cache_rk3588.md` §D。

### 9c. 🔴【2026-10-10 新增】优化前先实测瓶颈占比；并行化必须连默认档一起测

**立项假设 vs 实测（嵌入式轮的真实教训）**：立项时假设"金字塔构建占 GMC fit 的 50%"，
按该假设设计的方案只能拿到 **1.16×**；实测发现 **Shi-Tomasi 占 65.8%、金字塔构建仅 3.2%**，
改按实测定位后拿到 **5.3×**。
- **规则**：任何"优化某阶段"的立项，必须先有**阶段级耗时占比实测**（或可复算的计时分段），
  与假设冲突时以实测为准。理由：嵌入式性能预算里，猜错对象等于白做。
- **配套**：「该阶段是某输入的纯函数」**不蕴含**"缓存它就有收益"：
  收益还取决于该阶段在总时间中的占比。缓存消不掉逐点迭代类的成本。
  引用加速比时**必须同时报该序列的点数/纹理等决定占比的量**，否则不可迁移
  （本轮实测 15.7 角点/拟合 → 4.30×，291.9 → 1.37×）。

**并行化的两条硬纪律**：
- **必须连默认档（threads=1）一起测**。本轮把 `median_residual` 无条件改走 `parallel_for_` 后，
  threads=8 时 median 快 2 倍，**threads=1 却慢 37%（66.4 → 90.8 ms）**——
  因为 body 经间接调用后 `history[i].at()` 的数据指针无法外提。只测多线程档会漏掉该回归。
- **"线程池吃不到"本身是可测信号**：同段代码里 `cv::warpAffine` 随线程 69 → 28 ms，
  紧邻的自写标量 `median_residual` 纹丝不动 —— 这个不对称直接指出下一个优化对象。
  **凡自写标量循环，必须自己 `cv::parallel_for_`；`cv::setNumThreads` 够不到它。**

### 9d. 🔴【2026-10-10 新增】缓存 / 环形缓冲必须以绝对索引为 key，且必须有运行时自检

本轮连续踩了两个**静默失效**：不崩溃、不断言、只输出错误数据。
1. **不能用「槽是否已填充」的布尔量**。槽填满后布尔量永远为真，且 `slot(43)` 与 `slot(0)` 同址
   ⇒ 第 43 帧之后一直拿第 0 帧的像素。
2. **`t_` 是 0 起始，clamp 下界必须是 0**。`frame_at_lag()` 把越过首帧的 lag 钳到 `first_`，
   而 `first_` 是 `t_=0` 那帧；按直觉写成 clamp 到 1，会给"实为第 0 帧"的图打上第 1 帧的标签。

- **规则**：任何按帧复用的缓存/环形缓冲，**必须**记录"该槽当前存的是哪个绝对索引"，
  命中条件是**索引相等**而非"非空"。
- **必须**配运行时自检（例：`GMC_VERIFY_CACHE=1`，每次命中重算并逐字节比对，不一致即 `exit(3)`）。
  **没有自检的缓存不可信**：这两类 bug 在代码评审与"读代码确认"中都不会暴露。
- **配套**：位精确被破坏时，**锚点正常、只有组合 lag 漂移**是缓存错帧的典型signature
  （易误判为"RANSAC 抖动"）。用 `--mats-all` 导出全帧变换链（30 KB）逐帧比对才能定位。
  证据档：`gmc_fit_cache_rk3588.md` §G/§H。

### 9e. 🔴【2026-10-14 新增】**int8 上板模型必须 0 个 CPU 计算算子** —— 交付前硬闸门

【用户 2026-10-14 明确要求，定为本项目铁律】

**闸门**：`rknn_init` 成功**不等于**模型全在 NPU 上。
构建日志的算子表里凡出现 `Target = CPU` 的**计算**算子，该模型**不得交付**。
`InputOperator` / `OutputOperator` 是 I/O 边界，不算违例。

**怎么数**（唯一权威来源 = 构建日志的 Network Layer Information Table）：

```bash
grep -oE '^[DWI] RKNN: \[[0-9:.]+\] [0-9]+ +[A-Za-z0-9_]+ +[A-Z0-9]+ +(CPU|NPU|GPU)' build.log \
  | awk '{print $NF}' | sort | uniq -c
# 期望：CPU 仅 3（InputOperator + 2×OutputOperator），其余全部 NPU
grep -ic 'fallback' build.log     # 期望 0
```

**为什么单列成铁律**（本轮两次实测坐实）：

| 现象 | 真实成本 |
|:---|---:|
| `nn.PixelUnshuffle` 在 640×640 上导出 → Transpose 超限 → 2 个 Transpose + 1 Reshape 落 CPU | **151.2 → 103.7 ms（−31%）** |
| 改写成 slice+stack+reshape（同样逐位精确） | **CPU 算子 4 → 10，更慢** |
| 改成 **stride-2 depthwise conv**（逐位精确） | CPU 计算算子 **1 → 0**，**103.7 ms** |

- **配套一**：`fallback` 警告行数必须为 0。**警告条数与算子表的 CPU 计数必须同时过**——
  只看其中之一会漏：改写版同样打印了 fallback 警告，但真正决定交付的是算子表的 Target 列。
  ⚠️ **两者不是一一对应**：v1 的 **2 条** `Transpose will fallback to CPU` 警告
  被 toolkit **合并进了同一个 `Reshape` 节点**，实际只有 **1 个** CPU 计算算子。
  报数时必须说清是「警告条数」还是「计算算子数」，不可混用。
  ⚠️ **闸门必须先确认日志非空**：`grep` 一个不存在的日志文件会**静默返回 0 并判过**。
  转换脚本常常自己不写日志（日志来自 shell 重定向），
  故判定前先 `test -s <log> || exit 1`，否则闸门形同虚设。
- **配套二**：**消除回退必须逐位等价**。本轮用 depthwise conv 重写 PixelUnshuffle，
  四种形状 `(1,16,640,640)/(1,3,320,320)/(2,16,128,96)/(1,64,8,8)` 全部 `torch.equal` 通过，
  且**整网 31 帧 NPU 输出与旧模型逐字节相同** ⇒ 加速零精度代价。
  改写若只做到"数值接近"，**先当作精度回归处理，不得当作性能优化上报**。
- **配套三**：**改写张量表达式救不了布局类回退**。RKNN 的 Transpose 上限是 `H*W ≤ 16384`
  （约 128×128），而 640×640 上的通道重排恒为 409600，**与怎么拼张量无关**；
  只有把布局变换改写成**原生算子**（卷积/池化）才可能逃出该上限。
- **推广**：本条与 §四·2f「对比臂必须自己上过板」同源 ——
  **编译成功只说明图能被接受，不说明图在你想的那块硬件上跑。**

### 9f. 🔴【2026-10-14 新增】**禁止用 MAC / FLOPs 外推 NPU 时延** —— 算术量与墙钟可以背离近 7 倍

**实测反例**（RK3588 NPU，Trial 0474 热图检测器，删 p0 highway 前后，同一板卡同一二进制）：

| | Conv MAC | `rknn_run` |
|:---|---:|---:|
| v2（带 p0） | 23.11 G | 103.7 ms |
| v3（去 p0） | 21.54 G | 55.5 ms |
| **变化** | **−6.8%** | **−46.5%** |

**两者差了近 7 倍。** 原因：被删的 p0 那几层是 **640×640 / C=16** 的卷积——
既是大分辨率（特征图必须整幅走 DDR 搬运），又是极窄通道（64 宽的 MAC 单元大量空转），
**同时踩中 NPU 的两个最差工况**。算术量只统计了「乘加次数」，没统计搬运与单元利用率。

- **规则**：任何「减算力 ⇒ 会更快」的推断，在 NPU 上**必须实测**，不得用 MAC/FLOPs 线性外推。
- **配套一**：**算子回退与结构劣化是两笔独立的账，代价可能相当。**
  本例 151→104 ms（回退，47 ms）与 104→56 ms（结构，48 ms）几乎相等。
  **只查回退会漏掉后一半**——两轮优化必须分别归因、分别记账。
- **配套二**：定位慢因时优先看**「空间分辨率 × 通道宽度」的组合**，
  而不是看层数或总 MAC。高分辨率 + 窄通道是最差工况。
- **交叉验证**：本条与 §四·10「计时类结论必须交叉验证」同源 ——
  **算术量与时延不同源，两者不一致时禁止取其一、禁止取平均，必须先定位机制。**

### 9g. 🔴【2026-10-14 新增】**验收输出不得靠 `grep` / `sed` 过滤来判成败** —— 过滤会把失败伪装成成功

- **规则**：判定一次运行「通过 / 失败」，只能依据**工具自身的退出码或显式 `--speed-only` 一类的开关**。
  **禁止**用 `... 2>&1 | sed -n '/SPEED/,$p'` 或 `| grep OK` 从混着 traceback 的输出里"挑出"成功段。
- **为什么**（本轮真踩）：报告脚本在无 GT 输入时因读不到 `detections.json` 抛 `SystemExit`，
  而驱动脚本用 `sed -n '/SPEED/,$p'` 过滤，**traceback 被一并吞掉，退出码变成 0**——
  于是一个根本没产出报告的运行，看起来像成功出报告。
  正确的做法是给报告脚本加**显式的 `--speed-only` 开关**，让"跳过精度层"成为**声明**而不是"沉默"。
- **配套一**：任何 `tee` / 管道收尾的步骤，必须保留**未过滤的完整输出**（写文件即可），事后可查。
- **配套二**：跨进程管道里 `cmd1 | cmd2` 的 `$?` 是**最后一个命令**的退出码，不是 `cmd1` 的；
  要判 `cmd1` 必须 `set -o pipefail` 或先落盘再判。
- **配套三**：同源问题——**静默失败比崩溃更危险**。板端批处理因清单里写了 host 的绝对路径，
  `stbi_load` 失败后直接 `return 1`，日志末尾没有任何摘要，只留下 **0 字节的产物**。
  ⇒ 产物为 0 行/0 字节时，**必须当作失败处理并追查日志全文**，不能当作"无检出"。

### 9h. 🔴【2026-10-14 新增】**预处理时延随输入分辨率近似线性增长，必须实测** —— 禁止按低分辨率的数字外推

**实测对照**（RK3588，同一序列、同一二进制、同一驱动）：

| 输入分辨率 | GMC fit p50 | GMC 合计 p50 | 40 ms 红线 | NPU 阶段 |
|:---|---:|---:|:---:|---:|
| 512×512 | **23.8 ms** | 31.9 ms | **PASS** | 56.9 ms |
| 1024×576 | **73.4 ms** | 86.6 ms | **FAIL**（p99 91.4） | 56.6 ms |

⇒ **GMC fit 随分辨率放大约 3.1×（与像素数之比 1.98× 同量级，接近线性），
而 NPU 阶段完全不受输入分辨率影响**（模型输入恒为 640×640，定时为常量）。

- **规则**：任何"实时性达标"的结论**必须绑定它被测时的输入分辨率**；
  引用时**必须同时写出分辨率**，不得跨分辨率外推。
- **配套一**：预处理侧的成本主要由**角点密度**决定，且存在**硬上限**——
  512×512 那轮 corners mean=267.0（未触顶），1024×576 那轮 `cornercap=117f/600calls`、
  mean=600.0（**顶到 `--fit-corners 600`**）。
  ⇒ 换更高分辨率前**先看角点预算有没有触顶**，触顶后 fit 成本与质量的关系会非线性。
- **推广**：与 §四·9f「禁止用 MAC / FLOPs 外推 NPU 时延」同源 ——
  **算术量、输入分辨率，二者都不能代替实测**；外推只用来决定"值不值得测"，不用来下结论。

### 10. 计时类结论必须交叉验证，出现不自洽立即停止引用


本项目同一次 `push()` 的成本在两套工具里相差 **5 倍**：
由两个 `anchor_step` 设置反解得 **9.06 ms/次拟合**，而 `stage timing` 直接测得 **1.80 ms/次**。

- **规则**：任何进入嵌入式预算的时延数字，必须至少来自**两套独立工具**或**两段独立的分段计时**；
  两者不一致时**禁止取其一、禁止取平均**，必须先定位机制。
- **配套**：耗时必须分「拟合 / warp / 其中值」等**与算法结构对应的分段**，
  而非只报单帧总耗时——否则无法判断差异出在哪一环。
- **前置**：测量前确认机器空闲，并**连着跑**两套工具（跨时段测量会把负载差异误判为算法差异）。

### 11. 跨语言移植的等位精确纪律 【2026-10-08 新增，必读】

> 来源：RK3588 C++ 移植（`manu/memory/cpp_port_rk3588.md`）。本节每一条都会让一次"看起来只差一点"的
> 等位精确结论当场失效。

**先问结构，再谈小心**：Python 侧若本身就是 C++ 库的薄绑定（如 `cv2` = OpenCV），
则「逐位一致」应建立在**调用同一批底层入口、同参数、同调用顺序、同库构建、同线程配置**之上，
而非建立在「移植时写得很仔细」之上。据此判定真正需要移植的只有**编排层**。
本项目的结论：原语零成本逐位一致，只需移植环缓冲 / 锚点网格 / 链式合成 / 中值 / 裁剪 / 通道序。

- **编译选项属于契约，不属于工程偏好**：`_compose` 的 float64 点积必须锁 `-ffp-contract=off`
  （防 FMA 把两次舍入并成一次），并**禁用 `-ffast-math`**（禁重结合）。
  构建脚本应**在检测到 `-ffast-math` 时直接失败**，因为被工具链悄悄注入的 fast-math 会
  让"位精确"无声失效。
- **跨语言等位精确只能在**「同库同构建 + 同调用顺序 + 单线程」**下主张**。
  库版本不同、线程数不同，结论都不成立；移植物应打印自身库版本供对照。
- **随机性原语是等位精确的天然敌人**：RANSAC 这类消耗全局 RNG 的算法，若两侧抽取序列不同，
  会在两个同样合理的解之间翻转，整条 warped 边缘随之位移。
  **加固手段（每次拟合重置种子）必须在两侧同时启用**，且启用后**不再复现未加固生成的冻结产物**。
- **空对照同样是移植的前置**：把被测变量退化为恒等（`anchor_step=2` 时合成深度为 0，
  该臂在数学上就是基线本身），此时与基线的差**只能是移植漂移**，无法与算法设计混淆。
  移植**未通过空对照前，其一切指标不可引用**。
- **指纹实现必须自检**：用作等位精确判据的哈希，必须在启动时用标准测试向量自检、不通过即拒绝运行。
  否则「哈希不一致」到底是特征漂移还是哈希写错，无法分辨。
- **闸门必须打印比较样本数**，比较数为 0 时显示 `SKIP` 而**非 `PASS`**——假 PASS 比 FAIL 更危险。
- **移植的对比通道必须是编码前数组**：三通道 JPEG 的 4:2:0 色度下采样与量化会让 decoded 像素差
  变成存储格式的度量（见本文件第三节第 8 条）。
- **跨语言一致性必须由既有实现做黄金侧，禁止为验证再写一份实现**：
  验证器应驱动**既有** Python 引擎，否则会出现第二个逐渐与第一个走偏的实现，
  而差异会被误归因为语言差异。
- **冻结产物的序号↔文件名映射必须复用冻结 builder 自己的 `idx_map`**：
  猜文件名正是"报告零漂移、实际在比不同帧"的经典成因。
- **手写的桩头文件只能证明「代码自洽」，不能证明「API 调用正确」**：
  桩是从记忆生成的，记忆错了桩会把错误**固化**，而且**比没有桩更危险**——
  它给出一个虚假的通过信号。实测：本项目用自写 OpenCV 桩编译通过，
  却在真实 OpenCV 4.10 下立刻暴露两处硬错误：`cv::uchar` 根本不存在（`uchar` 是全局 typedef），
  以及 `warpAffine` 参数顺序（真实为 `(src, dst, M, dsize, ...)`，**矩阵在 `dsize` 之前**）。
  规则：跨库移植的桩必须与真实头文件**逐行比对签名**；
  **桩编译通过绝不替代真实编译**，桩只能用来提前抓语法/类型错误。
- **计时器必须核对「累加器的单位」与「输出乘的系数」**：
  实测把已经是毫秒的累加器又乘了 `1e3`，打印成「ms」的其实是**微秒**，
  1000 倍错误。本项目时延数字本就有 5 倍不自洽的历史争议，
  再注入一个 1000 倍的单位错误，会让嵌入式预算彻底失去可信度。
  规则：新增计时输出时，**先用一次已知量级的负载反查单位**（例如 21 次拟合是否落在几十 ms），
  确认量级合理再落盘。
  **【2026-10-13 补充 · 必须自动化成闸门，且闸门输出必须被读到】**
  RK3588 NPU 移植时真踩了同款：板端印出 `preprocess 544817000000.00 ms`、
  `latency avg 126580866280.65 ms → 0.0 fps`（实为**皮秒**，纳秒被当成毫秒又乘了 1000）。
  讽刺的是它**看起来像"板卡慢到爆"**，即错误方向看起来像一个合理的硬件结论，比报错危险得多。
  ⇒ 两条硬要求：
  1. **量级反查必须写进程序本体**，不能靠人记得做。板端内置一行
     `usleep(50000)` 自检，`now_ms()` 差值不落在 49–52 ms 就打印
     **`[BAD -- durations below are meaningless]`**；本轮实测 `50.137 ms [ok]`。
  2. **读板端日志必须先确认这行是 `[ok]`**。⚠️ 实测事故：600 帧那次的日志我只读了**尾部**，
     `[1] clock sanity` 落在被截掉的部分，于是**差点在没验证计时器的前提下引用时延数字**。
     **闸门存在 ≠ 闸门被执行过；被 `tail` 掉的闸门等于没有闸门。**
- **闸门脚本本身也必须被测试**：闸门的失败模式不是「报错」，而是**自信地给出错误答案**——
  它的输出正是决策依据，因此比被测代码出错更危险。
  实测反例：`build_push_to_manifest` 把 `idx_map` 反转后又用帧号查，
  **10 帧只映射上 4 帧**，却照样打印整齐的零漂移表格。
- **「配置阶段自检」必须证明它会失败**：从未真正执行过的守卫，其保护力是**零**，
  且**比没有守卫更危险**——它让人误以为浮点/安全契约已被强制。
  实测反例：`CMakeLists.txt` 写 `set(... ${CMAKE_CXX_FLAGS_<CONFIG>})`，
  `<` 是非法变量名字符 ⇒ CMake 直接语法报错，工程根本配不出来；
  而**逐配置槽位恰恰是唯一能抓到「发行版往 `CMAKE_CXX_FLAGS_DEBUG` 注入 `-ffast-math`」
  的入口**。规则：每条配置期断言都要配一条**反向注入测试**（故意注入违规值，必须 FATAL_ERROR），
  否则不许宣称该守卫有效。

## 五、交付命令的路径与口径纪律 【2026-10-08 新增，必读】

> 本节每一条都曾让一条**已交付的命令当场跑不起来**，或让一个产物**无法作为证据引用**。

1. **交付命令前必须实测该路径存在**。本项目 CLion 编到**本地** checkout
   （`/media/manu/1TB-Volume/workspace/ultralytics/manu/pipeline/cpp/cmake-build-debug/`），
   而**服务器 SSHFS 挂载上没有任何编译产物**（`manu/pipeline/cpp/build/` 同样不存在）。
   ⇒ `--cpp-bin` 之类参数**必须给绝对路径**；脚本里的默认值不可信，必须逐个验证。
   这是第三节「代码已同步 ≠ 权重已就位」在**编译产物**上的同型翻版。
2. **不要把「GUI 配置成功」当作「命令行可复现」**。IDE 的 build 目录、profile、
   输出位置与 README 里写的命令可能完全不同；两者都要各自验证。
3. **`--help` 未打印的信息不要写进验收步骤**。本项目 `gmc_stream --help`
   **不输出 OpenCV 版本**（实测 0 处匹配），版本只在真实运行的 `[BUILD]` 行或 `ldd` 里。
   规则：验收命令要打印的量，先确认它真的被打印，再写进检查步骤。
4. **追加写的输出文件必须先清空**：`--md5-out` 是追加语义，直跑二进制时残留旧行会让
   逐帧比对**错行**。走封装脚本时若脚本已 `write_bytes(b"")` 截断，则风险自动消除——
   **但这要读脚本确认，不能假设**。
5. **「按构造跳过」的闸门不得记为失败，也不得记为通过**。
   `--skip-python` 会让 `g1.pass=false / matched_frames=0`，脚本自身打印
   「G1 is skipped by construction; do not read this as G1 evidence」。
   报告里必须写成 `SKIPPED（按构造）`，既不是 FAIL 也不是 PASS。
6. **共享输出目录 + 缺少命名空间 = 证据作废**。多序列共用一个 `--out-dir` 时，
   文件名若不含序列名则**互相覆盖**；随后 G2 会拿「最后一个序列的文件」去比
   「第一个序列的冻结帧」，得出整齐的零漂移假象。
   规则：**每轮验证用新的输出目录名**，历史目录一律不得再引用。
7. **数据集路径与层级必须实测**。当前挂载是 `/home/manu/mnt/data/siping/datasets/manu/...`
   （**不是** `/mnt/data/...`），且序列实际在 `anti-uav/train/<seq>/` 而非 `anti-uav/<seq>/`。
   本次两侧 `find_sequence_folder` 恰好都探测了 `train/` 子目录才解析成功——
   **这是运气好，不是契约**；换数据集布局就会炸。
8. **精度与时延要分开归因**：本项目实测位精确性在 `-O0` 与 `-O3` 下**都成立**，
   但 `-O0` 的耗时**完全不可用于性能判断**。
   规则：引用「位精确」时可以跨优化等级，引用任何 ms 数字时**必须先确认构建类型**。
  规则：任何「索引 ↔ 文件名」映射必须有**合成文件树**上的单元测试，
  并包含一条**回归守卫**——重现旧错误实现并断言它**不等于**正确映射。
- **输出文件名必须能唯一定位「来源」**：实测 `--out-dir` 只用 push 序号命名，
  多序列共用一个输出目录时**互相覆盖**，闸门随后拿另一个序列的文件去比对——
  **自信地输出错误结论**。规则：产物文件名必须包含足以唯一定位来源的标识
  （序列名 + 序号）。同一脚本里若一处带前缀、另一处不带，**不一致本身就是缺陷线索**。
- **跨分辨率必须各测一遍**：本项目数据集是混合分辨率（`512×512` 与 `512×640`），
  同一份代码在两种尺寸下的下采样尺寸、letterbox 假设、边界处理都不同。
  单分辨率通过不能外推到另一分辨率。**报告「已验证」时必须写明覆盖了哪些尺寸。**
- **「把字典反转一次」是高危写法**：`idx_map` 若已是 `帧号 → 下标`，
  就**直接用**，不要反转为 `下标 → 帧号` 再拿帧号去查。
  方向反了往往仍能「匹配到一部分」，因此不会报错，只会静默比对错帧。
- **「单序列调试全对」不等于闸门正确**：实测同一处 `[MATS]` 连续两个对齐 bug——
  其一拿「最后一帧」去比 C++ 的「第 0 帧」dump（**单序列也错**），
  其二用循环内共享变量配 `sequence[0]`（**只在多序列发作**）。
  规则：任何闸门必须在**单序列与多序列**两种配置下**各测一次**；
  只跑一种配置等于没测。特别警惕 `last_*` 这类名字——它天然指向「最近一次」，
  而落盘产物往往是「第一次」。
- **落盘点与读取点必须同源**：谁在第几帧写 `_mats.npy`，谁就必须在**同一帧**取；
  把两者写在不同位置又不起眼，是静默错位的常见来源。
- **测试必须能被证伪（变异检查）**：一个永远通过的测试证明不了任何东西。
  新增测试时必须回答「把被测行为改坏，它会不会失败」。
  实测做法：把该模块**历史上真实出现过的缺陷**原样重新注入，断言测试**必须失败**。
  本项目编排测试据此重注入「环缓冲按 lag 索引」，20/21 个 lag 变红，测试方被判为有效。
- **改动核心索引/寻址逻辑后，「靠阅读确认」不算验证**：本轮移植 7 个真实缺陷
  **全部由运行发现，阅读一个都没抓到**。凡是**索引、偏移、合成顺序、冷启动钳制**，
  必须有可运行的寻址测试：用「带标记的输入 + 携带输入身份的桩」把结果变成可直接断言的指纹。
  标记桩只能证明**寻址**，不得用于证明算法等价性——两者必须分开声明。
- **完备性要求可证明的东西，就不要抽样**（2026-10-09）。排序网络的正确性由 Knuth 0/1 原理
  （TAOCP 5.3.4）给出：比较网络排好所有输入 ⟺ 排好所有 0/1 输入。n=21 即 2^21 = 2,097,152
  个输入，几秒可枚举。随机抽样**永远无法**支撑这个结论，只能证伪。
  > 配套铁律：**用来给实现背书的工具本身不允许出现间歇性失败**。本轮完备验证抓到 3 个
  > 只在并发下暴露的真缺陷（共享 scratch 数组、reduction + critical 的丢失更新、
  > 剪枝「恢复」不是真 undo 导致网络被污染但 `g_nce` 不变）。它们全部表现为「时好时坏」，
  > 比工具直接报错危险得多——错误结论会被当成被验证对象的性质。
- **凡是要「猜」的外部语义，先用 oracle 探针把它读出来**（2026-10-09）。本轮把
  `cv::warpAffine` 的插值/坐标/边界三条语义全部实测锁定，而非读源码：
  ①**无半像素偏移**（`(x,y)` 99.58% vs `(x+0.5,y+0.5)` 0.79%，MAE 39.1）；
  ②**位置量化到 1/32 且半上取整**（阶跃 oracle 直接读出 33 级阶梯，phi·32 恰为 0.5 时
  取上排除 round-half-even）；③**边界是「两个 tap 各自反射」**（96000 个越界 tap：
  模型 A 错 29.0%、模型 B 错 0.0%）。第③条我一开始判反了，把反射搬进内核后
  Ch1 Max|Diff| 从 7 恶化到 **239**，是探针把它纠正回来的。
  > **边界类语义不能靠直觉推断**：两个模型只在 tap 基址越界时才有分歧，而那恰好是
  > `copyMakeBorder` 免费提供的那一种——凭直觉很容易以为「先反射基址再取 base+1」更合理，
  > 实测恰好错三成。
- **验证工具自身的错误会被当成被验证对象的错误**（2026-10-09）。本轮两个自伤实例：
  ①对账工具 CPU 参考写 `cv::Mat ch2(W, H, ...)` 把 rows/cols 颠倒，512×512 正方形时被
  掩盖，640 宽序列直接内存越界 + 未初始化，表现为内核 Ch2 Max|Diff| = 255；
  ②探针 tap 守卫写 `y0 < 1` 把所有 y0=0 行判成失配，误报 Max|Diff| = 145，结论作废。
  > **对策**：①非方形尺寸必须专门覆盖（正方形会掩盖 rows/cols 颠倒）；
  > ②结论必须**交叉验证**——GPU 直测 ↔ 独立 CPU 探针，两者一致才采信；
  > ③工具输出要有「分布」而不只是「最大值」（|diff| 直方图 + 超差像素坐标），
  > 「max=2、MAE=0.003」和「max=2、MAE=1.4」标题相同、成因完全相反。
