## 0. 一句话结论

**QAT 路线在 rk3588 + rknn-toolkit2 2.3.2 上，不能同时拿到「比 int8 基线更准」和「INT8 输入的延时」。**

- 唯一能保住 INT8 输入的 QAT 路线是 **A2f**（QAT 权重 + 工具链原生全 int8），但它的虚警爆炸 **5~8 倍**；
  根因不是量化，而是 **QAT 训练把 heatmap 头搬坏了**（见 §10.2）。
- 精度上最好的 QAT 臂 **A2**（QAT 权重 + LSQ 学到 clip）在 T3/2000 上仍**输给** int8 基线
  （0.6863@0.45 vs 0.7090@0.45），在 T2 赢（0.9509 vs 0.9428），T1 打平。
- 而 A2 的代价是 **FLOAT16 输入**（`inputs_set` 45.41 ms，不是 int8 的 0.34 ms）。

*(板端口径的完整数字见 §5/§6/§7；服务器侧、无板卡依赖的完整报告见 §10 与
`qat/trial_0080/report/qat_final_report.{md,json}`)*

## 1. 三个必须记住的构建事实（本次实测，与既有记忆不同）

### 1.1 `mean_values` / `std_values` **必须**给，不能省

| 配方 | 板端表现 | 判定 |
|---|---|---|
| FLOAT 输入 ONNX **+** `mean=[[0,0,0]] std=[[255,255,255]]` + `build(do_quantization=False)` | 正常，`[5] null control: heatmap CHANGED`，RC=0 | ✅ 唯一可用配方 |
| FLOAT 输入 ONNX **不给** mean/std + `build(do_quantization=False)` | `[FATAL] NPU output independent of input -- results are not trustworthy`，RC=1 | ❌ 数值全死 |

原因：板端驱动**永远上传 uint8 NHWC 缓冲区**（`rknn_heatmap_smoke.cpp` 只有 `RKNN_TENSOR_UINT8` 这一条上传路径）。
没有 mean/std 时 runtime 把 uint8 直接加宽成 FLOAT16（0..255），图里没有 `/255`，网络看到的是 255 倍大的输入 → 饱和 → 输出与输入无关。

> 这修正了 `17_probe_qdq_import.py` 的一个**误读**：探针里 `hm_plain` / `hm_qdq_dq` 两个 case 的 null control 报
> `IDENTICAL(BAD)`，当时被归因为「那一帧没有无人机」；实际是缺 mean/std 导致的 255 倍输入错误。
> 探针的 `QDQ_ADOPTED` 结论本身仍然成立（它读的是板端 `out[N]` 的 zp/scale，与输入数值无关），
> 但探针**没有**测过 mean/std 这条轴。

**这不构成「重复归一化」**：`mean_values/std_values` 描述的是**输入张量**的量化（uint8 缓冲区 = x/255），
与 Q/DQ 描述的**激活** clip 是正交的两件事。Q/DQ 带的激活标定没有被二次施加。

### 1.2 UINT8 图输入的 ONNX **不可用**

`manu/pipeline/npu/make_uint8_input_onnx.py` 产出的 uint8 输入图，工具链在 build 期直接拒绝：

```
Not Support Dtype: 2                      # 2 = UINT8
Missing quantization parameters for images, leading to ambiguity
```

所以 `22_export_qdq_onnx.py` 新增 `--uint8-input`（默认 **0**，保留 FLOAT 输入）。uint8 版本仍可导出，仅作留档。

### 1.3 `do_quantization=False` 硬约束成立

`rknn.build(do_quantization=False)` + Q/DQ ONNX → 工具链**采纳** Q/DQ 里的 scale/zero_point，
一路带到板端输出张量。板端打印（冒烟实测原文）：

```
    input dims=[1,640,640,3] fmt=NHWC type=FLOAT16
    out[0] dims=[1,1,320,320] fmt=NCHW type=INT8 zp=-128 scale=0.00392157
    out[1] dims=[1,2,320,320] fmt=NCHW type=FLOAT16 zp=0 scale=1.00000000
```

| 量 | ONNX 里写的 | 板端打印 | 判定 |
|---|---|---|---|
| out[0] scale | `0.003921568859368563`（float32 的 1/255） | `0.00392157` | ✅ 逐位一致 |
| out[0] zp | `0`（uint8） | `-128`（int8） | ✅ uint8 zp=0 被重心化到 int8 zp=-128，量程等价 |

### 1.4 新踩的坑：工具链 build **不是 bit-reproducible**

同一份 ONNX、同一个 config 两次 build 出来的 `.rknn` md5 不同。
PC 模拟器必须自己 build（`load_rknn()` 的模型不能上模拟器），
如果它 build 到**同一个目录**，板端驱动就会报 `model md5 MISMATCH` 并中止整轮评测。
→ `22h` 的 `--rknn-dir` 默认改到 `pc_sim_rknn/`，`22g` 在评测前先把模型重新 stage 到板端。

## 7. 结论

### 7.1 主问题：**QAT 没有把 int8 的量化损失从 0.0379 进一步压低**

以交接表的口径（T3 001324/2000，量化损失 = PT float 的 F1 − int8 臂的 F1）：

| 臂 | 最优 F1 | 最优 th | 量化损失（对 PT float 的 0.7484） |
|---|---|---|---|
| fp16（量化上界） | 0.7469 | 0.35 | 0.0015 |
| **int8 PTQ 基线** | **0.7090** | 0.45 | **0.0394** |
| **A2 QAT（头 int8 + 学到 clip）** | **0.6863** | 0.45 | **0.0621** |

**A2 的量化损失比基线大 0.0227。** 机制很清楚：**阈值重标定对基线的收益远大于对 A2 的收益**
（基线 0.6448→0.7090 = +0.0642；A2 0.6552→0.6863 = +0.0311），
量化引入的 FP 在抬阈值时没有被同样地消掉。

另外两个集合：

- T2 golden_pool/1197：**A2 反而更好**（0.9509 vs 0.9428，量化损失 0.0446 vs 0.0527，领先 0.0081）。
- T1 tier1_sensitive/100：**打平**（两者最优点都是 0.8352）。
- 在**标称阈值 0.30** 上，A2 在三个集合上全部优于 int8 基线（+0.0104 / +0.0089 / +0.0391），
  但这个领先在把阈值各自重标定到最优点后就消失了 —— 也就是说 A2 的优势在 0.30 这个阈值下成立，
  不在最优工作点成立。

### 7.2 部署建议：**不要替换现有 PTQ 模型**

继续用 `p0_off_A_normal`（工具链全 int8）+ **th=0.45**：T3/2000 F1 **0.7090**、TP 1207、FP 198。
A2 在同一套口径下是 0.6863 / TP 1209 / FP 256 —— FP 多 58，F1 少 0.0227。

若一定要走 QAT 路线：**A2（QAT 权重 + LSQ 学到的 clip）** 是唯一可用的臂，
它比其它 QAT 变体好一个量级（A1 0.6741、A0 0.6750@0.70、A1b 0.5716、A2f 0.4374），
部署阈值建议 **0.45**（T3 最优点 0.6863；T2 从 0.25 起是平台区，0.30~0.60 全部 0.9509）。

### 7.3 最重要的负面结论：**QAT checkpoint 不能当 PTQ 模型用**

| 用法 | T3/2000 @0.30 | 说明 |
|---|---|---|
| A2：QAT 权重 + 学到的 clip + Q/DQ 混合 | 0.6552 | ✅ 唯一可用 |
| A0：QAT 权重 + fp16（无 Q/DQ） | 0.3595（FP 2672） | ❌ 权重自身在 float 下严重过自信 |
| A2f：QAT 权重 + 工具链自己的全 int8 标定 | 0.2574（FP 4433） | ❌ 灾难性 |

QAT 权重是**和它训练时那套 clip 绑死的**：换一套量化方案（A0）或换量化器（A2f）都会崩。
所以「把 QAT 权重丢回 PTQ 流水线」这条路不通，只能连同 `*.qdq_meta.json` 里的 scale 一起发布。

### 7.4 为什么 A2 在 T3 上打不过全 int8 基线（下一步该查什么）

1. **量化范围不同**：基线是**全网络 int8**（工具链标定 250 张），A2 是 **fp16 主体 + int8 头**（Q/DQ 只覆盖 3 个头部位点 + 输出）。
   T3 是最吃 FP 的集合，主体不量化 → 头部位点的激活噪声更容易造出假峰。
   A2 在 0.45 的 FP=256 vs 基线 198，差 58。
2. **A2 的 clip 在 feat_conv1 上比 max 标定紧一倍**（0.0187 vs 0.0376），
   真实激活可能被硬裁掉（LSQ 会为了 loss 牺牲长尾）。
3. **可验证的下一步**：把 3 个 Q/DQ 位点的激活直方图在 2000 帧 T3 上统计出来，
   看有多少像素落在 [255*s, ∞) 被裁掉；如果比例高，就把 feat_conv1 的 clip 放宽再训。

### 10.2 a2f 虚警爆炸的根因（四刀定位，每刀排除一类原因）

| 诊断 | 结果 | 排除了什么 |
|---|---|---|
| 1. ORT 跑 **float** ONNX（base 权重 vs QAT 权重），同一批帧 | 检出数 tier1 237→976（×4.12）、黄金池 1240→3645（×2.94）、**001324 7847→51373（×6.55）**；@0.30 的 FP 10→65 / 3→54 / **171→2582** | **排除「量化范围被撑爆」** —— float 就已经爆；base 侧逐位复现板端 pt_float |
| 2. 两个 ONNX 的算子直方图 | 完全一致（Conv 85 / Mul 93 / Sigmoid 77 / Softmax 1 / MaxPool 3 …），只差 3 个 Constant | **排除「导错图」** |
| 3. a2f 与 int8 基线的 RKNN 算子表逐行 | 149 算子全 INT8、输入 INT8，逐项相同 | **排除「构建配方不一致」** |
| 4. 权重级 diff（QAT ckpt vs base ckpt） | 494 张量全部匹配（0 问题）、66 个冻结未动；`head.heatmap.0.weight` rel_l2=0.266、均值 +0.004326→+0.006635（**+53%**） | **排除「checkpoint 存错 / 伪量化留在图里」** |

**根因：QAT 训练把 heatmap 头搬坏了** —— 权重整体位移（rel_l2 0.266）且均值抬高 53%，
等价于给 heatmap logit 加了一个正偏置 → sigmoid 饱和 → 热力图过度自信 → 固定阈值下虚警爆炸 5~8 倍。
这与训练 loss 变好（0.3487→0.3243）不矛盾：focal+offset 的 loss 不约束热力图的绝对标度。

⇒ **A0/A2f 的爆炸是「权重问题」，不是「量化问题」**；QAT 权重与它训练时那套 clip 绑定，
换量化方案就崩，只有 A2（QAT 权重 + 学到的 clip）能恢复大部分精度。

### 10.4 明确回答：能否兼得「精度」与「INT8 输入延时」？

**不能。** 三条互相锁死的约束：

1. **要 INT8 输入 ⇒ 只能用工具链全 int8 配方 ⇒ 只能用 base 权重**（A2f 证明 QAT 权重走这条路必炸）。
2. **要 QAT 权重 ⇒ 必须用 Q/DQ + `do_quantization=False` ⇒ InputOperator 退化为 FLOAT16**
   （inputs_set 45.41 ms，比 int8 的 0.34 ms 慢两个数量级，板端帧率 5.64 vs 13.16 fps）。
3. **即便接受 FLOAT16 输入换来的 QAT 精度，在 T3 上仍低于 int8 基线**
   （0.6863 vs 0.7090，损失 0.0473 vs 0.0247）—— 精度上也不划算。

⇒ **部署建议不变：维持 toolkit 原生 int8 + 逐轨阈值重标定（T3 0.45 / T2 0.30 / T1 0.50）。**
若要继续推进 QAT，最高价值的下一步是**把 LSQ 从 3 个头部位点扩到全网络**，
让 Q/DQ 覆盖主体，`build(do_quantization=False)` 才能把主体也保持 int8。
