## 一、动机：当前 OpenCV GMC 的两个工程痛点

现有 GMC 链路（`manu/models/st_bgnet.py::GMCWarpEngine`，原始灰度图上 Shi-Tomasi + LK 光流 + RANSAC 仿射）存在两个已确认瓶颈：

1. **CPU 算力与能效**：
   - 单对帧对齐耗时波动约 5~25 ms，占满 DataLoader worker，是四卡训练 GPU 利用率长期跑不满的直接原因（已实测：batch=4 时约 15 batch/s，rank 间抖动明显）。
   - 训练过程中每 sample 需 3 次 GMC（t-6、t-2、t-1），CPU 成为端到端瓶颈。
2. **大晃动/大颠簸失效**：
   - 光电吊舱在低空遭遇气流颠簸、快速俯仰时，位移可达数十像素并伴随运动模糊；
   - 特征点脱靶 → RANSAC 内点率崩塌 → 输出退化矩阵 → `Ch1 = |I_t - W(I_{t-2})|` 全图撕裂 → 虚警（FP）暴涨。
   - 现有防御仅为健康度门控（`min_inlier_ratio=0.4`），属于**事后降级**，不能提升大晃动下的对齐精度。

**为什么不用预对齐缓存**：640×640 letterbox 窗口缓存实测约 500 GiB 量级，**磁盘不可接受，已手工删除**。结论：GMC 优化必须在网络内部完成，而不是靠缓存绕过。

## 二、GMC-Net 核心设计规范

### 1. 4 点位移参数化（严禁直接回归 3×3 矩阵）

- 在基准空间 `W=160, H=128` 上定义标准矩形四点：
  ```
  p1=(0,0)  p2=(W,0)  p3=(0,H)  p4=(W,H)
  ```
- 网络输出 8 维位移增量：
  ```
  Δy = [Δu1,Δv1,Δu2,Δv2,Δu3,Δv3,Δu4,Δv4]
  ```
- 目标顶点 `p'_i = p_i + (Δu_i, Δv_i)`，通过**可微 DLT**（纯 PyTorch，`A·h=0` 闭式解，SVD/解析求逆）得到归一化 `H_160`。
- 全尺寸尺度映射（纯张量，支持梯度）：
  ```
  H_orig = S_up · H_160 · S_down
  S_down = diag(160/640, 128/512, 1)
  ```
- 要求：含尺度反转保护与除零保护。

### 2. 微架构约束

| 项目 | 规格 |
| :--- | :--- |
| 输入 | `[B, 2, 128, 160]`，`I_curr` 与 `I_prev` 通道拼接，均在原始灰度上降采样 |
| 骨干 | 4~5 层 stride=2 卷积，通道 `16 → 32 → 64 → 64`，ReLU/SiLU + BatchNorm |
| 池化 | `AdaptiveAvgPool2d((2,2))` → 256 维 |
| 预测头 | `Linear(256,64) → ReLU → Linear(64,8)` |
| 参数量 | **30K~60K（必须打印并落在区间内）** |
| FLOPs | < 0.05 GFLOPs |
| 延迟 | NPU 单帧 < 0.8 ms |
| 禁止 | 全分辨率跳跃连接（会击穿低通瓶颈并直通前景点） |

**下采样的物理意图**：抹杀 1~3 像素弱小点目标，强迫网络只感知天际线、山脊走向、建筑物轮廓等低频宏观几何。

### 3. 无监督自监督复合损失

```
L_total = L_photo + λ_edge · L_edge + λ_reg · ||Δy||²
```

- **光度项**：`α · (1 - SSIM(I_curr, W(I_prev)))/2 + (1-α) · ||I_curr - W(I_prev)||₁`，`α = 0.85`；`W(·)` 用 `F.grid_sample` 可微双线性实现。
- **边缘项**：固定 Sobel 算子提取两帧边缘幅值图，`L_edge = ||Sobel(I_curr) - Sobel(W(I_prev))||₁`，抑制亚像素微漂移。
- **正则项**：惩罚极端离群位移，保持大晃动预测的物理连续性。

## 三、真实帧客观评测体系（不依赖人工标注、不依赖合成帧）

### 1. `DatasetMiner`：从无标注连续视频自动挖掘两个评测集

- **集合 A（大晃动失效集）**：两帧平均像面位移速度 > 20 px，或 OpenCV RANSAC 内点率 < 35%，或跟踪失败/矩阵退化。场景：吊舱颠簸、大过载转弯、贴地俯冲。
- **集合 B（稳态强纹理集）**：位移速度 ∈ [1, 5] px，内点率 > 75%，且含丰富地表建筑/山脊强边缘。用于检验亚像素精度是否退化。

### 2. 双物理度量（严禁直接比对单应性参数数值）

| 指标 | 定义 | 判定标准 |
| :--- | :--- | :--- |
| **CCD**（时序闭环闭合漂移） | 取连续 3 帧，估计 `H1=H(t-2→t-1)`、`H2=H(t-1→t)`、`H3=H(t→t-2)`；`H_loop = H3·H2·H1`；`CCD = ¼ Σ ||H_loop·p_i − p_i||₂` | 集合 A：OpenCV 会闭环发散到几十 px；GMC-Net 要求稳健收敛 **< 2.0 px** |
| **ELE**（地表强边缘泄漏能量） | 当前帧 Canny 得 `M_edge`；`ELE = mean(|I_t − W(I_{t-2})|)` 在 `M_edge` 区域上；同时报告 95% 分位 | 集合 A：GMC-Net 必须显著低于 OpenCV；边缘相减后应呈均匀暗色，禁止成排亮白双轨拉丝 |

**CCD 的价值**：无需真值位姿，纯几何自洽性即可判尺，这是本方案最重要的免标注度量。

### 3. 交付结构（规划）

```
models/dlt.py            # 可微 DLT（4pt → 3×3，含除零/尺度保护）
models/gmc_net.py        # 30K~60K 双帧配准微架构
losses/homography_loss.py# SSIM + Sobel + 位移正则
pipeline/warp_engine.py  # 下采样推理、尺度回放、可微 grid_sample
benchmark/data_miner.py  # 真实帧挖掘集合 A / B
benchmark/evaluate_real.py# 输出 CCD / ELE / 推理时延的 Markdown 对比表
train_gmc.py             # 端到端自监督训练
```

`evaluate_real.py` 需直接读真实视频对，同时跑 OpenCV 与 GMC-Net 两套变换，输出含 CCD(px)、ELE 均值、耗时(ms) 的对比表。`__main__` 需用带旋转+平移+高斯亮度的张量验证 Loss 回传稳定、DLT 求逆稳定。

## 六、待决与风险

1. **不可辨识性风险**：无监督光度/边缘对齐在大晃动下容易收敛到**局部最优**（例如只对齐地平线一条线而放弃整体），CCO/CCD 度量必须与损失同时监控，否则可能"损失下降但闭环漂移变大"。
2. **BatchNorm 风险**：小 batch + 域外数据易导致 BN 统计漂移；部署到 NPU 需要 fold BN，训练脚本需同时输出 fold 前/后数值一致性校验。
3. **与 STBgNet 的耦合**：若 GMC-Net 替换 GMC，`Ch1` 与 `B̂_t` 质量同时变化，无法用单次 A/B 归因；建议先单独替换 `Ch1`（只做对齐 A/B），再接 STBgNet 的 `Ch2`。
4. **验收闸门**：GMC-Net 上线前必须满足：集合 A 的 CCD < 2.0 px 且 ELE 显著低于 OpenCV，同时 **Anti-UAV 官方 val 的 Trial 0474 单帧 F1=0.9064 零回归**（TP 21,643 / FP 1,004）。任一不满足即判负，不进入 Phase-C。

## 七、竞争路线对照：直接删除 GMC（No-GMC 消融，2026-09-30）

> **状态**：单变量构造已验证成立，全量构建与评测**待回填**。本节只记录**已实测**事实，
> F1/Recall/Precision 一律不预写。

### 1. 研究问题与动机

GMC-Net（第二~三节）的立项动机之一是「GMC 单对帧 5~25 ms、占满 DataLoader worker」。
在嵌入式端口上存在一条更激进的竞争路线：**干脆不要 GMC**，令 `W(.) = I`。
必须先量出这条路线相对冻结权重的代价，才能决定是「用网络替代 GMC」还是「直接删除 GMC」。

### 2. 单变量构造与已验证的等价性

- 新脚本：`manu/data/build_nogmc_median_dataset.py`（Twin A/B 新臂，0 GMC fits/帧）。
- 通道语义：`Ch0 = I_t`、`Ch1 = |I_t - I_{t-2}|`、`Ch2 = (I_t - median{I_{t-2k}})^+`。
- 与冻结 `uav_gmc_median` **完全复用同一份代码路径**的项：文件名清单、帧索引解析、
  序列起点钳位、history lags（2,4,...,42）、`np.median` 表达式、uint8 取整、
  `np.stack` 通道序、`cv2.imwrite` JPEG 编码、label 硬链接。
- **唯一变量**：`W(.) = I`。跳过 warp 在数学上等价（identity 的 INTER_LINEAR 权重恰为
  1/0/0/0，输出逐像素等于原图），且省掉 22 次拟合 + 22 次重采样。

**已实测的等价性证据**（`DJI_0175_2`，编码前后各验证一次）：

| 检查 | 实测 | 判定 |
| :--- | :--- | :--- |
| native(GMC) 数组重编码 → 冻结文件 `Ch0` maxdiff | **0** | 编码路径与冻结 builder **逐位一致** |
| no-GMC 数组重编码 → 冻结文件 `Ch0` MAE | **0.01060 灰阶** | JPEG 4:2:0 色度下采样底噪 |
| 两条分支的 `Ch0` 编码前 | 同一个数组对象 | 单变量在数组级成立 |

- `Ch0` 文件级漂移 0.01 灰阶**可放行**：标尺是 PNG↔JPG 格式切换（粗好几个数量级）历史上
  使单帧 F1 从 0.9064 掉到 0.9023（TP −206）。二者不在同一量级。
- **教训**：3 通道 JPEG 存在 4:2:0 色度下采样，`Ch1/Ch2` 内容一变就会让 `Ch0` 的**解码值**
  产生 1~8 灰阶抖动。**「Ch0 必须逐字节为 0」是错误的验收判据**，判据必须下到编码前数组层。

### 3. 关键实测：GMC 的像素级边际贡献远小于预期（采样有缺陷，仅作方向性参考）

`DJI_0175_2` 连续 8 帧，编码前数组级对比：

| 量 | 实测 |
| :--- | --- |
| `|native − nogmc|` 的 Ch1 均值 | **0.0192** 灰阶（max 1~5） |
| `|native − nogmc|` 的 Ch2 均值 | **0.0316** 灰阶（max 1~6） |
| no-GMC 的 Ch1 自身均值 | 0.814 ~ 1.042 灰阶 |

解读：GMC 与 no-GMC 的两通道在**绝大多数像素上几乎相同**，差异集中在结构边缘的少数像素上。
若成立，意味 GMC 在该序列上拟合出的仿射接近 identity，其像素级改动极小。

> **该组数字的采样缺陷，不可作为结论引用**：这 8 帧取自 `000003~000010`，全部落在
> **序列起点钳制区**（`ci − 2×21 < 0`，21 帧历史里 20 帧被钳到 frame 0），不代表稳态；
> 且为 8 帧逐帧采样而非全量。**正式结论以 24 序列 / 31,613 帧的
> `ab_test_chained_gmc.py --stage compare` 为准**（该工具已复用，无需新写）。

### 4. 已成立的工程事实：移除 GMC 后的新瓶颈是 21 帧全图 median

冒烟实测（`DJI_0175_2`，512×512，单 worker，`cv2.setNumThreads(1)`）：

```
34.84 ms/frame  =  read 0.59  +  median 32.46  +  write 1.13
                                 ^^^^^^^^ 占 93%
```

**GMC 拿掉后，21 帧 `np.median` 成为 CPU 主导成本（93%）。** 该结论不依赖后续 F1 数字，
是独立成立的嵌入式移植事实。

预判解法（**尚未实现、未实测**）：

- 窗口固定 21 帧、奇数长度 → 中位数就是第 11 个顺序统计量，无需全量 partition；
- 改为**有序环形缓冲**：新帧 O(21) 插入、取中位数 O(1)，**输出与 `np.median` 逐位相同**，
  复杂度从 6.9M 元素（`np.median` 在 `stack(21,H,W)` 上做 partition）降到 21；
- 对 NPU 天然适配：21 路比较-选择定长排序网络，每帧只有 21 个标量在动。

> **战略含义**：嵌入式移植「GMC 太耗时」的真正解法，可能不是牺牲 GMC 换 32 ms，
> 而是**保留 GMC 语义 + 把 median 降为 O(21)**。需与第 7.4 节的 F1 代价一起权衡。

| `runs/optuna_p0_nas/trial_0474/weights/best.pt` | **缺失**。远端 `runs/` 仅含 `onnx/`（`yolo26s_p1_heatmap.onnx`，属已止损的 YOLO26s 扩容路线，**不是 Trial 0474**）与 `test_zoom/`；本地 `runs/` 同样只有这两个目录；数据集盘全盘仅搜到 `selfsup_bg_runs/st_bgnet_online/best.pt` |
| `runs/gmc_eval/` | **不存在**——原生臂 cache 也需重新生成，不能假定服务器已有 |

**结论：第 1 步建集可直接跳过（数据已就位）；第 3/4 步（双臂推理 + F1 判决）被权重缺失硬阻断。**
第 2 步 `stage compare` 与第 5 步 `stage timing` **不依赖权重，现在即可执行**。

**新增工程纪律**：本项目的 SOTA 权重位于 `runs/`，而 `runs/` **未纳入代码同步链路**（代码同步只覆盖 `manu/` 与 ultralytics 包），因此"代码已同步"绝不等于"权重已就位"。凡涉及推理/评测的交付，必须把**权重路径存在性**单列为前置检查项，不能凭 memory 中的路径直接下发命令。

## 八、No-GMC 消融最终判决（2026-10-08，全链跑通）

> 三阶段实测完成，**指标全部有效**（GT 25,111 两臂一致、key 集合 31,613 对齐、逐序列求和断言通过）。
> 本节是第七节「待回填」的正式回填，第七节 7.1~7.5 的结论**全部以本节为准**。

### 8.1 掉分判决（`stage eval`，th=0.25，Distance<=8.0px，官方 val 24 序列 / 31,613 帧 / 25,111 GT）

```
[HEADLINE]  native F1=0.9062  ->  no-GMC F1=0.9009   dF1=-0.0054
[HEADLINE]  Recall 86.18% -> 85.64%  (-0.54pp)   Precision 95.55% -> 95.02%  (-0.53pp)
[HEADLINE]  TP 21640 -> 21504 (-136)   FP 1007 -> 1126 (+119)
```

**结论：去掉 GMC 的代价是 F1 -0.0054（相对 0.6%）、Recall -0.54pp、Precision -0.53pp。**

**SELF-CHECK 偏差定性**：native 臂实测 `F1=0.9062351 / TP=21,640 / FP=1,007`，与冻结标称 `0.9064 / 21,643 / 1,004` 差 **3 个 TP / 3 个 FP / 0 个 GT**，F1 差 `-0.000165`。这是**抽峰深度差异**（本次 `conf_thresh=0.02 / top_k=100`，权威口径为 `0.08 / 80`）的特征性表现：多收的极低分峰既可能抢占贪心匹配（TP -3）也可能新增 FP（FP +3）。**`ΔF1=-0.0054` 是该复现噪声（0.000165）的 33 倍，判决成立。** 复现噪声下限记为 **±3 TP ≈ ±0.0002 F1**，后续任何小于该值的差异一律不下结论。

**关键性质：`dF1` 在全阈值区间几乎恒定（0.10→0.45 共 8 档，仅 -0.0033 ~ -0.0054），且两臂峰值同在 th=0.25。** 说明 no-GMC 臂**不是** native 臂的阈值平移版本，重调门限救不回来，是真实的信息损失。

### 8.2 掉分是集中的，不是均匀的（本次最有价值的发现）

**GMC 空转的序列：去掉 GMC 反而变好。** 下列 5 条序列在 `stage compare` 中 **Ch0 MAE 恰好 = 0.00000**（即 GMC 拟合出恒等矩阵，两臂 Ch0 逐字节一致，构成**零 JPEG 编码混淆的纯净对照**）：

| 序列 | compare Ch2 MAE | dF1 | dTP | dFP |
| :--- | ---: | ---: | ---: | ---: |
| `25_1` | 0.110 | **+0.0030** | 0 | -4 |
| `34_1` | 0.109 | **+0.0044** | 0 | -5 |
| `43_1` | 0.283 | -0.0008 | 0 | +1 |
| `5_1` | 0.152 | +0.0000 | +1 | +1 |
| `3700000000002_102004_3` | 0.067 | +0.0000 | 0 | 0 |
| **合计** | | **+0.0066** | **+1** | **-7** |

即：**在 GMC 可证明没干活的序列上，删除 GMC 净收益 +0.0066 F1（虚警更少）。全盘 -0.0054 的亏损完全来自 GMC 真在干活的少数序列。**

**亏损高度集中**：total `dTP=-136` 中 `wg2022_ir_052_split_08` 独占 **-74（54%）**、`DJI_0051_2` **-22（16%）**，二者合计 70%。

| :--- | ---: | ---: | ---: | ---: |
| `DJI_0051_2` | **-0.0640** | -22 | 1.182 | 0.1246（两臂都极难） |

注意 `DJI_0051_2` 与 `wg2022_ir_011_split_03` 的 Ch2 MAE 并不高却掉得最狠，**说明 Ch2 偏离量单独不足以解释掉分，序列自身难度（Recall 7.44% / 8.70%）是混淆项**。不得把 Ch2 MAE 当作掉分的充分预测量。

### 8.3 代价表（`stage timing`，24 序列跨全序列均匀抽样 × 30 帧，单进程 `cv2.setNumThreads(1)`）

| 项 | ms/帧 | 占 native |
| :--- | ---: | ---: |
| GMC 拟合（**22 次/帧**，每 lag 各一次） | 39.66 | 21.6% |
| **warp（21 次 `warpAffine` @640×512）** | **~80** | **~43.7%** |
| 21 帧全图 median | 61.71 | 33.7% |
| 读帧 | ~2 | ~1% |
| **native 合计** | **183.32** | 100% |
| **no-GMC 合计** | **61.78** | **33.7%** |

- **删除 GMC 共省 121.54 ms/帧（66.3%），单帧加速 2.97×。**
- **归因修正（重要）**：开销大头是 **21 次 warp（~80 ms），不是拟合（39.66 ms）**。此前 memory 记载的「GMC 单对帧 5~25 ms、占满 DataLoader worker」只覆盖了拟合侧，**漏掉了 warp 侧约 2 倍的代价**。
- 删除 GMC 后残留 61.78 ms 中，**61.71 ms（99.9%）是那个 21 帧全图 median**。

> **timing 曾有一处使结论失效的缺陷（已修）**：原实现只拟合 1 个 GMC 矩阵就复用给全部 21 个 lag，
> 而真实管道是**每 lag 一次拟合 = 22 次/帧**，导致 `GMC ms` 列被低估约 22 倍。已改为逐 lag 拟合，
> 并新增 `fits/frm` 列使 22 这个数显式可见。**任何计时类结论必须先核对拟合次数与真实管道一致。**

### 8.4 判决与推荐方案：恒等门控 GMC（identity-gated GMC）

**单纯 no-GMC 已可交付**：F1 -0.0054 换 CPU -66.3%、加速 2.97×，对嵌入式是压倒性划算。

**但由 8.2 可推出一个严格更优的方案，且几乎零额外成本**：

1. 只拟合 **1 个** GMC 矩阵（约 1.8 ms），读出净平移/旋转/缩放；
2. 若该矩阵**近恒等**（8.2 那 5 条序列实测即恒等），则 `warp(I, I) == I` 逐像素成立，
   **跳过全部 21 次拟合 + 21 次 warp**，直接对未对齐帧做 median；
3. 否则走完整 GMC（22 拟合 + 21 warp）。

| 方案 | ms/帧 | 相对 native | 预期 F1 |
| :--- | ---: | ---: | --- |
| native（22 拟合 + 21 warp） | 183.32 | 1.00× | 0.9062 |
| chained GMC（1 拟合 + 21 warp，已有脚本） | ~146 | 0.80× | 未测 |
| 纯 no-GMC（0 拟合 + 0 warp） | 61.78 | 0.34× | 0.9009 |
| **恒等门控 GMC（1 拟合，按门限决定是否 warp）** | **~65** | **0.35×** | **接近 0.9062** |

理由：8.2 已证明那 5 条序列（GMC 空转、Ch0 逐字节一致）上省掉 GMC 是**净收益**，
而高运动序列（如 `wg2022_ir_052_split_08`、`DJI_0051_2`）必须保留 GMC 才能守住那 136 个 TP。
门控把两者的优点合并，代价只有约 2~4 ms/帧的一次拟合。

**门限尚未确定**：需要在真实帧上测 GMC 拟合出的**净位移幅度分布**，才能定「近恒等」的阈值
（建议 `|t| < 0.5~1.0 px` 且 `|scale-1| < 1e-3` 且 `|rot| < 0.1°`）。
**在测出该分布之前，禁止拍脑袋定门限。** 该诊断可复用 `manu/models/st_bgnet.py::GMCWarpEngine`
或 `FastGMCEstimator`，属下一步唯一待做实验。

### 8.5 中值优化的期望值修正

第七节 7.4 曾称滑动中位数可带来「量级改善」。**该表述需要收紧**：复杂度确由
`O(W·H·21·log21)`（逐像素完整 partition）降到 `O(W·H·21)`（有序环单次插入），
**输出逐位相同**，且在 NPU 上是 21 路比较-选择定长网络、无数据相关分支；
但**在 CPU + numpy 上这只是约 log21 ≈ 4.4 倍的运算量削减，不应期待 100 倍常数因子改善**。
