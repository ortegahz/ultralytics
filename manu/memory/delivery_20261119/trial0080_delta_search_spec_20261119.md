## 2. C++ 跟踪器参数搜索空间（物理帧差 `Δn = fid - last_fid` 驱动状态转移）

| 参数名（C++ 变量） | 物理含义（25 fps 基准） | 搜索区间 | 说明 |
|:--|:--|:--|:--|
| `dt` | 卡尔曼状态转移时间步长 | `0.04f * Δn`（**不搜**） | 按 Δn 严格线性计算 |
| `min_hits` | 航迹起批确认所需命中次数 | `{2, 3}` | 2 次 ≈ 80~160 ms，3 次 ≈ 160~240 ms；**不要搜 ≥4**（起批超 300 ms 响应太慢） |
| `max_age_phys` | 丢失后航迹保留的最大物理帧数 | `{10, 12, 15, 18}` | 对应 400 ms ~ 720 ms；`fid - last_hit_fid > max_age_phys` 立即销毁，防幽灵框拖尾 |
| `R_base` | 相邻帧（Δn=1）基础关联半径 | `{4.0, 6.0, 8.0, 10.0}` px | 覆盖 40 ms 内的目标最大位移与检测抖动 |
| `R_slope` | 每多跳 1 帧放宽的关联半径增量 | `{2.0, 3.5, 5.0}` px/帧 | 实际门限 `R = R_base + R_slope*(Δn-1)` |
| `alpha` | 单帧（40 ms）置信度/能量保留率 | `{0.75, 0.82, 0.88, 0.93}` | `score = score * std::pow(alpha, Δn) + curr_score` |

## 3. 评测口径对齐（线下 vs 板上）

1. **全帧 vs 回调帧**：确认嵌入式 `app` 的消费方式——
   - 若 app 只在收到算法回调时刷新目标框（~14 Hz）⇒ 服务器 F1 在**抽样后的 fid 帧集合**上与对应帧号的 GT 计算；
   - 若 app 要求每个 25 Hz 采集帧都输出框（跳过的中间帧由跟踪器补一次纯预测 `predict(dt=0.04f)`）⇒
     服务器评测需在**全量 25 fps 帧**上逐帧对 GT 算 F1 ⇒ 搜索器会自动把外推偏离的惩罚算进去。
2. **Δn ≡ 1 回归底线**：选出最高平均 F1 的 `opt_params` 后，用同一套参数跑一遍**全量 25 fps（Δn≡1）**序列，
   确认其 F1 与 **v3 逐帧对齐基准（94.7469%）**几乎一致 ⇒ 才可直接合入板卡 C++ 工程。
3. 判据沿用交付三联：`F1 ≥ 0.88 ∧ Recall ≥ 0.85 ∧ FAR ≤ 0.03`（v3 的 FAR 余量 30.6%）。
