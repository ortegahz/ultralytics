## 一、模型契约（全部从 checkpoint 读出，无一项是猜的）

- **权重**：`/home/manu/mnt/pycharm_project_10ae9e2e/runs/optuna_p0_nas/trial_0474/weights/best.pt`，
  **7,375,044 字节**（实测 `ls -l`）。
- **checkpoint 键**：`epoch, model, metrics, stride, imgsz, p0_kwargs`
  ⇒ **`stride = 2`**、**`imgsz = 640`**。
- **`p0_kwargs`（读出，不硬编码）**：

  ```python
  {'use_spatial_gate': True, 'stem_type': 'standard_dw', 'downsample_mode': 'pixel_unshuffle',
   'gate_input_mode': 'diff_only', 'gate_mid_channels': 16, 'gate_depth': 2,
   'fusion_mode': 'scalar_gate'}
  ```

- **模型类**：`manu/models/heatmap_model.py::YOLO26HeatmapDetector`，
  构造参数 `temporal_mode="standard"`、`use_p0_highway=True`、`scale='n'`。
  **scale 的确定方法**（写下来是因为它可复用）：`scale='n'` 与 state-dict **523/523** 个张量逐名匹配；
  `scale='s'` 只匹配 **107** 个 ⇒ 只能取 `'n'`。
- **学到的 P0 门控**：`α = 0.125926`；P0 highway 可训练参数 **4,418**。
- **输入**：`(1, 3, 640, 640)` float32 RGB，**数值 = uint8 / 255**。通道语义：

  | 通道 | 语义 |
  |:---:|:---|
  | `ch0` | `I_t`（原始 IR 灰度） |
  | `ch1` | `|I_t − W(I_{t−2})|`（GMC 短差，**GMC 在原始灰度上估计**） |
  | `ch2` | `(I_t − B_t)^+`（21 帧时域中值残差） |

- **输出**：`heatmap (1,1,320,320)`（sigmoid，**clamp 到 [1e-5, 1−1e-5]**）；
  `offset (1,2,320,320)`（**stride-cell 单位**的原始亚像素）。
  `stride = 2` ⇒ 单元 `(x, y)` 映到 `((x+dx)*2, (y+dy)*2)`。
- **抽峰协议**（`manu/evaluation/heatmap_evaluate.py::extract_peaks`）：
  3×3 max-pool **免 NMS**，保留条件 `keep = (hmax == hm) & (hm >= th)`，再按分数取 **top-k**。

## 四、量化标定策略（本轮唯一最关键的转换选择）

- **标定集 = 200 张已建好的三通道特征 JPEG**，取自 **`images/train`**：
  **绝不取原始 IR**（那是完全不同的输入分布，会在纸面上量化得很好、实际悄悄丢掉热图头赖以生存的次阈值脉冲）；
  **绝不取 val**（虽然量化本身不是指标，但在评测集上标定是不必要的污染）。
- **分层**：**轮转（round-robin）跨 199 个不同序列**取 200 张（每序列 1 张，其中 1 个序列贡献 2 张），确定性（排序 + 固定步长），可复现可审计。
  清单落盘：`/media/manu/1TB-Volume/rknn_work/hm/calib_train_features.txt`（**200 行**，实测）。
- **量化配置**：`mean_values = [[0, 0, 0]]`、`std_values = [[255, 255, 255]]`、`target_platform = "rk3588"`。
  即 **图直接吃 uint8，由 RKNN 自己除 255** —— 与 PyTorch 侧的 `uint8/255` **逐比特等价**，
  所以 host 与板卡看到的是同一组数，差异只可能来自 NPU 本身。
- ⚠️ **本条与 yolov5 轮的标定结论相反，不可互相引用**：见 `rknn_npu_board_run.md` §9.6（标定集大小**不影响**与官方模型的一致度）——
  那测的是**两个模型之间的一致性**，本条测的是**部署精度**，二者不是同一个命题（`rules.md` §四·9）。

#### v1 → v2 的差异来源：**不是调参，是把一个算子搬回了 NPU**

| | v1 原始 | v2 depthwise |
|:---|---:|:---|
| 算子总数 | 163 | 162 |
| **Target = CPU** | **4** | **3** |

| `rknn_run` | 151.2 ms | **103.7 ms** |

```
ID 14  Conv  INT8  NPU  (1,16,640,640),(64,16,2,2)  → (1,64,320,320)   819,200 cycles
```

剩余 3 个 CPU 算子是 `InputOperator` + 2×`OutputOperator` —— **I/O 边界，不是计算**。
构建日志中 **fallback 警告 0 条**。

**精度代价：0。** 31 帧探针逐帧比对 v1/v2 的 NPU 输出：**31/31 逐字节相同**。

⇒ 详见第七·5 节。

⇒ **本模型上算力就是全部预算，I/O 与预处理都不是**。

#### 6.2.4 🔴 int8 的代价是**统计显著**的 —— 本节推翻了初版结论

初版写的是「两臂 Wilson 区间大幅重叠 ⇒ 不足以判定为统计显著劣化」。
**这个判断方法是错的**：两臂跑的是**同一批帧**，是**配对**数据，
拿两个独立样本的 Wilson 区间是否重叠来判显著，功效被严重低估，**不能用**。
正确做法是配对的 McNemar 检验（只看两臂结论不一致的那些帧）。重算：

| 口径 | 不一致帧（CPU 更好 / NPU 更好） | 合计 | 精确二项双侧 p |
|:---|:---:|---:|:---:|
| 全部 600 帧 | **19 / 2** | 21 | **0.0002** |
| **剔除 DJI 后 550 帧** | **12 / 2** | 14 | **0.0129** |

⇒ **即使完全剔除 DJI 这个混淆项，int8 量化仍然带来统计显著的召回损失**
（ex-DJI recall 0.8955 → 0.8727，**−2.27 个百分点**（精确 −2.2727 pp = 394/440 − 384/440），p = 0.0129 < 0.05）。
方向也一致：TP 净差 `NPU − CPU = −10`（ex-DJI）/ `−17`（全部）。

**结论（修正后）**：

- int8 **不改变任何检出位置**（>8 px 分歧 **0/600**），这一点依然是移植质量的强证据；
- 但 int8 **确实会削掉阈值附近的热图峰值**，代价是 ex-DJI 上 **−2.27 pp recall**，且**统计显著**；
- 该代价的量级（2 pp）与 DJI 域弱点（42 个 FN）**不是同一个东西**，两者必须分开陈述。

> ⚠️ 此处 p 值基于**帧级**配对（14 个不一致帧），相对 GT 级配对偏保守；
> 即使如此仍显著，故结论方向不因口径而改变。`n = 14` 的 discordant 数仍偏小，
> 按 `rules.md` §三·6b，**只报效应量 + p 值，不宣称「已定量刻画」**。

「只有一边触发」的 28 帧中，**10 帧落在两个 DJI 序列**（`DJI_0051_2` 6 帧、`DJI_0175_2` 4 帧），
其余 18 帧散落在 **10 个**正常序列 —— 与「阈值附近的少数帧」这一解释一致。

## 七、踩坑清单（每一条都已升级为 `rules.md` 条目）

### 7.1 🔴【新规 `rules.md` §三·10】`torch.onnx.export` 会把模块留在 **train 模式**

- **实测**：`torch.onnx.export(wrapper, ...)` 返回后 **`model.training == True`**，且**不会恢复**。
  任何**在导出之后、在同一进程内**做的 PyTorch↔ONNX 比较，实际上是在拿
  **eval 态 ONNX 图**去比 **train 态 PyTorch 模型** —— BatchNorm 走的是**批统计**而不是 running stats。

| 参考值取法 | heatmap max abs diff | offset max abs diff |
|:---|---:|---:|
| ❌ 导出**之后**取参考 | **0.2801**（均值 1.597e-4） | **1.677**（均值 0.131） |
| ✅ 导出**之前**取参考 / 导出后强制 `model.eval()` | **5.07e-7** | **2.48e-5** |

- **为什么它特别危险**：上表第一行看起来**完全就是「导出坏了」**，而且不是。
- **同轮被实测排除的两个假设**（排除过程同样有价值）：
  1. Resize / PixelUnshuffle 往返 **max diff 恰为 0.0**；
  2. 逐块导出（`b0..b10`、`c13/c16/c19/c22`、`fuse_p1/p2`）**每一块都在 8.6e-6 以内**。
- **铁律**：任何 `torch.onnx.export` 之后，**先 `assert not model.training` 再使用该模块**；
  **参考值必须在导出之前抓取**。

### 7.5 🔴【新规 `rules.md` §四·9e】`nn.PixelUnshuffle` 让 1 个计算算子落 CPU（151 → 104 ms）

- **机制**：`nn.PixelUnshuffle` 导出为 `reshape → permute → reshape`。
  对 P0 highway 的 (1,16,640,640) 输入，rknn-toolkit2 把 permute 结果折成单次 `Reshape`
  到 **(1,16,4,102400)**，随后的 Transpose 超限：

  ```
  W RKNN: Transpose will fallback to CPU, because input shape has exceeded
          the max limit, height(4) * width(102400) = 409600,
          required product no larger than 16384!
  ```

- **🔴 计数口径（本条曾因措辞不准被误读，权威值来自 `logs/build_verbose.log` 的算子表）**：
  v1 落 CPU 的算子共 **4 个** = `InputOperator` + **`Reshape`（id 68）** + 2× `OutputOperator`。
  按 `rules.md` §四·9e 的口径（`InputOperator`/`OutputOperator` 属 I/O 豁免），
  真正的**违例计算算子只有 1 个**，而它由 **2 条 fallback 警告**（两个 Transpose 超限）引发
  ——**两条 Transpose 被 toolkit 合并进了同一个 `Reshape` 节点**。
  ⇒ 三代权威计数：`fallback` 警告 **v1 = 2 / v2 = 0 / v3 = 0**；
  CPU **计算**算子 **v1 = 1 / v2 = 0 / v3 = 0**；CPU 总数（含 I/O）**4 / 3 / 3**。

- **关键认知：上限卡在「空间乘积」，与张量怎么拼无关。**
  RKNN 的 Transpose 要求 `H*W ≤ 16384`（约 128×128），而 640×640 上的通道重排**恒为 409600**。
  实测改写成 slice+stack+reshape（同样逐位精确）⇒ 落到 (1,16,1280,320)，
  **同样的 409600**，且**多出 6 个 CPU Slice（CPU 算子 4 → 10，更慢）**。
  ⇒ **改写张量表达式救不了布局类回退。**

- **解法：把布局变换改写成算术。** 一个 2×2 / stride-2 的 **depthwise conv** 读窗口写小图，
  **不需要任何 transpose**，而卷积是 RKNN 在任意尺寸下的原生算子。
  四个 0/1 delta 平面一次取出四个子格；`groups=C` 时 PyTorch 把输出通道编为 `c·f²+i·f+j`，
  **与 PixelUnshuffle 的定义天然一致，无需重排**。

- **正确性（四种形状全部 `torch.equal`）**：

  | 输入形状 | `nn.PixelUnshuffle` vs 改写 |
  |:---|:---|
  | (1,16,640,640) | **EXACT** |
  | (1,3,320,320) | **EXACT** |
  | (2,16,128,96) | **EXACT** |
  | (1,64,8,8) | **EXACT** |

  整网层面：**31 帧 NPU 输出与旧模型逐字节相同** ⇒ **加速零精度代价**。

- **改写时的两个真实坑**（都会「形状对、数值错」，C=1 时还测不出来）：
  1. one-hot 必须落在**通道对角线** `w[o, o, i, j] = 1`。写成对所有 `c` 置 1 ⇒ 输出变成
     `sum_c x[c, ...]`（通道求和）而非逐通道拷贝。
  2. **输出通道索引必须是 `c·f²+i·f+j`**（通道优先、偏移交错）。
     卷积天然吐出 `(i·f+j)·C + c`（偏移优先分块），写反了顺序**在 C=1 时完全正确**。
- 实现：`manu/pipeline/npu/hm_pixelshuffle.py`（`--verify` 自检逐位等价）。
