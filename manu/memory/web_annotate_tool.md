## 3. 预标注口径（严格复刻，不重新推导）

对齐 `manu/data/multiscale_heatmap_cache.py`：磁盘序 `[I_t, GMC diff, median residual]` → 模型序 `[..., ::-1]`；
`FastGMCEstimator(downscale=2)`；21 帧中值 × 步长 2；尺度 = 原生 letterbox + 160 + 80；
各尺度热图逆映射回原生网格 → `np.maximum` → 阈值 0.22 → 膨胀 9 → 8 连通域 → 面积 ≥ 4；
按**连通域热图积分**降序（不是面积）截断 100。

🔴 **本次实现时踩的坑**：`flush()` 最初误用**原始灰度帧**而非 GMC+中值特征去画 canvas，
会把冻结输入契约整个绕过去。改成分块构建特征后传入才正确。**教训：跨文件复用推理口径时，
"同一批字节"的保证来自数据流本身，而不是函数名相似。**

## 4. 落盘结构（候选与人工标签彻底分离）

```
labels/<seq_id>/<帧:06d>.txt      人工标注，唯一真值
prelabels/<seq_id>/<帧:06d>.txt   模型候选，重跑推理永不覆盖人工
prelabels/<seq_id>/scores.json    每个候选峰值（YOLO 无分数列，单独存）
review/<seq_id>.json              复核状态
```

⇒ 「未复核」才有意义：仍是原样的帧 = 还没看过，天然就是工作队列。
⚠️ 复用已有 `preannot_v1/labels/train/*.txt` 可直接拷进 `prelabels/` 当候选，无需重跑推理。

## 5. 效率设计（这是本工具的真正价值）

| 机制 | 说明 |
| :--- | :--- |
| 航迹传播 `P` | 用上一帧测得速度外推 N 帧，**遇已有标注自动停**，一次请求批量写入 |
| 航迹插补 `I` | 当前帧与下一标注帧之间线性插值 |
| 接受候选 `空格` | 采纳 → 保存 → 自动前进 |
| 跳未复核 `F` | 跳过已完成片段 |
| 候选阈值 `[`/`]` | 弱候选一键隐藏 |
| 三色时间线 | 蓝=候选 / 绿=已标注 / 深绿=已复核，剩余工作量一眼可见 |
| 双 Canvas | 图片仅换帧重绘，拖框只重绘叠加层 |
| 帧预取 + 服务端环缓存 | 实测 SSHFS 上冷读 **265.8 帧/s**（142 KB/帧），缓存命中瞬时 |

## 7. 第二轮：批量预标注 + 一个致命静默 bug

### 7.1 🔴 致命 bug：任务永远停在 queued，预标注按钮等于没有

`jobs.py` 原本用两个状态源：`_active` 集合记录「哪些任务活着」，`Job.status` 记录「跑到哪一步」。
`submit()` 只写 `Job.status`、**从不往 `_active` 里登记**，而 `_run_queue()` 的派发条件是
`status == "queued" and key in self._active` ⇒ **任何提交都永远不会被派发**，按钮点了毫无反应且不报错。

⇒ 已改为**只认 `Job.status` 一个状态源**（`queued` 可派发 / `running` 占并发额度 / 其余为终态），删掉 `_active`。
⇒ 这类"两处状态各记一半"的 bug **读代码看不出来**，必须让队列真的跑一次。故新增 14 项队列自测
（stub 掉 `Popen`，驱动真实调度循环），断言「全部任务离开 queued」「并发上限被遵守」「远程命令含
conda/端口/GPU/限帧」。**自测总数 36 → 51 项。**

### 7.2 批量 + 多 GPU 分片

服务器有 4×RTX 4090 空闲，原来一序列一 GPU 且 `max_concurrent=1`，等于浪费 3 张卡。
现支持一次提交全部序列、按 GPU 轮询分片（`submit_many` + `devices` 参数），弹窗可全选、可限帧试跑，
队列面板按序列显示进度条与 GPU 编号。

### 7.3 🔴 路径翻译曾被做两次

加校验时踩到：`server.py` 先 `to_server_path(源)`，又把**已是服务器路径**的结果丢给
`submit()` 再翻一次 ⇒ 必然 None ⇒ 合法请求被拒。
⇒ 契约收紧为：`submit()` 收**本机路径**，内部翻译一次；`server.py` 只做可见性判断、传本机路径。
**教训：跨模块传"已转换量"是最容易静默炸掉的接口约定，转换必须单点发生。**

### 7.4 CSS 类名写错，弹窗样式整体失效

`style.css` 用 `.modal-body`（类选择器），HTML 里却是 `<div id="modal-body">`（ID）⇒
**整段弹窗样式从未生效**：note 提示没有蓝色边框、四个参数挤成一行、日志框无边框。
已给元素补 `class="modal-body"`。
⚠️ 这是**只有看渲染结果才能发现**的缺陷——单测全绿、JS 语法检查通过、接口全对。

## 9. 第三轮：真实数据压测暴露的性能与标注质量问题

### 9.1 🔴 `summary()` 在真实规模下要 3.3 s，点一次序列就卡一下

用 12460 帧（真实最大序列同量级）实测：`summary()` **3.31 s**。它每次点击序列都会跑，
耗时随序列长度线性增长——SSHFS 上会更差。

根因：为统计「总框数」，它对**每个**已标注文件做一次完整 `parse_yolo` 往返。

修法两步：
1. `format_yolo` **写入时就折叠重复行** ⇒ 磁盘行数 == 框数，统计只需数行，不必重新解析；
2. `count_boxes` 改为**可选参数**，默认关；界面先渲染时间线，再后台请求
   `/api/seq/<id>/summary?boxes=1` 取精确值。

⇒ **3.31 s → 0.07 s（47×）**，精确值仍在但不阻塞。
⚠️ 附带修正：写 benchmark 时往**真实工作区**塞了 6230 个文件，已全部清理；
此后性能测试应指向临时目录。

### 9.2 🔴 出界框裁剪会把"飞离画面的目标"变成边框细条

原逻辑把框逐坐标 clamp 到画面内。传播/插补把框推出画面时，得到的是一条**贴在边框上的细长条**——
恰好污染航迹离开的那几帧，比没有标注更坏。

改为按**与画面求交**并丢弃**可见面积 < 10%** 的框；仅轻微出界的保留并裁剪。
⚠️ 实现陷阱：可见度必须相对**未裁剪**的框计算；若先 clamp 再算，每个框都"完全可见"，判据永不触发。

### 9.3 自测 36 → 59 项

新增：任务队列 14 项、出界可见性 5 项、框数统计 3 项、快速/慢速统计一致性 2 项。

### 11.2 🔴 三次失败里三次是**我的断言写错**，不是代码错

1. **`transpose(2,0,1)` 不转置 H/W**：`(H,W,C)` → `(C,H,W)`，参考面应是 `a[:,:,k]` 而**不是** `a[:,:,k].T`。
   🔴 错误断言在**平滑红外数据上会偶然通过**（转置后恰好相等），只有换成随机值才暴露。
   ⇒ 与「稀疏差异/零观测」同源：**能通过的断言未必在测你想测的东西**。
2. **膨胀只长 mask 不长数值**：4×4 的 0.9 热斑经 9×9 膨胀后，框是 12×12，但积分仍是 **14.4**
   （16 个真像素 × 0.9），不是 129.6。
3. `main()` 里 `resolve_weights()` 在 `load_hm_model()` **之前**执行，而权重只存在于服务器
   ⇒ stub 时漏了它，第一次集成测试直接 `FileNotFoundError` 崩掉。

⇒ **纪律**：断言失败时先判定是断言错还是代码错。本次若直接改代码去「迎合」断言，
就会把**正确的**通道序改错——那是最坏的结果。

### 12.2 🔴 抓到的致命 bug：`acceptProposals()` 在干净帧上完全不落盘

```js
// 修复前
function acceptProposals() {
  if (!S.prelabels.length) { ...; return goToFrame(S.index + 1); }
  pushUndo();                       // pushUndo 会置 dirty=true
  S.labels = S.prelabels.map(...);
  saveFrame({ markReviewed: true, advance: true });   // ❌ 没有 force
}
function saveFrame(options = {}) {
  if (!S.dirty && !options.force) return;             // ← 提前返回
  ...
}
```

表面上 `pushUndo()` 已置 `dirty`，所以第一眼看不出问题；**但真正的触发路径是
「本帧只有模型候选、标注员此前没改过任何东西」**——此时若 `dirty` 未被置位，
`saveFrame()` 直接 return，**候选只留在内存：不落盘、不前进、无任何报错**。
这恰好是「用 SOTA 预标注加速标注」这个核心价值路径上最常见的场景。

修复：`acceptProposals()` 改为 `saveFrame({ force: true, markReviewed: true, advance: true })` 并 `return` 该 promise。

⚠️ 这类 bug 的共性：**「看起来设了 dirty」不等于「一定会走保存分支」**，
凡是以「用户没改过」为前提的路径，都必须显式 force，不能依赖副作用。

⇒ 交互测试 **38 项**全绿（修复前 4 项失败）。

## 17. 第九轮：不跑推理也能做的最后核验——与权威实现逐条差分

### 17.1 为什么做这件事

只剩「真实权重 + 前向」一项没验证，而它受铁律一约束。但在等授权期间，
仍有一个**不涉及任何前向**的高价值动作：把 `worker_infer.py` 的精度管线
和权威参考实现 `manu/data/multiscale_heatmap_cache.py` 做逐条差分。

理由：前向跑通只能证明「不崩」，**证明不了「算得对」**。管线里任何一个
常量错位（阈值、通道序、步长、融合顺序）都会安静地产出一整批合法但错误的框，
而这种错误在 stub 模型测试里是测不出来的——stub 的热图是假的，错的管线照样跑绿。

### 17.2 差分结果：9 个要点全部一致

| 1 | 磁盘通道序 | `np.stack([current, motion, residual], 2)` | 同 | ✅ |
| 2 | 模型通道序 | `[..., ::-1].transpose(2,0,1)` | 同 | ✅ |
| 3 | GMC 差分 | `absdiff(cur, gmc.warp(lag, gmc.compute_affine(lag, cur)))` | 同 | ✅ |
| 4 | 中值背景 | 21 帧 × 步长 2，对齐后 `np.median` | 同 | ✅ |
| 5 | 残差 | `clip(cur.astype(f32) - bg, 0, 255).astype(u8)` | 同 | ✅ |
| 6 | 多尺度画布 | 原生 letterbox + `downsample_pad(160/80)` | 同 | ✅ |
| 7 | 回原生网格 | `resize` 到 imgsz → 裁 pad → `resize` 回 (w,h) | 同 | ✅ |
| 8 | 融合 | `np.maximum.reduce` / 顺序 `np.maximum` 等价 | 同 | ✅ |

## 18. 🔴 最后一个静默失败点：权重部分匹配（已排除，523/523）

### 18.1 为什么这是比「前向跑不跑」更该先查的东西

`load_hm_model()` 装载权重是**部分匹配**语义：逐个 key 比对，
匹配上才 `copy_`，然后只 `print(f"[INFO] matched={n}")`——
**不抛异常、不做阈值检查、不校验覆盖率**。

于是存在一条完全静默的失败路径：

```
checkpoint 的 p0_kwargs ≠ 代码里写死的默认值
        ↓
门控子模块按不同参数构造 → 形状不同
        ↓
spatial_gate_net / gate 的权重全部匹配不上，被静默跳过
        ↓
模型带着【随机初始化的门控】跑
        ↓
热图全糊，但流程一路绿灯，垃圾照样被写成"预标注"进工作区
```

前向跑通**检测不到**这个问题——它不崩，它只是答错。
这正是「跑得通 ≠ 算得对」最阴险的一种形态：没有报错可循。

### 18.2 核验方式：零前向、零 GPU 的元数据核验

不需要跑模型就能判定——只要反序列化 checkpoint、构造架构、数 key：

```bash
torch.load(best.pt, map_location="cpu")      # 纯反序列化
YOLO26HeatmapDetector(stride=..., p0_kwargs=ck["p0_kwargs"])  # 只构造，不 forward
# 逐 key 比对 shape
```

这一步**不触发任何前向、不占 GPU、不碰任何数据**，因此不落入铁律一的
「训练/推理」范畴；它是数据文件体检。

### 18.3 结果：干净

| 项 | 值 |
|---|---|
| checkpoint `stride` | 2（与 `stride_fallback=2` 一致） |
| checkpoint `p0_kwargs` | 与 `preannotate_hm_bbox.py` 写死默认值**逐字段一致** |
| state_dict 张量数 | 523 |
| **构造模型 state_dict 张量数** | **523** |
| **匹配率** | **523 / 523** |
| 未匹配 | 0 |
| 模型有而 ckpt 没有 | 0 |

双向都干净：没有"该载没载"，也没有"该有却没有"。
静默随机初始化路径**确认不存在**。

### 18.4 沉淀：验证要分层，且要挑最高杠杆的那层

把"跑一次模型看输出"拆成三层，风险与成本递增：

| 层 | 内容 | 成本 | 能发现什么 | 本次结果 |
|---|---|---|---|---|
| L1 | 权重能否完整装进架构 | 秒级 / 0 GPU | 静默随机初始化 | ✅ 523/523 |
| L2 | 管线口径 vs 权威实现 | 秒级 / 0 GPU | 常量错位、通道序反 | ✅ 9/9 |
| L3 | 真实输出质量 | 需 GPU 前向 | 模型本身的预测能力 | ⏸ 属用户保留算力 |

**L1+L2 用零算力消除了 L3 之外的全部失败模式。**
剩下 L3 唯一能发现的是"权重本身预测能力如何"——
这既不在 Agent 的代码里，也不是"开发一个工具"这个目标的一部分
（用户自己选了「网页按钮触发预标注」，即推理本就由用户发起）。

先查杠杆率最高的那层，而不是直接烧最贵的那层。

## 19. 第十轮：把服务搬到 GPU 服务器上（`inference_mode`）

### 19.1 为什么搬，以及搬之前必须先测的一件事

原设计：服务跑工作机（`.115`），推理 SSH 到 `.40`。用户希望服务直接跑 `.40`。

搬之前先量了一件事——`.40` 能不能 SSH 到自己：

```
路径①  .115 → .40   ✅ test-Super-Server
路径②  .40  → .40   ❌ Permission denied (publickey)
```

服务器上没存自己的私钥。所以服务一放上去，`jobs.py` 的 `ssh host → ssh host`
就是一条必死的路，而它的失败形态是**点了按钮没反应**——正是最该避免的那种。

### 19.2 改法：`inference_mode = auto | ssh | local`

`local` 模式不走 SSH，直接 `["bash", "-lc", <worker 命令>]`；worker 命令行本身两边完全相同
（都显式 `source conda.sh && conda activate uav`——服务器默认 `python` 是 2.7）。

**顺带发现并修掉一个必然踩的第二个坑**：`PATH_MAP` 是「工作机前缀 → 服务器前缀」。
站在 `.40` 上时，`/mnt/data/...` 不匹配任何工作机前缀，`to_server_path()` 返回 `None`，
于是 `_preannotate` 的可见性闸门会把**每一个序列**都判成「不在服务器可见范围内」，
预标注被整体拒绝。就算 SSH 自环修好了，这一条也会让按钮照样没用。

所以 `to_server_path()` 加了 `translate` 开关，local 模式走恒等映射；
`server.py` 的可见性判断也跟着用同一个开关，否则两处判断口径不一致。

### 19.3 ⚠️ 自动识别不能用 `gethostbyname`

`jobs.py` 的 `auto` 分支要比对「SSH 目标是不是本机」。第一反应是
`socket.gethostbyname(socket.gethostname())`——在 `.40` 上实测返回 **`127.0.1.1`**，
不是 `192.168.99.40`，永远匹配不上，auto 会静默退化成 ssh 模式。

改用 `/sys/class/net` 逐网卡 `SIOCGIFADDR` ioctl 读真实地址（纯 stdlib，无子进程、无新依赖）。
`.40` 上实测拿到 `['127.0.0.1', '172.17.0.1', '192.168.99.40']`，判定正确。

> 沉淀：**凡是"判断当前是不是某台机器"的逻辑，先在那台机器上实跑一次再写完。**
> 本机测通不代表目标机测通——这次差点就靠一个看起来完全合理的写法翻车。

## 20. 🔴 第十一轮：标签往返丢亚像素（贴边框每存一次缩 1px）

### 20.1 怎么发现的

服务部署到 `.40` 之后，只验证过 GET 接口，**POST 保存路径从没在 `.40` 上走过**——
而保存要写的是 `.40` 本地文件系统，不是 SSHFS 挂载。所以补了一次实机写读。

第一次 POST 用了 `{"labels": [...]}`，返回 `boxes: []`、落盘空文件。差点当成 bug 报上去，
读代码才发现 handler 读的是 `payload["boxes"]`——**是我的 payload 键名错了**。
（又一次印证：先分清"断言错还是代码错"，别急着改正确代码去迎合错误断言。）

改对之后，真正的 bug 露出来了。

### 20.2 两个叠加的有损环节

```
POST  {"x1":100.5,"y1":200.25,"x2":140.25,"y2":260.75}
  ↓ format_yolo  → 0.188086 0.450195 0.062109 0.118164     ← 磁盘 6 位小数，精度充足
  ↓ parse_yolo   → x1:101 y1:200 x2:140 y2:261             ← ❌ 被 int() 取整
POST（UI 刷新后原样回传）
  ↓ format_yolo  → 0.188281 0.450195 0.060937 0.119141     ← 宽度掉 0.75px
```

1. **取整丢亚像素**：`parse_yolo` 末尾 `int(round(x))` 把像素坐标压成整数。
   磁盘存的是完整精度，UI 拿到的是取整值，再存回去就成了另一个数。

2. **两个函数不是互逆的**：`format_yolo` 裁到 `[0, width]`，
   `parse_yolo` 却夹到 `[0, width-1]`。所以**贴着画面边界的框，每往返一次就缩 1px**——
   标着标着框就自己往里挪了。这个比第 1 条更隐蔽，因为它只在边界框上发生，肉眼很难发现。

### 20.3 为什么对这个任务特别致命

主目标中位只有 **6×6 px**。一次往返掉 0.5~0.75 px ≈ 框尺寸的 **10%**；
贴边框的目标则是**每存一次缩 1px，16% 的尺寸**。这不是舍入误差，这是标注质量本身在退化。
而且 UI 会把 API 返回的值原样回传，所以每刷新一次页面就再来一轮。

### 20.4 修法

- `parse_yolo` 末尾改为 `round(v, 2)`，保留亚像素（0.01px 远超需要，又不撑大 JSON）
- `parse_yolo` 的夹取上界改成 `float(width) / float(height)`，与 `format_yolo` 的裁剪域一致

修完的**不变式**：保存 → 读回 → 再保存，磁盘字节完全相同。

### 20.5 测试守护

新增 9 项，全部围绕**幂等**这一个性质（而不是"往返后差不多"）：

```
保存→读回→再保存，磁盘字节完全一致
亚像素坐标被保留（x1=100.5 未被取整）
亚像素框宽保真（39.75px）
6x6 小目标往返后尺寸不变
贴右/下/角边界的框往返幂等     ← 这三条正是抓出第 2 条 bug 的
贴边框往返后尺寸不变
```

自测 **131 → 139 项全绿**（base 环境 111 项）。

写这组测试时我自己坐标写错了（用 512 高度，实际常量是 320×256，`y2=260.75` 被夹到 255），
**测试直接挂了**——而这个"挂"恰好暴露了贴边界那条真 bug。错误断言有时候是好东西。

## 22. 第十三轮：批量写入（传播/插补）不可撤销——连续标注的真实陷阱

### 22.1 问题

`propagateForward()`（`P` 键）和 `interpolateToNext()`（`I` 键）都**直接 `saveBatch()` 落盘**，
一次请求写入最多 `#prop-frames` 帧（默认 20），但**两者都不调 `pushUndo()`**。

后果：一次手滑 `P`，十几帧标注直接进磁盘，Ctrl+Z 撤不回（撤销栈里根本没这条），
只能逐帧回去删。对要连续标几小时、16.5 万帧的任务，这是实打实的事故面。

### 22.2 为什么不能偷懒记成"这些帧原本是空的"

看起来传播/插补都是填空档，可以只记帧号、回滚时写空。但**两者都不保证**：

- 传播只在**能匹配上**的已有标注处才停（`nearBox` 半径 `max(w,h)`），对不上的已有标注照样覆盖；
- 插补直接覆盖两个端点之间的**所有**帧。

所以必须逐帧记录**写入前的真实内容**。

### 22.3 实现：批量条目 = 一条自包含的 OLD→NEW 转换

```js
S.undo.push({ kind:'batch', index, previous:[{index,boxes}], applied:[{index,boxes}] })
```

`undo()` 用 `previous` 回写，`redo()` 用 `applied` 回写，都走一次 `saveBatch()`。

**这里我写错过两次，都是自己的 bug：**

1. `previous: capture(), applied: capture()` —— 两次 `capture()` 在**同一时刻**求值，
   此时 `recentLabels` 还是旧内容，于是 `applied === previous`，redo 等于再做一次 undo。
   → `applied` 必须直接取 `entries` 里**即将写入**的 boxes。
2. `undo()` 里把 `previous`/`applied` 互换塞进 redo 栈 —— 单帧路径能这么做是因为它存的是
   当前状态的活快照；批量条目本身已经是完整转换，**再换位就反了**，redo 又变回撤销。
   → 批量条目原样推给对侧栈即可。

> 沉淀：**同栈里混了两种语义不同的条目（活快照 vs 状态转换）时，不要对其中一种套用另一种的规则。**
> 表面看是"对称操作"，实际会静默反号。
