## 一、核心洞察：**NPU 推理时间只取决于「结构」，不取决于「权重」**

⇒ 图的形状 / 算子数 / 搬运量全由结构决定 ⇒ **周末训练出的任意臂，速度查表即可**，
**不需要周末再碰板卡**（板卡已断电）。
⇒ 唯一例外：**塌陷模型被 int8 常量折叠**（算子表骤减）⇒ 那是病态，必须用 **null control** 排除。

## 三、⭐ 三条硬结论（直接决定搜索设计）

1. **p1（320×320 头）家族整体出局**：head_conv 从 96 一路降到 16，速度只从 62.6 → 32.2 ms，
   **始终 >21 ms** ⇒ **320×320 这个头本身就是瓶颈**，靠收窄通道救不回来。
2. **p2_fused（160×160 头）的宽度收益在 hc32 就饱和**：hc16/24/32 = 17.87/18.00/17.97 ms（几乎相同）
   ⇒ ⇒ **hc32 是甜点**；再窄只掉精度、不省时间 ⇒ **不要往窄了调，要往宽了调（hc48 = 20.60 ms）**。
3. **⚠️ 周期表完全没给 SiLU 定价**：合并拟合 `ms ≈ -2.24 + 0.830×cycles(M) + 0.243×RW(MB)`，
   **SiLU 结构的残差 +6.7~+8.8 ms，而 relu 结构残差 ≤3.3 ms**
   ⇒ **`ConvExSwish` 的真实代价高于周期表** ⇒ **all-relu 的收益比模型显示的更大**
   （实测：p2f_hc64 SiLU 32.01 ms vs relu 约 25 ms）。

## 四、离线速度预测器（表外结构兜底）

```
ms ≈ -2.24 + 0.830 × NPU周期(百万) + 0.243 × RW(MB)      # 15 点拟合
残差：relu 结构 −3.3 ~ +0.8 ms；silu 结构 +6.7 ~ +8.8 ms
```

⇒ **表内结构一律用实测值**（比预测准）；表外用预测器，**且对 SiLU 结构要加 ~7 ms 的修正**。
⇒ 预测器的 cycles/RW 来自 **RKNN 构建日志的算子表**（零板卡成本）⇒ **任何新结构在导出后即可预测速度**。

## 五、null control 的一个重要副产物

有 3 个探针（`p1_hc64_relu` / `p2f_hc64_relu` / `p3_hc64_relu`）报
`[FATAL] NPU output independent of input -- results are not trustworthy`
⇒ 原因：**这些探针是用 cs_t0043 的权重直接搭的、没训练过** ⇒ 结构真变了 ⇒ 权重语义错位 ⇒ 输出对输入不敏感。
⇒ **⇒ 这恰好证明「结构真变了就必须重训」**（不能拿 cs_t0043 的权重直接上线新结构）；
⇒ **⇒ 但速度数仍然有效**（时间只由结构决定，与权重语义无关）。
⇒ ⚠️ 教训：**null control 不只排除"坏模型"，它还直接告诉你"这个结构必须训练"**。

## 六、⚠️ 一个必须记住的口径

**p1（现状结构）在板卡上是 55.48 ms，而不是历史文档里的 55.5 ms「单尺度口径」**：
本表的 55.48 ms 与历史 55.5 ms 数值接近，但**口径不同**（本表走板卡 `rknn_heatmap_smoke` 的 mosaic 输入，
历史 55.5 是 §二十九~三十二 的单尺度探针口径）。
⇒ **引用时必须写清是哪个口径**；本线内部的对比一律用**本表**（同板同日同 binary）。

## 七、⭐⭐⭐ 探针3 的关键发现：**`late_upsample` 让「输出分辨率」与「计算量」解耦**

| 探针 | 结构 | 输出 | NPU周期(M) | RW(MB) | 实测ms |
|:--|:--|:--|--:|--:|--:|
| **p2f_hc32_late** | 结构B + late | **320×320** | 8.72 | 67.5 | **20.83 ✅ ≤21** |
| p2f_hc48_late | 结构B + late | 320×320 | 11.25 | 69.5 | 23.45 |
| p2f_hc64_late | 结构B + late | 320×320 | 11.25 | 71.5 | FATAL（null control） |

⇒ **只多花 2.9 ms（17.97 → 20.83），输出分辨率就从 160×160 提回 320×320（与原模型完全一致）**
⇒ **头在 160 上算、最后 2× 上采样到 320** ⇒ 定位能力保住、卷积计算量降 4×。
⇒ **⇒ 这是「≤21 ms 且精度下降微小」的最优候选**（结构 B + hc32 + late_upsample）。
⇒ **门槛零改动**：该结构的 ckpt `stride=2`（输出 320×320）⇒ **门禁/缓存/评测的 stride 口径与原模型完全一致**
⇒ 这就是项目历史上 `late` 臂（36.6 ms）的思路，但**精度从未测过**；本线把它落到 20.83 ms 并可继承权重。

### 十三、⚠️ 闸门 key 不一致的致命坑（2026-11-06 修）

**症状**：闸门日志显示 `[SPEED-GATE] 载入 14 个结构的速度`，但**所有查询都返回「表外」**
⇒ ⇒ **闸门等于没有** ⇒ 超限结构（p3/hc64 等）会被全部放行 ⇒ **浪费本就紧张的周末预算**。

**根因**：**建表与查询用了两套不同的 key**：
* `load_speed_table` ⇒ `(head_src, head_conv, act, ablate_p0)`（4 维，含 P0 标志）
* `speed_of_structure` ⇒ `(head_src, head_conv, act, late_upsample, p2_out_scale)`（5 维）
⇒ **维度不同 ⇒ 永远查不到**。

**修法**：抽一个**共享**的 `structure_key()`，两边都调它；且 **key 里不含 `ablate_p0`**
（部署形态恒为 P0 关 ⇒ 建表时只收 `ablate_p0=True` 的项）。
修后：载入 **21** 个结构（22 distinct keys 去掉 P0 开的那 1 个），关键结构全部命中。

⇒ **教训：凡"建索引"与"查索引"成对出现，就必须共用同一个 key 函数**，
     并且**必须做一次端到端查询自测**（用真实候选逐条查一遍，确认全部命中，而不是只看"载入 N 个"）。

### 十四、⚠️⚠️ 最后一个"会报废整个周末轮"的坑（2026-11-06 12:58 修）

**症状**：训练侧手工起一个 `p2_fused` 臂 ⇒
`optuna_mix_ratio_search.py: error: argument --head-level: invalid choice: 'p2_fused' (choose from 'p3', 'p2')`

**根因**：`--head-level` 的 argparse `choices` 只有 `('p3','p2')`，**不含 `p2_fused`**。
⇒ ⇒ 周末轮里 **`p2_fused` 的臂（绝大多数）会被 argparse 直接拒绝 ⇒ 0.1 min 全崩 ⇒ 整个周末报废**。

**修法**：`choices=["p1","p3","p2","p2_fused"]`。

⇒ ⚠️ **这个坑是"训练侧结构验证"抓到的**（用空闲 GPU 跑一个 `--max-iters 2 --skip-gate` 的 worker），
   **不是门禁侧或导出侧能抓到的**（那两处当时都正常）。
⇒ ⇒ **⇒ 教训（写进流程）**：**每加一个结构维度，必须在四个闸门各跑一次最小闭环**：
   ① argparse 接受 ② 模型构建（STRUCT 行 + 输出形状）③ 门禁重建 ④ 导出/板卡。
   **只验导出与门禁会漏掉 argparse 这一层。**
