**三个推翻初始假设的实测结论**：① trial_0080 是**热图模型**不是 YOLO 检测器 ⇒ 现有 NPU 链路零改动可用；

③ 门禁三轨**全部 `--ablate-p0`** ⇒ memory 里的 T1/T2/T3 是 **p0_off** 数字，只有 p0_off 能对账。

**阶梯链**：`L0 PT(p0_on) → L1 PT(p0_off) → L2 ONNX → L3 f16(板端) → L4 int8(板端)`，同帧同解码器同 GT ⇒ 逐级可归因。

**参照臂锚点（用户要求：BMP 复现 memory 精度）——双证明通过**：
像素级 4,000 帧抽样 `mismatches=0 / max_abs_diff=0`；端到端用 BMP 软链伪装 `.jpg` 让原管线零改动重建缓存，
与门禁存储缓存 **191/191 帧逐帧一致** ⇒ **BMP 路径 ≡ memory 记录路径**。

**像素契约**：磁盘 `[I_t, diff, res]` → 模型 `[res, diff, I_t]`；恒等式 `stbi_load(f) == reverse(cv2.imread(f))`
⇒ 用 `cv2.imwrite(dst, cv2.imread(src))` 写出的 BMP，板端与 PC **逐字节相同**；中间放 JPEG 会被解码差异污染 ⇒ 一律 BMP。

**校准集 4×250 已建成**（分位数自适应分层；`n_gt` 来自 GT ⇒ "刚体穿行"=该帧有目标）。

**🔴🔴 int8 全帧 0 检出的真因（2026-10-22 17:00 定位，**推翻本节早先的"输入 dtype 陷阱"结论**）**：
真因是**输出张量被量化范围削顶**，与输入 dtype 无关。
`kl_divergence` 把 heatmap 输出激活的范围标定得过窄 ⇒ `out[0] zp=-128 scale=0.00094072` ⇒ **可表示上限仅 0.2399 < 判定阈值 0.3**
⇒ 真实峰值 0.85~0.97 全被削到 0.24 以下 ⇒ 每帧 0 检出。
板端阈值探针（同一模型 500 帧 001324）：`th=0.3 → 0/500 帧检出；th=0.1 → 389/500；th=0.05 → 431/500`，
且 `score_max` **恒等于 0.2399 = 255×0.00094072**（硬削顶的指纹）⇒ 降阈值即恢复检出 ⇒ **模型没坏，是范围被剪**。
**换 `normal` 算法即解**：`scale=0.00378871`（上限 0.9661）⇒ 板端 `th=0.3` 恢复 **328/500 帧**检出。
**2×2 交叉验证**（两个标定集 × 两个算法）：

| 标定集 | 算法 | out[0] scale | 上限 | 判定 |
|---|---|---|---|---|
| Set-A (BMP) | kl_divergence | 0.00094072 | 0.2399 | ❌ 全帧零检出 |
| trial-0474 原配方 (JPEG) | kl_divergence | 0.00092659 | 0.2363 | ❌ 同上 |
| Set-A (BMP) | **normal** | 0.00378871 | 0.9661 | ✅ 活 |
| Set-B (BMP) | **normal** | 0.00364057 | 0.9283 | ✅ 活 |

⇒ **算法是决定性变量，标定集不是**（KL 裁剪对稀疏高饱和热图是致命的：它按最小 KL 散度选截断点，把峰值剪掉）。
`trial-0474` 那份可用模型 `scale=0.00365272` 正是 **default `normal`** 的量级 ⇒ 与历史一致。

**⚠️ 因此本节早先两条结论作废**：① 「int8 上板陷阱=输入 dtype（正解=uint8 图输入 ONNX）」——**已证伪**：

### 11.3 ⭐ 2026-10-23：fp16 输入路径 —— 零拷贝的**否定结论** + 唯一可用的杠杆（CPU 绑核）

> 完整记录：**`manu/memory/fp16_input_io_mem.md`**（含全部中间量、复现命令、7 条坑）
> 代码 `manu/pipeline/npu/rknn_heatmap_smoke.cpp`（**全部 opt-in**，默认路径与已认证旧二进制**逐位一致**）

**(1) 五条替代路径全部实测，没有一条比驱动快**（f16 模型，12 帧，绑 A76，空闲板卡）：

| 路径 | 输入侧 | `rknn_run` | NPU 段合计 |
|:--|--:|--:|--:|
| **驱动 uint8 NHWC（基线）** | **11.15 ms** | 102.07 ms | **113.2 ms** ✅ |
| `rknn_set_io_mem` 零拷贝（NHWC） | **0.78 ms** | **115.59 ms** | 116.4 ms ❌ |
| `rknn_set_io_mem` 零拷贝（NCHW） | — | — | ❌ 驱动忽略数据（输出与输入无关 ⇒ FATAL） |
| `type=FLOAT16` 类型上传（我们的 NEON fp16） | 13.28 ms | 102.25 ms | 115.5 ms ❌ |
| `pass_through=1` 直传 | — | — | ❌ 驱动按 4 B/px 校验 → 报错 / SIGSEGV |

**(2) 零拷贝为什么反而慢（中间量）**：驱动的 uint8 路径是"边转换边写进 NPU 输入缓冲"（一趟）；
零拷贝则要**再拷一次**到 NPU 内存，而那条路只有 **≈180 MB/s**（2.4 MB / 13.6 ms），
且代价**按字节线性**（int8 1.2 MB → +6.2 ms；fp16 2.4 MB → +13.6 ms）。
⇒ **只比较"输入侧"这一个指标会得出错误结论**（本轮先误判过一次）。

**(3) 流水线端到端（537 帧，T 档绑核）**：
旧二进制 **15.33 fps** / 新二进制默认路径 **15.32 fps** / `--io-mem` **15.04** / `--io-mem --io-mem-f16` **14.99**
⇒ 流水线是 **NPU 绑定**（`rknn_run` 占 88–99%），输入侧省 14 ms 全被 `rknn_run` 多吃的 17 ms 吃掉。
四臂帧数 537、检测 571、每 worker 链哈希一致。

**(4) ✅ 已推广：CPU 绑核**：`inputs_set` **45.41 ms（A55）→ 11.15 ms（A76）= 4.1×**，零精度影响。
**已落地**：`manu/pipeline/npu/ptq/{04_run_board_fast_eval.py,14_run_full_scale_nofs.py}` 的板端命令
加 `taskset -c <cpu>`（新增 `--board-cpu`，默认 **6**）⇒ **不需要替换已认证的板端二进制**。
板端实测（已认证二进制，f16）：不绑核 `inputs_set` **30.85 ms / 7.3 fps** ⇒ 绑核 **11.12 ms / 8.7 fps**，
检测 **md5 逐位一致** ⇒ **整帧 +19% fps**。

**(5) 顺带修掉的两个真 bug**：① `e2e_core.cpp` 的 `letterbox_feature_f16` 非 div255 分支把**原始字节当 fp16 位模式**；
② int8 输入张量存的是**码**（`x + zp = x − 128`），零拷贝不能 memcpy（否则 **TSV md5 不同**）。
另附一个**逐位一致、带自检**的 fp16 画布生成器 `letterbox_to_f16`（`--selftest-lb` PASS，3 种几何）——
当前对主路径无收益，但留给未来的 runtime/驱动替换。

**(6) 数值空间结论**：fp16 图的输入张量 `scale=1.0` ⇒ 存**原始 0..255**（`--conv-div 255` 会全灭）。

**(6) ⭐ QAT 路线的最终判定（负结果，详见 `manu/memory/QAT_RK3588_交付报告.md`）**
**在 rk3588 + toolkit 2.3.2 上，QAT 不能兼得「比 int8 基线更准」与「INT8 输入的延时」。**

  T2 黄金池 **A2 0.9509@0.25**（0.0446）**胜** 基线 0.9428@0.35（0.0527）0.0081；T1 tier1/100 **打平**（都 0.8352）。

- `a2f_qatw_toolkit_int8` 是**唯一 InputOperator=INT8 的 QAT 产物**（149 算子全 INT8、算子表与基线逐项相同），但**精度爆炸**：
  板端 @0.30 FP T1 20→127 / T2 68→700 / T3 527→4433。
- **a2f 爆炸的四刀定位（根因＝权重/训练问题，不是量化问题）**：① ORT 跑 **float** ONNX 已爆（001324 检出 7847→51373，×6.55；
  @0.30 FP 171→**2582**、F1 0.7484→**0.3671**）⇒ 排除"量化范围被撑爆"；② 两张 ONNX 算子直方图一致（仅 Constant 64→61）⇒ 排除"导错图"；
  ③ RKNN 算子表逐项相同 ⇒ 排除"构建/导出 bug"；④ 权重级 diff：494 张量 **0 个 key/shape 问题**、66 个冻结未动，
  **`head.heatmap.0.weight` rel_l2=0.266、均值 +0.004326→+0.006635（+53%）** ⇒ **根因＝QAT 把 heatmap 头搬坏**
  （logit 正偏置 → sigmoid 饱和 → 过自信 → 固定阈值下 FP 爆炸）。
- **训练损失变好但部署指标变差**：`train_loss` 0.3487→**0.3243**，而 F1@0.30 0.7817→0.5304 ⇒ focal+offset 不约束热图绝对标度

- **QAT checkpoint 与它学到的 clip 绑死**：QAT 权重单独跑 fp16 得 0.3595、交给 toolkit 全 int8 标定得 0.2574，

- **下一步最高价值**：把 LSQ 从 3 个头部位点扩到全网络（约 85 个 conv），让 Q/DQ 覆盖主体。
- 未完成：QAT 臂的**全量三轨**（T3 11810 / T2 17187 / T1 anti 31613）没跑（板端 ≈5.8 h，板卡被别的 harness 占用）。

**(7) 🔴 本轮对既有记忆的两处更正**
