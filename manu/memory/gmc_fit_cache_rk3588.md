# GMC Fit 半分辨率 + 环形缓存：板卡 fit 18.5 → 3.9 ms，位精确

> 2026-10-10 实测。全部数字来自 RK3588 板卡 `evm3588` 与 x86 同二进制同参数对照，非估算。
> 目标：把 GMC Fit 从 17.3 ms 压到 <5 ms。

## 0. 一句话结论

**在 memory 一直使用的参考序列 `01_4485_1167-2666` 上，fit 18.46 → 3.94 ms（4.68×），
端到端 20.2 → 8.5 ms（49.5 → 117.6 fps），且输出 MD5 与基线逐位相同 —— 精度零损失，
不需要任何精度让步。** 但这个收益**强依赖纹理**：另一条纹理丰富的序列只拿到 1.43×，
要压到 5 ms 以下必须把角点砍到 ~50，平移最大偏差 5.4 px，那已经不算"稍微下降"。

## 1. 先纠正两条既有认知

### 1.1 "半分辨率"早就不是待做项，而是冻结现役配置

`FastGMCEstimator` 一直有 `downscale_`，`gmc_stream_ocl.cpp` 的默认值就是 `downscale=2`
（`--help` 里写明 "frozen = 2"），640×512 → **320×256**。目标书方案二的第 2 条
"半分辨率拟合（320×256）" **已经是现状**，不是可拿的收益。

### 1.2 金字塔不是瓶颈，Shi-Tomasi 才是

x86 上按阶段实测（195 次拟合，与生产管道同调度，`fit_profile.cpp`）：

| 阶段 | 耗时 | 占比 |
| :--- | ---: | ---: |
| **goodFeaturesToTrack** | **136.19 ms** | **65.8%** |
| LK（金字塔在内部构建） | 56.76 ms | 27.4% |
| resize | 10.54 ms | 5.1% |
| RANSAC | 3.64 ms | 1.8% |
| **buildOpticalFlowPyramid 本身** | **5.73 ms** | **3.2%** |

⇒ 目标书假设"金字塔构建占 fit 的 50%"**与实测相反**：金字塔构建只占 3%。
真正的大头是角点检测，而它和金字塔一样，是**单张输入图的纯函数**，却在每次拟合里
被重复计算。**每帧平均是 5 个锚点 + 若干缓存步拟合的 `prev` 侧 ⇒ 重算约 3.25 次。**

⇒ 真正该做的是把**每帧派生量按绝对帧号缓存**，而不只是金字塔。方案二的"金字塔环形缓存"
这个直觉是对的，只是命名窄了：把它扩到 resize + 角点 + 金字塔三项，收益从 1.16× 变成 5.3×。

## 2. 实现：`--pyr-cache`（默认关，不影响冻结基线）

`manu/pipeline/cpp/gmc_stream_ocl.cpp`，三处缓存，均以**绝对帧号**为 key：
半分辨率图 / Shi-Tomasi 角点 / 光流金字塔。另有 `--cache-parts` 位掩码做消融
（1=resize, 2=角点, 4=金字塔），以及四个精度/性能旋钮（见 §5）。

### 2.1 为什么复用金字塔是**位精确**而不是"差不多"

`calcOpticalFlowPyrLK` 的 `prevImg`/`nextImg` 接受 `std::vector<Mat>`
（`_InputArray::STD_VECTOR_MAT`，`lkpyramid.cpp:1302/1330`），此时跳过内部构建；
并用"层数为奇 + 通道/深度比值"识别预计算梯度（`:1309`），令 `lvlStep=2`
直接取用导数平面（`:1392`），连每层的 Scharr 重算也一并省掉。
关键前提：`buildOpticalFlowPyramid` 的默认值
（`withDerivatives=true, pyrBorder=BORDER_REFLECT_101, derivBorder=BORDER_CONSTANT`）
**正是 `calc()` 自己内部构建时传的参数**，所以平面是同一批字节。
坐标**无需平移**：金字塔 level 0 是带 pad 缓冲的 ROI 视图，`LKTrackerInvoker`
相对该视图索引（`:204-220`），点始终在**未加 pad 的图像坐标系**里。

### 2.2 两个静默失效的坑（都踩了，都由自检抓出）

🔴 **坑一：环形槽不能用"是否已填充"的布尔量。** 槽填满后布尔量永远为真，
`slot(43)` 又与 `slot(0)` 同址 ⇒ 第 43 帧之后一直拿第 0 帧的像素，**不崩溃、不断言、
只出静默错误数据**。必须存"该槽当前存的是哪个绝对帧号"。

🔴 **坑二：`t_` 是 0 起始，clamp 下界必须是 0。** `frame_at_lag()` 把越过首帧的 lag
一律钳到 `first_`，而 `first_` 是 **t_=0** 那帧。若按直觉写成 clamp 到 1，
则 t=2 时会给"实为第 0 帧"的图打上第 1 帧的标签，下一帧命中该错标签槽位 ⇒ 喂错帧。
⚠️ 这个 bug 只让**组合 lag** 的矩阵漂移，5 个锚点完全正常，肉眼看 diff 会误判成
"RANSAC 抖动"。

⇒ 因此内置了运行时自检 `GMC_VERIFY_CACHE=1`：每次命中都重算一遍并逐字节比对，
不一致立即 `exit(3)`。x86 与板卡均已跑通，0 失败。**这类缓存没有自检就是不可信的。**

## 6. 为什么收益强依赖纹理（这是本轮最重要的可迁移结论）

| 序列 | 角点/拟合 | 基线 fit | 缓存后 | 缓存加速 |
| :--- | ---: | ---: | ---: | ---: |
| seq1 `01_4485_1167-2666` | **15.7** | 16.91 ms | 3.93 ms | **4.30×** |
| seq2 `02_1610_0001_1500` | **291.9** | 48.93 ms | 35.68 ms | **1.37×** |

缓存消除的是 gFTT / 金字塔构建 / resize，**消除不了 LK 的逐点迭代**，
而后者正比于点数。纹理贫瘠序列（15.7 点）里 LK 本来就不是大头 ⇒ 缓存几乎吃掉全部；
纹理丰富序列（291.9 点）里 LK 变成绝对主导 ⇒ 缓存只能啃掉一个零头。

⇒ **任何"每帧纯函数可缓存"的优化，其收益都等于"该阶段在总时间中的占比 × 缓存命中率"。
引用任何此类加速比前，必须先报该序列的点数/纹理水平，否则不可迁移。**

# 追加（同一日 13:46）：多线程（Level 1）—— 板卡实测，且**证伪了一条既有铁律**

## A. 结论先说

1. **多线程在本管道里是位精确的。** x86 与板卡、缓存臂与非缓存臂、2 条序列、
   2/4/8/12 线程、每档重复 3 次，**输出 MD5 全部不变**。
   ⇒ `rules.md` / 源码浮点契约里「多线程下 RANSAC 与 Lucas-Kanade 不可复现」这条
   **在本工程不成立，已被实测推翻**。见 §D 说明该怎么改写。
2. **速度收益强依赖纹理**，与缓存那轮同一个规律：LK 逐点迭代才是能被线程切分的大头。
   - seq1（15.7 角点/拟合）：线程几乎无收益，**绑核**才是关键（3.56 → 2.65 ms）。
   - seq2（291.9 角点/拟合）：线程收益巨大（35.63 → 9.57 ms，**3.72×**）。
3. 缓存 + 多线程**叠加后仍位精确**，且两条序列都把 fit 压到远低于 5 ms。

## C. 两条反直觉的实测结论

🔴 **threads 2 比 threads 1 还慢（seq1：4.026 vs 3.929 ms）。**
线程池同步开销 > 可切分的工作量。只有 ~15 个特征点时，`parallel_for_` 几乎没有
可并行的段，反而每次调用都要付一次同步。**seq1 上的收益全部来自绑核，不是来自线程数。**

🔴 **绑大核比加线程更有效（seq1：threads 4 从 3.561 → 2.652 ms，只需绑到 a76）。**
RK3588 默认调度会把工作线程随机扔到 1.8 GHz 的 A55 上。**先绑核、再谈加线程。**

⚠️ **`--affinity a76` 只有 4 个核，给它 6 或 8 线程会超订**：seq2 上
threads 8 + a76 会比 threads 8 + all 慢。要么线程数 ≤ 绑定的核数，要么用 `all`。

## D. 对「多线程破坏位精确性」这条记载的处理（重要，不要静默改写）

**原记载**（`rules.md` 铁律区、`gmc_stream_ocl.cpp` 浮点契约第 3 条、
`gmc_stream.cpp` 同处）：「OpenCV 必须同版本，且两端都单线程运行。
**多线程下 RANSAC 与 Lucas-Kanade 不可位复现**，一次锚点拟合可能在两个同样合理的
解之间翻转，从而移动整条 warp 边缘。」

**本轮实测推翻其字面主张**：同一二进制在 threads=1/2/4/8/12 下输出 MD5 完全一致
（x86 与板卡、缓存与非缓存两条 LK 路径、2 序列、各 3 次重复 = 48+ 次运行）。

**为什么会这样（可解释，非侥幸）**：
- `calcOpticalFlowPyrLK` 的 `parallel_for_` 切分的是**点**，
  `LKTrackerInvoker::operator()` 对每个点只读共享的 const 图像、写互不相交的
  `nextPts[ptidx]/status[ptidx]/err[ptidx]` ⇒ **与切分方式无关**。
- Scharr 导数在 `parallel_for_` **之外**计算（`lkpyramid.cpp:1388`），
  不存在跨线程争用 `derivIBuf`；走预建金字塔时 `lvlStep=2` 连该缓冲都不需要。
- `estimateAffinePartial2D` 的 RANSAC 是顺序循环，按固定次序消费全局 RNG，
  线程数不改变取数序列 ⇒ 「解翻转」没有发生条件。
- `_compose` 是标量 float64 代码，不经 OpenCV 并行。

**必须保留的边界（不要把结论吹大）**：本轮证明的是「**这个 C++ 二进制**的输出
不随线程数变化」。它**没有**重新验证「Python/cv2 参考端在多线程下仍与本端一致」——
那才是原条款的原始语境。若要动这条铁律，需补一次 Python 多线程 vs C++ 单线程的
对账；在那之前，**正确做法是把它降级为「未验证的担心」并附本条实测证据，
而不是继续当作已知事实引用。**

# 追加（同一日 13:53）：中位值并行化 —— 端到端提速的真正大头

## G. 为什么要做这一步

线程化 fit 之后，CPU 臂（`--fused cpu`）的构成变成了：

| 阶段 | threads 1 | threads 4 + a76 | 是否吃到了线程 |
| :--- | ---: | ---: | :--- |
| fit | 3.93 ms | 2.87 ms | ✅ |
| **warp**（`cv::warpAffine`） | 68.9 ms | 27.9 ms | ✅ 2.47× |
| **median** | 66.0 ms | **64.0 ms** | ❌ 纹丝不动 |

warp 是 OpenCV 调用，`cv::setNumThreads` 直接生效；**median 不动**。
查代码：`median_residual()` 是本工程自己写的标量循环 + 每像素 `std::nth_element`，
根本不是 OpenCV 调用，**线程池碰不到它**。这个不对称就是线索。

median 占 CPU 臂总时间的 **47%**（66/139），是当时最大的单一瓶颈。

## H. 改法与实测

按列切分 `cv::parallel_for_`，`col` 暂存移入 lambda（每 worker 独占），
**保持原 x-外层/y-内层的遍历次序不变**。

**位精确**：每个输出像素都是对它自己那 21 个值的一次**独立选择**，
切分方式改变不了任何像素的结果；n 为奇数所以是选择而非求平均，不存在求和次序被扰动。
x86 + 板卡、2 序列、threads 1 vs 8，MD5 全部不变。

### 🔴 过程中自己引入并修掉的一个回归（记录在案）

第一版无条件走 `parallel_for_`，板卡 threads=1 时 median **66.4 → 90.8 ms（慢 37%）**，
端到端 139.9 → 164.2 ms。因为 body 经间接调用后，`history[i].at()` 的数据指针无法外提。
**threads=1 是默认路径**，等于把默认配置改慢了。

修法：`if (cv::getNumThreads() <= 1)` 走原来的串行循环，>1 才走 `parallel_for_`。
修后 threads=1 回到 65.6~66.3 ms、总 139.0 ms，与改动前持平。
⇒ **并行化必须连默认档一起测**，只看多线程档会漏掉这个回归。

## I. 两种后端的最终选择（重要：别默认 GPU 臂总是赢）

| 后端 | 配置 | seq1 总 | seq2 总 |
| :--- | :--- | ---: | ---: |
| `--fused gpu` | threads 4 + a76 | **7.76 ms / 128.8 fps** | — |
| `--fused gpu` | threads 8 + all | 8.42 ms / 118.7 fps | **12.21 ms / 81.9 fps** |
| `--fused cpu` | threads 8 + all | 65.2 ms / 15.3 fps | 72.7 ms / 13.8 fps |

⇒ **GPU 融合尾段仍然完胜**（seq1 差 8.4×）。median 并行化虽然把 CPU 臂提速 2.1~2.4×，
但**没有改变后端选择的结论**——GPU kernel 的 5 ms 尾段对 CPU 的 31~37 ms 尾段是碾压。
后续若要继续压 CPU 臂，median 仍是第一位（它现在仍占 CPU 臂总时间的 48%）。

## J. 本节遗留

1. **median 的内存访问模式仍未改**：当前是 x 外层、y 内层，每像素跨 21 个 Mat 取数
   （21 条独立内存流、按行宽跨步），对缓存极不友好。
   改成"按行块把 21 个 Mat 拷进连续小缓冲再选"应能进一步大幅提速，且同样位精确
   （还是对同一批 21 个值做选择）。**这是 CPU 臂剩下的最大一块。**
2. 仍未验证 Python 侧多线程对账（同 §D），动铁律前必须补。
3. 仍是 2 条序列。
