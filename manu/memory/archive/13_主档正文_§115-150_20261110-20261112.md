### 116.1 轨迹（9603 = P2-fused hc32+late / RC2 init / w2.0，同一臂）

  而不是「再训久一点」。⇒ **选臂判据不能只看 F1**（晚期 F1 走平而 nano 持续下滑）。

### 116.3 ★ 由此换血：加「短周期 + 完整退火」臂 9647
- **9647** = p1_late hc32 + late，**init = 冻结基线 474**，**epochs 10（cosine 跑满 10 轮 ⇒ 完整退火）**，w2.0，lr_scale 3.5。
  依据：冻结基线是 **3 轮跑完完整 cosine**（lr 7.2e-4 → 2.4e-5）⇒ **收敛即停**；
  而 50 轮臂在高峰 LR 上泡 50 轮 ⇒ 微小目标能力被磨掉。
- 同时停掉 **9603**（ep1/2/3/9 数据已取，剩余 40 轮大概率继续下滑）。
- 当前 4 臂：**9647**（GPU0，10 轮）｜**9646**（GPU1，50 轮 + fb init + **w8.0**）｜**9644**（GPU2，真 2px + 颈0.5）｜**9645**（GPU3，50 轮 + fb init + w2.0）。
  ⇒ 形成 2×2：**{50 轮 vs 10 轮} × {w2.0 vs w8.0}**（9645 / 9646 / 9647 / +9643 历史）。

### 116.4 ★ 混样上报修复的**实证**：9647 日志 `mix LQ/UAV 9/23`
- 9647 用修复后代码启动 ⇒ 每步显示真实批内混样：**9 LQ / 23 UAV ≈ 1:2.56**，与 w2.0（P(UAV)=0.667 ⇒ 期望 10.7/21.3）吻合。
  ⇒ **反证「采样一直是对的」**：历史 bug 只污染了上报字段，训练数据组成从未出错。

### 116.5 ★ 验收脚本选臂判据已改（`manu/pipeline/npu/route2_acceptance.py`）
- 旧：**按 F1 最高选 epoch** ⇒ 会挑到 nano 最差的晚期（§116.1）。

### 118.2 ★★ 主指标与两个「必须知道」的坑
- **主指标**：**孤立微小假峰 FP** = 尺寸 ≤8px 且孤立的 FP 数（占全部 FP 的比例）。
- **坑一：FP 的物理尺寸不能用融合行自己的 bbox** —— 建缓存时融合行被 `--fusion-dilate 32` 膨胀过 33×33 核，
  其 bbox 最大边恒 ≥33px ⇒ 全部 FP 会被打成 `regular`、主指标恒 0（数值"干净"实则完全失真）。
  ⇒ 默认把尺寸归因到**未膨胀的 native 行（tag=0）**，粗尺度只作回退，归因不到单列 `unknown` 绝不丢弃，
  报告里给「档位 × 归因来源」+ 归因距离分布（native n=371 p50=11.7 p90=26.4 max=31.8 px）。
- **坑二：孤立判据会被平凡满足** —— 8px 孤立半径 **≤ 8px 去重半径**，而去重本身保证候选池任意两点 > 8px

  ⇒ 保留 8px 默认值但**打印退化提示**，另给 `--isolation-radius` / `--isolation-scope sequence`
  （实测 sequence 范围 = 18 孤立 / 8 非孤立，**有区分度**）⇒ **汇报时用 sequence 作用域的数字**。
- **坑三：no-GMC/GMC 混用** ⇒ `build` 拒绝不含 `nogmc` 的 `--features-root`，`report` 复查缓存 meta 记录的

## 133. ★★★ 方向一落地：跨层高频残差注入（`hf_skip`）侧枝 + ckpt 自描述接线（2026-11-10 17:20）

> 目标（文档方向一「高频残差注入（侧枝）」）：≤4 px 微目标在 P3(/8) 网格上不足一个 cell，
> 浅层的**高频脉冲**（局部峰值相对局部背景的对比度）在下采样与语义融合中被抹平
> ⇒ 把浅层高频能量以 **1~2 个窄通道**压到**头网格**，以**加性残差**注入 head 输入。

### 133.1 设计（`manu/models/heatmap_model.py:568` 新增 `class HighFreqSkip`）
```
b1(160×160×32) ─Conv1x1(32→1)→ narrow
                 ─MaxPool2d(2) ─┐
                 ─AvgPool2d(2) ─┴→ contrast = 峰 − 局部背景（高通）
                 ─MaxPool2d(2) → 80×80×1（头网格）
                 ─Conv1x1(1→48)→ delta（★权重+偏置零初始化）
feat(80×80×48) + delta → head.feat_conv
```
- 注入点 = `head_in` **之后**、`Head.feat_conv` **之前** ⇒ **主特征通道数不变**
  ⇒ `head.feat_conv.0.conv.weight` 仍是 (64,48,3,3) ⇒ **旧 ckpt 的头照常可加载**。
- **为什么用 MaxPool 不用 AvgPool 降采样**：AvgPool 把 1~2 px 微目标脉冲摊平成背景（能量被抹掉）；
  MaxPool 保峰（峰值正是微目标的能量载体）。2×2 窗口**不带 padding** ⇒ 无 `count_include_pad` 语义歧义。
- **为什么取 b1 不取 b0**：搬运量减半（b0 源 320×320×16×4B = 6.55 MB vs b1 160×160×32×4B = 3.28 MB）；
  且 b1 在 no_p2 下**照样被算出来**（b0→b1→b2 是 P3→P5 必经之路，删 P2 融合不影响骨干）⇒ 取 b1 **零额外骨干开销**。
- **零初始化 `project`** ⇒ 侧枝一开恒输出 0 ⇒ **起点与原模型逐位一致**，改善全部来自训练。
- 代价：新增 **129 个参数**（全模型 +0.008%），额外搬运 ≈ **8.18 MiB(FP32) ⇒ 2.04 MiB(int8)**；
  ⚠️ 若头换成 p2_fused(160×160)，融合项涨到 14.7 MB ⇒ **P3 头是最优点，不建议换头**。

## 134. ★★ 方向二（双通道解耦 nano 头）的**三个静默必改项**（2026-11-10 17:40 复核确认）

> 任务书方向二：Head 最终输出前把热图分支拆成**通道 A（≤4px 专职）/ 通道 B（常规）**，
> A 通道只对 nano 目标挂权重、B 通道只监督 micro/regular，后处理做 Max-fusion。
> 评估结论：**工程可行，但风险高** ⇒ **不作主线**，仅在方向一/三全灭后再考虑。

### 134.1 🔴 必改项 ①：`late_upsample` 的切通道会**静默丢掉第 2 个热图通道**
`manu/models/heatmap_model.py:133-135`（复核确认）：
```python
both = F.interpolate(torch.cat([hm_logit, offset], dim=1), scale_factor=self.late_scale, mode="nearest")
hm_logit, offset = both[:, :1], both[:, 1:]      # ← 热图只取 :1！
```
- 单通道热图下这是对的（1 通道 hm + 2 通道 offset = 3 通道）。
- **一旦热图变成 2 通道（方向二），`both[:, :1]` 只保留通道 0 ⇒ 通道 1 被静默丢弃**
  ⇒ 训练看着正常、导出后 nano 通道消失 ⇒ **"看起来能用其实没生效"**。
- ⇒ 必须改成按通道数切分：`n_hm = hm_logit.shape[1]`；`hm_logit = both[:, :n_hm]`、`offset = both[:, n_hm:]`。

### 134.2 🔴 必改项 ②：能量项（focal）的 **per-channel gather**
- 现在是对**整张热图**求 max/统计；拆成双通道后必须**按通道分别 gather**，
  否则通道 A/B 的正样本计数互相污染 ⇒ 权重分配失效（且**不会报错**，只是效果差）。

### 134.3 🔴 必改项 ③：`num_pos` 必须**按通道归一化**
- 单通道时 `num_pos` 是全局正样本数；双通道时每个通道各有自己的正样本集
  ⇒ 不按通道归一化 ⇒ 通道 A（nano 样本极少）的 loss 会被放大/缩小到失真。

### 134.4 ⚠️ 另外两个硬风险
1. **int8 per-channel 量化**：新增 1~2 个输出通道 ⇒ RKNN 的 per-channel scale 重算
   ⇒ 可能把 nano 通道的动态范围压掉（**必须上板重测 T2 虚警与 nano 召回**）。
2. **R5 跨通道 NMS 抑制**：现有后处理是**跨通道**取峰并抑制
   ⇒ 双通道下同一物理目标的 nano 峰与常规峰会**互相抑制**（把 nano 峰吃掉）⇒ 必须改成**通道内 NMS + 通道间 Max-fusion**。
3. **板端 C++ 也要改**：`manu/pipeline/npu/e2e_core.cpp:400/519` 与 `rknn_heatmap_smoke.cpp:532-577`
   （形状门禁 + `extract_peaks`）⇒ **必须重新交叉编译上板** ⇒ 这是它"风险高"的主因。

### 148.1 🔴 隐患①（致命）：守护的续跑轮号会把整轮重跑（~2.5 h 白烧 + 判优被污染）

- **实测事实**：台账 `nano_search_ledger.json` 此刻**顶层根本没有 `rounds` 键**
  （实测顶层只有 `arms / waves / baseline_v2 / baseline_registry / created / deliver_criteria / beat_to_pass / base_recipe`）。
- **根因**：守护 v1 的 `rounds_now()` 只读台账 `rounds`，而**轮记录是每轮末尾才写**（`led.setdefault("rounds",[]).append(rec)` 在 `run_round` 尾部）
  ⇒ **轮中途崩溃时台账查不到该轮** ⇒ 续跑轮号被算成 `0+1 = 1`
  ⇒ 守护重启时会 `kill` 掉正在跑的调度器并用 `--start-round 1` 重启
  ⇒ **R1/R2 整轮重训 48 个臂（~5 h）**，且**同一配方重复入账 ⇒ `recipe_stats` 的 n 与均值被重复样本污染 ⇒ 冠军判优失真**。
- **修法（双保险）**：
  1. `adaptive_runner.py`：每轮开头**原子写** `round_state.json{last_started_round, last_completed_round, ts}`；
     新增 `resume_round(led, requested)`：续跑轮号 = `max(--start-round, 台账已完成+1, 最近开跑轮)`
     ⇒ `--start-round` **只会被向上修正、不会被向下带偏**（守护算错也兜得住）。
  2. `run_adaptive_watchdog.sh` v2：`NEXT = max(台账已完成+1, 最近开跑轮)`（不再是 `len(rounds)`，也不是纯 `rounds+1`）。
- **验证（真跑，不是推断）**：
  - `python manu/pipeline/npu/adaptive_runner.py --selftest` 实跑输出
    `[resume] --start-round 1 < 自算续跑轮 2（台账已完成=0 最近开跑=2）⇒ 从 R2 续跑`，末尾 `selftest PASS`。
  - 守护 `next_round` 场景推演：`(0,2)→2`（R2 中途崩 ⇒ 重跑 R2）· `(2,3)→3` · `(4,5)→5` · `(0,0)→1`（全新起点）。

### 150.3 🔴🔴🔴 新发现（记忆库**首次**记录）：板卡 RGA 驱动偶发**内核 oops**

- 板卡 `dmesg` 两次 `Internal error: Oops: 96000146`（**08:52:47** `Comm: rknn_mosaic_e2e` / **10:10:54** `Comm: mosaic_contract`），
  调用栈完全相同：`__clean_dcache_area_poc → iommu_dma_sync_single_for_device → dma_sync_single_for_device →
  rga_mm_sync_dma_sg_for_device → rga_mm_get_buffer → rga_mm_map_job_info → rga_job_commit`，
  解引用 `ffffff8000000000`。**触发方是交付包里的二进制，崩在内核态。**
- **后果是进程永久死锁**：那次契约测试 7.5 min 只用掉 13 s CPU 就再也醒不过来 ⇒
  `copy_to_nfs.sh --verify` 会**无限期挂死**且日志无任何线索（手工复跑则正常通过，199/0 ⇒ 低概率竞态）。
- **根因是新旧板驱动库不同**（用户记忆里的那一族问题的**第二例**，第一例是 OpenCV 影响位级）：
  旧板内核 RGA **`v1.3.1`**（Ubuntu 20.04.6，librga md5 `7136ae54…`）→ 新板 **`rockchip_rga v1.3.0`**
  （Orange Pi CM5 / Debian 12，librga md5 `32c4b08f…`）；**用户态 RGA API 版本相同（1.10.0_[9]），是内核驱动版本不同**。
  ⚠️ 记忆库此前**从未**把 `rga: buffer[0] mm release buffer failed!`（旧板记为「疑似跨进程资源泄漏」）与内核 oops 联系起来。
- **本轮已做**：① 库 `mosaic_core.h` 把 `pat` 缓冲改为**正确 import**（原来以 `handle=-1` 传给 `improcess()`）——
  A/B 证明**对输出零影响**（同一 e2e 二进制挂新旧两库跑 300 帧，`feature_md5.txt` 与 mosaic TSV **逐字节相同**）；
  ② `copy_to_nfs.sh` 的板卡测试加**硬超时**（`timeout -k 10`，默认 600 s）⇒ 再 oops 也不会挂死交付。
- **仍需平台方**：升级新板 RGA 内核驱动 / 向镜像维护方报；排查判据 `dmesg | grep -c 'Internal error: Oops'`（计数是否增加）。
