## 二十、NPU int8 去 P0 vs PC SOTA：三臂受控消融（2026-10-15 实测）

**实验设计**：PC SOTA 模型配置一字不改、脚本沿用原样，特征仍用 PC 版本，
**只替换推理后端**为 ARM NPU int8（去 P0）。铁律五强制同源受控 A/B ⇒ 三臂：

| 臂 | 说明 | 峰值 th | F1 | P% | R% | TP | FP |
|---|---|--:|--:|--:|--:|--:|--:|
| 臂1 | PC-FP32 **+P0**（冻结基准） | 0.25 | **0.902316** | 94.87 | 86.02 | 21,601 | 1,167 |
| 臂2 | PC-FP32 **−P0** | 0.25 | **0.901935** | 94.86 | 85.96 | 21,586 | 1,169 |
| 臂3 | **NPU-int8 −P0** | **0.20** | **0.882231** | 94.27 | 82.90 | 20,818 | 1,265 |

**代价分解**

| 分解项 | 峰值 ΔF1 | ΔTP | 15 档均值 | 区间 | 负档 |
|---|--:|--:|--:|---|--:|
| 去 P0（臂1→臂2） | −0.000382 | −15 | −0.004296 | [−0.028273, +0.001676] | 11/15 |
| **int8 量化（臂2→臂3）** | **−0.019704** | −768 | −0.016615 | [−0.026206, −0.001469] | **15/15** |
| **合计（臂1→臂3）** | **−0.020085** | −783 | −0.020911 | [−0.029743, +0.000048] | 14/15 |

固定 th=0.25 同点：臂2 0.901935 vs 臂3 0.880949，ΔF1 = **−0.020986**。

### 20.1 三条可复用结论

1. **损失 98% 来自 int8 量化，不来自去 P0。** 去 P0 的 −0.000382 仅 15 TP，
   噪声下限是 ±3 TP（≈±0.0002）；int8 是它的 **51 倍**。⇒「去掉 P0 highway 不掉点」在 FP32 域成立，
   但**不能外推到 int8**。
2. **int8 是全档位一致劣化**：15/15 档全负，区间上界也仅 −0.001469，是系统性下移而非抖动。
3. **NPU 最优阈值从 0.25 漂到 0.20。** int8 压低分数分布 ⇒ e2e 脚本固化的 `TH=0.25`
   **不是 NPU 模型的最优工作点**，后续调参须单独扫。
4. 召回是唯一受创项：R 85.96%→82.90%（−3.06pt，TP −768）；P 仅 −0.59pt。
   NPU 更稀疏：每帧均 **0.83** 检出，**7,823/31,613 = 24.8% 帧零检出**（PC cache 每帧最多 11 个）。

### 20.2 受控性

三臂共用同一批 PC-BMP 特征、同一 harvest（`--conf-thresh 0.08 --top-k 80`，板端 `--th 0.08 --topk 80`）、
同一 15 档 0.05~0.75、同一 8px 匹配，GT 一律取自 PC cache。
每臂均报 `严格同集配对 31613 帧` + `GT 逐项一致 GT=25111`；
自校准闸门两道全 PASS（对比1/3 以臂1 硬校验 `0.902316/21601/1167`；
对比2 以臂2 为 A 臂、期望值**从对比1 的 JSON 读取而非手抄**）。
板卡完整性硬校验：24/24 序列、总行数 **31,613**、**零失败零重试**；不齐即 `exit`，不拿残缺数据算 F1。

### 20.3 ⚠️ RK3588 NPU 并行度硬上限 = 2（本轮附带发现）

RK3588 标称 3 个 NPU 核，但**第 3 个并发上下文一提交就撞 RKNPU 6 秒 job timeout**，
驱动 `soft reset` 整个 NPU，在飞上下文全部陪葬（`rc=1` / `139`）。干净条件实测：

| 并发 P | 成功 worker | 真实吞吐 | dmesg 崩溃 |
|--:|--:|--:|--:|
| 1 | 1/1 | 9.92 f/s | 0 |
| **2** | **2/2** | **19.64 f/s** | 0 |
| 3 | 2/3 | 20.03 f/s | **1** |
| 4 | 2/4 | 6.34 f/s | 0 |
| 6 | 2/6 | 6.31 f/s | 0 |
| 9 | 2/9 | 6.29 f/s | 0 |

- **6 进程 / 9 进程不可行**，任何 P>2 不更快，只空耗 ~19 s 超时窗口；P≥4 时吞吐数字是假的
  （9 进程只有 2 个真产出 60 帧）。
- `/sys/class/devfreq/fdab0000.npu/load` 单进程即 `100@1GHz`，是**三核合计**口径，
  **不能**用来判断空核，必须实测吞吐 + 看 dmesg。
- 本轮最终按用户决定走**单进程**（稳优先），全程零失败零重试。

### 20.4 踩坑（勿复现）

## 二十一、`e2e_demo.cpp` 单进程纯 C++ demo，与 shell demo 输出逐字节一致（2026-10-15 实测）

**目标**：弃用 `run_hm_demo.sh` 的 shell 编排，单写一个 `e2e_demo.cpp`（纯 C++ 执行），
在同一个短序列上验证两个 demo 输出**完全一致**——三通道特征 + 推理 heatmap。

**验证序列**：`34_1`（537 帧，真实 val 序列，有 GT）。

| 产物 | 一致数 | 结果 |
|---|--:|---|
| 三通道特征 BMP（537 张） | **537 / 537** | 逐字节一致 |
| heatmap + offset 张量（535 帧 × 2，float32 `.bin`） | **1070 / 1070** | 逐字节一致 |
| 检出 TSV（535 行） | **535 / 535** | 逐行一致 |

两边 GMC 特征序列 md5 相同 `5caa3c6fc72eb7fad4dd5dfd08ebf4ad`，
回退计数均为 0（`fitgate=0 chain=0 fitdeadline=0 cornercap=0`）。
检出总数 ref 545 / e2e 547，差 2 恰为 e2e 多出的 push 0/1 两帧，非差异。

### 21.1 做法：核心代码复用而非重写（本节方法论，可迁移到任何「等价性证明」任务）

```
e2e_core.h     可复用 API 声明（后续并行 demo 直接调）
e2e_core.cpp   API 实现：#include 两个生产源，main 编译掉
e2e_demo.cpp   纯 C++ 驱动，串行调两个 API
```

复用同一批类与函数：
- 阶段 A（`cpp/gmc_stream_ocl.cpp`）：`OnlineFeaturePipeline` / `FusedGpu` /
  `find_sequence_folder` / `list_dir` / `mkdir_p`
- 阶段 B（`npu/rknn_heatmap_smoke.cpp`）：`letterbox` / `run_once` / `dequant` /
  `extract_peaks` / `Ctx` / `write_bin` / `fnv1a`

对既有生产文件**只加一行 `#ifndef ..._NO_MAIN` 包裹 main，函数体一字未改**。

**等价性的最强证据**：加 guard 后重编两个原二进制，与板上原有那份**逐字节一致**：

| 二进制 | 重编后 md5 | 板上原版 md5 |
|---|---|---|
| `rknn_heatmap_smoke` | `170379506adb4aeaef2f5a5f8ce65cc2` | 同 |
| `gmc_stream_ocl_arm64` | `aa99da811356694d66a0bce6de108b92` | 同 |

⇒ 编译器产出的机器码都没变，**「同一份代码」是可证事实而非说法**。
本方法可直接套用于任何「A/B 必须等价」的改造：**只加编译开关，不动被测函数体，
然后用产物 md5 自证**。

### 21.2 帧号映射（PUSH_OFFSET=1，比对时必须显式换算）

| | 命名 | 覆盖 |
|---|---|---|
| 参考 GMC 产出 | `feat/34_1_<push:06d>.bmp` | push 0..536 |
| 参考改名后 | `feat_named/34_1__<id:06d>.bmp`，`id = push + 1` | id 3..537 |
| 参考 NPU 阶段 | 读 id 3..537 | = push **2..536**，535 帧 |
| e2e_demo NPU 阶段 | 读 `feat/34_1_<push:06d>.bmp` | push **0..536**，537 帧 |

⇒ **参考 id N ≡ e2e push N−1**。shell 版需要 host 侧 python 建符号链接改名，
是因为两个独立进程必须就文件名达成一致；单进程后这个协调步骤**结构性消失**。
不做这层映射就会得到假的「一致」或假的「差异」。

### 21.3 为并行 demo 预留的能力

`e2ecore::extract_features()` 返回该序列写出的特征路径列表（push 顺序）；
`e2ecore::run_infer()` 接受任意 `frames` 子集 ⇒ 并行 GMC 可按序列或按帧切分，
并行 NPU 每个 worker 传自己的 shard。

### 21.4 ⚠️ Mali 驱动锁泄漏 → 板卡必须断电重启（重要运维教训）

§20.3 那次 NPU 并行度扫描触发了 RKNPU 软复位与
`BUG: spinlock bad magic on CPU#2, kswapd0/146`（debug kernel oops），
**此后任何打开 `/dev/mali0` 的进程都永久阻塞**：

- 卡在内核 `rwsem_down_write_slowpath`，进程 D 状态，`kill -9` 无效

```sh

  192.168.0.115:/run/media/manu/SSD960-LOCAL/nfs /mnt/manu
```

⇒ **教训**：NPU/GPU 压测前先确认失败模式可恢复；这类驱动 oops 之后不要再假设

（`timeout 60 /root/gmc_stream_ocl --help` 冒烟）。

## 二十二、并行流水线 e2e demo：GMC ∥ NPU，输出逐位一致，1.76× 提速（2026-10-15 实测）

**目标**：特征提取（fit+warp+median，CPU 侧）与 NPU 推理并行，中间加缓存 buffer；
CPU 侧保留全部逻辑与 bad case handle 且 **≤40 ms**；NPU 全力做。
验证：短序列 `34_1`（537 帧），特征通道 + heatmap 必须完全一致。

| 配置 | FPS | 墙钟 | GMC p50 | GMC p95 | GMC max | ≤40ms |
|---|--:|--:|--:|--:|--:|---|
| 原版（串行 + 落盘） | 5.78 | 93.0 s | 27.33 | 28.11 | 28.65 | **PASS** |
| 去中间落盘（串行） | 8.16 | 65.8 s | 27.71 | 28.56 | 28.99 | **PASS** |
| **去落盘 + 并行流水线** | **10.15** | **52.9 s** | 27.40 | 28.10 | 30.71 | **PASS** |

**累计 1.76×，40 ms 全程守住。** 拆解：去落盘 +41%，并行重叠再 +24%。

### 22.1 等价性（三重独立证明）

| 证明 | 内容 | 结果 |
|---|---|---|
| 逐字节 | shell demo 基准 ref vs 并行版：三通道特征 | **537/537** |
| 逐字节 | heatmap + offset 张量 | **1070/1070** |
| **哈希链（跨 I/O 边界）** | 文件路 vs 无 I/O 路逐帧链式 fnv1a | **三档全 `d5e81977`** |

GMC 序列 md5 四档均 `5caa3c6fc72eb7fad4dd5dfd08ebf4ad`，
`fitgate=0 chain=0 fitdeadline=0 cornercap=0`（bad case handle 全保留未触发）。

第三条最关键：**证明绕开 BMP 落盘没有偷换通道**，且不落一字节即可证明与文件路逐位相同。

### 22.2 NPU 分阶段归因（ms/帧）

| 阶段 | 文件路 | 无 I/O |
|---|--:|--:|
| load（stbi_load 读+BMP 解码） | 8.46 | **0.00** |
| letterbox（512→640 双线性） | 27.51 | 25~29 |
| **rknn（set+run+get）** | 55.32 | **59.96** |
| dequant / peaks | 2.73 / 0.35 | 同 |
| **write（写 heatmap/det 到 NFS）** | **27.39** | **0.00** |

⇒ 带落盘时**每帧 35.85 ms 纯 I/O**（占 NPU 段 31%）。这就是"5.78 fps 不可信"的来源：
每帧往 NFS 写 2 × 1.2 MB heatmap。
剩余真瓶颈：**rknn ~60 ms**，其次 **letterbox ~29 ms**（`rknn_heatmap_smoke.cpp:193`）。

### 22.3 ⚠️⚠️ RK3588 CPU 不是同质的（务必记住）

| CPU | 架构 | capacity | max_freq |
|---|---|--:|--:|
| cpu0-3 | A55 | 405 | 1.8 GHz |
| cpu4-7 | A76 | **1024** | 2.352 GHz |

**算力最重的 GMC 必须绑大核。** 第一次默认绑 `cpu-feat 0-3`，
GMC p50 从 **27 ms 变 93 ms（3.4× 劣化）**，而代码看起来完全正确。

最终默认：`--cpu-feat 4-7` / `--cpu-npu 0-3`（NPU 线程多阻塞在 `rknn_run`，小核够用）
/ `--npu-nice 5`。绑定到位后并行版 GMC **p95 从 62.05 ms 回落到 28.10 ms**，
40 ms 从"被抢占打断"变回"稳定满足"。

⇒ **并行化前必须先读 `/sys/devices/system/cpu/cpu*/cpu_capacity` 确认拓扑**，
否则"绑核优化"会变成实打实的降速，而且没有任何报错。

### 22.4 设计要点

- **批量路径收成流式薄壳**：`extract_features` 循环 `feature_stream_next`，
  `run_infer` 循环 `infer_one`；帧体抽成共享 `infer_frame()`（文件路与内存路共用）。
  ⇒ 串行版与并行版跑同一份逐帧代码，一致是构造性的。
- **两个 demo 编进同一二进制**（`--mode serial|parallel`）、**同一套计时代码**，
  FPS 对比不可能是两个测量口径的产物。
- **通道序**：`cv::imwrite` 存 BGR、`stbi_load` 读回 RGB ⇒ 模型实际看到 `[Ch2,Ch1,Ch0]`。
  内存路径必须原样复现这个翻转，否则每张 heatmap 都变。
- 缓存是**有界队列**（`--depth`，默认 6），不是无界的——无界时生产者会把整个序列
  的 512×512×3 BMP 攥在内存里。

### 22.5 ⚠️ 四个"看起来对"的 bug（全部踩过）

1. **帧名丢目录前缀**：改用构造函数构建 `FeatureStream` 时漏了拼 `seq_dir` 的一行，
   `imread` 拿裸文件名 → `[FATAL] failed to read 000001.bmp`。
2. **`setpriority(PRIO_PROCESS, 0, n)` 降的是整个进程**：`who=0` 指当前进程而非当前线程，
   GMC 被连带降优先级，**p50 27 ms → 91 ms**，代码完全正确。
   改为按 tid：`setpriority(PRIO_PROCESS, syscall(SYS_gettid), n)`。
   ⇒ **per-thread 调优 API 的 `who=0` 语义必须确认**。
3. **双重析构**：`feature_stream_close()` 留着 placement-new 时代的显式析构调用，
   构造函数版本下 `delete` 又析构一次 → `double free detected in tcache 2`，
   且只在 stdout 重定向到文件时显形；块缓冲还把崩溃前日志全吞了。
   ⇒ 已给两个 demo 加 `setvbuf(stdout, nullptr, _IOLBF, 0)`。
4. **`--no-io` 写在组装之后**：`if (no_io) dump_heatmap=0;` 放在
   `if (dump_heatmap) ip.dump_dir=...` 之后 ⇒ "不落盘"其实还在写 heatmap，
   NPU write 仍 25 ms，FPS 只从 5.74 走到 6.59 几乎看不出差别。
   ⇒ **配置覆盖必须早于它要影响的那次组装**，否则"关掉了"只是看起来关掉了。

## 二十三、三级流水线：letterbox 独立成一级，14.07 fps（累计 2.45×）（2026-10-15 实测）

承接 §22。§22 的归因显示 NPU 线程 94.45 ms 里只有 59.96 ms 是硬件，
**28.60 ms 是挤在同一线程上的 CPU letterbox**，硬件全程空转。
把 letterbox 拆成流水线上的独立一级（`--split-lb`）：

| 配置 | FPS | 帧时间 | GMC p50 | GMC max | ≤40ms | hash |
|---|--:|--:|--:|--:|---|---|
| 原版（串行 + 落盘） | 5.74 | 174.3 ms | 27.52 | 28.83 | PASS | `d5e81977` |
| 去落盘（串行） | 8.16 | 122.5 ms | 27.71 | 28.99 | PASS | `d5e81977` |
| 去落盘 + 并行 2 级 | 10.15 | 98.5 ms | 27.40 | 30.71 | PASS | `d5e81977` |
| **去落盘 + 并行 3 级** | **14.07** | **71.1 ms** | 27.93 | 32.10 | **PASS** | **`d5e81977`** |

**累计 2.45×（5.74 → 14.07）。四档 hash 全部 `d5e81977`，逐位等价。**

三级各段（ms/帧）：GMC 33.19（cpu 4-5）、**letterbox 12.23（cpu 6-7）**、NPU 66.99（cpu 0-3，
其中 rknn 60.77 + dequant 2.75 + peaks 0.35）。

### 23.1 两条可迁移结论

1. **letterbox 独占线程只要 12.23 ms，挂在 NPU 线程上要 28.60 ms——差 2.3 倍是争抢，不是算法。**
   ⇒ **"这段代码慢"必须先分清是算法慢还是被抢慢**：把它挪到独占线程再测一次，
   代价近乎为零，若明显变慢就说明瓶颈在争抢而不在代码。
2. **等价性是白送的**：三级路径调的是**同一个 `letterbox()`、同样参数**，只换线程。
   hash 与两级/文件模式一致即可证。**凡是纯搬运/纯计算的无状态阶段，
   挪到独立线程不需要重新验证精度**——这与 §21 的"核心代码复用"是同一条原则。

### 23.2 当前瓶颈与天花板

- 帧时间 71.1 ms，NPU 线程 66.99 ms（占 94%）
- 理论上限 max(33.19, 12.23, 66.99) = 66.99 ms → **14.93 fps**（当前重叠效率 94%）
- **硬地板 rknn 60.77 + dequant 2.75 + peaks 0.35 = 63.87 ms → 15.7 fps**
- 再往下只能动 `rknn`：`inputs_set / rknn_run / outputs_get` 目前合并统计，
  需加 `RKNN_FLAG_COLLECT_PERF_MASK` 拆开才能判断是硬件还是 1.2 MB 回读。
  **本轮未测，不得声称已定位。**

## 二十七、e2e 双 NPU 并行：CPU 绑核决定 fp16 能否过 12 fps（2026-10-16 实测）

### 27.1 一句话

### 27.3 三条可复用铁律级结论

1. **异构核上「优化某一级」会转移瓶颈，不能只看那一级**。臂 P/Q 把 NPU 级从 81.5 压到 59.9 ms/帧
   （理论 16.7 fps），但 GMC 被挤到 A55 后 32.09 → **106.25 ms**，GMC 变新瓶颈，总帧率反而掉到 9.12。
2. **`inputs_set` 是单线程标量循环，给两个核与给一个核完全一样**（臂 Q 14.72 vs 臂 P 14.73）。
   ⇒ 判「某段代码吃不吃得满多核」不能凭直觉，要用「1 核 vs 2 核」实测。
3. **NPU worker 线程 111 ms 在 `rknn_run` 上阻塞等待，CPU 闲置**。
   ⇒ 把两个 A55 小核整块划给 worker 是纯浪费；正确解是 1 大核 1 worker。

### 27.4 `inputs_set` 45.41 ms 的定性与 `pass_through` 证伪（用户叫停，留档）

定性成立且已定位：**小核上的标量逐元素循环**。同一份 1228800 B uint8 上传、同一个驱动：

| 模型 | `in_attr.type` | attr `size` | `inputs_set` |
|---|---|--:|--:|
| int8 | `2` UINT8 | 1,228,800（1 B/px） | **0.34 ms** |
| fp16 | `1` FLOAT16 | 2,457,600（2 B/px） | **45.41 ms** |

45.41 ms ÷ 1,228,800 = **37 ns/元素 ≈ 74 cycles @2 GHz**。

三条建议路线逐条实测：
- `pass_through=1` + 2 B/px fp16 缓冲 ⇒ 驱动拒绝
  `E RKNN: rknn_inputs_set, param input size(2457600) < model input size(4915200)`，每帧失败
- 同上补齐到 4 B/px ⇒ **SIGSEGV**，`__memcpy_generic` ← `librknnrt.so` ← `rknn_inputs_set`
- 声明 `type=FLOAT32`（不过直通）⇒ `inputs_set` 46.74 / 47.78 ms，**没降**；
  先除 255 ⇒ 537 帧 **0 检测**（运行时又除一次），不除 ⇒ 571 检测（对，但没提速）

⇒ **`pass_through` 在这个 fp16 图上是驱动自相矛盾，不是调用姿势问题**：
`RKNN_QUERY_INPUT_ATTR` 报 `type=1 fmt=1 n_elems=1228800 size=2457600`（2 B/px），
但直通检查要 `4915200`（4 B/px）。按声明给 → 报错；按检查给 → 段错误。SDK 头文件解释不了。
代码保留 `--f16-in` / `--f32-in` 两条路径作可复现负面对照。

⚠️ **旧误判更正**：早先记为「arm I 挂死」是错的。真因是尺寸校验失败后 worker 吞掉错误继续跑，
队列永不排空，producer 侧看着像不动（NPU load 100% 是上次崩溃的残留读数）。

**仍未执行、需用户裁决的唯一剩余路线**：转模型时把输入固化为 uint8 节点，
让 Cast/Mul 成为图内算子跑到 NPU——这正是 int8 档 `inputs_set` 只有 0.34 ms 的原因。
要改 ONNX 输入 dtype + rknn-toolkit2 2.3.0 重新转换，属模型侧改动。

**「输入保持 int8 + 量化损失大的层用 fp16」这个组合，在 rknn-toolkit2 2.3.0 上构建不出来。**
四条独立路径逐一实测封死。而"逐层量化损失"本身做出来了，结论很集中。

完整记录：`docs/experiments/2026-10-16_hybrid_precision_int8_input.md`

### 28.2 为什么"输入必须 int8"是硬约束

| 模型 | 输入 attr | `inputs_set` | `rknn_run` |
|---|---|--:|--:|
| int8 | `type=2` INT8，1228800 B (1 B/px) | **0.34 ms** | 61.56 ms |
| fp16 | `type=1` FLOAT16，2457600 B (2 B/px) | **45.41 ms** | 111.46 ms |

133× 差距来自输入张量字节宽度：int8 图输入原样上传；fp16 图输入要由运行时在用户态展宽
全部 640×640×3 元素（45.41 ms ÷ 1,228,800 = 37 ns/元素 ≈ 74 cycles）。

### 28.3 逐层量化损失（两条独立方法互相印证）

**toolkit 自己的**（`hybrid_quantization_step1(proposal=True, proposal_dataset_size=1)`，rc=0，
产出 `trial0474_hm_nop0.quantization.cfg` 97,662 B）：`custom_quantize_layers` 给出
**76 个应保 float16 的张量**，每行带逐层分数 0.977864–0.999718（中位 0.999273）。
按算子：Conv 29、Mul 24、Concat 5、Add 4、Slice 3、MaxPool 2、其余 9。
最低分：`/model/b1/act/Mul` 0.9779、`/model/b0/act/Mul` 0.9882、`/model/Concat_5` 0.99635、
`/model/b2/Concat` 0.99635、`/model/b2/Slice` 0.99639、`/model/b2/cv1/act/Mul` 0.99670。

**我自己独立算的**（`analyze_quant_loss_per_layer.py`，426 张量全暴露为图输出，
onnxruntime 跑 12 张标定图，按 toolkit 配置做 per-tensor 非对称仿射 int8 fake-quant）：
SQNR p1=**27.7 dB** / p10=34.4 dB / 中位 40.3 dB。最差实体张量：
`/model/b2/cv2/conv/Conv` **27.24 dB**、`attn/Softmax` 28.73、`head/Clip` 29.98、
`head/Sigmoid` 29.98、`/model/b2/cv1/conv/Conv` 30.16、`c19/m.0/cv3/conv` 30.40、
`/model/b2/m.0/cv2/conv/Conv` 30.55、`/model/fuse_p2/conv/Conv` 30.97。

⇒ **两套方法都把 `/model/b2`（stem 与颈部衔接段）排在最前**，其次是 attention 的 Softmax
与 head 的 Sigmoid/Clip。量化损失高度集中，不是均匀分布。

### 28.4 四条封死的路径

| 路径 | 结果 |
|---|---|
| 两步式 `hybrid_quantization_step1/2` | step1(size=1) 通、给出层清单；**step2 崩**：`KeyError '/model/head/feat_conv/feat_conv.1/act/Sigmoid_output_0'`，`quant_optimizer._p_adjust_tanh_sigmoid` |
| `quantized_hybrid_level=1/2/3` | **三档输入全是 FLOAT16、内部内存全是 105,600 KB（与 fp16 相同，int8 是 20,400 KB）** |
| UINT8 图输入 ONNX | **abort rc=134** `Not Support Dtype: 2`，在 `rknn::RKNNInitRNNConst`；`--no-quant` 与 hybrid 两种配置**同样 abort** ⇒ 与量化无关 |
| `quantized_dtype='w8a16'` | toolkit 直接拒绝：`not support in 'rk3588'` |
| `custom_string` 混合 DSL | 2.3.0 已移除（二进制里搜不到任何 DSL 字符串） |

**根因**：toolkit 把「图输入张量 dtype」与「计算精度」绑死。
`--no-quant` ⇒ 输入 FLOAT16；量化 ⇒ 全图 int8；混合 ⇒ 它选中间态，把**输入**判成 float16
而只量化**部分中间层**。没有开关能让输入停在 int8 而图内混精度。

**step2 崩溃的根因（实测确认）**：原 ONNX 有 **77 个 Sigmoid**，step1 图融合后只剩 **1 个**
（`/model/head/Sigmoid`，其余 Conv+Sigmoid 被融合）。step1 自己的 quant_optimizer 输出
`adjust_tanh_sigmoid: ['/model/head/Sigmoid']` 是对的；step2 重建图后同一优化器拿 ONNX 级
Sigmoid 列表查融合后图的参数表 → KeyError。**toolkit 自身缺陷，不是本模型的问题。**
（把缺失 Sigmoid 塞进 fp16 列表绕过 → 报 `Invalid operands name`，因为该张量在图里不存在。）

## 二十九、🔴 Head 分支合并（heatmap.0 + offset.0 → 单个 Conv2d(64,128,3)）：**实测负结果，双臂均变慢**（2026-10-16 实测）

### 1. 动机与结构依据

静态枚举全网 85 个卷积（stride=2 / imgsz=640 / scale=n / 去P0 / nearest，**21.48 G MAC**，
与交付版 v3 构建日志 21.54 G 差 0.3%，口径已还原正确）发现：
**82.4%（17.70 G MAC）全部压在 320×320 上的 5 个 3×3 卷积**（`head.feat_conv.1` 3.775G、
`head.heatmap.0` 3.775G、`head.offset.0` 3.775G、`fuse_p1.conv` 3.539G、`head.feat_conv.0` 2.831G）。
`heatmap.0` 与 `offset.0` 输入/kernel/padding 完全相同、仅权重不同 ⇒ 可拼成 `Conv2d(64,128,3)`，
**数学等价、4 键重映射、零重训、不碰 Trial 0474 冻结底模**。

⚠️ **纠正一个当时差点照抄的错误判据**：「HW≥320×320 且通道窄（C≤32）= 几十毫秒黑洞」在本模型**会指错靶子**。
命中该判据的 `b0.conv`（320×320/C=16）MAC 仅 0.044G = 全网 0.2%；真正的大头是 **C=64（完全 32 对齐）** 的层。
本轮真正规律是「**高分辨率 + 高 MAC**」，不是「窄通道」。

### 2. 🔴 实测结果：变慢，不是变快（板卡 RK3588，`--warmup 10 --loops 30`，时钟自检 4/4 `[ok]`）

| 臂 | `rknn_run` | `inputs_set` | NPU+dequant | fps | 判定 |
|:---|---:|---:|---:|---:|:---|
| **base int8** | **55.501 ms** | 0.252 ms | 56.448 ms | **17.7** | 基线（复现案卷 55.5 ms ✅） |
| **merge int8** | **56.882 ms** | 0.246 ms | 57.835 ms | **17.3** | 🔴 **+1.381 ms / +2.49% 变慢** |
| **base fp16** | **103.104 ms** | 42.404 ms | 146.307 ms | **6.8** | 基线 |
| **merge fp16** | **105.458 ms** | 42.274 ms | 148.540 ms | **6.7** | 🔴 **+2.354 ms / +2.28% 变慢** |

**结论：合并没有省下任何搬运开销。** 机理：把两次读换成一次读省下的带宽，
被 RKNN 为通道切分插入的 `Split` 的拷贝成本**抵消有余**，净亏约 1.4~2.4 ms。
佐证：NPU 内部内存 **20,400 KB → 25,600 KB（+25.5%）** —— 128 通道输出多占了一块 scratch。

### 3. 连带证伪：`Conv:/model/b5/conv/Conv` 的 3Core→单核不是形状问题

fp16 两臂构建日志的 fallback **逐字相同**（只差时间戳），仍是那条既有的
`Conv:/model/b5/conv/Conv` 3Core→单核 ⇒ **本次改动未引入任何新 fallback**。
同时静态枚举证实 `b5.conv` 参数全部健康（输出 128ch / 40×40、**C%32=0**、groups=1），
三把尺子全不命中 ⇒ 该警告是 **fp16 编译器调度决策，不是模型结构缺陷，改网络结构修不掉**。

### 4. 踩到的两个真 bug（均为「静默失效」型，已修）

1. **`nn.Sequential` 按位置建键**：少放一层导致 1×1 尾层从 `heatmap.2` 挪到 `heatmap.1`，
   整个 checkpoint 对不上。由自检 Gate 立即炸出（`missing: head.heatmap.1.weight`）。
2. 🔴 **rknn-toolkit2 2.3.0 对 `Conv → Split` 直连会丢 pads**：
   `[ShapeInferenceError] (Conv: /model/head/branch3x3/Conv) Inferred shape and existing
   shape differ in dimension 2: (318) vs (320)`（**318 = 320−3+1 即 pad 被当 0**）。
   降 `optimization_level=2` **无效**，是结构问题不是融合深度问题。
   **解法：把 ReLU 整体提到 Split 之前** —— ReLU 逐元素，`relu(h)[:, :64] ≡ relu(h[:, :64])`，
   数学等价且让 Split 不再紧贴卷积。改后 4 个 RKNN 全部构建成功。
   ⚠️ 另：`chunk` 会被 ONNX 追踪成 Shape/Gather/Add/Div 约 9 个标量节点，**必须用静态 `torch.split`**。

### 5. 上板闸门（§四·9e）

`int8` 双臂 **fallback 警告 0 条 = PASS**（交付口径只约束 int8）；
`fp16` 双臂各 1 条，是**既有的 b5 警告**，非本次引入。

## 三十、🔴🔴【关键证伪】DW+PW 轻量化 Head：MAC 降 72%，int8 时延只降 10.2% —— **20 ms 目标的前提被推翻**（2026-10-16 实测）

第一次是 P0（MAC 降 6.8% 而时延降 46.5%，方向相反）；本次是 MAC 降 72% 而时延仅降 10.2%。
**两个方向都说明 MAC 与 NPU 时延之间不存在稳定映射。**

### 5. 🔴 对「20 ms」目标的重新裁决

原假设「总 MAC 压到 6~8 G 就能进 20 ms」**已被实测推翻**：
6.05 G MAC 的实测是 **49.86 ms**。
⇒ **杠杆不在 MAC，而在空间分辨率 H×W**（那才是带宽的驱动量）。可行方向按优先级：

1. **动态 ROI 局部裁剪**（用户原方案步骤 3）：跟踪态只跑 160~256 patch。

2. **stride 2 → 4**（全网 21.48 → 7.55 G，H×W 320→160）：

3. **进一步压缩 320×320 段的张量宽度**（如 head_conv 64→32）：

§四·9e：late_int8 **fallback 0 = PASS**；late_fp16 的 1 条仍是既有 b5 警告。
320×320 上的卷积层数 **8 → 1**。

### 3. 🔴 证据闭合：**NPU 时延跟的是「搬运量」，不是 MAC**

三组受控对照，把变量分离开了：

| 改写 | MAC 变化 | 搬运变化 | 时延变化 |
|:---|---:|---:|---:|
| merge（§二十九） | 0% | +Split 拷贝 | **+2.5%（更慢）** |
| dw（§三十） | **−72%** | **+1%（几乎没动）** | **−10.2%** |
| late（本节） | −62% | **−44%** | **−33.9%** |

🔴 **决定性反证：late 的 MAC（8.20 G）比 dw（6.05 G）多 35%，时延却快 26%**
（36.657 vs 49.860 ms）。
⇒ 只要搬运量不变，砍 MAC 基本白干；**动分辨率才是唯一有效的杠杆**。

至此 §四·9f「禁止用 MAC/FLOPs 外推 NPU 时延」获得了三次方向一致的实证
（P0：MAC −6.8% / 时延 −46.5%；dw：MAC −72% / 时延 −10.2%；late：MAC −62% / 时延 −33.9%）。

### 4. 对 20 ms 目标的现状裁决

**36.657 ms（26.6 fps）已达成，但离 20 ms 仍差 1.83 倍。** 剩余杠杆：

1. **Head 进一步瘦身**（`head_conv` 64→32、`fuse_p1` 再降）：只减搬运不增，已在 160×160 上，空间有限。
2. **动态 ROI 局部裁剪**：再把 160×160 压到 64~128，搬运再降 2~6 倍 —— **目前唯一还有大空间的路**。
3. ⚠️ **不再推荐 stride 2→4**：late 已把 Head 压到 160，等价于「只保留 P2 尺度」，
   再降 stride 会连 P1/P2 融合一起砍掉，且 §四·9h 的 40 ms 红线风险仍在。

### 5. 🔴 本轮修掉的两个真 bug（都会静默毁掉产物）

1. **输出目录名与建目录名不一致**：`mkdir` 建 `pass_seqs`/`un-pass_seqs`，而写文件用的是
   TSV 里的判定词 `pass`/`un-pass` ⇒ 视频全落进 `pass/`、`un-pass/` 两棵平行的目录树，
   目标目录里只剩 1 条。**编译期与 shell 期都发现不了，只有数文件才发现**。
   ⇒ 已改为让 TSV 的 group 列**直接就是目录名**，建目录与写路径同源。
2. **`--show-scales` 遇空尺度直接抛异常**：`VIDEO00012_002251` 最优 `th=0.60` 时
   160/80 尺度**零检出**（tag 不存在），脚本 `raise ValueError` 中止整段视频。
   ⇒ 已降级为 `[WARN]` 并跳过该尺度。**「某尺度在当前门限下零检出」是合法状态，不是错误**。

### 4. 工程含义（交付路径选择）

- **单一全局工作点**：工程上简单、参数可冻结，但 2 条序列判不过（`00012`/`00032`），
  且 FAR 0.2569 / 0.2761 远超 0.030 合格线。
- **逐序列调参**：24 条里 22 条能上 80%+，但**需要 24 组不同参数**，
  意味着工作点无法冻结，跨批次/跨场景不可直接复用。
- ⇒ 若要收敛成可交付的单点方案，**要么为这 2 条序列做条件分支**（按场景特征选门限），
  **要么接受它们不达标**并在合同里划出特化区段。**这已超出现有单点评测口径的裁决范围，待用户拍板。**

### 6. ⚠️ 本轮又踩了一次「校验脚本自己写错」

连续三次把校验脚本写错并误报全量缺失，**根因都是手写 shell/python 的字段映射**：
① `IFS` 读 5 个变量却对 8 列 TSV；② 旧版 TSV 的 group 已是 `pass_seqs` 却仍按 `pass` 映射一次。
