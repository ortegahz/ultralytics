# RK3588 板端 f16 multi-scale 拼图（Canvas Mosaic）推理 —— 对照报告

> **实验目标**：在 RK3588 上用 C++ 实现「**一次前向喂满 640×640、把三个尺度塞进同一张画布**」的 f16 热图模型推理，
> 并与 PC 侧已冻结的 PT float32 multi-scale 基准做**逐口径**对照。
>
> **实验范围**：**龙泉山两个 val 轨**（no track / 单帧臂）
>
> | 轨 | 序列 | 帧数 | GT | 说明 |
>|:--|:--|--:|--:|:--|
> | `track2_golden` | 7 条黄金池序列 | **17,187** | 16,638 | T2，空域白热基准 |
> | `track3_blind` | `VIDEO00007_19700101_001324` | **11,810** | 10,535 | T3，盲测难例留出 |
>
> 合计 28,997 帧 —— 正好是 official val 全量。
>
> **结论一句话**：**拼图打包本身几乎无损（f32 下只损失 0.0027 F1，却保住了多尺度的 +0.016~0.023 增益）**；
> 板端 f16 的代价也可以干净地隔离出来，**拼图装配（RGA）只占 ~1 ms，单次 NPU 前向与单尺度完全一致**。

## 1. 实验设计

### 1.1 为什么需要「拼图」

PC 侧 multi-scale 的做法是**逐尺度各跑一次前向**：native(640×512)、thumb160(160×128)、thumb80(80×64)
各自 letterbox 到 640×640 再进模型。也就是 **3 次 NPU 前向**。

拼图方案把三张画布压进**同一张 640×640**：native 贴左上、thumb160 贴左下、thumb80 贴在 thumb160 右侧，
**只跑 1 次前向**。因为 RKNN 的输入张量静态是 `[1,3,640,640]`，卷积代价由形状决定、与像素无关，
所以 **NPU 时间与单尺度完全相同**（实测 `rknn_run` 100~102 ms，见表 C）。

### 1.2 画布布局（v1）

```
canvas 640 x 640 x 3 (RGB, 模型通道序 [residual, diff, I_t]), 背景 114 填满 3 通道
┌────────────────────────────────┬──────────────┐
│                                │              │
│   native 640x512  (1:1)        │  背景 114    │
│   = 画布 (0, 0, 640, 512)      │              │
│                                │              │
├──────────┬──────────┬─────────┤  ← 行 512
│ thumb160 │ thumb80  │ 背景114 │              │
│ 160x128  │  80x64   │         │              │
└──────────┴──────────┴─────────┴──────────────┘
   0      160        240
```

三个 tile 由 **RGA `improcess` ×3** 从同一张 640×512 源图一次装配完（缩放 + 落位一步到位），
逐帧**零 CPU 图像拷贝**：stb_image 解出来的缓冲直接 `importbuffer_virtualaddr` 交给 RGA。

### 1.3 七个 arm（全部用同一个打分器重算）

| arm | 计算图 | 用途 |
|:--|:--|:--|
| **A** | PC f32，逐尺度 3 次前向 | **冻结基准**（gate 产物，0.897694） |
| **A0** | PC f32，逐尺度，仅 native | 多尺度增益的逐尺度口径基线 |
| **B** | PC f32，拼图 1 次前向（缩略图 INTER_AREA） | **隔离「打包损失」** |
| **B1** | PC f32，拼图 1 次前向（缩略图 INTER_LINEAR ≈ 板端 RGA 语义） | 隔离「缩略图重采样语义」 |
| **B0** | PC f32，拼图 1 次前向，仅 native | 多尺度增益的拼图口径基线 |
| **C** | **板端 f16，拼图 1 次前向** | **本次交付的产物** |
| **C0** | 板端 f16，拼图 1 次前向，仅 native | 隔离「画布里塞了缩略图」对 native 检测的扰动 |

> **B 臂是本次实验的关键补件**：没有它，C 与 A 的差值无法归因（那是「打包 + 量化」的合计）。
> 加上 B 之后，A→B 是打包损失、B→C 才是 f16/量化损失。

**两版 TSV 逐字节相同**（md5 `0bf598a1d890040bcfa8d157dc69c032`）⇒ `--pyr-cache` 在 11,810 帧全量上
证明**端到端逐位等价**，只买速度不换精度。

**瓶颈分析（为什么不是 14 fps）**：

- 每个 NPU worker 的串行链 = upload 12.78 + run 108.20 + outputs 0.75 + backproj 10.89 = **132.6 ms**；
  2 个 worker ⇒ **66.3 ms/帧 ⇒ 理论上限 15.1 fps**。
- GMC 线程 = 62.8 ms/帧（第二个瓶颈，缓存后从 72.1 降下来）。
- 实测 79.95 ms/帧（12.507 fps）⇒ 距理论上限还有 ~13.6 ms/帧，是三个线程（GMC + 2×NPU worker + 主线程解码）
  在 4 个 A76 核上的争用。
- **板卡 RKNN 上下文硬上限为 2**，加不了 worker；`rknn_run` 108 ms 是模型本身的硬件代价。
- ⚠️ **曾经报出的 13.905 fps 作废**：那次是在**损坏特征**上测的（拟合提前返回恒等 ⇒ 根本没做拟合）。
  同理 **300 帧小样本测出的 13.885 fps 也不可信**（序列开头帧静止，拟合提前返回）⇒ **速度数必须全量测**。

**CPU 亲和性 A/B（2,000 帧，同一二进制、同一输入）**：

| `--cpu-affinity` | gmc_fit | rknn_run | total_wall | fps |
|:--|--:|--:|--:|--:|
| **4-7**（4×A76，**当前交付配置**） | 65.329 | 107.619 | **77.924** | **12.833** |
| 0-7（放开到 8 核，含 4×A55） | 65.496 | 107.513 | 80.614 | 12.405 |

⇒ **放开到 A55 反而更慢**（内存带宽与核性能都吃亏），**当前 `4-7` 已是最优**，不需重跑全量。

#### 2.5.1 服务拓扑与「帧可以丢在哪」

```
相机 25fps ──push() 永不阻塞/永不丢──▶ [相机队列 8] ──▶ [GMC 服务 2引擎] ──▶ [特征缓冲 8] ──▶ [NPU 服务 ×2] ──▶ [热图缓冲 8] ──▶ [POST 服务] ──▶ 回调
                                        ▲ 丢=GMC特征丢失      ▲ 丢=只丢检测        ▲ 丢=只丢检测
                                          [WARN]                无告警(设计内)        无告警(设计内)
```

| 丢帧点 | 后果 | 计数器 | 日志 |
|:--|:--|:--|:--|
| 相机队列 | **GMC 特征丢失 ⇒ 配准链断裂**，其后每一帧都对不上 | `dropped` | `[WARN] a GMC FEATURE was LOST: …` |
| 特征缓冲（GMC→NPU） | 只丢一个检测，**特征流完整** | `features_dropped` | 无告警（设计内行为），计入收尾汇总 |
| 热图缓冲（NPU→POST） | 只丢一个检测 | `detections_dropped` | 无告警（设计内行为），计入收尾汇总 |

**为什么丢帧点必须在 GMC 之下**：GMC 的变换链由历史帧拟合 + 一步拟合组合而成，丢一帧 ⇒ 其后每一帧的配准都错；
而 NPU 的一次前向是**逐帧独立**的，跳过一帧只损失一个检测。推理侧是慢的那一段（GMC 反而跟得上 25 fps），
所以让推理跳过、让 GMC 完整，是唯一正确的分工。

> 上表只测了**速度**。本轮把 250 角点跑完整条盲测序列（11,810 帧）并用同一个打分器算分后：

> 把上限砍到 250 ⇒ LK/RANSAC 的跟踪点锐减 ⇒ 拟合变差 ⇒ 特征不再正确配准 ⇒ 检测全线下滑。

**杠杆二：GMC 引擎数**（600 角点）——**更多引擎更慢**

| 引擎数 | gmc_fit 均值 | p50 | p95 | p99 | 端到端 ms/帧 | fps |
|:--|--:|--:|--:|--:|--:|--:|
| **2** | **70.365** | 58.349 | 140.842 | 173.617 | 65.953 | **15.162** |
| 3 | 103.852（+47.6%） | 93.232 | 185.777 | 246.544 | 67.642 | 14.784 |
| 4 | 86.908（+23.5%） | 75.217 | 162.804 | 211.309 | 66.790 | 14.972 |

**根因（结构性，不是核争用）**：GMC 组合非锚点 lag 时要查一步拟合缓存 `step(t-L)`，而 `step(a)` 是**帧对 (a, a+2)**。
引擎按轮转分配时：

- **2 引擎**：engine0 拿奇数帧、engine1 拿偶数帧 ⇒ 帧对 (a, a+2) 两端**同奇偶 ⇒ 同属一个引擎** ⇒ 缓存命中，每帧只新算 **1** 个一步拟合；
- **3/4 引擎**：帧对 (a, a+2) **必然跨引擎** ⇒ 每帧要**惰性重算**若干对 ⇒ fit 成本 +48%/+24%，尾延迟同步恶化。

⇒ 库已把 `gmc_workers` 上限**硬钳到 2**（契约测试有对应断言），越界会打 `[WARN]` 并钳回。
**结论：2 引擎是唯一正确的并行度；压 GMC 用角点预算，不要加引擎。**

**⇒ 根因（两次误诊之后才定位到）**

误诊一：「CPU 不够」——把**线程的 wall 时间**当成了**CPU 时间**（`rknn_run` 的 115 ms 是等硬件，不是烧 CPU）。
线程级实测（`/proc/<pid>/task/*/stat` 的 utime+stime 差分）：

| POST | 0.19 核 |
| 生产者（BMP 解码） | 0.04 核 |
| **合计** | **2.57 核 / 8 核** |

⇒ **总占用远未饱和**；而且放开到 8 核后**丢帧几乎没变（810 → 796）、GMC 每帧 wall 时间也没变**
（0-3 是 1.8 GHz 的 A55、4-7 是 2.352 GHz 的 A76 ⇒ **多出来的核更慢**）。

误诊二：「总占用才 2.57 核 ⇒ 根本不是 CPU 问题」——**结论对、推理错**：
**总占用**不代表**关键线程能不能拿到整核**；两个 GMC 引擎每个只拿到 0.94 核，
而一次 60 ms 的拟合**被抢占就足以让相机队列溢出**。

**⇒ 真根因（板端实测，2026-10-27）：单线程 ingest 被「历史窗口护栏」单向限流，形成自我维持的限流死锁。**
- `manu/pipeline/npu/mosaic_pipeline.cpp` 的 `ingest_loop()` 是**唯一**把帧从相机队列搬进 GMC 引擎的线程。
- 历史窗口护栏 `window_ok()` 在 `abs - min_e(oldest_pending_e) > ring_slack` 时**阻塞 ingest**；
  而护栏的**放行速率 = 引擎完成速率**。
- 护栏一挡 ingest ⇒ 引擎作业队列被抽干 ⇒ 引擎空等（实测 18.75 ms/own 帧）⇒ 引擎周期从 63.4 拉长到 **85.9 ms**
  ⇒ 护栏放行更慢 ⇒ **自我维持**。
- 实测证据（svc_L / Exp-C）：ingest **42.880 ms/帧 > 帧周期 40 ms**；
  `gmc_window_blocks=2469`（**22% 的帧撞护栏**）vs `gmc_space_blocks=18`（几乎不撞作业队列）
  ⇒ 瓶颈是**护栏**，不是队列深度、不是算力、不是 CPU。
- 稳态吞吐 **23.29 fps < 相机 25 fps** ⇒ 相机队列溢出 **794 帧** ⇒ **GMC 特征流断裂**（配准链断）。

**⇒ 两个护栏是耦合的：只放大队列深度无效。**
`ring_slack`（16）恰好 = 2 × `queue_depth`（8）：lookahead 预算把引擎作业队列深度一起卡死 ⇒
Exp-D 把 `queue_depth` 提到 32 后，窗口阻塞反而**涨到 3311**，丢帧只从 794 降到 438
（引擎空等 18.75 → 15.56 ms，GMC 多看到 356 帧）。
⇒ **必须同时放大 lookahead 预算与作业队列深度。**

##### 2.5.8.1 帧内并行 5 个锚点拟合（LK 并行 + RANSAC 保序 ⇒ 位级一致）

##### 2.5.8.2 🔴 25 fps 的真正瓶颈在 **NPU**，不在 GMC

**证据：全量臂 `svc_N_bitexact_lookahead`（11,810 帧，串行基线，不 paced）的 `timing.txt`**：

```
rknn_run 112.3796 ms/帧   upload 13.2597   backproject_cc 10.8928
gmc_fit 60.5303   gmc_total 64.3163   total_wall 67.0785   fps 14.908
```

**链式算术（关键路径）**：

| 项 | ms/帧 | 依据 |
|:--|--:|:--|
| NPU 单 worker 串行链 = upload 13.26 + rknn_run 112.38 + outputs 0.80 + backproj 10.89 | **137.33** | svc_N timing.txt |
| ÷ **2** 个 NPU 服务（**RKNN context 硬上限就是 2**，加不了 worker） | **68.66** | 同上 |
| ⇒ **理论天花板** | **14.57 fps** | 同上 |
| **实测**（svc_N，11,810 帧全量） | total_wall **67.0785** ⇒ **14.908 fps** | 同上 |
| GMC 服务占用（`gmc_total` ÷ 2 引擎） | 64.3163 ÷ 2 = **32.16 ms/帧**（**远小于 68.66 ⇒ 不是瓶颈**） | 同上 |

⇒ **管线已经贴着 NPU 天花板在跑**（实测甚至略高于按「严格串行」算出的 14.57 fps，因为
`outputs_get` / `backproject_cc` 在两个 worker 间并非严格串行）。
⇒ **GMC 只占 25.9 ms/帧且与 NPU 并行重叠 ⇒ 把 GMC 优化到 0 也只能到 ~15 fps 量级（乐观上限 ~16 fps）**，
**离 25 fps（40 ms/帧）差得远**。

**⇒ 25 fps 需要什么**：把 `rknn_run` 从 **112.38 ms** 压到 **≤55 ms（−51%）**。
而 **RKNN context 硬上限为 2** ⇒ **加不了 worker** ⇒ 只能让每个 context 用上 RK3588 的 **3 个 NPU 核**。

**⇒ 其它零代价项的上限（都不够）**：

| 手段 | 链（ms/帧） | ÷2 | fps | 够 25 fps 吗 |
|:--|:--|--:|--:|:--|
| 现状 | 137.33 | 68.66 | 14.57 | ❌ |
| upload 整段移走（`iomem` 路径） | 137.33 − 13.26 = **124.07** | 62.04 | **16.1** | ❌ |
| **core mask 把 `rknn_run` 112.38 → ~64**（服务化口径链：rga 2.3 + upload 13.3 + 64 + outputs 0.8） | **80.4** | **40.2** | **≈24.9** | ✅ **唯一够得着的** |

**⇒ core mask 是唯一零精度代价的杠杆（假设 RK3588 有 3 个 NPU 核、当前只用了 1 核）**：
- `manu/pipeline/npu/mosaic_core.h` 的 `rknn_init(&s->npu.ctx, model.data(), size, 0, nullptr)`
  **从头到尾从未调用过 `rknn_set_core_mask`**（参考实现 `manu/pipeline/npu/e2e_core.cpp:795` 有现成封装）；
- ⇒ 新增公开旋钮 **`npu_core_mask`**（0..7，默认 **0 = 不调用 `rknn_set_core_mask`，即保持现状**）；
- ⚠️ **但它可能同时改变吞吐与数值**（不同核 = 不同执行路径）⇒ **任何非默认值都必须标注 deviation**；
- ⇒ **本轮这条假设「当前只用 1 核」尚未被实测验证** ⇒ **core mask 8 组对照实验见 §2.5.8.5（未跑）**。

**⇒ 🔴 正面结论（不要写成「GMC 优化无用」）**：
GMC 侧仍有约 25.9 ms/帧 的优化空间（并行锚点已吃掉其中 29.5%），而且它是**零精度代价**的；
它之所以救不了 25 fps，是因为**瓶颈已经整体搬到 NPU 侧**，不是因为 GMC 没得优化。
⇒ **两条都成立**：GMC 优化**有效**（−29.5% 拟合、位级不变），但**不是瓶颈**（端到端 +2.0%）。

> 🔴 **本节推翻的既有归因**：此前把「25 fps 丢帧」归因到 **GMC 护栏 / 角点预算 / LK 成本**，并认为
> **「优化 GMC 即可达到 25 fps」** —— **这是错的**。
> 证据：并行锚点把 GMC 拟合降了 **29.5%**（29.619 → 20.871 ms/帧），**端到端只 +2.0%**；
> 而全量臂实测**管线贴着 NPU 天花板**（`rknn_run` 112.38 ms/帧、2 context ⇒ 68.66 ms/帧 ⇒ 14.57 fps，实测 **14.908**）。
> ⇒ **25 fps 的缺口在 NPU 侧**，须靠 **core mask 等零代价手段**打开。

## 3. 实现要点

### 3.1 板端 C++（`manu/pipeline/npu/rknn_mosaic_heatmap.cpp`）

| 段 | 说明 |
|:--|:--|
| 解码 | stb_image 直读 BMP（板卡无 OpenCV）。**stb 返回的 RGB 字节序 == 模型通道序**，无需翻转 |
| 拼图 | `importbuffer_virtualaddr` + `wrapbuffer_handle` + `improcess` ×3 |
| 输入 | `rknn_inputs_set` uint8 NHWC（`--input-mode set`） |
| 输出 | `rknn_outputs_get` + dequant → float32 320×320 热图 |
| 反投影 | CPU float32：裁出该 tile 在 320 格上的窗口 → INTER_LINEAR 放大到 640×512 |
| 连通域 | CPU float32：阈值 `>= 0.06`、8 连接、area ≥ 4、按 **sum 降序** 取 top 100 |

**两个消融模式**：`--canvas-mode {mosaic,single}`（single = PC 同构的 native letterbox 画布）、
`--tiles 0,1,2`（只输出部分 tile 的检测）。两者组合可用于把「画布扰动」和「多尺度贡献」分开。

**自带保护**：
- RGA 自检：native tile 是 1:1 拷贝，**必须逐字节等于源图**，否则判定 RGA「返回 SUCCESS 但没写数据」并切到对齐 staging 缓冲。
- 阈值比较在 **double** 里做（对齐 numpy 的 float32-vs-float64 比较语义）。
- 8 段计时（decode / rga_import / rga_improcess / fp16_or_upload / rknn_run / outputs_get / backproject_cc / write）。

### 3.2 PC 侧对照臂（`manu/pipeline/npu/ptq/37_mosaic_pc_control.py`）

复用**同一批 BMP**（不是另读 JPG），保证像素逐字节相同；同一张画布布局、同一次前向、
同一套反投影 + **直接调用 PC 侧的 `detect_components()`**（不是重写），输出**与板端相同格式的 TSV**，
因此两侧可以走**同一个打分器**。

### 3.3 ⭐ 库交付：`libmosaic_pipeline.a` + 端到端测试程序

嵌入式组要的是**可调用的库**，不是一次性 demo。本轮把整条链路封成库，并另写了一个**只调公共 C ABI**
的测试程序来驱动它。

| 层次 | 文件 | 说明 |
|:--|:--|:--|
| 公共 ABI | `manu/pipeline/npu/mosaic_pipeline.h` | **纯 C**（主机 `gcc -std=c11 -Wall -Wextra` 与交叉 aarch64 均编译通过）：配置 / 推帧 / 收结果 / 取耗时 / 取特征指纹 |
| 库实现 | `manu/pipeline/npu/mosaic_pipeline.cpp` | **服务化**：GMC 服务（2 引擎，各持独立 OpenCL ctx）+ NPU 服务 ×2（各持**独立 RKNN ctx 与独立 RGA 画布**）+ POST 服务 + 四段**有界**队列（见 §2.5.1 的丢帧点分工） |
| 内部头 | `manu/pipeline/npu/mosaic_core.h` | RGA/NPU/反投影/连通域；从 `rknn_mosaic_heatmap.cpp` 的匿名 namespace **逐字抽出**，单一真相源 |
| 测试程序 | `manu/pipeline/npu/rknn_mosaic_e2e.cpp` | 只 include `mosaic_pipeline.h`（**不碰内部头**）：列目录 → `cv::imread(GRAYSCALE)` → `push` → `collect` → 按 frame_id 排序写 TSV |

**线程模型（服务化，v2）**：`producer(调用方) → GMC 服务(2 引擎) → 特征缓冲 → NPU 服务 ×2 → 热图缓冲 → POST 服务 → 回调`。

| 服务 | 实例 | 职责 | 丢帧策略 |
|:--|:--|:--|:--|
| GMC | **2 引擎**（OpenCL fused tail，各持独立 ctx） | 特征提取 | **绝不丢**（丢在这里会断配准链） |
| NPU | **2 服务**（各持独立 RKNN ctx + RGA 画布） | RGA 拼图 + f16 前向 | 跟不上就**跳过最旧的特征** |
| POST | 1 worker（独立 `PostWorkspace`） | 反投影 + 8 连通域 | 跟不上就跳过最旧的热图 |

- GMC 是因果、有状态的 ⇒ **每帧的计算只依赖像素**，所以多个引擎可以各算**交错帧**；但帧分配必须让
  「一步拟合的帧对 (a, a+2)」落在同一个引擎内 ⇒ **引擎数上限为 2**（实测 3/4 引擎更慢，见 §2.5.4）。
- **板卡 RKNN 上下文硬上限为 2** ⇒ `npu_workers` 被钳到 2（第三个上下文会触发 6 s job timeout 并软复位 NPU）。
- 对外只有 `push()` + 结果回调；服务编排全在库内部，公开 ABI 是 v2。

**重构保真**：`rknn_mosaic_heatmap.cpp` 被重写为薄壳（`#include "mosaic_core.h"`），
**行为由 300 帧 TSV 逐字节比对证明不变**（md5 `1f78eb4d7b873d779d160c29c46c4e4b`），
重编后二进制 md5 仍为 `c68477c2b8984dafc90bb44bb6ae645d`。

**默认配置（开箱即用的交付配置）**：

| 字段 | 默认 | 为什么 |
|:--|:--|:--|
| `gmc_anchor_step` | 10 | 用户拍板「速度优先」；代价 −0.003879 F1（见 §2.1 表 B） |
| `gmc_pyr_cache` | **1** | **已验证端到端逐位等价**（11,810 帧 TSV md5 相同）且 GMC 拟合 −16% ⇒ 默认打开 |
| `gmc_gate_shift` | 1000（= 1.0 帧宽） | **必须**是参考实现的 1.0；0.25 会拒绝龙泉山 FPV 的真实运动，把变换退化成恒等 |
| `npu_workers` | 2 | 板卡 RKNN 上下文硬上限 2（第三个会触发 6 s job timeout 并软复位 NPU） |
| `gmc_workers` | **2（硬上限）** | 3/4 引擎会让「一步拟合帧对 (a,a+2)」跨引擎 ⇒ 缓存失效、拟合成本 +48%（§2.5.4） |

| `gmc_deadline_ms` | **0（关）** | 看门狗一旦启用，超时帧的变换会退化 ⇒ 破坏位级一致。实时部署时打开（≥250 ms，见 §2.5.5） |

**API 防御**：`mosaic_pipeline_config_defaults()` 初始化**每一个**字段；

一个**垃圾门限值**不会崩，它会**静默**把变换退化成恒等（GMC 特征不再配准）——
这正是本轮那版 0.25 门限构建丢掉 0.07 F1 的机制。
