**逐位交叉验证（决定性）**：CANON6 vs A_gate 共同帧 3914，**差异 91**；而**库自己报告**的历史有洞帧（逐条 `[WARN] ... the PHYSICAL history has a HOLE`，从 `CANON6_live25_s3.log` 提取）**恰好也是 91 个**。两个集合**双向差集为空** ⇒

**@S 存活帧口径打分**：

| 口径 | 帧数 | TP / FP / FN | **F1** | 结论 |
|:--|--:|--:|--:|:--|
| CANON6 arm @S（真 25 fps 实时） | 3893 | 2867 / 66 / 617 | **0.893564** | — |

> ⇒ **真 25 fps 实时工况下，本方案不因「跳帧算特征」而损失精度。**
> `arm@fullGT F1 = 0.425750` 是**覆盖率口径**（只看 3893 帧却对全序列 10535 个 GT），衡量的是「处理了多少帧」而非「每帧算得准不准」——按用户验收口径（覆盖率不重要）**不作为判据**。

**cadence=3 仍有 34 帧残留的原因：不是平均速率不够，而是 GMC 拟合抖动。**
`gmc_fit p50 = 53.0 ms` 但 **`p99 = 200.2 ms`、`max = 249.2 ms`**（约 4.7 倍）；单组比平均多耗 ~147 ms ⇒ 期间相机多进 ~3.7 帧 ⇒ FIFO 瞬时堆积。
`gmc_ingest_window = 46.4 ms/帧`、`gmc_window_blocks = 1855` 表明抖动直接转化成窗口守卫的长时间阻塞。
抖动源是 **RANSAC 消耗 OpenCV 全局 RNG**（`gmc_stream_ocl.cpp:338-345` 注释明确记载「RANSAC consumes OpenCV's global RNG (theRNG())」，且为保 bit-exact 必须串行跑 RANSAC 阶段）——**这是下一轮真正该攻的点，比继续加 cadence 更本质**（§7.10）。

### 0.4 一句话结论

**这个架构成立，而且本轮把它推到了「精度可判定一致」**：**canonical 方案（step2 锚点 + 物理帧号锚定 + 双缓存 0 拷贝 + cadence + 连续单环读槽 Pin）使「处理的帧与无丢帧子集精度完全一致」成为可判定的等式——零洞臂 CANON5_nodrop 全量 11810/11810 逐位 md5 相同、different = 0，精度 F1 = 0.891871 与 P1b 认证基线逐项相同；实时臂 CANON6（cadence 3）的 91 处差异与库自报的 91 个有洞帧双向差集为空；实时交付臂 CANON7（cadence 4）掉帧 0、洞 0、逐位 2953/2953 相同、ΔF1 = 0.000000**；洞的唯一来源被物理帧号锚定钉死在相机队列溢出这一个点上，于是工程目标从「别丢帧」变成「**调 cadence 让 GMC 组速率覆盖相机速率**」（实测组产能 12.6~14.7 组/s ⇒ 帧覆盖上限 29.4 → 37.9 → **54.0 fps**，cadence 4 才够，且**余量必须按抖动后的速率算**：cadence 3 平均覆盖 37.9 fps 已远超 25 fps，仍被 `gmc_fit` p99 ≈ 200 ms 的尾部击穿 34 帧，cadence 4 才归零）；同时**双缓存的二级缓存从深拷贝改为浅引用 pin，拷贝成本 0.01 ms/帧（原 0.92–1.86 ms/帧）**，因为深拷贝「白搬 ~7 MB/帧」且「会把『槽位已被换帧』的错误状态一起冻结、把要暴露的问题掩盖掉」——两处都证明**深 FIFO 与深拷贝都是错的工具**，正确的工具是**物理锚定 + 0 拷贝 + cadence**。

## 3. 一个被实测证伪的旧结论：「丢帧 → 精度灾难性」

## 4. 关键工程杠杆：锚点 LK 并行（免费 3.26×）

**成本结构（本轮首次量化）**：step2 每帧要做 **21 个锚点拟合**（lag 2,4,…,42），step10 只有 **5 个**（lag **{2, 12, 22, 32, 42}**）——**204.63 ms vs 59.92 ms 的全部成因就是这个**。
（锚点集合依据源码：`manu/pipeline/cpp/gmc_stream_ocl.cpp:820-836` 的 `anchor_grid()`，`max_lag = window × stride = 21 × 2 = 42`（同文件 `:1531`）——step10 得 {2,12,22,32,42}，与 `manu/pipeline/npu/mosaic_pipeline.cpp:1032` 的注释一致；step2 得全部 21 个 lag 2,4,…,42，与上文一致。）

**为什么可以并行**：锚点 LK 阶段本来就是按并行的设计的——phase 1（缓存准备）串行、**phase 2（LK 拟合）并发**、phase 3（RANSAC + 门限）**串行且严格按锚序**。只有 RANSAC 消费 OpenCV 全局 RNG，而它的抽取顺序不变 ⇒ **输出逐位不变**。

板端实测（600 帧、零丢帧、step2、同一二进制）：

| 臂 | 配置 | `gmc_fit` ms/帧 | wall ms/帧 | fps | 与 K0 逐帧指纹 |
|:--|:--|--:|--:|--:|:--|
| K0 | 串行（认证路径基准） | 214.758 | 246.28 | 4.060 | 基准 |
| **K1** | **锚点 4 线程 @ cores 4-7** | **65.779** | **125.19** | **7.988** | **600/600 完全相同** |
| K2 | 锚点 8 线程 @ cores 0-7 | 95.208 | 144.49 | 6.921 | **600/600 完全相同** |
| K3 | K2 + 物理帧号锚定 | 95.421 | 144.93 | 6.900 | **600/600 完全相同** |

**结论：**
- **锚点并行 = 免费 3.26×**（214.758 → 65.779 ms/帧），**逐位不变**。
- **8 线程反而比 4 线程慢**：锚点线程把 NPU 驱动线程和 POST 的核抢了。**约束不是核数，是核的分配**。
- 首次让**精确的 step2 语义**跑得接近 step10 的成本——**step2 不再需要「慢 3.4 倍」这个原罪**（canonical 保持 step2，不需要靠换语义换速度）。

## 5. 物理帧号锚定改造（用户指定的核心防线）

**要防的是什么**：GMC 的历史用**消费计数**（`abs_counter`，每 ingest 一帧 +1）寻址，而**物理帧号**（`next_id`，每 push 一帧 +1）是另一个计数器。零丢帧时两者恒等（`abs = id + 1`）⇒ 锚定即物理锚定；**一旦丢帧就发散** ⇒ GMC 取「lag 2」实为物理 lag 3+ ⇒ 21 帧中值窗口的物理跨度被压缩 ⇒ **静默错位**（无崩溃、无报错）。

**改造内容**：

### 6.5 吞吐瓶颈分析（`starvation` 解读）

**⚠️ 解读方向已更正（2026-10-28）**：`starvation[gmc/npu/post]` **不是**「等上游的时长」，而是**「各级服务等活干的时长」**。源码原文 `manu/pipeline/npu/mosaic_pipeline.h:570-574`：

```c
/* Starvation: how long each service waited for work.  In a healthy
   pipeline these are ~0 -- that is what the jitter buffer is for. */
double gmc_wait_ms;   /* the GMC engines waiting for a frame to compute   */
double npu_wait_ms;   /* the NPU services waiting for a feature frame    */
double post_wait_ms;  /* the post workers waiting for a heatmap          */
```

⇒ **数值大 = 这一级在饿 = 这一级没活干 ⇒ 它不是瓶颈，约束在它上游**：

| 观察项 | 正确解读 |
|:--|:--|
| `post_wait` 大 | post 在**等 NPU 的热图** ⇒ post 没活干 ⇒ **约束在 NPU**（不是 POST） |
| `npu_wait` ≈ 0 | NPU 线程**几乎从不等特征** ⇒ NPU 有活干 ⇒ **NPU 就是瓶颈** |
| `gmc_wait` 大 | GMC 在**等相机帧** ⇒ 约束在输入侧（相机速率 / 缓冲深度 / **cadence**） |

| 臂 | `gmc_fit` | `rknn_run` | `starvation[gmc / npu / post]` ms/帧 | `gmc_fit_max` | 判定（**更正后**） |
|:--|--:|--:|:--|--:|:--|
| **D0**（step10，已否决·深 FIFO） | 60.825 | 114.169 | 12.642 / **1.535** / **56.892** | 218.025 | **约束在 NPU**：`post` 饿 **56.892** ms/帧 ⇒ post 在等 NPU 的热图；`npu` 只饿 **1.535** ms/帧 ⇒ NPU 有活干 |
| **D1**（step2，已否决·深 FIFO） | 157.585 | 104.134 | **90.139** / **141.353** / **126.756** | 872.747 | step2 下 **GMC 产能不足为主因**（gmc 饿 **90.139** ms/帧 ⇒ 在等相机），NPU 与 POST 都在等上游 ⇒ 全链同步降速 |
| **S2b**（step10，slack 64） | 68.045 | 114.404 | 9.020 / 2.279 / 57.564 | 512.764 | 与 D0 同型：**约束在 NPU**（npu 饿 2.279、post 饿 57.564） |
| **S5_j16**（step10，jitter 16，副线） | 66.933 | 114.446 | 8.260 / **0.043** / 56.334 | — | **约束在 NPU**：`npu` 只饿 **0.043** ms/帧 ⇒ NPU 几乎从不等特征 |

**原结论（已作废）**：旧表写「**新瓶颈 = POST**：`post` 饥饿 **56.892 ms/帧** 是最大项（C 臂同样以 post 饥饿 56.892 ms/帧 为新瓶颈），`npu` 只饿 1.535 ms/帧 ⇒ **NPU 不再是瓶颈**」——**方向反了**：

- post 饥饿 **恰恰说明 post 没活干**（它在等 NPU 的热图）⇒ 约束在 **NPU**，不在 POST；
- `npu_wait` 小 **恰恰说明 NPU 有活干** ⇒ 这是 **NPU 是瓶颈**的证据，而不是相反的证据。

**本轮实测的两条反证（把结论钉死）**：

| 反证 | 实测 | 推论 |
|:--|:--|:--|

### 6.7 GMC 双缓存：一级环 + 二级读槽 pin（**0 拷贝**）

**为什么要两级**：GMC 的单次计算要反复回读历史环的同一批帧；共享 ring 会被后写覆盖 ⇒ 静默错位。

- **插桩实测（读集 census）**：单次计算实际读取的物理帧集合**恒为** `{t} ∪ {t−2, t−4, …, t−42}` = **22 帧**（step2 与 step10 **都是 22**，不是 21/5 —— 因为 GPU 尾与 CPU 尾都无条件遍历 `lags_` 的全部 21 个 lag）。证据留档 `manu/pipeline/cpp/gmc_snapshot_census/`。
- **一级缓存（原始帧环）**：`ring_.assign(max_lag + 1 + ring_slack)`（`gmc_stream_ocl.cpp:1572`），canonical 用 **slack=1 ⇒ 44 帧**（43 + 1），640×512 B × 44 ≈ **14.4 MB**；伴随数组 `ring_id_.assign`（:1578）记录每个槽当前持有的帧号。
- **二级缓存（计算快照 / 读槽 pin）**：`snap_.resize(lags_.size() + 1)` = **22 槽**（:1586）；`build_snapshot()`（:2282）在**任何拟合之前**一次性 pin 出本次计算要读的 22 帧；`hold_snapshot_slot()`（:2301）逐槽处理；`frame_at_lag()`（:2368）改为「**快照优先，miss 回退 ring**」（快照命中分支 :2378-2379）。
- **0 拷贝的实现**：`snap_[slot] = src;`（**`gmc_stream_ocl.cpp:2339`**）——OpenCV 的 `Mat::operator=` 是**浅拷贝**，只加 refcount 并复制数据指针（**没有 `clone()`**）。producer 不写回已交出的 buffer，它只是**换掉环槽**（`ring_[s] = frame`，仅重绑指针）⇒ 快照 pin 住的像素在整个计算期间**不变**，producer 仍可自由推进环。
- **GPU 端历史缓存**：`gpu_slots_ = max_lag_ + 3`（**`gmc_stream_ocl.cpp:1580`**）⇒ **45 槽**；按**内容身份**寻址而非取模（`FusedGpu::put`，**`gmc_stream_ocl.cpp:1092`**）⇒ 命中不重传，冷启动钳位帧不会被错配。
- **回退语义**：快照查不到 ⇒ 走**原 ring 路径**（洞检测 / `nearest_older` / gap 计数全部保留），**正确性不依赖快照完整性**。
- **内存**：一级 44 帧 ≈ 14.4 MB ＋ 二级 22 槽浅引用（**不复制像素**，只加 refcount）⇒ 净增几乎为零。

**为什么深拷贝是错的工具（两次）**：

| # | 深拷贝（`copyTo`）错在哪 | 浅引用 pin 对 |
|:--|:--|:--|
| 1 | **白搬 ~7 MB/帧**（22 帧 × 320 KB）过 CPU，什么都没换来 | 只加 refcount，**拷贝成本 0.01 ms/帧** |
| 2 | **它会连同「槽位已被换帧」的错误状态一起冻结**——`copyTo` 复制的是**那一刻槽里装的东西**，槽已被换帧时它会把**错的帧**静默冻进快照，**把要暴露的问题掩盖掉** | pin 的是**帧身份**（按物理帧号校验 `ring_id_`，:2311-2318），有洞就**留空槽**回退原路径，洞照常计数 |

**拷贝成本实测对比**：

### 6.8 计算节拍（cadence）：**只改「哪些帧被算」，绝不改「帧 f 的特征由什么算出」**

**结论：cadence 是 canonical 的产能开关——它把「GMC 组速率 ≥ 相机速率」这个硬约束变成一个可调旋钮（1..8），而不是用内存去扛速率差。**

#### 7.3.1 ⭐ 算力赤字如何传回相机（代码级链条）

这是理解整件事的关键。**掉帧不是「相机太快」的错，而是「GMC 算不完」的错。**

| 环节 | 代码位置 | 发生了什么 |
|:--|:--|:--|
| 算力赤字 | `gmc_fit p50 = 49.7 ms`；`gmc_total = 71.6 ms/帧` | 单引擎 GMC 一帧要 ~72 ms，25 fps 的预算是 40 ms ⇒ 每秒缺口 ≈ 8 帧 |
| 回压传导 | `window_ok(abs)`（`mosaic_pipeline.cpp:352`），等待点 `:429` | 守卫基准是 `oldest_pending`（引擎队列**最老的待算帧**），**不是 GMC 正在算的那一帧** ⇒ INGEST 被迫**按序补算**，不能跳到最新帧 |
| INGEST 停顿 | `gmc_window_blocks = 2968`；`gmc_ingest_window = 20.9 ms/帧` | 实测：INGEST 被守卫挡住 2968 次，平均每次等 20.9 ms。停顿直接顶回相机侧 |
| 相机堆积 | `in_q` 溢出丢最老（`mosaic_pipeline.cpp:1689`） | 停顿期间相机仍按 25 fps 灌 ⇒ 64 深 FIFO 被顶爆 ⇒ 丢帧 ⇒ 物理帧号出现空洞 |
| 洞 → 精度 | `gmc_history_gaps` | 洞使 21 帧历史窗口被拉伸，特征改变 ⇒ 与无丢帧基准不再一致 |

**两种打断点**：

| 打断点 | 做法 | 代价 | 本轮选择 |
|:--|:--|:--|:--|
| **(a) 让 GMC 少算** | **cadence**：`gmc_compute_stride` 提高帧覆盖速率 | 处理的帧变少（用户口径：覆盖率不重要） | ✅ **采用**（零语义改动） |
| (b) 让 GMC 会跳步 | 守卫基准从 `oldest_pending` 改为「正在算的帧」，INGEST 可自由超前 | 要改守卫语义、会动「引擎欠账」不变式、且**环深度不够**（见下） | ❌ 本轮不做 |

#### 7.3.2 ⭐「自由跳步」（GMC 空闲时直接抓环里最新的一帧）方案的可行性算术

这个方向**是对的**，但有一个容易忽略的硬约束：**环深度**。

| 项 | 数值 | 说明 |
|:--|:--|:--|
| 历史跨度 | 42 + 1 = **43 帧** | GMC 算 f 必须同时持有 f−42 … f 共 43 帧 |
| canonical 环深 | **44 帧** | 43 帧历史 + **1 帧余量**（= `gmc_ring_slack 1`） |
| GMC 算一组的耗时 | p50 53.2 / p95 165.1 / p99 199.8 / max 249.6 ms | = `gmc_fit` + `gmc_post`（CANON5 实测） |
| 期间 producer 推进 | p50 1.33 / p95 4.13 / p99 4.99 / max **6.24** 帧 | = 组耗时 ÷ 40 ms（25 fps） |
| 所需 slack | p50 ≥ 2，p95/p99 ≥ 5，max ≥ **7** | **slack=1 的环装不下跳步所需的历史** |

GMC 跳到最新帧 f+K 时，它的新历史窗口是 f+K−42 … f+K，**最老那一帧必须还在环里**。环深 44 只比历史跨度 43 多 1 帧余量，而 GMC 算一组期间 producer 就要推进 1.3（p50）～ 6.2（max）帧 ⇒ **余量不够，窗口会被覆盖**。

要让自由跳步安全：环深需 ≥ 43 + 7 = **50 帧**（约 16 MB，仍在可接受范围），且必须处理「窗口被覆盖 ⇒ 该组作废」这一**新失败模式**。

**结论**：cadence 是**零语义改动**（GMC 仍按序补算，只是每组覆盖 N 帧）；自由跳步需要改窗口守卫语义 + 环深 44→50 + 新失败模式。**本轮选 cadence**，把自由跳步列为后续方向（§7.10）。


### 7.4 必做：物理帧号锚定常开

| 项 | 数值 |
|:--|:--|
| 依据 | 消费计数 ≠ 物理帧号 ⇒ 丢帧后 GMC 取到的历史是**错的但静默**；实测缺口检测能定位到具体帧（丢 id25 → 35 次缺口查找 / 17 帧被标记） |
| 验证 | 零丢帧时与消费计数锚定**逐帧完全一致**（惰性）；多引擎也逐位一致 |
| 配套 | 相机队列丢弃策略保持「**丢最老**」（`gmc_input_drop_policy=0`，`mosaic_pipeline.cpp:1689-1691`）：丢最新在持续过载下**延迟无界增长**，实时相机不可用 |
| 价值 | 它把「洞」从**静默错位**变成**可判定事件**——这是 §3.1 那个等式（「精度一致 ⇔ 历史完整」）能够成立的前提 |

### 7.5 必须坚持的分工：丢帧只能发生在「推理跳帧」这一层

| 队列 | 满了怎么办 | 后果 | 判定 |
|:--|:--|:--|:--|
| **相机原始队列（input FIFO）** | **绝不能让它溢出**（满了丢最老） | 丢一帧 ⇒ 该帧**永远进不了 GMC 历史环** ⇒ 21 帧历史出现空洞 ⇒ 配准链降级 | **深度上限 = 64（用户硬约束）**，**不得用深 FIFO 兜底**（§7.8）；**靠 cadence 让 GMC 组速率覆盖相机速率**来保证不溢出（§6.8） |
| **GMC 历史环** | 不许丢 | 读到被覆写像素 = 静默错误 | 靠 `gmc_ring_slack` 保证（canonical slack=1 ⇒ 环深 44 帧） |
| **Feature Queue** | 丢最老 | 只是跳帧推理，逐帧独立的推理阶段 | **可接受**（官方口径：「the inference skipping frames is fine」）；canonical 深度 3（§0.5 规格②） |

**这就是这个架构的核心设计**：解耦的收益不是「让一切变快」，而是**让不可接受的丢帧（破坏配准链）变成可接受的丢帧（跳帧推理）**。
本轮把它升级为**三级保证**：① 相机 FIFO **靠 cadence 保证不溢出**（§6.8），且深度**硬约束 ≤ 64**；② 万一还是丢了，**物理帧号锚定**把它变成**可检测**而非静默（§5）；③ **Feature Queue 是唯一被允许跳帧的层**。

### 7.7 板卡运维约束（新增）

- **e2e 调用次数是稀缺资源**：RKNPU/RGA 驱动跨进程泄漏（每次退出刷 `rga: buffer mm release buffer failed`），累积后触发 `job timeout(6s)` → `soft reset` → `rknn_init` **SIGILL** → **整机失联，必须物理断电重启**。
- **必须**：长任务打包进单个脚本；每个 e2e 调用前做 3 帧健康检查；调用之间留静置暂停；**绝不并发跑两个 e2e**（2 上下文 × 2 进程 = 4 > 硬上限 2）。
- `/mnt/srv2`（服务器 SSHFS）**重启后不自动恢复**，且板卡**没有 `mountpoint` 命令** ⇒ 检测挂载要用 `mount | grep`。

### 7.8 **已否决：深原始缓冲**（`input_queue` 64 → 8192）

**结论：深 FIFO 已被用户否决，不得再作为任何方案的一部分。**

| 否决依据 | 内容 |
|:--|:--|
| **① 用户硬约束** | **相机侧 FIFO ≤ 64 帧**。深 FIFO（1024 / 4096 / 8192）**直接违反**。 |
| **② 深 FIFO 不是解决方案** | 它只是「**用内存买洞**」：起作用的是「零洞」这个中间变量，不是「缓冲有多深」（§3.1）。零洞已有更便宜的手段（cadence，§6.8）。 |
| **③ 内存代价** | 640×512 B/帧；**1024 帧 = 327 MB**；**8192 帧 = 2.6 GB**（板卡可用 ~6.6~7.3 GB）。 |
| **④ 延迟代价** | step2 全量需缓冲约 **8900 帧 = 2.9 GB**，**追帧延迟 ≈ 24 分钟**。实时相机不可接受。 |

| 项 | 数值 |
|:--|:--|

### 7.10 后续方向（本轮范围外：需改源码或换模型）

**A. canonical 主线的瓶颈（优先级最高）**

canonical（step2 + cadence + 0 拷贝）当前的真实瓶颈**不是 NPU**，而是 **GMC 的拟合抖动**：

| 观测 | 数值 | 含义 |
|:--|:--|:--|
| `gmc_fit` p50 | **53.0 ms** | 中位数在 25 fps 的 40 ms 预算附近（单帧略超，靠 cadence 分摊） |
| `gmc_fit` p99 / max | **200.2 / 249.2 ms** | **约 4.7 倍**于 p50 ⇒ 单组尖峰期间相机多进 ~3.7 帧 ⇒ FIFO 瞬时堆积 |
| `gmc_ingest_window` | **46.4 ms/帧** | 抖动直接转化成窗口守卫的长时间阻塞 |
| `gmc_window_blocks` | **1855** | INGEST 被挡住 1855 次 |
| 结果 | dropped **34** / 3914 组（0.29%） | cadence=3 覆盖上限 37.9 fps 已高于 25 fps，但尖峰仍会击穿 FIFO；**cadence=4（覆盖上限 54.0 fps）已把溢出压到 0** |

**抖动源（已定位到源码）**：**RANSAC 消耗 OpenCV 全局 RNG**（`theRNG()`）—— `gmc_stream_ocl.cpp:338-345` 的注释明确记载：
「RANSAC consumes OpenCV's global RNG (theRNG()), so the ORDER of the fits is part of the output」，且为保 bit-exact，RANSAC 阶段必须**串行**跑（LK 阶段可以并行）。
⇒ **把 RANSAC 阶段变成可并行**（例如每个 anchor 用独立 RNG 流、且保持输出逐位不变）是最本质的下一步；它比继续加 cadence 更有效（cadence=4 已经把覆盖上限抬到 54.0 fps，掉帧归零 ⇒ 继续加 cadence 只是浪费覆盖率，**下一步应该降抖动、然后把 cadence 退回 3 少算 25% 的帧**）。

**B. NPU 侧（吞吐目标已饱和）**

吞吐目标已饱和（§6.5：NPU 线程占用 **95.4%~97.2%**，剩余空间 **≤3%~5%**），再往上走只有这三条路：

|:--|:--|:--|:--|

| 2 | 把 `rknn_run` 压到 **~100 ms** | 压 NPU 线程的串行占用（模型 / 量化层面） | 换模型 |
| 3 | 换 **INT8** 模型 | 同上 | 换模型 |

### 7.11 **已否决：A/B 乒乓块**（滑动窗口重叠断层）

**结论：不做 A/B 乒乓块。一级环保持「连续单环 + 读槽 Pin」。**

**否决理由（两条，都由结构决定，不是调参能解决的）**：

| # | 理由 | 事实 |
|:--|:--|:--|
| **① 滑动窗口重叠断层** | GMC 的 21 帧历史是**滑动重叠窗口**：算 f=122 需要 **[100,120]**，算 f=124 需要 **[102,122]** ⇒ **20/21 帧重叠**。切块后 **producer 必须跨块搬移历史帧**（块边界附近的帧在新块里还没有）⇒ **零拷贝立即失效**——而零拷贝正是 canonical 的核心收益（§6.7：拷贝成本 0.01 ms/帧）。 | 读集实测恒为 `{t} ∪ {t−2…t−42}`（§6.7，census 留档 `manu/pipeline/cpp/gmc_snapshot_census/`） |
| **② 批处理延时** | 切块天然要求「等一块填满才能算」：一块要装下 **42 帧**（max_lag+1）⇒ **42 帧 × 40 ms ≈ 1.68 s** 的闭环延时。这直接违反用户裁定「**不能等 buffer 满了才开始计算**」（随到随算，无攒批门槛）。 | 42 × 0.040 s = 1.68 s |

**「随到随算」在代码里的体现**：引擎拿到 job 立刻 `process_frame`；`gmc_job_depth` 是**背压上限，不是攒批阈值**（§6.8）。端到端延时的实测（§6.9）就是用来证伪「攒批设计」的那个数——**CANON5 已给出该数**（p50 323.6 ms，pace 0 工况），**它不含 1.68 s 的攒批台阶**（那个台阶若存在，p50 会是 ~1700 ms 量级）。

**替代方案（canonical 采用）**：**连续单环 + 读槽 Pin**——一级 `ring_`（44 帧）连续滚动，producer 永不搬帧；GMC 计算时用二级 `snap_` 的**浅引用** pin 出自己需要的帧（`snap_[slot] = src`，`gmc_stream_ocl.cpp:2339`）⇒ **既零拷贝、又不攒批、又是单环**。
