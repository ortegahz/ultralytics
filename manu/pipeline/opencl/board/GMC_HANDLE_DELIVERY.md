`--fit-deadline-ms` 从头到尾都默认关闭，理由是「墙钟判据会让输出随机器负载变化，
破坏位可复现契约」。此前这是**纯论证**。现在是**实测**：

- 满载小核干扰下，p99/max **零劣化**；
- 因此看门狗在这类干扰下**不会救任何一帧**，只会因噪声误触发；

## 2. `--pin-pad`：handle A 的补全，以及一个被板卡推翻的成本估算

### 2.1 为什么需要它

arm D 已经把预分配做到位（`devrealloc` 五序列全 →1），**VIDEO00034 仍以 43.16 ms 超线**。
逐帧分解（`board/v34_forensics.py`）：

```
img_up p50 1.56 / p99 16.47 / max 31.06，2..10 ms 区间【一帧都没有】
296/300 帧 < 2 ms，2 帧 > 20 ms；最坏帧仍是 frame 169
```

**这是离散事件，不是长尾。** 成因在源码注释里（`gmc_stream_ocl.cpp:876-879`）：

> *"pad_ is shared state: the moment it grows, the resident frames are at the
> **WRONG offset** and must be dropped and re-uploaded, **even when the
> allocation itself does not change**."*

`pad_` 增长 → 45 个驻留槽位整体作废 → 整批重传。这条路径不经过重分配分支，
**所以 `devrealloc=1` 根本没测到它**。预分配消除的是分配事件，尖峰来自环形失效事件。

### 2.2 实现

`--pin-pad 1` 让 `bucket = max(bucket, quantise_pad(prealloc_cap_))`，
`pad_` 从第一帧就等于上限、永不增长 ⇒ `pad_grew` 恒假 ⇒ 环形永不失效。

### 2.3 源码里那句成本估算被板卡推翻了

原注释（`gmc_stream_ocl.cpp:867-871`）写：

> *"Uploading the whole allocation would scale H2D by cap/bucket (**32x** at cap 1024
> vs bucket 32) and trade a 41 ms spike for a **permanent tax**."*

板卡实测：

| pad | 上传字节 | img_up p50 |
| --: | --: | --: |
| 32 | 0.405 Mpixel | **0.37 ms** |
| 512 | 2.555 Mpixel | **1.56 ms** |
| 1024 | 6.881 Mpixel | **2.45 ms** |

**17× 的字节只换来 6.6× 的时间**——H2D 路径带宽饱和、固定开销占主导。
所谓"permanent tax"实测是 **~2 ms**，不是 32×。**只有板卡能给总线定价。**

⇒ 实测代价 `VIDEO00002 +1.50 ms`，换取 `VIDEO00034 −28.81 ms`，且 `img_up` 全序列
统一到 2.44–2.46 ms。**这是一笔明显划算的交易，原注释据此更正。**

### ⚠️ 关于 x86 耗时：本次新发现，报告此前未记录

x86 上的 OpenCL 是

```
[OCL] platform : Portable Computing Language (OpenCL 3.0 PoCL 6.0+debian, LLVM 18.1.8, ...)
[OCL] device   : cpu-haswell-Intel(R) Core(TM) i5-10500 CPU @ 3.10GHz
[OCL] image fmt : CL_RGBA (4 byte/px, PoCL fallback)
```

板卡是

```
[OCL] platform : ARM Platform (OpenCL 3.0 v1.g13p0-01eac0...)
[OCL] device   : Mali-G610 r0p0
[OCL] image fmt : CL_R    (1 byte/px)
```

**x86 的"GPU 臂"是 PoCL 在 CPU 上模拟的 OpenCL**，而且像素格式都从 `CL_R`（1 B/px）
退化成 `CL_RGBA`（4 B/px）。实测 x86 每帧 110–245 ms，两臂全部 300/300 帧超 40 ms。

⇒ **x86 耗时数字不能作为板卡延迟的任何代理**，之前的「x86 比率套板卡绝对值」
这类迁移方式在这台机器上尤其站不住。本轮 x86 只用于**计数**与**精度**，
耗时一律只报板卡实测。

  ```cpp
  ++n_reconfigure_;                                                        // 否则重分配
  ```
  即：**只有当所需分配 > 已分配时才重分配**。开启预分配后 `want_alloc` 恒 ≥ `quantise_pad(N)`，
  启动时一次性建到该尺寸，运行期 `bucket` 再大也不超过它 ⇒ **运行期重分配恒为 0**。
- **计数**：`devrealloc` = `n_reconfigure_`
- **副作用（必须知道）**：`pad_grew`（`bucket > pad_`）时清空驻留槽位
  （`slot_key_.fill(kNoKey)` + `key_to_slot_.clear()`）。因为槽内帧按上传时的 `pad_` 偏移定位，
  `pad_` 变了旧槽就不能复用。**这一条曾导致一个逐帧 MD5 抓不到的 GPU 臂真 bug**
  （一致率 46.55% → 12.86%），当时因漏清槽位而未发生。

#### Handle B —— 角点预算 `--fit-corners N`
- **代码位置**：`gmc_stream_ocl.cpp:510-526`（`detect()`）
- **触发条件**（精确，非估计）：
  ```cpp
  cv::goodFeaturesToTrack(small, all, max_corners_ + 1, 0.01, 4, cv::noArray(), 3);
  if (static_cast<int>(all.size()) > max_corners_) {
      ++n_corner_capped_;
      n_corner_dropped_ += static_cast<long>(all.size()) - max_corners_;
      all.resize(static_cast<size_t>(max_corners_));
  }
  ```
  多要 1 个点，**命中即精确判定**，不是采样估计。
- **计数**：`cornercap=<帧>f/<调用>calls(<丢弃>pts)`
  - 帧口径：`n_corner_cap_frames_`，在 `push()` 内 `gmc_stream_ocl.cpp:1457-1458`
    按「本帧内计数是否增长」累加；
  - 调用口径：`n_corner_capped_`，每次 `detect()` 调用。
- **前置条件**：仅在 `--corner-probe 1`（默认）时计数。关掉探针则**完全不计数**，
  所以普查数据必须在探针开启下采集。

#### Handle C —— 墙钟看门狗 `--fit-deadline-ms F`（**默认关闭**）
- **代码位置**：`gmc_stream_ocl.cpp:1388-1420`（anchor 循环）
- **触发条件**：每个 anchor 拟合**之前**检查本帧已耗时，
  `spent > fit_deadline_ms_` ⇒ `blown = true; break;`（**整帧退化**，不是跳过当前 anchor）
- **退化动作**：
  - `--fit-degrade hold` ⇒ 复用**最后一个成功拟合的帧**的 `last_mats_`
  - 否则（含无可复用时）⇒ `IDENTITY`
  - **注意**：连续退化时 `hold` 会坍缩成 `identity`（没有"成功的帧"可 hold），二者不可区分。
- **计数**：`fitdeadline` = `n_fit_deadline_`

### 交付决策：`--prealloc-pad` 保持全局 1024（2026-10-12 裁决）

量化过全局 1024 的代价（`board/prealloc_memory_cost.py`，
几何取自源码：`quantise_pad` 按 2 的幂向上取整 `:833-839`、`gpu_slots_ = max_lag+3 = 45` `:1266`
（与横幅 `ring slots=45` 一致）、板卡 `CL_R` 1 B/px）：

| 序列 | 实测 devpad | 现状 MiB | @prealloc1024 | 差额 | 倍数 |
| :-- | --: | --: | --: | --: | --: |
| VIDEO00034 | 512 | 109.7 | 295.3 | +185.6 | 2.7× |
| VIDEO00028 | 1024 | 295.3 | 295.3 | 0 | 1.0× |
| VIDEO00032 | 1024 | 295.3 | 295.3 | 0 | 1.0× |
| VIDEO00002 | **32** | **17.4** | 295.3 | **+277.9** | **17.0×** |
| VIDEO00036 | 128（带角点预算时 512） | 109.7 | 295.3 | +185.6 | 2.7× |

**裁决：保持全局 1024 不变。**

理由，不是「余量充足所以无所谓」，而是按序列下发会**把交付保证本身换掉**：

- `want_alloc = max(bucket, quantise_pad(prealloc_cap_))` —— cap 只是**下限**，
  不是上限。所以按序列下发（取实测 devpad）在本语料上确实能做到运行期零重分配，
  省下 186–278 MiB，VIDEO00002 降到 21.1 MiB。
- 但预分配的全部意义是**分配决策发生在第一帧之前**。按实测最大值钉死 cap，
  等于把「语料外的视频也可能需要更大 pad」这件事从保证里删掉，拿它换一块
  这块板子可能并不需要的显存。
- 而这块板子的余量**从宿主侧测不出来**：Mali 设备内存在 `/proc/meminfo` 里不体现，
  `bench_run.sh` 的头注记着一次运行在 `MemAvailable` 还有 7.4 GiB 时被 SIGKILL
  （`file-rss:7623308kB`）。**测不到的头寸只能预留，不能赌。**

因此保留保守值。这条代价是**已量化的、已知的、被接受的**，不是未知风险。
