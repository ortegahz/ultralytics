## 1. 计时账本：为什么是这六段

六段取自硬件真实边界且两两相邻，`Σ各段 ≡ total` 由构造保证，每帧独立校验。
**修复后残差 mean 0.034 ms / max 0.051 ms**（占端到端 0.3%）⇒ 账本铺满，无隐藏成本。

| 段 | 内容 | 归属 |
| :-- | :-- | :-- |
| 0 | 帧解码（eMMC 读 BMP + 灰度解析） | CPU + 存储 |
| 1 | 环形缓冲推入 / 形状准入 | CPU A76 |
| 2 | GMC 拟合：Shi-Tomasi + LK + RANSAC + 有界链式复合 | CPU A76 ×4 |
| 3 | **图像上传 H2D**（`configure()` 可能重分配 + `copyMakeBorder` + 最多 22 次 `clEnqueueWriteImage(CL_TRUE)`） | 总线 / Mali |
| 4 | 21 个仿射矩阵上传（504 B） | 总线 / Mali |
| 5 | 融合内核：manual 2×2 warp + 21 帧无分支中值 | Mali-G610 |
| 6 | 三通道回读（`clEnqueueReadBuffer` ×3） | 总线 / CPU |

> **段 3 的边界在修复中被移动过一次**：原本 `configure()` 落在所有标记之外，
> 它的重分配表现为一条 41 ms 的无归属残差 —— 只在残差里可见，任何单段都看不到，
> 这正是缺陷藏身的方式。现在 `p0` 打在 `configure()` 之前。

**OpenCL 异步陷阱**：本驱动不接受 `CL_QUEUE_PROFILING_ENABLE`
（`clCreateCommandQueueWithProperties` 返回 `CL_INVALID_VALUE`，且 `clCreateEvent` 未声明），
故 kernel 段采用「入队 + `clFinish`」并把墙钟归给 kernel；入队是微秒级且回读在其之后。

**分位数方法**：最近秩，不插值 —— 每个 P99 都是某帧真实发生过的值。

### 3.2.1 超 40 ms 帧普查 —— p99 会掩盖「迟到的频率」

分位数回答「尾部有多糟」，**不回答「有多常迟到」**。在本语料上这两者恰好给出相反的重点，
所以必须直接数帧（`board/breach_census.py`，从原始 CSV 重算）：

| 序列 | 帧数 | 稳态帧 | 超线（全序列） | **超线（稳态）** | 稳态超时率 | p99 | max |
| :-- | --: | --: | --: | --: | --: | --: | --: |
| VIDEO00002 | 400 | 300 | 0 | **0** | 0.0% | 16.62 | 16.82 |
| VIDEO00028 | 400 | 300 | 3 | **0** | 0.0% | 17.97 | 18.28 |
| VIDEO00032 | 400 | 300 | 3 | **0** | 0.0% | 30.37 | 31.60 |
| VIDEO00034 | 400 | 300 | 1 | **1** | 0.3% | 19.52 | 53.50 |
| VIDEO00036 | 400 | 300 | 27 | **20** | **6.7%** | 42.88 | 43.09 |
| **合计** | 2000 | 1500 | 34 | **21** | 1.4% | | |

四条结论，每一条都改变处置方式：

1. **`VIDEO00036` 是持续性超标，不是尖峰。** 稳态 300 帧里 **20 帧**超线（**6.7%**）。
   对 25 FPS 交付而言，这意味着**每 15 帧就有 1 帧掉到 25 FPS 以下**——
   这不是尾部问题，是常态产能问题。
2. **`VIDEO00034` 相反：只超 1 次**（0.3%），且那 1 帧就是设备重分配尖峰。
   ⇒ 它属于「预分配」能干净解决的类型（§5A.1）。
3. **`VIDEO00028` / `VIDEO00032` 各有 3 帧超线，但全部落在预热窗口内**，
   稳态 0 帧。这是 Mali JIT 与上下文构建的一次性成本，**不是稳态属性**，
   不应计入交付考核（但冷启动本身仍值得单列，见 §7）。
4. **只看 p99/max 会看错重点**：最近秩 p99 把 `VIDEO00034` 那唯一一帧 53.50 ms
   排除在 p99 之外（p99 = 19.52 → PASS），而 `VIDEO00036` 的 42.88 ms 刚好压在 p99 上。
   单看这张 §3.2 表会以为「34 是小问题、36 是尾 问题」；
   数帧之后才知道 **36 才是主要矛盾**。这也解释了为什么修复路径必须是
   「34 用零代价的预分配、36 才动角点预算」，而不是一刀切。

### 3.3 设备内存（修复后）

`devpad` 上界 1024（= `kMaxPadDevice` 兜底），最坏设备图像
`(640+2048) × (512+2048) = 2688 × 2560` = 6.9 Mpixel/槽 × 45 槽 ≈ **310 MB**，
且**实际未触及**兜底（越界告警 0 条）。修复前为 106 Mpixel/槽 × 45 ≈ 4.8 GB。

## 5. 缺陷与修复

### 5.1 现象（修复前）

板卡在 400 帧处被 OOM killer 杀死：`total-vm:7930788kB, anon-rss:60792kB, file-rss:7623308kB`
—— **7.6 GB 是 file-backed RSS，匿名内存仅 60 MB**。
`/proc/PID/smaps` 在 `VmRSS` 报 5065 MiB 时所有映射加起来只有约 147 MiB
（`[heap]` 65 MiB、`[anon]` 40 MiB、`libmali` 35 MiB，共 205 个映射）。
宿主侧分配全程平坦（ring 13.44 MiB、cache 25.5 MiB 不变）
⇒ 增长全在 **Mali 驱动不计入 `/proc/meminfo` 的设备内存池**。

工程后果：**等内存指标再跑永远无效**（`MemAvailable` 全程 7.4 GiB 而驱动照样 OOM），
必须**退避重试**。

### 5.2 根因

`FusedGpu::configure()` 只增不减（"allocate at the largest pad seen so far"），
而 `required_pad` 追踪的是**全序列历史最大相机位移**：
实测 `devpad` 2 → 313 → 3551 → 4863，单序列内单调增长，
644×516（上传 0.18 ms）→ 7742×7614（上传 42 ms），最终 106 Mpixel/槽 × 45 ≈ 4.8 GB。

### 5.3 这不是数值发散 —— 一次被实测推翻的假设

最初假设「GMC 拟合在业务域发散」。**实测推翻并撤回**：
`--mats-all` 显示尺度 `sqrt(det)` 全在 0.995~1.004；相邻帧平均绝对差 0.5~1.4 灰阶、
最大 2.59，5 序列逐帧扫描零尖峰（无场景切换）；lag2 直接拟合稳定在 1.4~5.7 px。
⇒ 这是一条**持续的真实相机横摇**（~1.5~1.8 px/帧），拟合是对的。

### 5.4 修复（三层，越往下越关键）

1. **拟合合理性闸门**（`check_fit`）—— 在 `fit_similarity` 中拒绝
   「平移 > 1.0 帧宽」或「尺度 ∉ [0.5, 2]」的**有限但离谱**的拟合，
   该帧退化为 `W(.) = IDENTITY`（即 A/B 对照已验证的对照臂），
   并计入 `n_fit_rejected`。选 IDENTITY 而非夹紧的理由：夹紧仍是错的 warp，
   而 IDENTITY 让下游时域中值吸收单坏帧，且拒绝是**可计数、可上报的显式事件**。

2. **角点范围闸门**（同一函数内）—— 只限平移和尺度**各自**是不够的：
   `required_pad` 取决于二者**之积**。实测「尺度 2.0 + 平移 640 px」的变换
   每一项都合法，却把角点送到 ~1980 px、需要 ~1340 px padding。
   故改为直接约束**角点位移**（仿射极值必在角点，4 点求值是精确的）。
   加这一层后越界告警 4 → 2。

3. **逆矩阵闸门** —— `required_pad` 消费的是**逆**变换，kernel 采样的也是逆变换。
   正向尺度 0.5 正好在下界，但它的逆是 2.0，角点范围翻倍。
   只闸正向仍漏 2 帧；闸逆向后 **告警归零**。

### 5.5 修复过程中被实测否掉的两个方案（记录在此以免重犯）

| 方案 | 实测结果 | 机理 |
| :-- | :-- | :-- |
| `configure()` 允许**收缩**，乘性迟滞带 `[0.7×, 1.4×]` | 上传段 60.9 ms 尖峰、41 ms 无归属残差 | `required_pad` 是 21 个 lag 的当前最大值，会波动；收缩给波动留了振荡空间，每次振荡都重分配 45 张图 |
| `configure()` 收缩 + **幂次量化**到 2 的幂 | 33~400 次重分配/400 帧（最坏逐帧重分配） | 量化只减少**边的数量**，不消除边上的振荡 |

**最终采用：仍然只增不减**，但
(a) 幂次量化（把连续增长变成分级增长，整序列约 6 次重分配，实测 1~6 次），
(b) 上界由**拟合闸门**提供，而不是靠运气。

原注释说"grow-only 是对的"，这句话本身没错 —— **错的是 grow-only 之上没有变换上界**。

### 5.6 尚可继续优化（按性价比）

1. **消除 `VIDEO00034` 的 41.6 ms 尖峰**：全序列 5 次重分配，稳态窗口内 4 次
   `img_up` > 10 ms，最坏 frame 169 = 41.56 ms。
   两条可选做法（都确定性、都不改输出）：
   - *上移 bucket 预留余量*：按 `need * 1.5` 量化，最多 2 倍内存换零重分配。
   - *启动期一次性预分配到上界*：按 `kMaxPadDevice` 建一次图像对象，运行期只改
     `pad_` 与 kernel arg。**必须保持上传 region = pad 后的实际尺寸**
     （现为 `gmc_stream_ocl.cpp` `put()` 中 `r[3] = {padded.cols, padded.rows, 1}`），
     否则 H2D 量会按上界放大而非按需求，代价远超收益。
     几何安全性已核实：`pad_` 经 `clSetKernelArg(kWindow + 5)` 下发给 kernel，
     故 buffer 大于需求时多余尾部既不读也不写。
     代价：最坏设备图像 2688×2560 × 45 槽 ≈ **310 MB**（§3.3）。
2. **`VIDEO00036`（400 角点）真实超标**：GMC 拟合 p50 28.185 ms，占该序列 33.365 ms 的 **85%**。
   ✅ **收益已实测**（§5A.3）：`--fit-corners` 是弱杠杆，600→200 只省 **33.0%** 的 fit，
   而先前跨序列回归外推的 56% 乐观了 1.7 倍。投影 p99 42.88 → 30.46 ms，进 40 ms 有余量。
   ⚠️ 投影比值来自 x86，**板卡验收仍须实测**。
3. **搬运去阻塞**：22 次 `clEnqueueWriteImage(CL_TRUE)` 改非阻塞入队 + 一次 `clFinish`。
   现在 img_up 已只占 7.3%，收益有限，但尾延迟仍受益。

### 5.7 一条**不建议**做的改动：运行期墙钟看门狗

有人提出「fit 超时即熔断，跳过 LK 并以 `M_t = M_{t-1}` 恒速外推替代 `W(.) = IDENTITY`」。
本报告**不建议**采纳，理由是实测而非偏好：

1. **它防的场景没出现过。** 被防的是「系统抢占导致计算路径超时」。
   **2026-10-12 用交付配置复测了这个场景**（arm JB，实验 B）：小核 CPU0-3（A55）挂满载
   自旋（`### background load on cpu0-3 pid(s): 36846`，governor `performance` @2352 MHz），
   流水线钉在 A76 cpu4-7。

   | 序列 | 干净 p99/max | **满载 p99/max** | 差异 |
   | :-- | :-- | :-- | :-- |
   | VIDEO00034 | 14.51 / 14.82 | **12.84 / 13.35** | −1.67 / −1.47 |
   | VIDEO00028 | 18.22 / 18.45 | **16.56 / 16.65** | −1.66 / −1.80 |
   | VIDEO00032 | 30.32 / 31.85 | **30.14 / 31.44** | −0.18 / −0.41 |
   | VIDEO00002 | 19.10 / 19.21 | **19.00 / 19.28** | −0.10 / +0.07 |
   | VIDEO00036 | 24.19 / 24.45 | **24.44 / 24.65** | +0.25 / +0.20 |
   | **超 40 ms 帧** | 0 / 1500 | **0 / 1500** | — |

   **全部差异落在板卡噪声底噪 0.07–0.55 ms 之内**，两个序列甚至略快。
   ⇒ **干扰没有造成可测量的劣化**，看门狗在这类干扰下不会救任何一帧，
   只会因噪声误触发。而误触发按设计会把输出变成负载相关的。
   本条理由此前是纯论证，现在有实测。
2. **它会把输出变成「随机器负载变化」。** 现有闸门只看**几何合理性**
   （位移/scale/角点范围/逆矩阵），纯函数、对负载免疫 ⇒ 同一输入在任何负载下
   给出同一输出。换成墙钟判据后，**同一段视频在空闲板与满载板会给出不同结果**，
   而「可复现」是本项目的交付前提（§6.1 的零回归对账全部依赖它）。
3. **叠加既有的线程非确定性会更糟。** `gmc_stream_ocl.cpp:60-61` 已注明
   *多 OpenCV 线程下 RANSAC 与 LK 非位可复现*，而基准跑的是 `--threads 4`。
   实测印证：`FIX4` 与 `FIX5` 闸门计数完全相同（65/2436、87/2436），
   但 `VIDEO00028` / `VIDEO00032` 的 `[SEQ]` md5 不同（`e1669f…` vs `e07313…`、
   `861c65…` vs `e664ed…`），而未触发闸门的三个序列 md5 完全相同。
   ⇒ 病态序列的输出本就对线程调度敏感，**再叠一个负载耦合的分支，会让可复现性无从谈起**。
4. **`M_t = M_{t-1}` 并不比 IDENTITY 更接近真值。** 它只是把「一帧静止」
   换成「一帧按上一帧速度匀速外推」。二者都是错 warp，差别是量级而非有无。
   真正能证明优劣的是业务侧 F1 差异，即 §7 的未验证项 —— 在测出来之前，
   把 IDENTITY 换成外推是**用未测量的假设替换已论证的选择**。

> 结论：若确需抗超时应走**确定性**路线（预算角点数、预算金字塔层数、
> 固定上限预分配），而不是墙钟熔断。

## 5A. 40 ms 硬保证：三个特殊 handle（实现 + 已验证部分）

为把「每帧 ≤ 40 ms」从观测变成保证，实现三类**可计数**的 handle。
三者共用一条上报口径：`[SEQ]` 行尾的 `[HANDLE]` 计数块，一行读完触发次数。

| handle | 机制 | 输出是否改变 | 默认 |
| :-- | :-- | :-- | :-- |
| **A 预分配** | `--prealloc-pad N`：设备图像一次性按 `(W+2N)×(H+2N)` 建好，运行期只涨 `pad_`，永不重建 | **否**（逐位相同） | 关（`N=0`） |
| **B 角点预算** | `--fit-corners N`：超过 N 个角点的帧按响应截断，**逐帧精确计数** | **是**（见 §5A.2） | 600（冻结值） |
| **C 墙钟看门狗** | `--fit-deadline-ms F`：单帧拟合超 F ms 即放弃剩余 anchor，整帧退化 | **是**，且**随负载变化** | **关** |

### 5A.1 关键设计：分配范围与实际 pad 解耦

`pad_` 有两个身份——`copyMakeBorder` 的边宽、以及 kernel 定位内容的偏移。
它必须**单调不减**：驻留槽位里的帧是按上传当时的 `pad_` 放进去的，
`pad_` 一变，缓存帧的偏移就全错了。

预分配只解耦**分配范围**，不碰这条不变量：

```
want_alloc = max(quantise(need), prealloc_cap)      // 分配多大
pad_       = max(pad_, quantise(need))              // 实际用多大（只增不减）
上传 region = (W + 2*pad_) × (H + 2*pad_)            // 仍按 pad_，不是按 want_alloc
```

上传 region 若改成按分配范围，H2D 会放大 `cap/pad_` 倍（1024 vs 32 时 32 倍），
把一次 41 ms 尖峰换成永久税。

**这里实测抓到一个 bug，且逐帧 MD5 抓不到它。** 首版预分配让 `pad_` 增长时
不再清空驻留槽位，于是「槽内帧按旧 `pad_` 偏移、kernel 按新 `pad_` 采样」。
CPU 臂根本不碰设备图像，**MD5 100/100 一致**，但 GPU-vs-CPU A/B 一致率
从 **46.55% 掉到 12.86%**。

⇒ **零回归协议已加固**：现在必须同时比对 **CPU 臂逐帧 MD5** 与
**GPU 臂 A/B 六个一致率数字**。前者只证明 CPU 路径，后者才证明设备路径。

修复后（`--prealloc-pad 1024`，x86，2 序列 × 50 帧，`--fused both`）：

| 配置 | CPU 臂逐帧 MD5 | GPU 臂 A/B exact%（Ch0/Ch1/Ch2 逐序列） | devrealloc |
| :-- | :-- | :-- | :-- |
| 改造前二进制 | — | 100.0000 / 99.9132 / 99.6424 / 46.5467 / 49.7575 / 55.6855 | 4 |
| 新二进制，默认关闭 | **100/100 一致** | **六个数字完全相同** | 4 |
| 新二进制 `--prealloc-pad 1024` | **100/100 一致** | **六个数字完全相同** | **1** |
| 新二进制 `--corner-probe 0` | **100/100 一致** | **六个数字完全相同** | 4 |
| 新二进制 `--fit-deadline-ms 15 --fit-degrade hold` | **100/100 一致** | **六个数字完全相同** | 4（触发 0 次） |

预分配把设备重分配**在全部五个序列上**收敛到 **1 次**（仅启动那次），
CPU 侧状态字节不变（13.44 MiB）。

> **2026-10-12 扩充**：早先这里只报了 VIDEO00028 一个序列（4 → 1）。
> 本轮补齐五序列 A/B 对照（`board/x86_evidence_regen.sh timing`，
> 产物 `board/.bench_out/REGEN/{A,B}/`）：

| 序列 | A: devrealloc（基线） | B: devrealloc（`--prealloc-pad 1024`） | A: devpad | B: devallocpad |
| :-- | --: | --: | --: | --: |

这是 `configure()` 里 C++ 侧的**计数器**，与架构无关，因此可迁移到板卡。
「运行期重分配恒为 0」这条交付断言现在有五序列证据，而不是单序列。

⚠️ **同时发现一个副作用**：VIDEO00036 在施加角点预算后 `devpad` 从 **128 变成 512**。
角点预算改变了变换估计，进而改变了所需 padding。预分配把 `devallocpad` 顶到 1024
换来了重分配归零，**代价是显存占用上升**。这一条此前未记录，需业务侧确认可接受。

#### 预分配能把 VIDEO00034 拉回 40 ms 吗 —— 移除实测事件，而非迁移比率

§5A.3 的投影靠「x86 比率套板卡绝对值」，而 x86 与 A76 不共享内存系统，这种迁移本来就弱。
**预分配这一条不需要这种迁移**：被删掉的是 trace 里**逐帧定位到的重分配事件本身**，
其余各段一个字节都不动。所以直接做反事实——只从发生尖峰的帧上减去实测到的上传超额。

VIDEO00034，300 稳态帧（warmup 100 已丢）：

| | p50 | p95 | p99 | max | 超 40 ms 帧数 |
| :-- | --: | --: | --: | --: | --: |
| **实测**（闸门版） | 10.67 | 12.10 | **19.52** | **53.50** | **1** |
| 反事实·紧（只减 p95 以上的超额） | 10.67 | 11.98 | 12.49 | **13.04** | **0** |
| 反事实·松（减 p50 以上的全部超额） | 10.65 | 11.98 | 12.47 | **13.02** | **0** |

**两条边界情形几乎重合**（p99 差 0.02 ms，max 差 0.02 ms），所以结论不依赖
「上传超额里有多少该归给重分配」这个判断。原因是 `img_up` 极度双峰：
**p95 = 1.097 ms，max = 41.562 ms**，中间几乎没有过渡，地板取 1.078 还是 1.097 无关紧要。

⇒ 预分配一旦生效，VIDEO00034 的 **max 53.50 → ≈13.0 ms，5 个序列里的第 4 个进 40 ms**，
只剩 VIDEO00036 需要靠角点预算。残留超线只可能来自 fit 或 kernel，
而 trace 显示这两段分别平在 5~7 ms 与 ~4 ms，不具备越线条件。

> ⚠️ 这仍是**反事实**，不是实测：它依赖一条因果断言「上传尖峰就是重分配」。
> 支撑该断言的证据是 `devrealloc=5` 与稳态内 4 帧 `img_up` > 10 ms 的数量吻合，
> 且这些帧的 `img_up` 高达 41.56 ms 而 p50 仅 1.078 ms。
> 复现：`board/v34_prealloc_counterfactual.py`

1. **`--pyr-cache` 把每帧 ~6.1 次 `detect()` 压到 ~1 次**（398 vs 2436），

2. **`--pyr-cache` 对输出是位中性的** —— 四组对照的输出 MD5 **完全相同**。
   它只改检出节奏，不改角点集合。这独立佐证了 §5A.1 的零回归结论。
3. ⚠️ **板卡会报 ≈170，不是 306**（`bench_run.sh` 传了 `--pyr-cache`）。
   把 306 当作板卡预期触发数是错的；引用触发数必须同时声明缓存口径。

**角点数与 `pick_sequences.py` 采样值的关系（400 帧，未截尾）**：

| VIDEO00028 | 60.6 | 73.7 | **0.8×**（采样反而偏高） |
| VIDEO00032 | 221.3 | 170.6 | 1.3× |
| VIDEO00002 | 1056.3 | 336.4 | 3.1× |
| VIDEO00036 | 1566.5 | 400.0 | 3.9× |

⇒ 两者**连方向都不一致**（VIDEO00028 是 0.8×）。`pick_sequences.py` 的值可以用来**排序**
（它当初就是为了选序列），**但绝不能当作角点数引用**。本报告所有角点结论均以流水线实测为准。

#### 本表推翻了本报告的一个早期结论

**早先的 40 帧版本错了，而且错了两次，两个方向都相反**：

| 序列 | 40 帧版本（已作废） | 400 帧实测 | 错在哪 |
| :-- | :-- | :-- | :-- |
| VIDEO00032 | 「逐位不变」 | Ch1 max **68** / Ch2 max **48** | **样本不足**：它 306/400 帧才截断，前 40 帧几乎没截 |

第二个错误的成因值得单独记下，因为它正是本项目写过纪律要防的那类错误：
聚合脚本用 awk 的**字符串**比较取最大值，而 `"51" < "6"` 在字典序下为真。
**凡是出现两位数的序列，报出的「最大偏差」都是错的**，而且错得没有任何征兆。
已改为显式数值比较，并额外记录最大值出现在第几帧以便回查
（`board/npy_diff_summary.sh`）。已交付的 §6.2 不受影响 —— 那些数字来自 C++
`minMaxLoc`，本来就是数值比较。

⇒ **「零观测 ≠ 不存在」这条纪律，这次是我自己踩的**：一个 40 帧样本
同时给出了「过于乐观」和「过于悲观」两个方向相反的错误结论。

#### 三条可用结论

1. **Ch0 在全部 5 个序列、全部 2000 帧上位精确**（max 0，100.0000%）。
2. **VIDEO00034 / VIDEO00028 零触发、逐位不变**（实测角点 85.1 / 60.6，均低于预算），
   handle B 在这两个序列上**零代价**。
3. **代价与「是否真的需要提速」不成比例 —— 这是本节最关键的一条**：
   - `VIDEO00002` 每帧都截断，代价却只有 Ch1 max 6 / Ch2 max 5（均值 0.008 / 0.034）；
   - `VIDEO00036` 每帧都截断，代价 Ch1 max 59 / Ch2 max 39（均值 0.61 / 0.64）—— **它需要提速**；
   - `VIDEO00032` 只有 306/400 帧截断，代价却是全表最大的 Ch1 max **68** / Ch2 max **48**，
     **而它的板卡 p99 只有 30.37 ms，本来就不需要提速**。

⇒ **角点预算不应当全局一刀切。** 给一个已经达标的序列降预算，
是用真实的精度代价换一件它并不需要的东西。正确形态是**按序列设定预算**，
或至少把全局档位抬到 VIDEO00032 不触发的水平（见 §5A.4）。

> ⚠️ 本表为 **x86 CPU 臂**；板卡 GPU 臂口径待补（§7）。板卡角点检出数预计与本表
> 同量级但未逐帧核验，**验收以板卡实测为准**。复现：`board/corner_budget_full.sh`。

### 5A.2b 角点普查能否迁到板卡：SIMD 敏感性实测

板卡是 NEON，宿主是 SSE/AVX。IPP 这条嫌疑已排除（§7），剩下的就是**向量宽度不同导致的浮点舍入**。
OpenCV 的 `OPENCV_CPU_DISABLE` 可以在**不改二进制**的前提下强制走标量路径，于是这件事可以在
x86 上直接测：

| 序列 | SIMD on | SIMD off | 相同 | 交付预算下的触发帧 |
| :-- | :-- | :-- | :--: | --: |
| VIDEO00036 | **1250.5** / 936 dets | **1250.5** / 936 dets | ✅ | 400/400 |
| VIDEO00002 | **1053.1** / 936 dets | **1053.1** / 936 dets | ✅ | 400/400 |
| VIDEO00034 | **87.1** / 936 dets | **87.1** / 936 dets | ✅ | 0/400 |

⇒ **角点检出数对向量宽度不敏感**，所以 `[HANDLE] cornercap` 的触发计数应当可以迁移到板卡。
同时输出 md5 在两种模式下**不同**（仅 VIDEO00036），与 §6.3 一致：
跨架构只能用逐像素计数判定，MD5 从来就不成立。

> **边界**：这证明的是「计数不受 SIMD 影响」，**不是**「aarch64 会给出同一个数」。
> 板卡仍是唯一权威。

#### 一个必须记下的测量陷阱

第一版这个实验用**交付预算 200** 跑，两次都报 `mean = 200.0`，一模一样——
但那是因为值被**截尾**了：真实计数 ≥201 被削到预算值，根本不可观测。
**比较两个都被削平的数据等于什么都没比。** 预算必须高于真实计数（本例 ~1250）才有意义。

#### 顺带更正一个量级错误

流水线真实角点数（预算 5000 下测得）与 `pick_sequences.py` 的采样值差距约 **3 倍**：

| 序列 | texture.tsv 采样值 | 流水线实测（SIMD 无关） | 倍数 |
| :-- | --: | --: | --: |
| VIDEO00036 | 400.0 | **1250.5** | 3.1× |
| VIDEO00002 | 336.4 | **1053.1** | 3.1× |
| VIDEO00034 | 44.3 | **87.1** | 2.0× |

这解释了为什么预算 600 时 `VIDEO00002`/`VIDEO00036` 是 **400/400 帧全触顶**：
它们本来就远超 600，不是「刚好压线」。**引用角点数必须带口径**，这句话现在有了具体数字。

复现：`board/simd_corner_portability.sh <sequence>...`

### 5A.3 角点预算能省多少 fit：受控实测（替代 R²=0.706 的外推）

§5.6 第 2 条曾用跨序列回归外推「cap=200 → fit 12.34 ms」。那个外推**被实测推翻，
而且乐观了约 1.7 倍**。

外推的问题是混淆：跨 5 个序列比较时，逐序列 LK 难度和角点数一起动，
fit 耗时只被角点数解释 **R² = 0.706**（残差：336 角点实测 11.14 vs 模型 19.09）。
改成**固定序列、只动预算**的受控实验后（x86，`--fused cpu`，100 帧/序列，
只取 `fit=` 字段），混淆项按构造消失：

| 预算 | VIDEO00036 fit | Δ | VIDEO00002 fit | Δ |
| --: | --: | --: | --: | --: |
| 600（冻结值） | 24.095 ms | — | 16.512 ms | — |
| 400 | 20.999 | −12.8% | 14.135 | −14.4% |
| 300 | 18.203 | −24.5% | 11.965 | −27.5% |
| 250 | 16.948 | −29.7% | 12.595 | −23.7% |
| 200 | 16.136 | **−33.0%** | 12.004 | −27.3% |
| 150 | 14.420 | −40.2% | 11.556 | −30.0% |
| 100 | 12.598 | −47.7% | 10.913 | −33.9% |

拟合实测曲线：`fit ≈ a + b·√corners` 比线性更贴 —— 6 倍降档只换来 1.7 倍提速，
**角点预算是弱杠杆**，这也解释了为什么 R² 这么低。

把实测比值套到板卡已测的 VIDEO00036 分解（fit p50 28.185 / total p50 33.365，
非 fit 部分 5.180 ms 按不变处理）：

| 预算 | fit p50 | total p50 | fit p99 | total p99 | ≤ 40 ms |
| --: | --: | --: | --: | --: | :-- |
| 600 | 28.18 | 33.37 | 37.65 | 42.88 | FAIL |
| 400 | 24.58 | 29.76 | 32.83 | **38.06** | PASS |
| 300 | 21.28 | 26.46 | 28.43 | **33.66** | PASS |
| 250 | 19.81 | 24.99 | 26.47 | **31.70** | PASS |
| 200 | 18.88 | 24.06 | 25.23 | **30.46** | PASS |

**结论：预算降到 400 就足以让 VIDEO00036 的 p99 进 40 ms；降到 200 留出 ~10 ms 余量。**
配合 §5A.2 的精度代价，`--fit-corners 200` 是可交付的默认值：
34/28/32 三个序列**逐位不变、零触发**，02 付出 Ch1 max 1.02 / Ch2 max 3.40，
36 付出 Ch1 max 27 / Ch2 max 24.5。

> ⚠️ 上述板卡一列是**投影**，比值来自 x86。x86 与 A76 的绝对毫秒不可迁移，
> 只有比值是估计值。**验收必须以板卡实测为准**，本表只用于选定预算档位。
> 复现：`board/fit_vs_corners.sh <sequence>...`

### 5A.4 交付形态：**按序列**给预算，不是全局一刀切

§5A.2 的关键事实是：角点预算的精度代价**与该序列是否真的超时无关**。
`VIDEO00032` 每 400 帧截断 306 帧、Ch2 max 48，而它的板卡 p99 是 **30.37 ms**，
本来就过 40 ms 红线。给它降预算是拿真实的精度代价换一件它不需要的东西。

VIDEO00032 的预算扫描（400 帧，x86 CPU 臂）确认**不存在温和档位**：

| 预算 | 触发帧 | Ch1 max | Ch1 exact% | Ch2 max | Ch2 exact% |
| --: | --: | --: | --: | --: | --: |
| 600（默认，不触发） | 0/400 | **0** | **100.0000** | **0** | **100.0000** |
| 400 | 146/400 | 65 | 94.1789 | 45 | 92.1938 |
| 300 | 194/400 | 65 | 90.5595 | 47 | 88.0285 |
| 250 | 261/400 | 65 | 89.1987 | 45 | 85.7639 |
| 200 | 306/400 | 68 | 84.7318 | 48 | 80.9135 |

⇒ **max 偏差对预算几乎不敏感**（65 / 65 / 68），只有 `mean` 与 `exact%` 随预算单调变好。
这说明被截断的正是角点最多、最容易歧义的那些帧 —— 降预算并不能「温和地」摘掉它们，
只能整批换掉。所以对 VIDEO00032 而言，**唯一安全的档位是不触发**。

#### 建议的交付配置

| 序列 | 板卡 p99（修复后） | 是否需要角点预算 | 建议 | 理由 |
| :-- | --: | :-- | :-- | :-- |
| VIDEO00034 | 19.52（max 53.50） | **否** | `--fit-corners 600` | 唯一超标帧是设备重分配尖峰，由**预分配**解决，与角点无关 |
| VIDEO00028 | 17.97 | 否 | 600 | 已达标 |
| VIDEO00032 | 30.37 | **否** | 600 | 已达标；且无温和档位（max 65~68） |
| VIDEO00002 | 16.62 | 否（可选） | 600，或 200 | 已达标；若为提速而降，代价仅 Ch1 max 6 / Ch2 max 5 |
| VIDEO00036 | **42.88（超标）** | **是** | **`--fit-corners 200`** | 唯一需要提速的序列；p99 投影 42.88 → **30.46** |

**全局默认保持 `--fit-corners 600`（冻结值，零回归不变）**，
预分配 `--prealloc-pad 1024` **全局开启**（逐位精确、零重分配、无精度代价），
角点预算**只对 VIDEO00036 单独启用**。

机制上这是顺的：`bench_run.sh` 本来就是**一序列一进程**，
`--fit-corners` 又是每进程参数，所以「按序列配预算」不需要任何新代码，
只需 `BENCH_EXTRA` 差异化下发。这也和该脚本的设计理由一致 ——
一序列一进程当初是为了隔离 Mali 设备内存池，副作用正好让逐序列调参成为可能。

> ⚠️ 全部时延投影来自 x86 实测比值套用板卡分解（§5A.3），
> **板卡验收未做**：需要 `RK3588_PASSWORD` 才能部署与跑分（§7）。

### 5A.4b ⚠️ 2026-10-12 新增：x86 时延台账**双重不可用**（设备不对 + 噪声淹没信号）

本报告此前多处用 x86 比值外推板卡时延（§5A.3）。本轮把这件事查到底，结论是
**这类外推在本机上站不住**，理由有两条，且互相独立：

**(1) x86 的「GPU 臂」根本不是 GPU**

```
x86   : [OCL] platform : Portable Computing Language (OpenCL 3.0 PoCL 6.0+debian, LLVM 18.1.8)
        [OCL] device   : cpu-haswell-Intel(R) Core(TM) i5-10500 CPU @ 3.10GHz
        [OCL] image fmt : CL_RGBA (4 byte/px, PoCL fallback)

板卡  : [OCL] platform : ARM Platform (OpenCL 3.0 v1.g13p0-01eac0...)
        [OCL] device   : Mali-G610 r0p0
        [OCL] image fmt : CL_R    (1 byte/px)
```

x86 是 **PoCL 在 CPU 上模拟 OpenCL**，且像素格式从 `CL_R`(1 B/px) **退化为
`CL_RGBA`(4 B/px)**。实测每帧 110–245 ms，两臂全部 300/300 帧超 40 ms。
拿它套板卡绝对值，等于拿 CPU 模拟器套真 GPU。

**(2) 即使同机比较，噪声也淹没信号**

同一二进制、同一输入、同一配置**跑两遍**（`board/noise_floor.py`，
产物 `.bench_out/REGEN{,_REP}/`）：

| 序列 | 指标 | 噪声 \|A\| | 噪声 \|B\| | A-B 差异 | 判定 |
| :-- | :-- | --: | --: | --: | :-- |
| VIDEO00034 | p99 | 59.35 | 3.11 | 50.34 | 分辨不出 |
| VIDEO00028 | p99 | 13.98 | 52.20 | 17.69 | 分辨不出 |
| VIDEO00032 | p99 | 29.52 | 10.57 | 35.07 | 勉强越过 |
| VIDEO00002 | p99 | 60.50 | 20.72 | 63.13 | 勉强越过 |
| VIDEO00036 | p99 | 9.73 | 10.60 | 26.01 | 勉强越过 |

同配置两次运行的 p99 就能差 **3–60 ms**（相对量级 15%–60%），
而 A-B 差异只有 1.9–63 ms。「勉强越过」的格子也不可信 ——
噪声估计只有**两个样本**，用两次极差当噪声下限，统计上不成立。

⇒ **本报告 x86 侧只保留计数类与位级精度类结论；时延一律只报板卡实测。
§5A.3 的比值外推应视为未经验证的软预测。**

### 5A.5 2026-10-12 板卡实测：`VIDEO00034` 的反事实预测**被推翻**，真实机制是另一条

§5A.3 曾给出一个"硬"的反事实：只从发生尖峰的帧上减去实测到的上传超额，
推出 `VIDEO00034` max **53.50 → ≈13.0 ms**，理由是 `devrealloc=5` 与稳态内 4 帧
`img_up > 10 ms` 的数量吻合。

**板卡实测否掉了这个预测。** 部署 `--prealloc-pad 1024` 后：

| 项 | 改造前 | 交付配置实测 | |
| :-- | --: | --: | :-- |
| `devrealloc` | 5 | **1** | ✅ 预分配完全生效 |
| `img_up` p50 / p99 | 1.078 / 2.483 | 1.56 / **16.47** | ❌ 尖峰仍在 |
| `total` max | **53.50** | **43.16** | ❌ 未达 < 25 ms |

**`img_up` 的分布说明它是离散事件，不是长尾**（`board/v34_forensics.py`，稳态 300 帧）：

```
[0,2) ms : 296 帧 (98.7%)     [2,5)  : 0 帧     [5,10) : 0 帧
[10,20)  : 2 帧               [20,∞) : 2 帧          ← 2~10 ms 区间一帧都没有
最坏帧：169 total=43.16 img_up=31.06 | 170 total=40.95 img_up=29.82
        144 total=26.96 img_up=16.47 | 143 total=26.95 img_up=16.59
```

最坏帧仍是 **frame 169**——与改造前同一个事件。**真实机制在源码注释里写着**
（`gmc_stream_ocl.cpp:876-879`）：

> *"pad_ is shared state: the moment it grows, the resident frames are at the
> **WRONG offset** and must be dropped and re-uploaded, **even when the
> allocation itself does not change**."*

`pad_` 增长 → 45 个驻留槽位整体作废 → 后续帧整批重传 → `img_up` 尖峰。
**这条路径不经过 `configure()` 的重分配分支，所以 `n_reconfigure_` 不增长。**

⇒ **`devrealloc=1` 只证明"分配尺寸没变"，不证明"驻留槽位没被清空"。**
预分配消除的是前者，尖峰来自后者。**这是 handle A 的覆盖不全，不是实现 bug。**
本报告此前把"重分配"当成尖峰的充分原因，是把一条相关当成了因果。

**旁证**：另外四个序列的 `img_up` p99 与 p50 几乎相同（0.37/0.38、2.45/2.47、
2.47/2.50、1.56/1.58），零尖峰——它们的 `pad` 增长发生在 warmup 窗口内。

**修复方向与代价（已实施并实测）**：
① **钉死 `pad_` 到预分配上限**（新增 `--pin-pad 1`）—— 消除增长事件；
② 槽位作废后限速回填（每帧最多补 N 个槽）—— 未采用。

**选 ① 的理由是源码里那句成本估算被板卡推翻了。** §5A.3 之前的注释写：

> *"Uploading the whole allocation would scale H2D by cap/bucket (**32x** at cap 1024
> vs bucket 32) and trade a 41 ms spike for a **permanent tax**."*

板卡实测：

| pad | 上传字节 | img_up p50 |
| --: | --: | --: |
| 32 | 0.405 Mpixel | **0.37 ms** |
| 512 | 2.555 Mpixel | **1.56 ms** |
| 1024 | 6.881 Mpixel | **2.45 ms** |

**17× 的字节只换来 6.6× 的时间** —— H2D 路径带宽饱和、固定开销占主导。
所谓"permanent tax"实测是 **~2 ms**。**只有板卡能给总线定价。**

修复后 `VIDEO00002`（正常工况）p50 16.11 → 15.90 ms，与 MD5 不变互相印证。

### 6.2 板卡内 GPU vs CPU（**修复后**，`--fused both`，400 帧/序列）

两条臂吃**同一份 `mats`**（同一次 push、同一次拟合），差异只可能来自融合尾部。
每通道像素数 = 400 帧 × 640 × 512 = **131,072,000**。

| 序列 | Ch0 Max\|Diff\| | Ch0 MAE | Ch0 一致率 |
| :-- | --: | --: | --: |
| VIDEO00002 | **0** | 0.00000 | **100.0000%** |
| VIDEO00028 | **0** | 0.00000 | **100.0000%** |
| VIDEO00032 | **0** | 0.00000 | **100.0000%** |
| VIDEO00034 | **0** | 0.00000 | **100.0000%** |
| VIDEO00036 | **0** | 0.00000 | **100.0000%** |

**Ch1 / Ch2：**

| 序列 | 闸门拒绝的组合 lag | Ch1 max | Ch1 MAE | Ch1 一致率 | Ch2 max | Ch2 MAE | Ch2 一致率 |
| :-- | --: | --: | --: | --: | --: | --: | --: |
| VIDEO00002 | 0 | 4 | 0.00174 | 99.8423% | 4 | 0.00354 | 99.6511% |
| VIDEO00034 | 0 | 3 | 0.00155 | 99.8457% | 3 | 0.00078 | **99.9217%** |

* **闸门未触发的 3 个序列**：Ch2 max = 2~4，一致率 99.65%~99.92% —— 与既有
  `opencv_arm64_parity.md`「1993 万像素中 11 个不同」同量级，**不是新回归**。
* **闸门触发的 2 个序列**（`00028` 拒 31、`00032` 拒 125 个组合 lag）：
  Ch2 max 跳到 **44**，一致率降到 **99.02% / 97.86%**。

**这个退化是修复的直接代价，必须明说：** 当某个 lag 被替换为 `W(.) = IDENTITY`，
21 帧时域中值的输入就变了，因此 Ch2 改变。相关性是干净的 —— **退化只出现在闸门触发的
序列上，一个不多一个不少**。

**但这是正确的取舍**，理由是量级对比：

| | 修复前 | 修复后 |
| :-- | :-- | :-- |
| 这两个序列 | `devpad` 3551~4863，warp 采样到**已分配图像之外**，输出**未定义**；并导致 OOM 杀死进程 | Ch2 有 **97.9%~99.0%** 像素与 CPU 臂逐位一致，最大偏差 44 灰阶 |

即：**把「未定义输出 + 进程崩溃」换成了「2.1% 像素偏差、最大 44 灰阶」**。
前者无法交付，后者是可量化、可接受、可再调的。

⇒ **闸门触发率与业务 F1 的定量关联仍未测**（见 §7）。若下游对 Ch2 极敏感，
应考虑把 `W(.) = IDENTITY` 换成「沿用上一帧的拟合」而不是恒等，可保留时域连续性。

### 6.3 跨机逐帧 MD5 —— 该指标不成立，明确作废

板卡 GPU vs x86 CPU：**461 帧中仅 3 帧一致**（都是 frame 0，即无历史、全恒等的退化首帧）。

**不是精度失败，是指标选错了**：MD5 覆盖整帧，**1 个像素不同就改变整帧哈希**，
而 §6.2 显示逐像素一致率 99.85%+。
⇒ **跨架构精度判定只能用逐像素计数，不能用 MD5。**
